# DocVec Project_2 유지보수 가이드

이 문서는 `docs/기술문서_시스템_아키텍처.md`(기능이 어떤 알고리즘으로 어떻게 동작하는지)와
`docs/design/*`(설계 의도와 화면/데이터 구조)를 보완하는 **운영·유지보수 실무 문서**다.
"지금 장애가 났는데 무엇을 봐야 하는가", "새 기능을 어디에 어떻게 붙여야 하는가"에
바로 답하는 것을 목표로 한다.

---

## 1부: 운영 런북

### 1.1 스택 구성

Docker Compose 프로젝트명은 `docvec-v2`. 서비스 구성(`docker-compose.yml`):

| 서비스 | 역할 | 비고 |
|---|---|---|
| `api` | FastAPI 앱 서버 | `./backend:/app` 마운트 — 코드 변경 시 재시작만 필요 |
| `worker` | Celery 워커 (기본 큐) | 대부분의 파이프라인 블록 |
| `worker-embed` | Celery 워커 (임베딩 전용 큐) | `rag_store` 등 임베딩 연산, GPU/CPU 부하 격리용 별도 큐 |
| `flower` | Celery 모니터링 UI | 큐/태스크 상태 확인 |
| `frontend` | React 정적 빌드 (nginx) | 코드 변경 시 **재빌드 필요**(핫리로드 없음) |
| `postgres` | 메타데이터 DB | documents/workflow_runs/chunks 등 |
| `redis` | Celery 브로커/백엔드 | |
| `qdrant` | 벡터 DB | 청크 임베딩 + summary index 컬렉션 |
| `minio` | 오브젝트 스토리지 | 원본 파일 + 대용량 아티팩트(`storage_service`) |

### 1.2 기본 명령어

```bash
# 백엔드 코드 수정 후 반영 (핫리로드 없음, 재시작만으로 충분)
docker compose -p docvec-v2 restart api worker worker-embed

# 프론트엔드 코드 수정 후 반영 (정적 빌드라 재빌드 필수)
docker compose -p docvec-v2 build frontend && docker compose -p docvec-v2 up -d frontend

# 전체 기동/중지
docker compose -p docvec-v2 up -d
docker compose -p docvec-v2 down          # 볼륨은 유지됨 (데이터 보존)

# 로그 확인
docker compose -p docvec-v2 logs -f api
docker compose -p docvec-v2 logs -f worker worker-embed --tail 200
```

### 1.3 DB 접근

```bash
docker compose -p docvec-v2 exec -T postgres psql -U docvec -d docvec -t -A -c "<SQL>"
```

자주 쓰는 점검 쿼리:

```sql
-- 문서별 상태/품질/청크 수 한눈에 보기
SELECT id, filename, status, quality_status,
       (SELECT count(*) FROM document_chunks WHERE document_id = documents.id) AS chunk_count
FROM documents ORDER BY created_at DESC LIMIT 20;

-- RUNNING 상태로 멈춰있는 run 확인 (아래 1.5절 watchdog과 함께 사용)
SELECT id, document_id, status, started_at FROM workflow_runs WHERE status = 'RUNNING';
```

### 1.4 컨테이너 내부에서 파이썬 스크립트 실행

호스트에 Python이 없다. 컨테이너 안에서 실행해야 한다. `test_data/`는 api 컨테이너에
마운트되어 있지 않으므로, 실제 문서 파일로 스크립트를 돌려야 할 때는 먼저
`backend/`(마운트된 경로) 아래로 복사한 뒤 실행하고, 끝나면 반드시 삭제한다.

```bash
docker compose -p docvec-v2 exec -T api sh -c "cd /app && /app/.venv/bin/python <script>.py"
```

임시 검증 스크립트는 `backend/_tmp_*.py`로 이름 붙여 컨벤션을 지키고, 실행 후 즉시 삭제한다
(레포에 디버그 스크립트가 남지 않도록).

### 1.5 자주 발생하는 장애와 대응

**(A) Celery 하드 타임아웃으로 run이 RUNNING에 영구히 멈춤**

원인: `time_limit`을 넘기면 billiard가 워커 프로세스를 SIGKILL로 직접 죽이기 때문에,
애플리케이션 코드(`except`)로는 절대 잡을 수 없다. 별도 워커/beat 인프라 없이,
`GET /documents/{id}` 호출마다 `reprocess_service.reconcile_stuck_run()`이 지연을
감지해 RUNNING인 run/step/document를 FAILED로 확정한다(유예시간 30초,
`_TIMEOUT_GRACE_SECONDS`). 즉 **문서 상세 페이지를 한 번 열어보는 것만으로 정리된다** —
별도 배치나 크론이 필요 없다.

대응: 큰 파일(예: OCR이 필요한 32MB PDF)이 기본 타임아웃(블록별 `config.timeoutSeconds`,
보통 300초)을 넘긴다면, 재처리 시 `timeout_overrides`로 개별 블록 타임아웃을 늘려서
`start_partial_reprocess`/`start_full_reprocess`를 호출한다:

```python
await reprocess_service.start_partial_reprocess(
    db, doc, from_block_type="text_extract",
    timeout_overrides={"text_extract": 1800, "rag_store": 1800},
)
```

`timeout_overrides`는 `WorkflowRun` 단위 dict라 공유 `WorkflowBlockInstance.config`를
건드리지 않는다 — 이 문서 하나만 임시로 늘어난 시간 제한을 갖는다.

**(B) 검토 없이 재처리해도 다시 WAITING_REVIEW로 멈춤 (skip_review 미전파)**

`start_partial_reprocess`는 부모 run의 `skip_review` 값을 명시적으로 복사해야 한다
(`skip_review=parent_run.skip_review`). 이게 빠지면 컬럼 기본값 False로 새 run이
생성되어, 이미 검토를 통과했던 문서가 재처리 때마다 다시 검토 대기에 걸린다.

**(C) 재처리 후 특정 탭(구조/정제/사전/PII)이 비어 보임**

`workflow.py`의 `_CACHE_SAFE_BLOCK_TYPES` 화이트리스트(현재
`{"file_validate", "format_detect", "text_extract"}`)에 없는 블록 타입은 **런-스코프
캐시를 절대 재사용하면 안 된다**. 이 화이트리스트는 deny-by-default이므로, 새 블록
타입을 추가했는데 그 결과가 재처리 시 빈 값으로 보인다면 이 목록에 실수로 넣었는지,
혹은 정말 캐시-안전(입력이 바뀌지 않는 한 출력이 결정적이고 다른 run에 영향 없음)한지부터
검증한다. 캐시 키 자체는 `sha256(document_id:input_hash:block_type:block_version:
config_hash:dict_version_part:skip_review_part)`.

**(D) 품질 검증(quality_check)이 청크 0개인데도 SUCCESS_WITH_WARNING으로 통과**

`overall_score`는 5개 지표(추출/구조/정제/청킹/일관성)의 평균이라, 청킹 점수가 0이어도
다른 지표(예: 표 문법만으로 `min_extraction_chars`를 넘긴 `textExtraction=100`)에
희석되어 평균이 fail 임계값을 넘을 수 있다. `quality_blocks.py::_determine_status()`가
`chunk_count == 0`이면 평균과 무관하게 무조건 FAILURE로 확정하도록 되어 있다
(`block_version` "1.4.0"). 만약 청크 0개 문서가 FAILURE 아닌 다른 상태로 나온다면
이 함수부터 확인.

**(E) 사전(동의어/불용어/사용자 사전) 항목을 추가했는데 검색/토크나이징에 반영 안 됨**

Kiwi 형태소 분석기의 캐시가 항목 추가 시점에 자동 갱신되지 않는 경로가 있다.
`app/services/dictionary_service.py::refresh_dictionary_cache(db)`를 호출해 캐시를
재빌드해야 한다. 사전 API(`/dictionary/*`)를 통해 등록하면 내부적으로 호출되지만,
DB에 직접 INSERT하는 등 API를 우회했다면 반드시 수동으로 호출한다.

### 1.6 DB 마이그레이션 (Alembic)

```bash
# 새 마이그레이션 생성 (모델 변경 후)
docker compose -p docvec-v2 exec -T api sh -c "cd /app && /app/.venv/bin/alembic revision --autogenerate -m '<설명>'"

# 적용
docker compose -p docvec-v2 exec -T api sh -c "cd /app && /app/.venv/bin/alembic upgrade head"

# 현재 리비전 확인
docker compose -p docvec-v2 exec -T api sh -c "cd /app && /app/.venv/bin/alembic current"
```

`backend/alembic/versions/`에 48개 리비전 존재. `autogenerate`는 JSON 컬럼의 내부
구조 변경(예: `elements` shape 변경)은 감지하지 못하므로, JSON 필드에 새 키를
추가하는 경우는 보통 마이그레이션이 필요 없다(컬럼 자체가 이미 JSON) — 마이그레이션은
컬럼/테이블 추가에만 필요하다.

### 1.7 백업

- **Postgres**: `docker compose -p docvec-v2 exec -T postgres pg_dump -U docvec docvec > backup.sql`
- **Qdrant**: 컬렉션 스냅샷 API(`/collections/{name}/snapshots`) 또는 볼륨 자체를 백업.
- **MinIO**: 볼륨 백업 또는 `mc mirror`로 버킷 단위 복제. 원본 파일(`documents` 버킷)과
  아티팩트(`artifacts` 버킷)를 구분해서 관리한다.

세 저장소가 서로 참조하는 ID(document_id, minio_key, qdrant point id)로 묶여 있으므로,
**세 저장소를 같은 시점에 함께 백업/복원**해야 정합성이 깨지지 않는다.

## 2부: 개발 유지보수 가이드

### 2.1 새 파이프라인 블록 타입 추가하기

블록 타입의 단일 진실 공급원은 `app/pipeline/blocks/registry.py::BLOCK_REGISTRY`
— workflow_service의 저장 시점 검증, 실행기(executor)의 dispatch, `GET
/workflows/block-types`(프론트 팔레트) 세 곳 모두 이 dict 하나를 참조한다.

1. `BaseBlock`(`app/pipeline/blocks/base.py`)을 상속하는 클래스 작성.
   - `block_type`(고유 문자열), `category`(팔레트 그룹, 필수 — 기본값 없음)를 구현.
   - `block_version`을 재정의: 출력 형태/동작이 바뀔 때마다 버전을 올려야 캐시가
     무효화된다(2.4절 참고). 버전 문자열만 바꾸는 것으로 기존 캐시된 결과를
     무시하게 만들 수 있다 — 데이터 마이그레이션 없이.
   - `run(context: BlockContext) -> BlockResult` 구현. `context.upstream_outputs`는
     업스트림 블록의 output을 block_instance_id로 키잉한 dict(병합 블록은 여러 개).
2. `registry.py`의 `BLOCK_REGISTRY`와 `BLOCK_TYPE_LABELS`(한글 표시명) 양쪽에 등록.
   `BLOCK_TYPE_LABELS`는 `frontend/src/lib/workflowBlocks.ts`의 팔레트 라벨과
   동기화되어야 한다(둘 다 사람이 수동으로 맞춰야 함, 자동 동기화 없음).
3. 캐시를 재사용해도 안전한 블록(입력이 같으면 출력이 결정적이고 부작용 없음)만
   `workflow.py::_CACHE_SAFE_BLOCK_TYPES`에 추가한다. 기본은 deny — 애매하면 넣지 않는다.
4. 검토(review) 게이트가 필요한 블록이면 `_REVIEW_GATED_BLOCK_TYPES`에, 사전 버전에
   의존하는 블록(사전이 바뀌면 캐시가 무효화돼야 함)이면 `_DICTIONARY_BLOCK_TYPES`에 추가.
5. `_STATUS_FOR_BLOCK_TYPE`에 이 블록이 끝났을 때 `Document.status`를 무엇으로
   바꿀지 매핑을 추가(없으면 상태가 멈춰 보인다).

### 2.2 새 문서 어댑터(포맷) 추가하기

`app/pipeline/adapters/`에 PDF/DOCX/HWP/HWPX 등 포맷별 어댑터가 있다. Docling
어댑터(`docling_adapter.py`)는 PDF 전용이며 `engine="docling"`으로 문서에 표시되고,
`elements` 컬럼(통합 요소 JSON)을 채운다. 다른(legacy) 어댑터는 `elements=None`을
남기고, 이 경우 `GET /documents/{id}/elements`와 `structure_analyze`가 각각 표 탭/
정규식 폴백 경로로 동작한다 — 새 어댑터를 추가할 때 `elements`를 채울지 여부를
먼저 결정하고, 채우지 않는다면 하위 소비자들의 폴백 경로가 실제로 동작하는지
확인해야 한다.

한국어 문서 OCR은 `EasyOcrOptions(lang=["ko"])`를 쓴다 — RapidOCR은 한글을 한자로
잘못 인식하는 문제가 실측으로 확인되어 배제됨. 새 어댑터에서 OCR 엔진을 바꿀 때
이 회귀를 주의한다.

### 2.3 임베딩 모델 추가하기

임베딩 모델 레지스트리(`app/services/embedding.py`)에 등록된 모델은 항상 헬스체크
임베딩 호출로 실제 차원과 선언된 차원이 일치하는지 검증한다. 새 모델을 추가할 때
이 검증 없이 등록하면, 차원이 다른 모델로 조용히 색인해 Qdrant 컬렉션과 차원이
어긋나는 장애로 이어진다.

### 2.4 캐시 무효화 이해하기

`BlockExecutionCache`는 런 단위가 아니라 `(document_id, block_type, block_version,
config_hash, ...)` 조합 단위로 키가 잡힌다. 즉 **블록 코드/설정이 바뀌지 않으면
재처리해도 이전 결과를 그대로 재사용**한다 — 의도적 성능 최적화지만, 블록 동작을
바꿨는데 `block_version`을 올리지 않으면 재처리해도 옛날 결과가 계속 나오는
당황스러운 상황이 생긴다. **블록의 `run()` 로직을 조금이라도 바꿨다면 반사적으로
`block_version`을 올린다.**

### 2.5 주석 컨벤션

- 주석은 **왜(WHY)**를 설명한다 — 코드가 이미 보여주는 **무엇(WHAT)**을 반복하지 않는다.
- "현재 작업", "이번 수정", "사용자가 요청/확인/지적한" 같은 대화·세션 귀속 표현은
  쓰지 않는다 — 시간이 지나면 맥락 없이 남아 오히려 혼란을 준다. 대신 근거가 되는
  설계서 절 번호(예: "§7.2"), 실측 근거("RapidOCR이 한글을 한자로 오인식함, 실측
  확인"), 혹은 재현 조건("chunk_count=0인데 overall_score가 fail 임계값을 넘는
  케이스에서 재현")처럼 **검증 가능한 사실**로 남긴다.
- 코드 리뷰/PR 설명에 들어갈 내용(누가 요청했는지, 어떤 이슈를 고쳤는지)은 커밋
  메시지·PR 본문에 쓰고 코드 주석에는 남기지 않는다.

### 2.6 테스트 작성 컨벤션

AAA 패턴(Arrange-Act-Assert), pytest, 80% 커버리지 목표. 순수 함수로 추출 가능한
로직(예: `quality_blocks.py::_determine_status`)은 블록 전체를 실행하지 않고 함수
단위로 직접 테스트한다 — 픽스처/DB 없이 빠르게 회귀를 잡을 수 있다.
