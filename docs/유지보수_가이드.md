# DocVec Project_2 유지보수 가이드

이 문서는 `docs/기술문서_시스템_아키텍처.md`(기능이 어떤 알고리즘으로 어떻게 동작하는지)와
`docs/design/*`(설계 의도와 화면/데이터 구조)를 보완하는 **운영·유지보수 실무 문서**다.
"지금 장애가 났는데 무엇을 봐야 하는가", "새 기능을 어디에 어떻게 붙여야 하는가"에
바로 답하는 것을 목표로 한다.

---

## 1부: 운영 런북

### 1.1 스택 구성

Docker Compose 프로젝트명은 `project_2`(디렉터리명이 기본값이라 컨테이너가 `project_2-<서비스>-1`로
뜬다). 같은 호스트에 이전 스택(`docvec-v2` 등)이 떠 있을 수 있으므로 아래 명령은 `-p project_2`를
항상 명시한다. 서비스 구성(`docker-compose.yml`):

| 서비스 | 역할 | 비고 |
|---|---|---|
| `api` | FastAPI 앱 서버 | `./backend:/app` 마운트 — 코드 변경 시 재시작만 필요 |
| `worker` | Celery 워커 (`critical/high/normal/low` 큐, concurrency 4) | CPU 블록(입력·추출·정제·청크 분할 등) |
| `worker-embed` | Celery 워커 (`embed` 큐 전용, concurrency 1) | **GPU 모델(BGE-M3 임베딩, 로컬 LLM)을 쓰는 작업은 전부 여기로만** 간다 — 아래 1.1-A |
| `beat` | Celery beat | 30초마다 `sweep_stuck_workflow_runs` 실행 — 1.5절 (A)·(A-4) |
| `flower` | Celery 모니터링 UI | 큐/태스크 상태 확인. 접속에 `FLOWER_BASIC_AUTH` 필요 |
| `frontend` | React 정적 빌드 (nginx) | 코드 변경 시 **재빌드 필요**(핫리로드 없음) |
| `postgres` | 메타데이터 DB | documents/workflow_runs/chunks 등 |
| `redis` | Celery 브로커/백엔드 | |
| `qdrant` | 벡터 DB | 청크 임베딩 + summary index 컬렉션 |
| `minio` | 오브젝트 스토리지 | 원본 파일 + 대용량 아티팩트(`storage_service`) |
| `caddy` | HTTPS 리버스 프록시 | 외부 노출 시 유일한 진입점(443/80). 내부적으로 `frontend:80`에만 전달 — 1.9절 참고 |

**1.1-A GPU 작업은 `embed` 큐 하나로만 보낸다.** 일반 `worker`(concurrency 4)도 GPU를 볼 수 있어서,
LLM/임베딩 작업이 거기서 돌면 프로세스마다 모델 사본을 올려 GPU 메모리를 두고 경합하고
`CUDA error: unspecified launch failure`로 문서가 FAILED가 됐다(컬렉션 재처리 + 자동 분석 실측).
그래서 `step_queue_for_block`(`tasks/workflow.py`)은 `rag_store`·`summarize`·`extract_keywords`·
`classify`·`extract_entities`·`output`(요약 인덱스 임베딩을 호출)과 `strategy=semantic`인
`chunk_split`을 `embed` 큐로, 나머지는 `normal`로 보낸다. 레거시 배치 태스크
(`continue_processing`·`generate_summary`·`extract_metadata`·`reembed_collection`)도 같은 큐다.
GPU 블록을 새로 추가하면 `_GPU_BLOCK_TYPES`에 넣어야 한다(`test_gpu_queue_routing.py`가 목록을 고정한다).
BGE-M3는 배치 크기 16으로 인코딩한다(`_BATCH_SIZE`) — 더 키우면 큰 PDF에서 VRAM이 모자란다.

**1.1-B 가상환경 볼륨.** `api`는 `backend_venv`, `worker`·`worker-embed`·`beat`는 `worker_venv`를
`/app/.venv`에 마운트한다. 워커 이미지의 venv에는 torch 등 GPU 의존성이 들어 있는데, api용 볼륨을
같이 쓰면 그 볼륨이 이미지의 venv를 가려 워커에서 torch를 import하지 못한다. 의존성을 바꾼 뒤에는
이미지를 다시 빌드하고 해당 볼륨을 지워야 새 패키지가 반영된다.

### 1.5 자주 발생하는 장애와 대응

**(A) Celery 하드 타임아웃으로 run이 RUNNING에 영구히 멈춤**

원인: `time_limit`을 넘기면 billiard가 워커 프로세스를 SIGKILL로 직접 죽이기 때문에,
애플리케이션 코드(`except`)로는 절대 잡을 수 없다. `GET /documents/{id}` 호출마다
`reprocess_service.reconcile_stuck_run()`이 지연을 감지하는 경로에 더해(유예시간 30초,
`_TIMEOUT_GRACE_SECONDS`), **`beat` 컨테이너가 `tasks.sweep_stuck_workflow_runs`를
30초마다 실행**해 아무도 문서 상세 페이지를 열어보지 않아도 능동적으로 정리한다
(2026-08-03 추가). 판정 기준(`_TIMEOUT_GRACE_SECONDS`, per-run `timeout_overrides`)은
두 경로가 동일하게 공유한다. `docker logs project_2-beat-1`로 30초 간격 실행을 확인할 수 있다.

블록 기본 타임아웃(`config.timeoutSeconds`)은 전 블록 1800초로 통일되어 있다(2026-08-03,
기존 300초에서 상향 — Docling+VLM OCR 에스컬레이션 이후 표/이미지 밀도가 높은 PDF의
text_extract가 300초를 반복적으로 초과했기 때문). 그래도 초과한다면 재처리 시
`timeout_overrides`로 개별 블록 타임아웃을 문서 하나에만 더 늘려서
`start_partial_reprocess`/`start_full_reprocess`를 호출한다:

```python
await reprocess_service.start_partial_reprocess(
    db, doc, from_block_type="text_extract",
    timeout_overrides={"text_extract": 3600, "rag_store": 3600},
)
```

`timeout_overrides`는 `WorkflowRun` 단위 dict라 공유 `WorkflowBlockInstance.config`를
건드리지 않는다 — 이 문서 하나만 임시로 늘어난 시간 제한을 갖는다.

**(A-1) `Document.active_run_id`가 이미 끝난 run을 계속 가리킴**

원인: `_maybe_trigger_analysis`(PREPROCESS run 완료 시 컬렉션 기본 분석 워크플로우를
자동 기동)와 `_fail_document`(run 실패 확정) 둘 다 `Document.active_run_id`를 새/실패한
run으로 갱신하지 않던 버그가 있었다(2026-08-03 수정 전). 그 결과 분석 run이 멈추거나
실패해도 `active_run_id`는 이미 `COMPLETED`된 이전 PREPROCESS run을 계속 가리켜, 문서
상세 조회·재처리·정체 감지가 전부 엉뚱한(이미 끝난) run을 보게 되고, 그 문서는
`ANALYZING`/`FAILED` 상태에서 영원히 멈춘 것처럼 보인다. 지금은 두 함수 모두 자기 run의
id로 `active_run_id`를 갱신하므로, 이 계열의 문제가 재발한다면 먼저
`SELECT active_run_id FROM documents WHERE id=...`와
`SELECT id, status FROM workflow_runs WHERE document_id=... ORDER BY created_at`을
비교해 `active_run_id`가 정말 최신 run을 가리키는지부터 확인한다.

**(A-2) 모든 step이 COMPLETED인데 `WorkflowRun.status`가 RUNNING에 영구히 멈춤**

원인: merge 블록이 아닌 블록에 incoming edge가 2개 이상 있으면(명시적 병합 없는
fan-in), 두 상류 분기가 각각 `run_workflow_step`을 디스패치해 같은 블록이 동시에
중복 실행될 수 있다. 두 실행 모두 완료 후 `_advance()`를 호출하는데, 늦게 끝난 쪽이
그 하류 블록에 대해 "이미 완료됨" 중복-디스패치 경로(`run_workflow_step`의
`step.status in ("COMPLETED","FAILED")` 조기 반환)로 빠지면서 run 전체 완료 여부를
재확인하는 코드(`_maybe_complete_run`)를 다시는 타지 않게 된다(2026-08-03 수정 전).
지금은 그 조기 반환 경로에서도 `_maybe_complete_run`을 호출해 안전망을 두었다.
재발 시 `SELECT block_instance_id, count(*) FROM workflow_run_steps WHERE run_id=...
GROUP BY block_instance_id HAVING count(*) > 1`로 중복 실행된 블록이 있는지부터 확인.

**(A-3) run은 이미 COMPLETED인데 문서는 계속 FAILED로 보임 (`_maybe_complete_run` 가드)**

(A-1)과 증상은 비슷하지만 원인은 다르다 — 이번엔 `active_run_id` 자체는 최신 run을
정확히 가리키는데, `_advance()`의 종료 분기(`_maybe_complete_run`)가 `Document.status`를
`INDEXED`로 되돌릴지 판단하는 조건이 잘못돼 있던 버그다(2026-08-03 수정 전 코드:
`if doc.status != "FAILED": doc.status = "INDEXED"`). FAILED 문서를 재처리(부분/일괄
재처리 모두)하면 그 run이 끝날 때까지 `doc.status`는 시작 블록이 끝날 때 갱신되지 않는 한
계속 리터럴 `"FAILED"`로 남아있다(`_STATUS_FOR_BLOCK_TYPE`에 매핑이 없는 블록에서
재처리를 시작한 경우 특히 그렇다). 옛 조건은 이 상태를 "다른 경로가 이미 정당하게
실패시켰다"로 오판해, run이 진짜로 성공해도 `INDEXED`로 되돌리길 거부했다 — 문서는
모든 스텝이 COMPLETED인데도 영원히 FAILED로 보인다.

수정: 판단 기준을 `doc.status != "FAILED"`가 아니라 **`str(doc.active_run_id) ==
str(run.id)`**로 바꿨다 — "이 run이 지금 이 문서의 활성 run이 맞는가"만 확인하면,
더 새로운 run에 이미 자리를 내준 뒤늦게 끝난 run만 정확히 걸러지고 정상 성공 케이스는
항상 `INDEXED`로 반영된다. 실제로 발견 당시 실패 목록의 문서 10건 전부가 이미
`COMPLETED`된 run을 가리키면서 상태만 `FAILED`로 굳어 있었다 — 배포 전 문서들은 아래
SQL로 일괄 확인·복구했다(코드 수정 이후 새로 완료되는 run은 자동으로 반영되므로,
이 SQL은 **과거에 이미 완료된 run에 대해서만** 1회성으로 필요하다):

```sql
-- 확인: active_run_id가 COMPLETED인데 문서 상태가 FAILED인 것들
SELECT d.id, d.original_filename, d.active_run_id, wr.status AS run_status
FROM documents d LEFT JOIN workflow_runs wr ON wr.id = d.active_run_id
WHERE d.status = 'FAILED';

-- 복구: 위 쿼리로 확인된 문서만 정확히 대상으로 삼는다(WHERE의 서브쿼리 조건이 핵심 —
-- 실제로 실패한 run을 가리키는 문서는 절대 건드리지 않는다)
UPDATE documents d SET status='INDEXED', updated_at=now()
FROM workflow_runs wr
WHERE d.active_run_id = wr.id AND d.status='FAILED' AND wr.status='COMPLETED';
```

재발 여부 확인 시 `_maybe_complete_run`(`workflow.py`)에 회귀 테스트 2건
(`test_terminal_block_flips_failed_document_back_to_indexed_when_run_is_still_active`,
`test_terminal_block_does_not_flip_document_superseded_by_a_newer_run`,
`backend/tests/unit/test_workflow_execution.py`)이 있다 — 이 케이스가 다시 깨지면
이 테스트들이 먼저 실패한다.

**(A-4) 다음 스텝 메시지가 유실돼 run이 RUNNING에 멈춤 (sweeper 재디스패치, 2026-10-12)**

워커/브로커가 죽어 "다음 블록 실행" 메시지가 사라지면 하드 타임아웃(A)과 달리 실행 중인 스텝이
없어 timeout 판정에 걸리지 않는다. `sweep_stuck_workflow_runs`는 이런 run을 `_redispatch_orphaned_run`
으로 되살린다. 동작 규칙은 다음과 같다.

- 마지막 활동(PENDING 스텝의 `created_at`은 "마지막 디스패치 시각", COMPLETED는 `completed_at`)으로부터
  600초(grace)가 지난 run만 대상이다. GPU 큐(`embed`, concurrency 1)에서 대기 중인 정상 run을
  건드리지 않기 위한 값이다. GPU 대기가 600초보다 길어지면 같은 스텝이 중복 디스패치될 수 있으나,
  `run_workflow_step`의 COMPLETED/FAILED 조기 반환(A-2)이 중복 실행을 막는다.
- **유실된 가지만** 다시 진행한다(`_advance(..., only_targets=...)`). 이미 카운트된 merge 엣지를
  다시 발화하면 `completed_incoming_edges`가 부풀어 merge 블록이 다른 가지가 끝나기 전에 실행된다.
- 모든 스텝이 COMPLETED인데 마지막 완료 처리가 유실된 run은 `_maybe_complete_run`으로 닫는다.
- `_maybe_complete_run`의 상태 전이는 `WHERE status='RUNNING'` 조건부 UPDATE라, 두 워커가 동시에
  완료 처리해도 AUTO_ANALYSIS run이 중복 생성되지 않는다.
- run 하나의 재디스패치가 예외를 내도(`_try_redispatch`: rollback + `logger.exception`) 나머지 run의
  정리는 계속된다. 반환값은 `{"swept_run_ids", "redispatched_run_ids"}`이다.

회귀 테스트: `backend/tests/unit/test_workflow_engine_hardening_pg.py`(실제 Postgres 필요).

**(B) 검토 없이 재처리해도 다시 WAITING_REVIEW로 멈춤 (skip_review 미전파)**

`start_partial_reprocess`는 부모 run의 `skip_review` 값을 명시적으로 복사해야 한다
(`skip_review=parent_run.skip_review`). 이게 빠지면 컬럼 기본값 False로 새 run이
생성되어, 이미 검토를 통과했던 문서가 재처리 때마다 다시 검토 대기에 걸린다.

**(C) 재처리 후 특정 탭(구조/정제/사전/PII)이 비어 보임**

`workflow.py`의 `_CACHE_SAFE_BLOCK_TYPES` 화이트리스트(현재
`{"file_validate", "format_detect", "text_extract"}`)에 없는 블록 타입은 **런-스코프
캐시를 절대 재사용하면 안 된다**. 이 화이트리스트는 deny-by-default이므로, 새 블록
타입을 추가했는데 그 결과가 재처리 시 빈 값으로 보인다면 이 목록에 실수로 넣었는지,
혹은 정말 캐시-안전(입력이 바뀌지 않는 한 출력이 결정적이고 다른 run에 영향 없음)한지부터
검증한다. 캐시 키 자체는 `sha256(document_id:input_hash:block_type:block_version:
config_hash:dict_version_part:skip_review_part)`.

**(D) 품질 검증(quality_check)이 청크 0개인데도 SUCCESS_WITH_WARNING으로 통과**

`overall_score`는 5개 지표(추출/구조/정제/청킹/일관성)의 평균이라, 청킹 점수가 0이어도
다른 지표(예: 표 문법만으로 `min_extraction_chars`를 넘긴 `textExtraction=100`)에
희석되어 평균이 fail 임계값을 넘을 수 있다. `quality_blocks.py::_determine_status()`가
`chunk_count == 0`이면 평균과 무관하게 무조건 FAILURE로 확정하도록 되어 있다
(`block_version` "1.4.0"). 만약 청크 0개 문서가 FAILURE 아닌 다른 상태로 나온다면
이 함수부터 확인.

**(E) 사전(동의어/불용어/사용자 사전) 항목을 추가했는데 검색/토크나이징에 반영 안 됨**

Kiwi 형태소 분석기의 캐시가 항목 추가 시점에 자동 갱신되지 않는 경로가 있다.
`app/services/dictionary_service.py::refresh_dictionary_cache(db)`를 호출해 캐시를
재빌드해야 한다. 사전 API(`/dictionary/*`)를 통해 등록하면 내부적으로 호출되지만,
DB에 직접 INSERT하는 등 API를 우회했다면 반드시 수동으로 호출한다.

  앞서 나오는(같으면 더 긴) 후보, 없으면 마지막 후보. 빈 후보는 무시된다.

### 1.9 외부 접속 — Caddy HTTPS 리버스 프록시 (2026-08-03 추가)

내부망(`http://<LAN IP>:3001`)에서만 쓰던 서비스를 외부(포트포워딩)로 열 때는 **`caddy` 서비스 하나,
즉 443(TCP)과 80(TCP)만** 공유기에서 포트포워딩한다. 2026-10-12부터 compose의 호스트 포트도
이 정책에 맞춰 Caddy(443/80)를 뺀 전부(`postgres` 5433, `minio` 9002·9003, `flower` 5556,
`api` 8001, `redis`, `qdrant`)를 `127.0.0.1`에만 바인딩한다 — 서버 PC 자신에서만
접속되고 같은 LAN의 다른 PC에서도 접속되지 않는다. DBeaver 등으로 다른 PC에서 DB를 봐야 하면
SSH 터널(`ssh -L 5433:127.0.0.1:5433 <서버>`)을 쓴다. 공유기 포트포워딩 표:

| 외부 포트 | 내부 대상 | 용도 |
|---|---|---|
| 443/TCP | 서버 PC 443 | 웹 시스템(HTTPS) — 필수 |
| 80/TCP | 서버 PC 80 | https 로 자동 리다이렉트 — 선택(없어도 `https://`로 직접 접속하면 됨) |

그 외 포트(8001, 5433, 9002, 9003, 5556 등)는 절대 포워딩하지 않는다. (호스트 3001·4443은 Caddy HTTPS이므로 포워딩 대상이 될 수 있다.)
`POSTGRES_PASSWORD`는 기본값 없이 `.env`에 반드시 있어야 기동된다(2026-10-12 — 공개 저장소에
있던 기본 비밀번호 제거). 이미 만들어진 Postgres 볼륨의 비밀번호는 `.env`를 바꿔도 따라 바뀌지
않으므로, 바꾸려면 `ALTER USER`를 함께 실행해야 한다.

**원본 문서 다운로드 경로**: 브라우저가 쓰는 presigned URL을 MinIO 포트(9002)가 아니라 Caddy
같은 출처로 중계한다(`/originals/*`, `/artifacts/*`, GET·HEAD만 허용 — 버킷은 비공개라 서명 없는
요청은 403). 이를 켜려면 `.env`에 `MINIO_PUBLIC_ENDPOINT=<Caddy 사이트 주소(포트 없이)>`와
`MINIO_PUBLIC_SECURE=true`를 넣어야 한다. 서명에 Host가 포함되므로 **사용자가 접속하는 주소와
`MINIO_PUBLIC_ENDPOINT`가 같아야** 한다(기본값 `localhost:9002`는 서버 PC 자신의 브라우저에서만 동작).
**현재 포워딩(2026-10-12 실측)**: 이 환경은 외부 443이 도달하지 않고 3001은 도달했다(통신사/공유기 차단 추정).
공유기는 **외부 4443/TCP → 서버 PC(192.168.0.3, DHCP 고정 권장)의 내부 3001**로 포워딩하고, 접속 주소는
`https://49.168.97.107:4443`이다. compose는 Caddy가 호스트 443·4443·3001 세 포트를 모두 컨테이너 443(HTTPS)에
연결하므로 내부 포트는 셋 중 아무거나 써도 된다. 이때 `.env`는 `MINIO_PUBLIC_ENDPOINT=49.168.97.107:4443`
(서명의 Host에 **외부 포트**가 들어가므로 접속하는 외부 포트와 일치해야 함), `MINIO_PUBLIC_SECURE=true`,
`CORS_ALLOWED_ORIGINS`에 `https://49.168.97.107:4443` 포함. 평문 http 3001(frontend 직접 노출)은 제거했다 —
외부 포트를 바꾸면 `MINIO_PUBLIC_ENDPOINT`·`CORS_ALLOWED_ORIGINS`도 같이 바꾸고 api를 재기동한다.

**MinIO 중계 응답 헤더(2026-10-12)**: Caddy 사이트 전역의 `X-Frame-Options: DENY` 때문에 hwpx/기타 변환 미리보기(HTML을
iframe으로 띄움)가 막혔다(PDF·DOCX는 PDF라 blob으로 받아 영향 없음). `/originals/*`·`/artifacts/*` 중계 블록에서만
`X-Frame-Options: SAMEORIGIN`으로 덮어쓰고, MinIO가 앱과 같은 출처가 된 만큼 문서에서 변환된 HTML이 앱 권한으로
스크립트를 실행하지 못하도록 `Content-Security-Policy: sandbox; default-src 'none'; img-src data: blob:;
style-src 'unsafe-inline'; font-src data:`를 함께 건다. 미리보기 HTML에 외부 이미지·스크립트가 필요해지면 이 CSP를 조정해야 한다.

`Caddyfile` 사이트 주소는 `192.168.0.3, 192.168.0.90, 49.168.97.107`(같은 인증서의 SAN)이다. 원본 다운로드 URL이
공인 IP 하나로 만들어지므로 **사내(LAN) 사용자가 원본을 열려면 공유기가 내부에서 공인 IP로의 접속(헤어핀 NAT)을
지원해야** 한다. 공인 IP가 바뀌면 `Caddyfile`·`.env`(`MINIO_PUBLIC_ENDPOINT`, `CORS_ALLOWED_ORIGINS`)를 함께 고치고
api·caddy를 재기동한다(Caddyfile은 단일 파일 bind mount라 수정 후 `restart caddy` 필요).

**요청 경로**: 외부 클라이언트 → `caddy`(443, TLS 종료) → `frontend:80`(nginx) →
`/api/`로 시작하는 요청만 `api:8000`으로 재프록시. 프론트엔드(`apiClient.ts`)가 상대경로
(`baseURL: '/api/v1'`)만 쓰기 때문에, 외부에는 443 하나만 열려 있어도 API까지 전부
도달한다 — **내부 대상은 항상 caddy(호스트 443·4443·3001, 모두 HTTPS)이다. 외부 포트는 환경에 따라 고른다.**

**인증서 구성** (`caddy/Caddyfile`): 도메인이 없어 Let's Encrypt 자동 발급 대신 Caddy
내장 로컬 CA로 자체 서명 인증서를 발급한다(`tls internal`). 외부 방문자의 브라우저에는
이 CA가 등록돼 있지 않으므로 최초 접속 시 "안전하지 않음" 경고가 뜨는 게 **정상**이다 —
접속 자체는 여전히 TLS로 암호화되며, 경고는 "이 서버가 진짜 그 IP인지 제3자(CA)가
보증하지 않는다"는 의미일 뿐이다. 나중에 도메인이 생기면 `Caddyfile`의 IP 주소를
도메인으로 바꾸는 것만으로 Let's Encrypt 자동 발급으로 전환된다.

**IP 리터럴 접속 시 SNI 관련 함정 2가지** (둘 다 2026-08-03 실측으로 확인, `openssl
s_client -connect <IP>:443 -servername <IP>`는 항상 성공하므로 이걸로 먼저 Caddy 자체가
정상인지 격리한다):

1. **사이트 주소를 `:443`처럼 포트만 쓰면 안 된다** — Caddy가 어떤 인증서를 낼지 SNI로
   고르는데, Windows schannel(`curl.exe`, 구형 .NET)은 IP 리터럴로 접속할 때 TLS SNI
   확장을 아예 보내지 않는다(RFC 6066상 허용된 동작). 사이트 주소를 실제 LAN IP로
   명시하면(`192.168.0.90 { ... }`) 그 IP를 인증서 SAN에 넣어 발급하고, 전역
   옵션 블록에 `default_sni <IP>`를 추가하면 SNI가 없는 연결도 이 사이트로 라우팅된다.
   이게 없으면 Caddy가 SNI 없는 연결 자체를 `internal error` TLS alert로 거부한다
   (curl: `SEC_E_INTERNAL_ERROR`, Chrome: `ERR_SSL_PROTOCOL_ERROR`).
2. **TLS1.3 키교환 그룹을 고전 커브로 제한**해야 한다 — 최근 Caddy/Go는
   포스트퀀텀 하이브리드 그룹(`X25519MLKEM768`)을 최우선 협상하는데, Windows 기본
   TLS 스택이 이를 아직 지원하지 않는다. `tls internal { curves x25519 secp256r1
   secp384r1 }`로 제한한다. (주의: 이 항목은 SNI 문제와 증상이 비슷해 보이지만 원인이
   다르다 — SNI 문제부터 `openssl s_client`로 먼저 배제한 뒤에 커브 문제를 의심한다.)

**LAN IP가 바뀌면**: `caddy/Caddyfile`의 IP는 하드코딩이다. 공유기에서 이 호스트에
DHCP 예약(고정 IP 임대)을 걸어두지 않으면, IP 임대가 갱신되며 주소가 바뀔 때마다
`Caddyfile`을 수정하고 `docker compose -p project_2 restart caddy`가 필요하다.

**CORS**: `.env`의 `CORS_ALLOWED_ORIGINS`에 외부 접속 origin(`https://<IP>`)이
추가돼 있어야 한다 — 리버스 프록시가 붙어도 백엔드의 CORS 검증은 별개로 통과해야 한다.

**외부 노출 전 별도 보안 점검 필요 항목(미착수, 이 세션에서 다루지 않음)**: Flower
UI 인증, 노출된 자격 증명 로테이션, 로그인 엔드포인트 rate limiting. 실제로 외부
포트포워딩을 켜기 전에 검토를 권장한다.

### 2.1 새 파이프라인 블록 타입 추가하기

블록 타입의 단일 진실 공급원은 `app/pipeline/blocks/registry.py::BLOCK_REGISTRY`
— workflow_service의 저장 시점 검증, 실행기(executor)의 dispatch, `GET
/workflows/block-types`(프론트 팔레트) 세 곳 모두 이 dict 하나를 참조한다.

1. `BaseBlock`(`app/pipeline/blocks/base.py`)을 상속하는 클래스 작성.
   - `block_type`(고유 문자열), `category`(팔레트 그룹, 필수 — 기본값 없음)를 구현.

   - `run(context: BlockContext) -> BlockResult` 구현. `context.upstream_outputs`는
     업스트림 블록의 output을 block_instance_id로 키잉한 dict(병합 블록은 여러 개).
2. `registry.py`의 `BLOCK_REGISTRY`와 `BLOCK_TYPE_LABELS`(한글 표시명) 양쪽에 등록.
   `BLOCK_TYPE_LABELS`는 `frontend/src/lib/workflowBlocks.ts`의 팔레트 라벨과
   동기화되어야 한다(둘 다 사람이 수동으로 맞춰야 함, 자동 동기화 없음).
3. 캐시를 재사용해도 안전한 블록(입력이 같으면 출력이 결정적이고 부작용 없음)만
   `workflow.py::_CACHE_SAFE_BLOCK_TYPES`에 추가한다. 기본은 deny — 애매하면 넣지 않는다.
4. 검토(review) 게이트가 필요한 블록이면 `_REVIEW_GATED_BLOCK_TYPES`에, 사전 버전에
   의존하는 블록(사전이 바뀌면 캐시가 무효화돼야 함)이면 `_DICTIONARY_BLOCK_TYPES`에 추가.
5. `_STATUS_FOR_BLOCK_TYPE`에 이 블록이 끝났을 때 `Document.status`를 무엇으로
   바꿀지 매핑을 추가(없으면 상태가 멈춰 보인다).

### 2.2 새 문서 어댑터(포맷) 추가하기

`app/pipeline/adapters/`에 PDF/DOCX/HWP/HWPX 등 포맷별 어댑터가 있다. Docling
어댑터(`docling_adapter.py`)는 PDF 전용이며 `engine="docling"`으로 문서에 표시되고,
`elements` 컬럼(통합 요소 JSON)을 채운다. 다른(legacy) 어댑터는 `elements=None`을
남기고, 이 경우 `GET /documents/{id}/elements`와 `structure_analyze`가 각각 표 탭/
정규식 폴백 경로로 동작한다 — 새 어댑터를 추가할 때 `elements`를 채울지 여부를
먼저 결정하고, 채우지 않는다면 하위 소비자들의 폴백 경로가 실제로 동작하는지
확인해야 한다.

한국어 문서 OCR은 `EasyOcrOptions(lang=["ko"])`를 쓴다 — RapidOCR은 한글을 한자로
잘못 인식하는 문제가 실측으로 확인되어 배제됨. 새 어댑터에서 OCR 엔진을 바꿀 때
이 회귀를 주의한다.

### 2.3 임베딩 모델 추가하기

임베딩 모델 레지스트리(`app/services/embedding.py`)에 등록된 모델은 항상 헬스체크
임베딩 호출로 실제 차원과 선언된 차원이 일치하는지 검증한다. 새 모델을 추가할 때
이 검증 없이 등록하면, 차원이 다른 모델로 조용히 색인해 Qdrant 컬렉션과 차원이
어긋나는 장애로 이어진다.

### 2.4 캐시 무효화 이해하기

`BlockExecutionCache`는 런 단위가 아니라 `(document_id, block_type, block_version,
config_hash, ...)` 조합 단위로 키가 잡힌다. 즉 **블록 코드/설정이 바뀌지 않으면
재처리해도 이전 결과를 그대로 재사용**한다 — 의도적 성능 최적화지만, 블록 동작을
바꿨는데 `block_version`을 올리지 않으면 재처리해도 옛날 결과가 계속 나오는
당황스러운 상황이 생긴다. **블록의 `run()` 로직을 조금이라도 바꿨다면 반사적으로
`block_version`을 올린다.**

### 2.5 주석 컨벤션

- 주석은 **왜(WHY)**를 설명한다 — 코드가 이미 보여주는 **무엇(WHAT)**을 반복하지 않는다.
- "현재 작업", "이번 수정", "사용자가 요청/확인/지적한" 같은 대화·세션 귀속 표현은
  쓰지 않는다 — 시간이 지나면 맥락 없이 남아 오히려 혼란을 준다. 대신 근거가 되는
  설계서 절 번호(예: "§7.2"), 실측 근거("RapidOCR이 한글을 한자로 오인식함, 실측
  확인"), 혹은 재현 조건("chunk_count=0인데 overall_score가 fail 임계값을 넘는
  케이스에서 재현")처럼 **검증 가능한 사실**로 남긴다.
- 코드 리뷰/PR 설명에 들어갈 내용(누가 요청했는지, 어떤 이슈를 고쳤는지)은 커밋
  메시지·PR 본문에 쓰고 코드 주석에는 남기지 않는다.

### 2.6 테스트 작성 컨벤션

AAA 패턴(Arrange-Act-Assert), pytest, 80% 커버리지 목표. 순수 함수로 추출 가능한
로직(예: `quality_blocks.py::_determine_status`)은 블록 전체를 실행하지 않고 함수
단위로 직접 테스트한다 — 픽스처/DB 없이 빠르게 회귀를 잡을 수 있다.

### 2.7 일괄 작업(batch) 엔드포인트 추가하기 — `POST /documents/batch-reprocess` 사례

문서 여러 건에 같은 동작(삭제/재처리 등)을 적용하는 엔드포인트를 만들 때, 단일 문서용
엔드포인트(`/{document_id}/reprocess`)를 그대로 반복 호출하게 하면 호출자가 문서마다
다른 컨텍스트(예: 이 문서가 실제로 어느 블록에서 실패했는지)를 매번 알아내서 넘겨야
한다. `batch_reprocess_documents`(`app/api/v1/endpoints/documents.py`)는 그 대신
서버 쪽에서 각 문서의 `active_run_id` → 가장 최근 `WorkflowRunStep(status="FAILED")`
→ `block_instance_id`를 역추적해 시작 블록을 **자동으로 해석**한다
(`resolve_start_block` + `start_partial_reprocess`, `reprocess_service.py` 재사용).

이 패턴을 따를 때 지켜야 할 것:

- **부분 실패가 전체 요청을 막지 않는다.** `ids` 배열을 순회하며 문서 하나가
  권한 없음/상태 부적합/실행 기록 없음 등으로 실패해도 `results` 리스트에
  `status="failed"|"skipped"` 항목을 쌓고 다음 문서로 계속 진행한다 — 응답은
  항상 `ids`와 같은 길이의 `results`를 반환하며, 프론트는 이걸로 큐잉/스킵/실패
  건수를 집계해 보여준다(`DocumentsPage.tsx`의 `reprocessSummary`).
- **상태 문자열은 3가지로 고정**: `"queued"`(재처리 시작됨, `run_id` 포함) /
  `"skipped"`(애초에 대상이 아님 — 예: FAILED가 아닌 문서) / `"failed"`(대상은
  맞는데 처리 중 오류 — 권한 없음, 실행 기록 없음, 실패 스텝 못 찾음 등). "성공적으로
  건너뜀"과 "처리하려다 실패"를 구분해야 사용자가 원인을 판단할 수 있다.
- **개별 문서 재처리(`/{document_id}/reprocess`)의 서비스 계층을 재사용**하고
  ­엔드포인트 레벨에서 새로 구현하지 않는다 — `resolve_start_block`/
  `start_partial_reprocess`는 이미 `skip_review` 승계(1.5절 (B))와 다운스트림
  폐포 계산(§12.1)을 처리하므로, 배치 엔드포인트가 이를 재구현하면 그 수정이
  단일 문서 경로에는 반영되지 않는 드리프트가 생긴다.

### 2.8 문서 체계

| 문서 | 목적 |
|---|---|
| `docs/design/*.md` | 설계 의도, 화면/데이터 구조, 최초 설계 시점의 결정 |

표시되어 있다 — 설계서만 보고 구현을 추측하지 말고 이 콜아웃을 먼저 확인한다.
