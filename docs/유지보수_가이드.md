# DocVec Project_2 유지보수 가이드

이 문서는 `docs/기술문서_시스템_아키텍처.md`(기능이 어떤 알고리즘으로 동작하는지)와
`docs/design/*`(설계 의도, 화면/데이터 구조)를 보완하는 **운영·유지보수 실무 문서**다.
"지금 장애가 났는데 무엇을 봐야 하는가", "새 기능을 어디에 어떻게 붙여야 하는가"에 바로 답한다.

**최종 갱신**: 2026-10-12 · **테스트 기준선**: 1471 passed / 1 skipped, 라인 커버리지 98%

---

## 1부: 운영 런북

### 1.1 스택 구성

Docker Compose 프로젝트명은 `project_2`(디렉터리명이 기본값, 컨테이너는 `project_2-<서비스>-1`).
같은 호스트에 다른 스택이 떠 있을 수 있어 아래 명령은 항상 `-p project_2`를 명시한다.

| 서비스 | 역할 | 비고 |
|---|---|---|
| `api` | FastAPI 앱 서버 | `./backend:/app` 마운트 — 코드 변경 시 재시작만 필요 |
| `worker` | Celery 워커 (`critical/high/normal/low` 큐, concurrency 4) | CPU 블록(입력·추출·정제·청크 분할 등) |
| `worker-embed` | Celery 워커 (`embed` 큐 전용, concurrency 1) | GPU 모델(BGE-M3, 로컬 LLM)을 쓰는 작업 전부 — 1.1-A |
| `beat` | Celery beat | 30초마다 `sweep_stuck_workflow_runs` 실행 — 1.5 (A)·(A-4) |
| `flower` | Celery 모니터링 UI | `FLOWER_BASIC_AUTH` 필요, 서버 PC에서만 접속(5556) |
| `frontend` | React 정적 빌드 (nginx) | 코드 변경 시 **재빌드 필요**(핫리로드 없음). 호스트 포트 없음 — Caddy 경유 |
| `postgres` | 메타데이터 DB | 호스트 `127.0.0.1:5433` |
| `redis` | Celery 브로커/백엔드 | 호스트 `127.0.0.1:6380` |
| `qdrant` | 벡터 DB | 호스트 `127.0.0.1:6335/6336` |
| `minio` | 오브젝트 스토리지 | 호스트 `127.0.0.1:9002`(API)·`9003`(콘솔) |
| `caddy` | HTTPS 리버스 프록시 | **외부 노출의 유일한 진입점** — 호스트 80/443/4443/3001 → 컨테이너 TLS. 1.9 참고 |

**1.1-A GPU 작업은 `embed` 큐 하나로만 보낸다.** 일반 `worker`에서 LLM/임베딩이 돌면 프로세스마다
모델 사본이 올라가 GPU 메모리를 두고 경합하고 `CUDA error: unspecified launch failure`로 문서가
FAILED 된다. `step_queue_for_block`(`tasks/workflow.py`)은 `_GPU_BLOCK_TYPES`(`rag_store`·`summarize`·
`extract_keywords`·`classify`·`extract_entities`·`output`)와 `strategy=semantic`인 `chunk_split`을
`embed` 큐로, 나머지는 `normal`로 보낸다. 레거시 배치 태스크(`continue_processing`·`generate_summary`·
`extract_metadata`·`reembed_collection`)도 같은 큐다. GPU 블록을 추가하면 `_GPU_BLOCK_TYPES`에
넣는다(`test_gpu_queue_routing.py`가 목록을 고정). 대가로 GPU 블록은 직렬 실행이라 컬렉션 재처리가 느리다.
BGE-M3는 배치 16(`embedding.py::_BATCH_SIZE`)으로 인코딩한다 — 키우면 큰 PDF에서 VRAM이 모자란다.

**1.1-B 가상환경 볼륨.** `api`는 `backend_venv`, `worker`·`worker-embed`·`beat`는 `worker_venv`를
`/app/.venv`에 마운트한다(워커 venv에만 torch 등 GPU 의존성이 있음). 의존성을 바꾼 뒤에는 이미지를
다시 빌드하고 해당 볼륨을 지워야 반영된다.


### 1.5 자주 발생하는 장애와 대응

**(A) Celery 하드 타임아웃으로 run이 RUNNING에 영구히 멈춤**
- 원인: `time_limit`을 넘기면 billiard가 워커를 SIGKILL 하므로 앱 코드(`except`)로 잡을 수 없다.
- 대응(자동): `beat`가 30초마다 `sweep_stuck_workflow_runs`를 실행하고, `GET /documents/{id}` 호출 시
  `reprocess_service.reconcile_stuck_run()`도 같은 기준(`_TIMEOUT_GRACE_SECONDS`=30초, run별
  `timeout_overrides`)으로 정리한다. `docker logs project_2-beat-1`로 30초 간격 실행을 확인한다.
- 블록 기본 타임아웃(`config.timeoutSeconds`)은 전 블록 1800초다. 그래도 초과하면 재처리 시 문서
  하나에만 타임아웃을 늘린다:

```python
await reprocess_service.start_partial_reprocess(
    db, doc, from_block_type="text_extract",
    timeout_overrides={"text_extract": 3600, "rag_store": 3600},
)
```

`timeout_overrides`는 `WorkflowRun` 단위라 공유 `WorkflowBlockInstance.config`를 건드리지 않는다.

**(A-1) `Document.active_run_id`가 이미 끝난 run을 가리킴**
- 증상: 분석 run이 멈추거나 실패했는데 문서 상세·재처리·정체 감지가 엉뚱한(완료된) run을 본다.
- 불변식: `_maybe_trigger_analysis`와 `_fail_document`는 자기 run의 id로 `active_run_id`를 갱신해야 한다.
- 확인: `SELECT active_run_id FROM documents WHERE id=...` 와
  `SELECT id, status FROM workflow_runs WHERE document_id=... ORDER BY created_at` 를 비교.

**(A-2) 모든 step이 COMPLETED인데 run이 RUNNING에 멈춤**
- 원인: merge 블록이 아닌 블록에 incoming edge가 2개 이상이면(명시적 병합 없는 fan-in) 같은 블록이
  중복 디스패치될 수 있고, 늦게 끝난 쪽이 "이미 완료됨" 조기 반환 경로로 빠져 run 완료 확인을 건너뛴다.
- 대응: 조기 반환 경로에서도 `_maybe_complete_run`을 호출한다(안전망).
- 확인: `SELECT block_instance_id, count(*) FROM workflow_run_steps WHERE run_id=... GROUP BY 1 HAVING count(*) > 1`.

**(A-3) run은 COMPLETED인데 문서는 FAILED로 보임**
- 원인/불변식: `_maybe_complete_run`이 문서를 `INDEXED`로 되돌릴지는 `doc.status`가 아니라
  **`str(doc.active_run_id) == str(run.id)`**(이 run이 지금 활성 run인가)로 판단한다. 더 새로운 run에 자리를
  내준 뒤늦은 run만 걸러진다.
- 과거에 완료된 run에 대해서만 1회성 복구가 필요하면:

```sql
UPDATE documents d SET status='INDEXED', updated_at=now()
FROM workflow_runs wr
WHERE d.active_run_id = wr.id AND d.status='FAILED' AND wr.status='COMPLETED';
```

- 회귀 테스트: `test_workflow_execution.py::test_terminal_block_flips_failed_document_back_to_indexed_when_run_is_still_active`,
  `::test_terminal_block_does_not_flip_document_superseded_by_a_newer_run`.

**(A-4) 다음 스텝 메시지가 유실돼 run이 RUNNING에 멈춤 (sweeper 재디스패치)**

워커/브로커가 죽어 "다음 블록 실행" 메시지가 사라지면, 실행 중 스텝이 없어 (A)의 timeout 판정에
걸리지 않는다. `sweep_stuck_workflow_runs`는 `_redispatch_orphaned_run`으로 되살린다.
- 마지막 활동(PENDING 스텝의 `created_at` = 마지막 디스패치 시각, COMPLETED는 `completed_at`)으로부터
  600초(grace)가 지난 run만 대상이다 — GPU 큐에서 대기 중인 정상 run을 건드리지 않기 위한 값. 대기가
  600초를 넘으면 같은 스텝이 중복 디스패치될 수 있으나 `run_workflow_step`의 COMPLETED/FAILED 조기
  반환(A-2)이 중복 실행을 막는다.
- **유실된 가지만** 다시 진행한다(`_advance(..., only_targets=...)`) — 이미 집계된 merge 엣지를 다시
  발화하면 `completed_incoming_edges`가 부풀어 merge가 일찍 실행된다.
- 전 스텝이 COMPLETED인데 마지막 완료 처리가 유실된 run은 `_maybe_complete_run`으로 닫는다. 상태 전이는
  `WHERE status='RUNNING'` 조건부 UPDATE라 두 워커가 동시에 완료 처리해도 AUTO_ANALYSIS run이 중복 생성되지 않는다.
- run 하나의 재디스패치 예외는 격리된다(`_try_redispatch`: rollback + `logger.exception`). 반환값은
  `{"swept_run_ids", "redispatched_run_ids"}`.
- 회귀 테스트: `test_workflow_engine_hardening_pg.py`(실제 Postgres 필요).

**(B) 검토 없이 재처리해도 다시 WAITING_REVIEW로 멈춤**
- `start_partial_reprocess`는 부모 run의 `skip_review`를 복사해야 한다(`skip_review=parent_run.skip_review`).
  빠지면 컬럼 기본값 False로 새 run이 생겨, 이미 검토를 통과한 문서가 재처리마다 검토 대기에 걸린다.

**(C) 재처리 후 특정 탭(구조/정제/사전/PII)이 비어 보임**
- `workflow.py::_CACHE_SAFE_BLOCK_TYPES`(현재 `{"file_validate","format_detect","text_extract"}`)에 없는
  블록은 런-스코프 캐시를 재사용하면 안 된다(deny-by-default). 새 블록 결과가 재처리 시 비어 보이면
  이 목록에 잘못 넣었는지, 정말 캐시-안전(입력이 같으면 출력이 결정적, 다른 run에 영향 없음)한지 검증한다.
- 캐시 키: `sha256(document_id:input_hash:block_type:block_version:config_hash:dict_version_part:skip_review_part)`.

**(D) 청크 0개인데 품질 검증이 SUCCESS_WITH_WARNING으로 통과**
- `overall_score`는 5개 지표 평균이라 청킹 점수 0이 다른 지표에 희석될 수 있다.
  `quality_blocks.py::_determine_status()`가 `chunk_count == 0`이면 평균과 무관하게 FAILURE로 확정한다
  (`block_version` 1.4.0). 다른 상태가 나오면 이 함수부터 확인.

**(E) 사전 항목을 추가했는데 검색/토크나이징에 반영 안 됨**
- Kiwi 캐시가 자동 갱신되지 않는 경로가 있다. API(`/dictionary/*`)를 우회해 DB에 직접 INSERT 했다면
  `app/services/dictionary_service.py::refresh_dictionary_cache(db)`를 수동 호출한다.

**(F) 원문대조에서 파일이 열리지 않고 다운로드됨 / 미리보기가 비어 있음**
- 원본이 `application/octet-stream`으로 저장됐을 가능성: 업로드는 알려진 확장자(.pdf/.docx/.hwp/.hwpx)를
  서버 매핑으로 고정한다(`upload.py::_resolve_content_type`). 기존 객체는 MinIO 객체와
  `documents.mime_type`을 함께 보정해야 한다.
- 일부 접속 경로에서만 안 열리면 `MINIO_RELATIVE_URLS=true`인지(상대 URL이 아니면 접속 주소와 `MINIO_PUBLIC_ENDPOINT`가 달라 실패),
  hwpx(HTML 미리보기)가 안 열리면 Caddy MinIO 중계 응답의 `X-Frame-Options`/CSP를 확인한다(1.9).

**(G) 워크플로우 편집기에서 블록이 한 점에 겹치거나 움직이지 않음**
- 게시된 버전은 읽기 전용이라 블록을 끌 수 없다(이동·추가·삭제·연결 모두). "새 버전으로 저장"으로 초안을 만들어야 편집된다.
- 블록 `position`이 `{}`로 저장된 워크플로우(시드/API 생성)는 편집기에서 모든 블록이 (0,0)에 겹친다. 마이그레이션
  `3c5e7a9b1d2f`가 좌표 없는 블록에만 위→아래(열당 6개, 다음 열로) 배치를 채우고, 프런트(`lib/workflowLayout.ts`)도
  좌표가 없으면 같은 규칙으로 펼쳐 보여 준다. 두 규칙은 항상 같아야 한다(카드 약 287×68, 간격 360×130).
- 확인: `SELECT block_type, position FROM workflow_block_instances WHERE version_id=...` 에서 `position`이 `{}`이면 좌표 없음.
  API/시드로 워크플로우를 새로 만들 때는 `position`을 채워 넣는다.

**(H) 블록 속성 패널의 선택형 입력(오타 방지)**
- 값의 종류가 정해진 설정은 자유 입력 대신 선택으로 제공한다: `text_extract.engine`(legacy/docling), `ocr.engine·language`,
  `pii_detect.mask_char`(단일 select), `file_validate.allowed_extensions`·`user_dict.term_types`·`pii_detect.entity_types`·
  `extract_entities.entity_types`·`stopword.scope_filter`(체크박스 다중 선택; 아무것도 체크하지 않으면 전체 적용).
- 선택지는 `frontend/src/lib/blockConfigSchema.ts::FIELD_OVERRIDES`(스키마 자동 생성 블록) 또는 `lib/workflowBlocks.ts`
  (하드코딩 블록)의 `options`에 둔다. `list` 타입에 `options`가 있으면 체크박스, 없으면 쉼표 입력이다. 저장 값은 선택지 순서로
  정렬되어 클릭 순서와 무관하다. `stopword.scope_filter` 선택지는 사전에 등록된 적용 범위에서 동적으로 만든다.
- 백엔드 Config의 허용 값이 바뀌면(예: 새 OCR 엔진, 새 PII 유형) 위 `options`도 함께 갱신한다. 자유 입력으로 남긴 것은 값이 사용자 정의인
  `classify.categories`, `summarize.prompt` 등이다.

**(I) 워크플로우 설정을 바꿨는데 재처리해도 반영되지 않음 (예: 텍스트 추출 엔진 docling)**
- 재처리(특정 블록부터/전체)는 문서를 처리했던 run의 `version_id`를 그대로 물려받는다. 새 버전을 게시해도 재처리에는 반영되지 않는다 —
  새로 업로드한 문서만 최신 게시 버전을 쓴다.
- 재처리 대화상자의 **"최신 게시 버전으로 처리"**(전체 모드) 또는 API `POST /documents/{id}/reprocess` 의 `use_latest_version: true`
  (+ `start_block_type`)를 쓰면 문서 워크플로우의 최신 게시 버전(컬렉션이 버전을 고정했으면 그 버전)으로 처음부터 새 run을 만든다
  (`reprocess_service.start_reprocess_on_latest_version`). 설정이 같은 블록은 `block_execution_cache`가 재사용한다. 이 경로는 상류 스텝을 복사하지
  않고, 특정 블록 지정·`edited_text`와는 함께 쓸 수 없다. 초안(미게시) 버전은 사용되지 않으므로 먼저 게시해야 한다.
- 백엔드 코드/설정(`config.py` 등)을 바꾼 뒤에는 api뿐 아니라 `worker`, `worker-embed`, `beat`도 재시작한다. 워커는 시작 시점의 모듈을
  메모리에 들고 있어 bind mount로 파일만 바뀌면 일부 모듈만 새 코드를 읽어 `AttributeError`(예: `minio_public_secure`)가 난다.

**(J) 품질 탭 점수 해석 (quality_check 1.5.0)**
- 종합점수는 **측정된 항목**의 단순 평균이다. 정규화(항상 100점 고정값)는 1.5.0부터 점수에서 제외했고, 과거(1.4.0 이하) 리포트의 종합점수는 이 값 때문에 높게 나와 있다.
- **원문 재현율(sourceRecall)**: 원본 PDF 텍스트 레이어를 5글자 조각으로 나눠 추출 결과(`parsed_text`)에 들어 있는 비율을 센다
  (`pipeline/blocks/source_recall.py`; 공백·표 구분자·마크다운 기호 무시). 기본 기준 `min_source_recall=0.8`. 스캔본(텍스트 레이어 없음)·PDF 아닌 문서는
  측정하지 않고 사유를 `metrics.source_recall_status`(`unsupported_format`/`no_text_layer`/`error`)에 남긴다.
- 기존 문서는 재처리해야 새 지표가 생긴다(블록 버전이 올라 캐시가 무효). 재처리 대화상자에서 "특정 블록부터 → 품질 검사"를 고르면 된다.
- 화면의 "점수는 어떻게 계산되나요?" 설명은 `frontend/src/components/document-detail/qualityCriteria.ts`에 손으로 옮겨 둔 것이라, 백엔드 계산식이나
  기본 임계값이 바뀌면 함께 고쳐야 한다.

**(K) 분석 워크플로우가 있는 컬렉션 문서의 재처리 / 품질 지표 갱신**
- 컬렉션에 기본 분석 워크플로우가 있으면 전처리가 끝난 뒤 AUTO_ANALYSIS run이 자동 실행되어 `documents.active_run_id`가 그 분석 run을 가리킨다.
  전처리 블록(`file_validate`, `quality_check` 등)은 분석 워크플로우에 없으므로, 재처리 API는 이 경우 문서의 최근 PREPROCESS run을 기준 run으로
  삼는다(`reprocess_service.resolve_reprocess_parent`, `find_preprocess_run`). "최신 게시 버전으로 처리"도 같은 기준으로 워크플로우를 찾는다.
- **`quality_check`나 그 이후 블록(`rag_store`)부터 재처리하지 마라.** 부분 재처리는 상류 단계 결과만 복사하고 노드·청크 행은 원래 run_id에 남기 때문에
  새 run에는 데이터가 없다(품질 검사는 부모 run을 거슬러 올라가 찾도록 보완했지만 `rag_store`는 아니다). 게다가 `quality_check` 뒤에 `rag_store`가 있어
  재처리하면 벡터가 다시 쓰이고, 경고가 있으면 검토 대기(WAITING_REVIEW)로 문서 상태가 바뀐다.
- 기존 문서의 품질 리포트만 새 기준으로 다시 계산하고 싶으면 run·상태·벡터를 건드리지 않고 `QualityCheckBlock.run()`을 기존 run_id로 직접 호출해
  리포트 행을 제자리 갱신한다(2026-10-12 17건 적용).

**(L) PDF 표 셀 텍스트 누락 (text_extract 1.16.0에서 수정)**
- 칸 선이 불완전한 표(머리글·가운데 열만 칸이 닫히고 첫/셋째 열 본문에는 칸 선이 없는 공고문 표 등)는 `pdfplumber`가 일부 글자를 어떤 셀에도 넣지 못해 빈 칸으로
  나오는데, 예전에는 표 영역(bbox) 전체를 본문에서 지워 그 글자가 사라졌다. 이제 본문에서는 **셀 사각형만** 가려(`pdf_adapter._table_exclusion_rects`,
  `RawTableCandidate.cell_bboxes`) 셀 밖 글자는 본문에 남는다 — 표 구조는 복원되지 않고 내용만 보존된다.
- 실측(원문 재현율): 공고문 `9de24659` 0.743→0.813, `1d5caddf` 0.874→0.910, 그 외 표가 정상인 문서는 변화 없음.
- 기존 문서는 재처리해야 반영된다(블록 버전이 올라 캐시 무효). 재처리 시 다운스트림과 AUTO_ANALYSIS(LLM 호출)가 다시 실행되므로 필요한 문서만 골라 `text_extract`부터 한다.

**(M) 스캔 PDF OCR 품질과 설정 변경 절차 (text_extract 1.18.2 / quality_check 1.6.0)**
- 증상: 스캔본(특히 글자가 윤곽선·이미지로 들어간 PDF)이 "성공"으로 끝났는데 RAG 텍스트가 비었거나 글자가 벌어져 있다(`서 울 시 도 시…`). 원인은 세 가지가 겹쳤다.
  ① Tesseract 설정(`--psm 3` + Otsu 이진화)이 한글 스캔에서 가장 나쁨 ② `engine=docling`은 비트맵 영역에만 OCR을 돌려 텍스트 레이어 없는 PDF가 빈 텍스트가 됨
  ③ 품질 지표가 이를 못 잡음(표 문법만으로 길이 통과, OCR 신뢰도는 단어 단위라 글자 벌어짐을 놓침).
- 수정: `pdf_adapter._TESSERACT_CONFIG = "--oem 1 --psm 4"` + 회색조(이진화 제거) / 추출 엔진 선택지를 **자동(기본)/Docling/legacy**로 두고, `extraction_blocks.resolve_extract_engine`이 자동 모드에서 텍스트 레이어 있는 PDF는 Docling, 없는 PDF는 legacy(전면 OCR)로 보내고
  그 사실을 경고로 남김(명시적 Docling은 따르되 스캔본이면 경고만 남긴다) / quality_check가 쪽당 실질 글자 30자 미만이면 평균과 무관하게 **FAILURE**(검토 우회 불가, 그래서 rag_store 앞에서 멈춰 기존 색인이 덮어쓰이지 않는다)이고,
  OCR 결과의 한 글자 토큰 비율(`ocr_single_char_ratio`, 기준 25%)을 ocr 점수에 반영한다.
- **근거(`backend/scripts/ocr_benchmark.py`, 32쪽·질문 56개, 텍스트 레이어 있는 PDF를 이미지로 렌더링해 원본 텍스트를 정답으로 사용)**:

  | 설정 | 4글자 F1 | 한 글자 토큰 | 검색 hit@1 | MRR |
  |---|---|---|---|---|
  | 이전 운영(psm3+Otsu) | 0.244 | 40% | 0.30 | 0.48 |
  | psm6 회색조 | 0.594 | 6% | 0.70 | 0.80 |
  | **psm4 회색조(채택)** | 0.628 | 5% | 0.68 | 0.78 |
  | psm4+Otsu | 0.621 | 5% | 0.64 | 0.77 |

  psm4와 psm6은 검색 지표 차이가 표본 노이즈 수준이라 텍스트 재현이 높은 psm4를 택했다. 한계: 렌더링 이미지는 실제 스캔보다 깨끗하다(기울기·노이즈 없음).
- **OCR/엔진 설정을 바꿀 때는 반드시 벤치마크를 다시 돌려 위 표를 갱신한다**(감으로 바꾸지 않는다):
  `docker compose -p project_2 exec -T worker-embed sh -c "cd /app && PYTHONPATH=/app python scripts/ocr_benchmark.py --retrieval --engines tesseract_legacy,tesseract_gray_psm4 --pdf /tmp/x.pdf:1,2,3"`
- 기존 스캔 문서는 재처리해야 반영된다.
- **운영 경로 ≠ 벤치마크 경로 사고(1.18.1)**: 처음엔 벤치마크가 `image_to_string`을 쟀지만 운영은 `image_to_data`의 단어 상자를 공백으로 이어 붙였다. 한글은 음절 단위로 쪼개져 나와 실제 스캔 보고서에서 한 글자 토큰이 63%(벤치마크 5%)였다.
  지금은 본문을 `image_to_string`에서, 신뢰도만 `image_to_data`에서 얻는다(스캔 쪽당 OCR 2회). 벤치마크는 운영 함수와 같은 호출을 쓰는지 먼저 확인한다. 실제 스캔 서울시 보고서 27쪽 기준 63% → 7%, 품질 75 → 100.
- **코드만 고치고 `block_version`을 안 올리면 재처리해도 예전 결과가 나온다**: `text_extract`는 `block_execution_cache`(키에 block_version 포함)를 쓰므로, 출력이 달라지는 수정은 반드시 버전을 올려야 한다(1.18.0→1.18.1에서 겪음).
  또 재처리는 활성 run이 COMPLETED/FAILED여야 시작되므로, 검토 대기(WAITING_REVIEW) 중인 run은 먼저 반려해 종료시킨다.
- **차트 안 글자(1.18.2)**: Docling 은 그림으로 분류한 영역의 글자를 본문에서 빼고, 그림 인식은 그 영역을 이미지 OCR 하므로 원본에 정확한 라벨·수치가 있어도 깨진 조각이 남았다.
  이제 `docling_adapter._attach_native_text_to_pictures`가 그림 영역의 원본 텍스트 레이어 글자를 `RawImageRegion.native_text`로 붙이고, `process._recognize_document_images`가 10자 이상이면 OCR 대신 쓴다.
  사례집 PDF 재현율 78.0% → 84.5%(누락 쪽 없음). 원본 텍스트가 없는 그림(래스터 이미지)은 여전히 OCR 에 의존한다.
- **게시된 워크플로우 주의**: 게시 버전은 불변이라 config가 그대로다. "표준 전처리 워크플로우" v5/v6은 `engine=docling`이 명시돼 있어 스캔 PDF를 우회하지 않는다(경고만 남고 텍스트는 거의 비게 된다) —
  스캔 문서를 처리하려면 엔진을 `자동`으로 바꾼 새 버전을 게시해야 한다. v1~v4는 engine이 미지정이었고 기본값이 `legacy`→`auto`로 바뀌어, 이 버전으로 재처리하면 텍스트 PDF가 Docling으로 처리된다.

**(N) 문서 메타정보(제목·쪽수·언어·분류) 자동 판정과 사용자 수정 (text_extract 1.21.0 / structure_analyze 1.10.0 / output 1.6.0)**
- 증상: 메타정보 화면의 제목이 "1. 사업개요"·"들어가기 앞서 (1/2) ⚫ …", 쪽수가 5쪽 docx에서 1, 언어가 영문 약어 섞인 한글 문서에서 비어 있음, 분류가 전부 "보고서"/"미분류".
  이유는 각각 ① 제목 = 트리의 첫 HEADING ② DOCX/HWP는 쪽 구분이 파일에 없어 1로 고정 ③ 한글·영문 비율이 비슷하면 판정 보류 ④ 기본 분류 목록이 빈약하고 모델이 주제로 분류.
- **제목**(`blocks/title_resolver.py`, structure_analyze가 호출): 쓸 만한 파일 속성 제목(PDF info·DOCX core, `source_title`에 원본 보관) → 1쪽 표지 줄(글자 크기 → 제목 표시 → 짧은 줄 덩어리, 장 제목("1. …", "Ⅳ. …")은 경계로만 쓰고 제목에서 제외) →
  OCR이 의심되면 정제 파일명(OCR 문서는 유사도 0.55↑, 그 외에는 글자 수가 비슷하면서 0.8↑일 때만) → 장 제목이 아닌 첫 heading → 정제 파일명. 슬라이드 불릿(`⚫`)·`(1/2)`·콜론으로 끝나는 줄·`<차례>`는 제목이 될 수 없다.
  구조 분석은 hwpx 공고문의 `□ 사업개요` 줄도 레벨 1 제목으로 인식한다(없으면 "제목이 하나도 탐지되지 않았습니다"로 검토 대기가 된다).
- **쪽수**: PDF는 원본 쪽수(Docling은 요소 있는 쪽만 세므로 원본 PDF 쪽수와 큰 값을 쓴다). DOCX는 Word 가 직접 저장한 `docProps/app.xml`의 `<Pages>`(단어 수 `<Words>`가 0보다 큰 문서만 — 생성기가 만든 문서는 Pages=1, Words=0 템플릿 값이라 제외)를 우선하고, 없으면 LibreOffice 미리보기 PDF 쪽수(글꼴 차이로 실제와 다를 수 있는 근사치). HWP/HWPX는 미리보기 PDF로 쪽을 나눈 경우만 값이 있고,
  **변환이 안 되면 NULL**(1로 적지 않는다 — 현재 `.hwpx`는 LibreOffice가 PDF로 변환하지 못해 NULL). **워커 이미지에 `libreoffice-writer`·`fonts-nanum`이 있어야 한다**(`Dockerfile.worker`; 예전에는 api 이미지에만 있어 워커의 재페이지네이션이 조용히 실패했다).
- **언어**: 한글 비율 ≥ 40%면 ko, ≤ 10%면 en(영문 약어가 섞인 한국어 문서가 ko가 되도록), 그 사이는 판정 보류.
- **분류**: 기본 목록 12종(공고문·제안서·진단보고서·가이드라인·매뉴얼·사례집·소개서·기준서·계약서·공문·보고서·기타). `ClassifyBlock`이 카테고리별 판단 기준(`_CATEGORY_HINTS`)과 파일명을 프롬프트에 함께 주고 "주제가 아니라 문서 종류로 고르라"고 지시한다(커스텀 카테고리에는 설명을 붙이지 않는다).
  워크플로우에 `categories`를 직접 둔 경우(분석 워크플로우 v3)는 그 목록이 우선이다. 분류는 AUTO_ANALYSIS(LLM)가 채우므로 "분석 없음" 컬렉션은 PENDING으로 남고, UI가 그 사실을 안내한다.
- **사용자 수정과 재처리 보호**: `PATCH /documents/{id}/metadata`가 `title`·`language`(ko/en/ja/zh)·`category`를 받으면 `documents.user_edited_fields`(JSON 배열)에 필드명을 기록하고, 재처리(`text_extract`·`structure_analyze`·`output`)는 그 필드를 덮어쓰지 않는다.
  값을 비우거나 `reset_fields: ["title", …]`를 보내면 값과 표시를 지워 다음 재처리 때 자동값이 다시 채워진다. 언어를 바꾸면 해당 문서의 `document_chunks.language`도 함께 갱신한다(Qdrant 페이로드에는 language가 없다).
  마이그레이션 `4d6f8a0c2e4b`(`source_title`, `user_edited_fields` 추가). UI는 문서 상세 사이드바에서 "직접 수정됨" 배지와 "자동값으로 되돌리기"를 보여준다.
- **UI 주의**: 인라인 스타일에 쓰는 색 변수는 `index.css`에 정의된 것만 쓴다(`--color-primary`는 없다 — 정의 안 된 변수가 든 `border` 선언은 통째로 무효라 테두리가 사라진다).
- 기존 문서는 재처리해야 반영된다. 17건을 한꺼번에 재처리하면 큰 PDF가 CPU 경합으로 text_extract 30분 제한(1800초)을 넘어 FAILED가 되고, 자동 재시도가 겹치면 `block_execution_cache_pkey` 중복 오류가 난다 —
  **쪽수 많은 PDF는 한 건씩 재처리**한다(단독이면 2~10분).

### 1.9 외부 접속 — Caddy HTTPS 리버스 프록시

**원칙**: 외부에는 `caddy`만 노출한다. `postgres`·`minio`·`flower`·`api`·`redis`·`qdrant`의 호스트 포트는
전부 `127.0.0.1` 전용이라 서버 PC 자신에서만 접속된다. `frontend`는 호스트 포트가 없고 Caddy가
`frontend:80`으로 전달한다.

**요청 경로**: 외부 → `caddy`(TLS 종료) → `frontend:80`(nginx) → `/api/`만 `api:8000`으로 재프록시.
프런트(`apiClient.ts`)가 상대경로(`/api/v1`)만 쓰므로 한 포트만 열어도 API까지 도달한다. 원본/아티팩트
다운로드(presigned URL)는 Caddy가 같은 출처에서 `/originals/*`·`/artifacts/*`를 MinIO로 중계한다
(GET·HEAD만, 버킷은 비공개라 서명 없으면 403).

**포트포워딩**: Caddy는 호스트 **443·4443·3001**(모두 컨테이너 TLS 443)과 80(https 리다이렉트)을 연다.
공유기 내부 대상은 이 중 하나이고 외부 포트는 환경에 맞게 고른다. 그 외 포트(8001, 5433, 9002, 9003,
5556 등)는 절대 포워딩하지 않는다.

**현재 구성(2026-10-12 실측)**: 이 환경은 외부 443이 도달하지 않아(통신사/공유기 차단 추정) 공유기에서
**외부 4443 → 서버 PC(192.168.0.3)의 내부 3001**로 포워딩하고 접속 주소는 `https://49.168.97.107:4443`.
`.env`는 다음과 같이 맞춰야 한다.

| 항목 | 값 | 이유 |
|---|---|---|
| `MINIO_RELATIVE_URLS` | `true` | presigned URL을 호스트 없는 **상대 경로**(`/originals/…?서명`)로 내려준다. 브라우저가 지금 접속한 출처(사내 IP·공인 IP·포트 무관)로 요청하므로 서버 PC 안에서도, 사내 PC·외부에서도 같은 URL이 열린다 |
| `MINIO_PUBLIC_ENDPOINT` | `49.168.97.107:4443` | **서명 계산용 Host**. Caddy가 MinIO로 보낼 때 `header_up Host`로 이 값을 되돌려 서명이 검증된다(접속 주소와 같을 필요는 없지만 Caddyfile·`.env`가 같은 값을 보게 되어 있음) |
| `MINIO_PUBLIC_SECURE` | `true` | `MINIO_RELATIVE_URLS=false`일 때 절대 URL을 https로 생성(상대 URL이면 영향 없음) |
| `CORS_ALLOWED_ORIGINS` | 위 주소의 `https://…` origin 포함 | 백엔드 CORS 검증은 프록시와 별개 |

`MINIO_RELATIVE_URLS=false`(기본)이면 URL이 절대 주소라 접속 주소와 `MINIO_PUBLIC_ENDPOINT`가 같아야 하고, 이 환경처럼 공유기가 내부→공인 IP 접속(헤어핀 NAT)을 지원하지 않으면 서버 PC·사내 PC에서 원본이 열리지 않는다. 그래서 `true`로 쓴다. Caddy 없이 직접 접속하는 개발 환경에서는 `false` + `localhost:9002`.

**주소·IP가 바뀌면**: `caddy/Caddyfile` 사이트 주소(`192.168.0.3, 192.168.0.90, 49.168.97.107`)와 `.env`의
위 두 값을 함께 고치고 `up -d api` + `restart caddy`. 서버 PC의 사내 IP가 바뀌면 공유기 포워딩이 어긋나므로
공유기에서 DHCP 예약(고정 IP)을 걸어 둔다. 공인 IP가 유동이면 DDNS 도메인을 쓰고, 도메인이 생기면
Caddyfile 주소만 도메인으로 바꿔 Let's Encrypt 로 전환한다.

**사내(LAN)·서버 PC 접속**: `MINIO_RELATIVE_URLS=true`라 사내 IP(`https://192.168.0.3:3001` 등)로 접속해도 원본이 열린다 —
공유기의 헤어핀 NAT가 필요 없다. 접속하는 주소가 Caddyfile 사이트 주소에 있고 `CORS_ALLOWED_ORIGINS`에 포함돼 있어야 한다.

**인증서**: 도메인이 없어 Caddy 내장 로컬 CA 자체 서명(`tls internal`)을 쓴다 — 최초 접속 시 "안전하지 않음"
경고는 **정상**이며 암호화는 유지된다.

**MinIO 중계 응답 헤더**(`/originals/*`·`/artifacts/*` 블록에서만 적용):
- `X-Frame-Options: SAMEORIGIN` — Caddy 전역 `DENY`가 iframe으로 띄우는 변환 미리보기(HTML, hwpx 등)를 막으므로 덮어쓴다.
- `Access-Control-Allow-Origin: *` — 서명 URL의 출처가 앱 출처와 다를 때(접속 주소와 `MINIO_PUBLIC_ENDPOINT`가 다른 경우)에도
  앱이 PDF를 fetch로 받을 수 있게 한다. 읽기 전용이고 서명이 없으면 403이라 노출 위험은 없다.
- `Content-Security-Policy: sandbox; default-src 'none'; img-src data: blob:; style-src 'unsafe-inline'; font-src data:` —
  MinIO가 앱과 같은 출처가 되어, 문서에서 변환된 HTML이 앱 권한으로 스크립트를 실행하지 못하게 한다. **PDF에는 걸지 않는다**:
  sandbox가 걸린 PDF는 Chrome이 iframe에서 뷰어를 차단해 "웹페이지가 일시적으로 다운되었거나…" 오류가 나고, 원문대조의
  대체 경로(blob 다운로드 실패 시 원격 주소를 iframe에 직접 로드)가 깨진다. 미리보기에 외부 이미지·스크립트가 필요해지면 조정한다.
- PDF 원문대조는 정상 경로에서 `usePdfBlobUrl`이 fetch로 한 번 받아 blob URL로 표시한다. 이 오류가 보이면 blob fetch가 실패해
  대체 경로로 떨어진 것이므로 브라우저 개발자도구 Console/Network의 fetch 오류(CORS, 연결 실패 등)부터 확인한다.

**IP 리터럴 접속의 TLS 함정 2가지**(2026-08-03 실측, `openssl s_client -connect <IP>:443 -servername <IP>`가
성공하면 Caddy 자체는 정상이다):
1. 사이트 주소를 `:443`처럼 포트만 쓰면 안 된다 — Windows schannel(curl.exe, 구형 .NET)은 IP 접속 시 SNI를
   보내지 않아 Caddy가 `internal error`로 거부한다. 사이트 주소를 IP로 명시하고 전역 `default_sni <IP>`를 둔다.
2. TLS1.3 키교환 그룹을 고전 커브로 제한한다 — `tls internal { curves x25519 secp256r1 secp384r1 }`
   (포스트퀀텀 `X25519MLKEM768`을 Windows TLS 스택이 지원하지 않음).

**남은 보안 점검**: 자격 증명 로테이션(노출 이력이 있는 값), MinIO 앱 계정과 root 계정 분리(현재 동일),
nginx location별 보안 헤더/CSP. 로그인·회원가입은 rate limit이 걸려 있다(`core/rate_limit.py`).

### 1.10 필수 환경변수와 동작 정책

`docker-compose.yml`은 아래 값이 비어 있으면 기동을 거부한다(`.env.example` 참고): `POSTGRES_USER`·
`POSTGRES_PASSWORD`·`POSTGRES_DB`, `MINIO_ROOT_USER`·`MINIO_ROOT_PASSWORD`, `SECRET_KEY`, `ENCRYPTION_KEY`,
`FLOWER_BASIC_AUTH`(평문 `사용자:비밀번호`, base64 아님).
- `POSTGRES_PASSWORD`는 기본값이 없다. 이미 만들어진 Postgres 볼륨의 비밀번호는 `.env`를 바꿔도 바뀌지
  않으므로 바꾸려면 `ALTER USER`를 함께 실행한다.
- `ENCRYPTION_KEY`는 BYOK API 키 암호화 키 — 데이터가 쓰인 뒤 바꾸면 기존 암호문을 읽지 못한다(분리·교체는
  추후 고도화).

코드로 고정된 정책:
- **업로드 Content-Type**: 알려진 확장자는 클라이언트 값과 무관하게 서버 매핑을 쓴다. 그 외는 비일반 선언값을
  존중하고, 없으면 확장자 추정(`upload.py::_resolve_content_type`).
- **presigned URL 유효시간 1시간**(`get_download_url`) — 권한이 회수돼도 발급된 URL은 만료 전까지 유효하다.
- **워크플로우 실행**(`POST .../run`)은 대상 문서/컬렉션의 editor 권한이 필요하다. 시스템 워크플로우의 run
  목록은 admin이 아니면 본인 문서·공유 컬렉션의 run만 보인다.
- **분류(`classify`) 응답 해석**: 정확히 일치하면 그 후보, 아니면 응답에 가장 앞서 나오는(같으면 더 긴) 후보,
  없으면 마지막 후보. 빈 후보는 무시한다.

### 2.7 일괄 작업(batch) 엔드포인트 — `POST /documents/batch-reprocess` 사례

문서 여러 건에 같은 동작을 적용할 때 단일 문서용 엔드포인트를 반복 호출하게 하면 호출자가 문서마다 다른
컨텍스트(어느 블록에서 실패했는지)를 알아내야 한다. `batch_reprocess_documents`
(`app/api/v1/endpoints/documents/listing.py`)는 서버에서 `active_run_id` → 가장 최근
`WorkflowRunStep(status="FAILED")` → `block_instance_id`를 역추적해 시작 블록을 자동 해석한다
(`resolve_start_block` + `start_partial_reprocess`, `reprocess_service.py` 재사용). 지킬 것:

- **부분 실패가 전체 요청을 막지 않는다.** 응답은 항상 `ids`와 같은 길이의 `results`이고, 프런트가 이걸로
  큐잉/스킵/실패 건수를 집계한다(`DocumentsPage.tsx::reprocessSummary`).
- **상태 문자열 3가지 고정**: `"queued"`(시작됨, `run_id` 포함) / `"skipped"`(대상 아님, 예: FAILED가 아닌 문서) /
  `"failed"`(대상인데 처리 중 오류 — 권한 없음, 실행 기록 없음, 실패 스텝 못 찾음). 건너뜀과 실패를 구분해야
  사용자가 원인을 판단할 수 있다.
- **서비스 계층을 재사용**하고 엔드포인트에서 재구현하지 않는다 — `skip_review` 승계(1.5 (B))와 다운스트림
  폐포 계산(기술문서 §12.1) 수정이 단일 문서 경로와 갈라지지 않도록.

### 2.8 코드 구조 메모

`documents`와 `workflows` 엔드포인트는 패키지다(`endpoints/documents/`, `endpoints/workflows/`).
`workflows/`는 `schemas`·`access`(권한 헬퍼)·`cloning`·`definitions`·`versions`·`runs`로 나뉘고
`__init__.py`가 라우터를 합친다. `tasks/workflow.py`는 약 940줄로 800줄 기준을 넘는다 — 큐 라우팅·sweeper·
스텝 실행으로 나누는 안이 있으나 테스트의 patch 경로(`app.pipeline.tasks.workflow.*`)가 많이 영향받아
추후 고도화로 보류했다.

### 2.9 문서 체계

| 문서 | 목적 |
|---|---|
| `docs/README.md` | 문서 폴더 안내(어디에 무엇이 있는지) |
| `docs/design/*` | 설계 의도, 화면/데이터 구조, 최초 설계 시점의 결정(`메타 정보 생성.txt`, `문서데이터 전처리 방안.md` 포함) |
| `docs/plan/` | 초기 기획·상세 설계 자료(구조·실행·구현·플랫폼·벡터화·기술 명세·고도화). 현행 구현과 다를 수 있어 `design/`·기술문서가 우선 |
| `docs/참고/` | 기술 브로셔, E2E 검증 보고서 등 보조 자료 |
| `docs/기술문서_시스템_아키텍처.md` | 현재 구현이 어떤 알고리즘으로 동작하는지(공식/임계값 수준) |
| `docs/유지보수_가이드.md` (본 문서) | 장애 대응, 운영 명령어, 코드 확장 방법 |
| `docs/인수인계서.md` | 새 작업자를 위한 입구 문서 — 현황, 기동, 보류 항목, 첫날 체크리스트 |

설계서와 구현이 갈린 부분은 설계서에 "⚠ 실제 구현과 차이" 콜아웃으로 표시되어 있다 — 설계서만 보고 구현을
추측하지 말고 이 콜아웃을 먼저 확인한다.
