# language_normalization.md
# Document Vectorization Platform - Language Normalization Rules

## 1. 문서 목적

본 문서는 `SemanticNormalizationModule`이 수행하는 한국어 및 다국어 텍스트 정규화의
상세 규칙을 정의한다. 정규화는 청킹 및 임베딩의 품질을 높이고, 검색 재현율을 향상시키기
위해 텍스트를 기계 처리 친화적인 표준 형태로 변환한다.

---

## 2. 처리 순서

정규화는 아래 순서로 적용된다. 순서를 바꾸면 결과가 달라질 수 있다.

```
1. 유니코드 정규화 (NFC)
2. 공백/줄바꿈 정규화
3. 특수 문자 처리
4. 수치 표기 통일
5. 날짜/시각 정규화
6. 단위 표준화
7. 한국어 특이 표기 처리
8. 엔티티 추출 (정규화 후 수행)
```

---

## 3. 유니코드 정규화

### 3.1 NFC 정규화

- 모든 텍스트는 **Unicode NFC** (Canonical Decomposition, followed by Canonical Composition) 형태로 정규화한다.
- 이유: 동일한 한글 음절이 NFC와 NFD로 다르게 인코딩될 때 토큰화, 검색 불일치 발생을 방지한다.
- 적용 시점: 파이프라인에서 텍스트를 처음 읽어들이는 시점.

### 3.2 전각/반각 변환

| 변환 | 원본 | 결과 | 예시 |
|------|------|------|------|
| 전각 숫자 → 반각 | `１２３` | `123` | 전각 문자 사용 문서 |
| 전각 알파벳 → 반각 | `ＡＢＣ` | `ABC` | 전각 문자 사용 문서 |
| 전각 공백 → 반각 공백 | `　` (U+3000) | ` ` | 일본어 혼용 문서 |

- 전각 문장부호는 유지한다 (`。`, `、`, `「`, `」` 등 — 일본어 문서 맥락 유지).

---

## 4. 공백 및 줄바꿈 정규화

### 4.1 공백 처리

| 규칙 | 원본 | 결과 |
|------|------|------|
| 모든 공백(스페이스/탭/줄바꿈 등) 제거 | `A  B\t\nC` | `ABC` |

**구현:** `_normalize_ws(text) = re.sub(r"\s+", "", text)` (backend/app/pipeline/tasks/process.py:335)

이 급진적 정규화는 HWP/HWPX 페이지 재분할 시 LibreOffice 렌더링 PDF의 per-page 텍스트와 매칭할 때만 사용된다.
텍스트 추출 결과 자체는 원본 공백을 유지한다.

### 4.2 줄바꿈 처리 (블록 단위 적용)

- 같은 단락 내 줄바꿈: 공백으로 치환 (단, 단락 경계가 명확한 경우는 유지)
- 단락 구분자(`\n\n`): 유지
- OCR 결과 임의 줄바꿈: 문장 연속성 휴리스틱으로 처리

### 4.3 한국어 줄바꿈 휴리스틱

한국어 OCR에서 자주 발생하는 불필요한 줄바꿈을 처리한다.

```
이전 줄이 아래 조건을 모두 만족하면 줄바꿈을 공백으로 치환:
1. 이전 줄 끝이 조사/접속사로 끝남 (이, 가, 을, 를, 은, 는, 과, 와, 의, 에, 에서 등)
2. 다음 줄 시작이 소문자 또는 불완전 어절로 시작
3. 이전 줄이 마침표/물음표/느낌표로 끝나지 않음
```

## 5. 수치 표기 통일

### 5.1 천 단위 구분자 제거

| 원본 | 결과 | 비고 |
|------|------|------|
| `1,000,000` | `1000000` | 임베딩 모델이 숫자로 인식 보장 |
| `1,000.5` | `1000.5` | 소수점 유지 |
| `$1,500` | `$1500` | 통화 기호 유지 |

- 단, 표 셀 내 수치는 원본 유지 (표 요약 청크 생성 시 정규화 적용).

### 5.2 한국 대형 수치 표기 통일

| 원본 | 결과 | 비고 |
|------|------|------|
| `1억` | `100000000` | 숫자 컨텍스트에서만 변환 |
| `1천만` | `10000000` | |
| `3조 5천억` | `3500000000000` | |
| `10만 5천` | `105000` | |

- 한글 수사 + 단위어(억, 조, 만, 천, 백) 조합을 아라비아 숫자로 변환.
- 변환 결과는 `semantic_tags`에 원본 표기(`number_korean_notation`) 태그로 기록.

### 5.3 분수/비율 표기

| 원본 | 결과 | 적용 조건 |
|------|------|---------|
| `3분의 1` | `1/3` | 명백한 분수 표현 |
| `두 배` | `2배` | 배수 표현 |

## 6. 날짜/시각 정규화

### 6.1 날짜 정규화

다양한 날짜 표기를 **ISO 8601** 형식(`YYYY-MM-DD`)으로 정규화한다.

| 원본 | 결과 | 비고 |
|------|------|------|
| `2026년 1월 1일` | `2026-01-01` | 한국어 날짜 |
| `2026.01.01` | `2026-01-01` | 점 구분자 |
| `2026/01/01` | `2026-01-01` | 슬래시 구분자 |
| `26년 1월 1일` | `2026-01-01` | 2자리 연도 (2000년대로 가정) |
| `'26.1.1` | `2026-01-01` | 어포스트로피 형태 |
| `1월 1일` | `--01-01` | 연도 없는 날짜 (월일만) |

### 6.2 시각 정규화

| 원본 | 결과 | 비고 |
|------|------|------|
| `오전 9시 30분` | `09:30` | 12시간제 → 24시간제 |
| `오후 2시 30분` | `14:30` | |
| `9:30 AM` | `09:30` | 영어 형식 |
| `14시 30분` | `14:30` | |
| `14:30:00` | `14:30:00` | 초 포함 시 유지 |

### 6.3 날짜+시각 복합

| 원본 | 결과 |
|------|------|
| `2026년 1월 1일 오전 9시` | `2026-01-01T09:00` |
| `2026.01.01 14:30` | `2026-01-01T14:30` |

### 6.4 날짜 정규화 비적용 케이스

- 문맥 없는 단순 숫자 `1.1` — 날짜로 오인식 방지
- 소수점 뒤에 오는 숫자 (`123.456`)
- 법령 조문 번호 (`제1조`, `제3항`)

## 7. 단위 표준화

### 7.1 한국어 단위 특수문자 → ASCII

| 원본 | 결과 | 유니코드 |
|------|------|---------|
| `㎞` | `km` | U+339E |
| `㎡` | `m²` | U+33A1 |
| `㎥` | `m³` | U+33A5 |
| `㎏` | `kg` | U+338F |
| `㎝` | `cm` | U+339D |
| `㎜` | `mm` | U+339C |
| `㎛` | `μm` | U+339B |
| `℃` | `°C` | U+2103 |
| `㏄` | `cc` | U+33C4 |

### 7.2 단위 표기 통일

| 원본 | 결과 | 비고 |
|------|------|------|
| `킬로미터` | `km` | 한국어 단위 이름 → 기호 |
| `킬로그램` | `kg` | |
| `섭씨 25도` | `25°C` | |
| `평방미터` | `m²` | 구 단위명 |
| `입방미터` | `m³` | |

### 7.3 단위 앞 공백 처리

SI 규칙에 따라 숫자와 단위 기호 사이에 단일 공백을 유지한다.

```
100km  → 100 km
100㎞  → 100 km
100KG  → 100 kg (대문자 단위 정규화)
```

## 8. 한국어 특이 표기 처리

### 8.1 구버전/혼용 맞춤법

- 구버전 맞춤법 교정은 **적용하지 않는다**. 원문 보존이 우선.
- 단, 명백한 타이핑 오류(OCR 아티팩트)는 신뢰도 임계값 이상일 때만 교정.

### 8.2 조사 붙임/뗌 처리

`SemanticNormalizationModule`은 조사를 분리하거나 처리하지 않는다.
한국어 NLP에서 형태소 분석은 임베딩 모델 내부에서 처리하도록 위임.

### 8.3 띄어쓰기 교정

- 띄어쓰기 교정은 적용하지 않는다.
- 이유: 전문 용어(기관명, 법령명 등)에서 오탐 발생 위험이 높음.
- OCR 결과의 공백 오류만 선택적으로 교정.

### 8.4 혼용 언어 처리

한글+영문 혼용 텍스트에서:
- 영문 단어는 원형 유지 (소문자 변환 안 함)
- 수치와 단위는 위 규칙 적용
- 영문 약어(GDP, IMF 등)는 원형 유지

### 8.5 법령 조문 표기 정규화

| 원본 | 결과 | 비고 |
|------|------|------|
| `민법 제393조제1항` | `민법 제393조 제1항` | 항 앞 공백 추가 |
| `법 제3조①` | `법 제3조 제1항` | 원문자 번호 → 텍스트 |
| `제5조2항` | `제5조 제2항` | 누락 공백 추가 |

## 9. 정규화 제외 대상

아래 경우는 정규화를 적용하지 않는다.

| 대상 | 이유 |
|------|------|
| 표 셀 원시값 | `records.jsonl` 출력 시 원본 보존 |
| 인용문 | 원문 변경 없이 보존 |
| 코드 블록 | 코드 구문이 깨질 수 있음 |
| 고유명사 (기관명, 인명) | 정규화로 오탐 위험 |
| 특수 포맷 데이터 (ISBN, 계좌번호 등) | 도메인 의미 손실 |

---

## 10. 정규화 후 원본 보존

정규화는 원본 텍스트를 덮어쓰지 않는다.

```python
@dataclass
class NormalizedText:
    original: str          # 정규화 이전 원본
    normalized: str        # 정규화 결과
    applied_rules: list[str]  # 적용된 규칙 목록
```

`CanonicalDocument` 내에서 청크/레코드/팩트에 `normalized_text`를 사용하며,
`original_text`는 review/diagnostics 출력에 함께 보존된다.

## 11. 언어 감지

### 11.1 언어 감지 우선순위

1. `ProcessingOptions.language.primary_language` 명시 설정
2. `langdetect` 라이브러리 자동 감지 (텍스트 20자 이상)
3. 폴백: `ProcessingOptions.language.fallback_language` (기본 `ko`)

### 11.2 혼합 언어 처리

- 문서 전체 언어 vs 블록별 언어를 구분하여 기록
- `CanonicalDocument.language`는 문서 주요 언어
- 블록별 `detected_language` 속성으로 개별 언어 기록
