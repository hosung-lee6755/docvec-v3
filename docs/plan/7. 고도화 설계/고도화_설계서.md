# DocVec 고도화 설계서 (1·2·4·5단계)

> 2026-07-11 기준. `문서_데이터_RAG_플랫폼_고도화_설계서.md`(프로젝트 루트)의 로드맵 중
> 실제로 구현·검증 완료된 4개 단계의 최종 설계를 기록한다.
> 3단계(서명/도장/체크박스 인식)는 의도적으로 보류되었다.

---

## 1단계 — 파싱 bbox/block_type 정합성 수정

- **문제**: PDF 어댑터가 생성하는 블록의 bbox 좌표와 block_type 라벨이 실제 레이아웃과 불일치.
- **구현**: `backend/app/pipeline/adapters/pdf_adapter.py` 보정. 회귀 테스트는
  `backend/tests/unit/adapters/`에 추가.

## 2단계 — 형태소분석기 교체 + 사전 관리

- **목표**: BM25 키워드 검색의 naive `.split()` 토큰화를 한국어 형태소 분석으로 교체하고,
  관리자가 불용어/동의어/사용자 사전을 UI로 관리.
- **토크나이저**: kiwipiepy 기반 `backend/app/services/dictionary_service.py::tokenize_batch`.
  조사/어미 제거, 불용어 필터(EXACT/CONTAINS/PREFIX/SUFFIX/REGEX), 동의어·별칭의
  대표어 확장을 수행. Kiwi 인스턴스 빌드 비용(수백 ms) 때문에 요청마다가 아니라
  **API 기동 시 + 사전 쓰기 직후**에만 `refresh_dictionary_cache()`로 인메모리 캐시를 재구축.
- **DB**: `dictionary_entries`(공통 상위) + `dictionary_entry_variants`(동의어/변형어) 2테이블.
  `문서_처리_사전_스키마.md` §5의 관계형 권장 구조를 따름. entry_type =
  stopword | synonym | custom_word.
- **API/UI**: `backend/app/api/v1/endpoints/dictionary.py`,
  `frontend/src/pages/DictionaryPage.tsx` (탭 3개 + 엑셀 일괄 업로드/다운로드).
- **주의**: REPLACE/TAG/TAGGING/EXTRACT/MASK 처리 규칙은 저장만 되고 검색 토큰화에는
  아직 미적용 (UI 안내문에 명시).

## 4단계 — 자동 메타데이터 생성 + 수정 기능

- **목표**: 문서 처리 완료 시 LLM이 키워드/개체명을 자동 추출해 태그 후보로 제안하고,
  사용자가 수락/무시로 확정.
- **트리거**: `process.py::continue_processing`이 문서를 INDEXED로 전환하는 두 지점
  (빈 문서 예외 경로 포함)에서 `generate_summary`와 나란히
  `extract_metadata.delay(document_id)` fire-and-forget 발행.
- **태스크**: `backend/app/pipeline/tasks/metadata.py::extract_metadata` (queue=low).
  로컬 Qwen2.5-3B로 `doc.parsed_text` 전체에서 키워드 추출 → 번호/불릿 제거,
  한자 비율 20% 초과 라인 드롭(중국어 드리프트 방어), 기존 태그 제외,
  대소문자 무관 중복 제거, 최대 10개. 상태 필드는 `summary_status`와 동일한
  `metadata_status` PENDING→GENERATING→DONE|FAILED 관례.
- **데이터 모델**: `Document.suggested_tags`(JSON), `Document.metadata_status`(String).
  제안 태그는 **Qdrant에 절대 직접 기록하지 않음** — 수락 시에만 `tags`로 승격되며
  그 순간 수동 태그와 동일한 `set_payload_by_document` 경로로 동기화.
- **API**: `POST /documents/{id}/tags/accept-suggestion` (승격+Qdrant 동기화),
  `POST /documents/{id}/tags/dismiss-suggestion` (제안만 제거, Qdrant 미접촉).
  둘 다 editor 이상 권한 필요.
- **UI**: `DocumentDetailPage.tsx` 태그 행 아래 "추천 태그" 행 — 점선 배지 + (수락)/×(무시),
  GENERATING이면 "자동 추출 중..." 스피너.

## 5단계 — 검색 품질: 쿼리 재작성 + MMR 다양성

- **쿼리 재작성 (사전 기반)**: `dictionary_service.py::expand_query`.
  `processing_mode=SEARCH_EXPAND`인 동의어 항목만 사용해 쿼리에 등장한 변형어의
  대표어(ONE_WAY) 또는 대표어의 변형어들(BIDIRECTIONAL)을 쿼리 뒤에 덧붙인다.
  부분 문자열 매칭(고유명사가 형태소로 안 쪼개지는 문제 회피), 이미 쿼리에 있는
  단어는 중복 추가하지 않음. LLM 미사용 — 검색당 추가 지연/비용 없음.
- **MMR 다양성**: `backend/app/services/mmr_service.py::mmr_rerank`.
  greedy MMR (λ=0.7): `λ·relevance − (1−λ)·max cosine(selected)`.
  `SearchRequest.diversify=true`일 때 후보 풀을 limit×3으로 확대해 Qdrant에서
  벡터 포함(`with_vectors=True`) 조회 후 최종 k개 선택. hybrid 모드에서는
  relevance로 `final_score`(BM25 융합 점수) 사용.
- **응답 구조 변경**: `POST /search`가 `list[SearchResultItem]` →
  `{items, expanded_query, added_terms}` 봉투로 변경. 검색 이력에는 사용자가
  실제 입력한 원본 쿼리만 기록.
- **UI**: SearchPage에 "다양성 검색" 토글, 확장 발생 시
  "사전에 등록된 동의어로 확장됨: …" 배너.
