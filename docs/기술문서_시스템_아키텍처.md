## 1. 시스템 개요

DocVec Project_2는 PDF/DOCX/HWPX/TXT 등 다양한 문서 형식을 **워크플로우 기반 전처리 엔진**으로 처리하고, 구조화된 청크를 벡터DB(Qdrant)에 저장해 RAG 검색을 지원하는 통합 플랫폼이다.

### 기술 스택

| 계층 | 기술 |
|------|------|
| 백엔드 API | FastAPI (async/await, Pydantic) |
| 스케줄러 | Celery + Redis |
| DB | PostgreSQL (SQLAlchemy ORM) |
| 벡터DB | Qdrant |
| 객체 저장소 | MinIO |
| OCR | Tesseract (한국어), 클라우드 VLM |
| 문서 추출 | 네이티브 어댑터 (PDF/DOCX/HWP/HWPX), Docling (PDF 전용) |
| 프론트엔드 | React 18 + Vite + TypeScript |
| 컨테이너 | Docker Compose (로컬: 7개 서비스) |

### 핵심 개념

- **Workflow** = DAG 기반 처리 파이프라인. 문서 업로드 시 컬렉션의 기본 워크플로우가 자동 실행
- **Block** = 워크플로우를 구성하는 개별 처리 단위 (텍스트 추출, 정제, 품질 검증 등)
- **WorkflowRun** = 특정 문서에 대한 워크플로우 1회 실행. 단계별 진행 상태와 캐시 활용 추적
- **DocumentChunk** = RAG 검색 대상이 되는 청크. 원본 텍스트, 정제 텍스트, 메타정보 포함

## 2. 문서 처리 파이프라인 아키텍처

### 2.1 워크플로우 엔진 핵심 데이터 모델

```
WorkflowDefinition (논리적 워크플로우)
  ↓
WorkflowVersion (버전 관리, 퍼블리시)
  ├─ WorkflowBlockInstance (블록 인스턴스 — 설정 포함)
  └─ WorkflowEdge (블록 간 연결 관계)

  ↓ (문서 처리 시)

WorkflowRun (1회 실행)
  ├─ WorkflowRunStep (각 블록 실행 결과)
  │   ├─ status: PENDING | RUNNING | COMPLETED | FAILED | SKIPPED
  │   ├─ output: 요약 메타데이터 (MinIO 아티팩트 참조)
  │   ├─ cached: 캐시 재사용 여부
  │   └─ started_at, completed_at
  └─ BlockExecutionCache (상류 재사용을 위한 캐시)
```

**주요 특징**:
- `WorkflowRun.started_block_id` — 부분 재처리 시 지정 블록부터 실행
- `WorkflowRun.version_snapshot` — 실행 당시의 블록 버전·모델 정보 스냅샷
- `WorkflowRun.skip_review` — "검토 없이 진행" 옵션 (실패는 여전히 검토 강제)
- `WorkflowRun.timeout_overrides` — 대용량 문서 처리 시 블록별 타임아웃 오버라이드

### 2.2 DAG 실행 흐름

```python
# backend/app/pipeline/tasks/workflow.py 실행기 (Celery 워커에서 실행)

1. 워크플로우 버전 로드 → 블록 인스턴스 + 엣지 구성
2. 상류 블록이 완료됐는지 확인 (또는 캐시 키 검사)
3. 각 블록을 위상 정렬 순서대로 실행:
   - 캐시 히트 → 아티팩트 로드, 스텝 상태 COMPLETED 마킹
   - 캐시 미스 → BlockContext 생성 + block.run(context) 호출
   - 실행 결과 → WorkflowRunStep + BlockExecutionCache 저장
   - 실패 → status FAILED, error_message 기록, 후속 블록 스킵
4. 최종 상태: WorkflowRun.status 결정 (COMPLETED | FAILED | WAITING_REVIEW)
```

**캐시 안전 범위** (`_CACHE_SAFE_BLOCK_TYPES`):
- **안전한 블록**: structure_analyze, text_clean, stopword, synonym, user_dict, pii_detect, chunk_split
- **캐시 불안전**: text_extract (OCR 설정 변경시 무효화 필요), rag_store (생성 시점마다 새 embedding_model), quality_check (block_version 1.4.0부터 청크 0개 감지)
- **노티**: 재처리 시 구조/정제/사전/민감정보 탭이 비던 버그 → 화이트리스트로 수정 (2026-07-25)

### 2.3 아티팩트 관리

대용량 산출물(구조 트리, 정제 텍스트, 청크 목록)은 MinIO `artifacts` 버킷에 저장:

```
runs/{run_id}/{step_id}/output.json  ← 상위 블록이 로드
```

`WorkflowRunStep.output`은 요약만 저장:
```json
{
  "artifact": "runs/RUN-ABC/STEP-7/output.json",
  "input_hash": "sha256:...",
  "output_hash": "sha256:...",
  "stats": {"changes": 182, "warnings": 0}
}
```

## 6. 검토(Review) 게이트 메커니즘

### 상태 전이

```
WorkflowRun: RUNNING
     ↓
quality_check 블록 실행
     ↓
상태 결정: SUCCESS | SUCCESS_WITH_WARNING | PARTIAL_FAILURE | FAILURE
     ↓
검토 필요 여부 판단:
  - FAILURE/PARTIAL_FAILURE → 무조건 검토 강제
  - SUCCESS_WITH_WARNING + review_policy="review_on_warning" → 검토 강제
  - SUCCESS + review_policy="always_review" → 검토 강제
  - skip_review=true → review_policy 무시하고 auto_pass로 취급 (단, FAILURE는 검토 강제)
     ↓
  - 검토 필요 → WorkflowRun.status = WAITING_REVIEW
  - 검토 불필요 → WorkflowRun.status = COMPLETED

Document.status는 WorkflowRun 상태에서 파생 (맵핑 §7.2)
```

**프론트엔드 UI** (`DocumentDetailPage.tsx`):
- 품질 상태 배지: SUCCESS(초록) | SUCCESS_WITH_WARNING(주황) | FAILURE(빨강) | REVIEW_REQUIRED(주황 또는 중립)
- 품질 점수 100점이어도 정책상 검토 필요하면 "검토 대기(정책)" 레이블 (오해 방지)

## 7. 재처리(Reprocess) 메커니즘

### 부분 재처리 흐름

```python
1. 사용자가 "사용자 사전 수정" 후 "이것만 재처리" 요청
2. start_partial_reprocess(doc, start_block="user_dict") 호출
3. 상류 블록 폐포 계산 (BFS)
4. 원본 런의 완료된 스텝 → 새 런으로 복사
5. 지정 블록만 직접 큐잉
6. DAG 실행기가 캐시 확인: 상류는 재사용, 지정 블록부터 신규 실행
```

### timeout_overrides

```json
WorkflowRun.timeout_overrides = {
  "text_extract": 1200,  // 대용량 PDF 텍스트 추출 20분
  "rag_store": 600
}
```
Celery 하드 타임아웃으로 먹통 → 별도의 타임아웃 값으로 재시도 (code change 불필요)
