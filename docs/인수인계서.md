## 1. 프로젝트 개요

DocVec Project_2는 PDF/DOCX/HWP/HWPX 문서를 **워크플로우(DAG) 기반 파이프라인**으로 파싱 → 정제 → 구조 분석 →
민감정보 탐지 → 청킹 → 임베딩해 저장하고, 하이브리드 검색(Dense + BM25 + MMR + Cross-Encoder)과 RAG 채팅으로
질의에 응답하는 플랫폼이다. Project_1(v1 고정 파이프라인)을 고도화한 재구축 버전이다.

- **처리 흐름**: 업로드 → 컬렉션에 지정된 전처리 워크플로우 실행 → (선택) 분석 워크플로우(분류·요약·키워드·개체) → 검색/채팅
- **워크플로우 블록 24종**(`pipeline/blocks/registry.py`): 입력·전처리(파일 검증, 형식 판별, 텍스트 추출, OCR),
  정제(text_clean, stopword, synonym, user_dict), 구조(structure_analyze, pii_detect), 분할·저장(chunk_split, rag_store),
  품질·제어(quality_check, validate, branch, merge, postprocess, output), 분석(classify, extract_entities,
  extract_keywords, summarize)
- **화면(프런트 페이지)**: 대시보드, 컬렉션, 문서 목록/상세(원문대조·구조·정제 변경·표·이미지·품질·이력 탭), 워크플로우
  편집기/실행 이력, 처리 현황, 검색, 채팅, 사전 관리, 정제 규칙, 감사 로그, 사용량, 사용자·설정, 프로젝트

## 2. 기술 스택과 구성

| 계층 | 기술 |
|---|---|
| 백엔드 | FastAPI(async) + SQLAlchemy(API는 async, 워커는 sync 세션), Pydantic, Alembic |
| 비동기 작업 | Celery(`critical/high/normal/low/embed` 5개 큐) + Redis, beat(30초 sweeper) |
| 저장소 | PostgreSQL(메타), Qdrant(벡터), MinIO(원본·산출물) |
| AI | BGE-M3 임베딩, bge-reranker-v2-m3, Qwen2.5-3B(로컬 LLM, 분류·요약 등), Docling/EasyOCR(PDF), Kiwi(한국어) |
| 프런트엔드 | React 18 + Vite + TypeScript (vitest + React Testing Library) |
| 인프라 | Docker Compose(프로젝트명 `project_2`), Caddy(HTTPS 리버스 프록시), GPU: RTX 3080 Ti 12GB(서버 PC 1장) |

디렉터리: `backend/app/{api,core,db,pipeline,schemas,services}`, `backend/tests`, `backend/alembic`, `frontend/src`,
`caddy/Caddyfile`, `docker-compose.yml`, `docs/`. 상세 서비스 구성과 포트는 가이드 1.1.

- **스캔 PDF OCR·차트 글자**: Tesseract 설정(`--psm 4`+회색조)·엔진 자동 선택·품질 지표 보강, 차트 안 글자는 원본 텍스트 레이어 우선(유지보수 가이드 1.5 M).
- **문서 메타정보 개선**(유지보수 가이드 1.5 N): 제목은 `title_resolver`(파일 속성 → 표지 줄 → 정제 파일명), 쪽수는 원본 쪽수·LibreOffice 미리보기 쪽수(HWPX 는 변환 불가라 NULL),
  언어는 한글 비율 기준, 분류는 12종 기본 목록+판단 기준 프롬프트. 사용자가 제목·언어·분류를 직접 고치면 `documents.user_edited_fields`로 기록되어 재처리가 덮어쓰지 않고, "자동값으로 되돌리기"로 해제한다.
  워커 이미지에도 LibreOffice·한글 폰트를 설치했다.
- **구조/테스트**: `documents`·`workflows` 엔드포인트를 패키지로 분리, 테스트 59% → 98%(실제 Postgres 기반 엔진 테스트 포함).
- **외부 접속**: Caddy HTTPS + MinIO 같은 출처 중계, 4443 포워딩 구성.

## 8. 작업할 때 꼭 지킬 것 (실제로 장애를 만들었던 함정)

1. **블록 `run()` 로직을 바꾸면 `block_version`을 반드시 올린다** — 안 올리면 캐시 때문에 재처리해도 옛 결과가 나온다(가이드 2.4).
2. **새 GPU 블록은 `_GPU_BLOCK_TYPES`에 추가**한다 — 일반 worker 에서 돌면 CUDA 경합으로 문서가 FAILED 된다(1.1-A).
3. **캐시 안전 목록(`_CACHE_SAFE_BLOCK_TYPES`)은 deny-by-default** — 함부로 넣으면 재처리 후 탭이 비어 보인다(1.5 C).
4. `MINIO_RELATIVE_URLS=true`(상대 URL)를 유지한다 — 끄면 URL이 절대 주소가 되어 `MINIO_PUBLIC_ENDPOINT`가 사용자 접속 주소와 같아야 하고, 이 환경(헤어핀 NAT 없음)에서는 서버 PC에서 원본이 열리지 않는다.
5. `Caddyfile`·compose 포트·`.env`를 바꿀 때는 **외부에 열린 포트가 늘지 않는지** 확인한다(DB·MinIO 등은 `127.0.0.1` 유지).
6. 새 마이그레이션 후에는 `alembic upgrade head`(현재 리비전 52개). JSON 컬럼 내부 키 추가에는 마이그레이션이 필요 없다.
7. 테스트는 일부가 **실제 Postgres**(`TEST_DATABASE_URL`)를 요구한다. 운영 DB 와 분리된 일회용 컨테이너를 쓴다(1.8).
8. 프런트는 정적 빌드라 **수정 후 재빌드**가 필요하다(핫리로드 없음).
9. 커밋 전: 비밀값 유무, 전체 테스트, 문서 갱신(`docs/*.md`)을 확인한다. 커밋 메시지는 `<type>: <description>` 형식.
