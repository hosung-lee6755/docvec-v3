# 문서 처리 사전 스키마

**최종 갱신**: 2026-07-28 — 아래 내용은 실제 구현 완료 상태를 반영함

문서 처리용 사전은 **불용어 사전**, **동의어 사전**, **사용자 사전**으로 구분하되, 공통 메타데이터 구조는 통일하여 관리하는 방식을 권장합니다.

---

## 1. 불용어 사전 스키마

문서 분석, 검색, 키워드 추출 과정에서 제외할 단어를 관리합니다.

실제 구현은 `DictionaryEntry` 모델(backend/app/db/models/dictionary_entry.py)과 `DictionaryEntryVariant`로 구성되며, `entry_type="stopword"`일 때만 불용어로 취급됩니다.

| 필드명 | 타입 | 필수 | 설명 | 예시 |
|---|---|---:|---|---|
| `id` | UUID | Y | 사전 항목 식별자 | UUID 문자열 |
| `entry_type` | enum | Y | 항목 유형(stopword\|synonym\|custom_word) | `"stopword"` |
| `term` | string | Y | 제외할 단어 또는 표현 | `그리고` |
| `match_type` | enum | Y | 일치 방식 | `EXACT` |
| `case_sensitive` | boolean | Y | 대소문자 구분 여부 | `false` |
| `language` | string | Y | 언어 코드 | `ko` |
| `scope` | JSON array | Y | 적용 범위(문서 유형 또는 "ALL") | `["ALL"]` |
| `description` | text | N | 항목 설명 또는 제외 사유 | `접속사` |
| `enabled` | boolean | Y | 사용 여부 | `true` |
| `created_by` | UUID | Y | 생성자 사용자 ID | UUID 문자열 |
| `created_at` | datetime | Y | 생성일시 | `2026-07-10T13:00:00Z` |
| `updated_at` | datetime | Y | 수정일시 | `2026-07-10T13:00:00Z` |
| `variants` | list[DictionaryEntryVariant] | N | 대체 표현(불용어는 보통 비어있음) | `[]` |

### JSON 예시

```json
{
  "stopwordId": "SW-0001",
  "word": "그리고",
  "matchType": "EXACT",
  "caseSensitive": false,
  "language": "ko",
  "scope": ["ALL"],
  "reason": "문서 분석 시 의미 기여도가 낮은 접속사",
  "enabled": true,
  "createdAt": "2026-07-10T13:00:00Z",
  "updatedAt": "2026-07-10T13:00:00Z"
}
```

### `matchType` 권장 값

| 값 | 설명 |
|---|---|
| `EXACT` | 단어가 정확히 일치할 때 제외 |
| `CONTAINS` | 해당 문자열을 포함하면 제외 |
| `PREFIX` | 해당 문자열로 시작하면 제외 |
| `SUFFIX` | 해당 문자열로 끝나면 제외 |
| `REGEX` | 정규식 기준으로 제외 |

## 2. 동의어 사전 스키마

서로 다른 표현을 하나의 대표 용어로 정규화하거나, 검색 시 동일한 의미로 확장하기 위한 사전입니다.

실제 구현에서는 `DictionaryEntry`(`entry_type="synonym"`)와 `DictionaryEntryVariant`로 구성되며, `term` 필드가 대표 용어이고 variants 배열이 동의어 목록입니다.

| 필드명 | 타입 | 필수 | 설명 | 예시 |
|---|---|---:|---|---|
| `id` | UUID | Y | 사전 항목 식별자 | UUID 문자열 |
| `entry_type` | enum | Y | 항목 유형 | `"synonym"` |
| `term` | string | Y | 대표 용어 | `인공지능` |
| `direction` | enum | Y | 동의어 적용 방향 | `ONE_WAY` \| `BIDIRECTIONAL` |
| `processing_mode` | enum | Y | 처리 방식 | `NORMALIZE` \| `REPLACE` \| `SEARCH_EXPAND` \| `TAGGING` |
| `case_sensitive` | boolean | Y | 대소문자 구분 여부 | `false` |
| `language` | string | Y | 언어 코드 | `ko` |
| `scope` | JSON array | Y | 적용 범위 | `["ALL"]` |
| `description` | text | N | 동의어 그룹 설명 | `AI 관련 표현 통합` |
| `enabled` | boolean | Y | 사용 여부 | `true` |
| `created_by` | UUID | Y | 생성자 사용자 ID | UUID 문자열 |
| `created_at` | datetime | Y | 생성일시 | `2026-07-10T13:00:00Z` |
| `updated_at` | datetime | Y | 수정일시 | `2026-07-10T13:00:00Z` |
| `variants` | list[DictionaryEntryVariant] | Y | 동의어 목록 | 각 variant_term 저장 |

### JSON 예시

```json
{
  "synonymId": "SY-0001",
  "canonicalTerm": "인공지능",
  "synonyms": [
    "AI",
    "A.I.",
    "인공 지능",
    "Artificial Intelligence"
  ],
  "direction": "ONE_WAY",
  "processingMode": "NORMALIZE",
  "caseSensitive": false,
  "language": "ko",
  "scope": ["ALL"],
  "description": "인공지능 관련 표현을 대표 용어로 통합",
  "enabled": true,
  "createdAt": "2026-07-10T13:00:00Z",
  "updatedAt": "2026-07-10T13:00:00Z"
}
```

### `direction` 권장 값

| 값 | 설명 |
|---|---|
| `ONE_WAY` | 동의어를 대표 용어로만 변환 |
| `BIDIRECTIONAL` | 그룹 내 모든 용어를 서로 동의어로 인식 |

### `processingMode` 권장 값

| 값 | 설명 |
|---|---|
| `NORMALIZE` | 내부 분석 시 대표 용어로 통합 |
| `REPLACE` | 실제 문서 텍스트를 대표 용어로 치환 |
| `SEARCH_EXPAND` | 검색 시 동의어를 함께 검색 |
| `TAGGING` | 동일 개념 태그를 부여 |

## 3. 사용자 사전 스키마

도메인 전문용어, 기관명, 제품명, 약어, 고유명사 등 사용자가 직접 정의한 용어를 관리합니다.

실제 구현에서는 `DictionaryEntry`(`entry_type="custom_word"`)와 `DictionaryEntryVariant`로 구성됩니다. `term_type` 필드는 용어의 분류(TECHNICAL_TERM, ABBREVIATION, ORGANIZATION, PERSON, PRODUCT, PROJECT 등)를 나타내고, `processing_rule` 필드는 이 항목을 어떻게 처리할지(KEEP, NORMALIZE, REPLACE, TAG, EXTRACT, MASK, IGNORE) 결정합니다.

| 필드명 | 타입 | 필수 | 설명 | 예시 |
|---|---|---:|---|---|
| `id` | UUID | Y | 사용자 용어 식별자 | UUID 문자열 |
| `entry_type` | enum | Y | 항목 유형 | `"custom_word"` |
| `term` | string | Y | 표준 용어 | `LangGraph` |
| `term_type` | enum | Y | 용어 분류 | `PRODUCT` \| `TECHNICAL_TERM` \| `ABBREVIATION` \| `ORGANIZATION` 등 |
| `processing_rule` | enum | Y | 처리 규칙 | `KEEP` \| `NORMALIZE` \| `REPLACE` \| `TAG` \| `EXTRACT` \| `MASK` \| `IGNORE` |
| `pronunciation` | string | N | 발음 또는 읽기 정보 | `랭그래프` |
| `case_sensitive` | boolean | Y | 대소문자 구분 여부 | `true` |
| `language` | string | Y | 언어 코드 | `en` |
| `scope` | JSON array | Y | 적용 범위(문서 유형) | `["요구사항정의서", "기술설계서"]` |
| `description` | text | N | 용어 정의 | `그래프 기반 AI 워크플로우 프레임워크` |
| `enabled` | boolean | Y | 사용 여부 | `true` |
| `created_by` | UUID | Y | 생성자 사용자 ID | UUID 문자열 |
| `created_at` | datetime | Y | 생성일시 | `2026-07-10T13:00:00Z` |
| `updated_at` | datetime | Y | 수정일시 | `2026-07-10T13:00:00Z` |
| `variants` | list[DictionaryEntryVariant] | N | 오탈자, 띄어쓰기, 별칭 | 각 variant_term 저장 |

### JSON 예시

```json
{
  "termId": "UD-0001",
  "term": "LangGraph",
  "variants": [
    "랭그래프",
    "Lang Graph"
  ],
  "termType": "PRODUCT",
  "definition": "그래프 기반 AI 에이전트 및 워크플로우 구성 프레임워크",
  "processingRule": "KEEP",
  "pronunciation": "랭그래프",
  "caseSensitive": true,
  "language": "en",
  "scope": [
    "요구사항 정의서",
    "기술 설계서"
  ],
  "metadata": {
    "category": "AI_FRAMEWORK",
    "referenceUrl": null
  },
  "enabled": true,
  "createdAt": "2026-07-10T13:00:00Z",
  "updatedAt": "2026-07-10T13:00:00Z"
}
```

### `termType` 권장 값

- `TECHNICAL_TERM`: 전문용어
- `ABBREVIATION`: 약어
- `ORGANIZATION`: 기관명
- `PERSON`: 인명
- `PRODUCT`: 제품 또는 서비스명
- `PROJECT`: 프로젝트명
- `POLICY`: 정책 또는 제도명
- `CUSTOM`: 사용자 정의 유형

### `processingRule` 권장 값

- `KEEP`: 원문 유지
- `NORMALIZE`: 변형 표현을 표준 용어로 인식
- `REPLACE`: 실제 텍스트 치환
- `TAG`: 용어 유형 태그 부여
- `EXTRACT`: 주요 개체로 추출
- `MASK`: 민감정보 마스킹
- `IGNORE`: 처리 대상에서 제외

## 3.1 DictionaryEntryVariant 스키마

각 DictionaryEntry는 여러 변형 표현(variant)을 가질 수 있습니다. 불용어는 보통 variants가 비어있고, 동의어와 사용자 사전은 variants 배열에 대체 표현들을 저장합니다.

| 필드명 | 타입 | 필수 | 설명 | 예시 |
|---|---|---:|---|---|
| `id` | UUID | Y | 변형 항목 식별자 | UUID 문자열 |
| `entry_id` | UUID | Y | 상위 DictionaryEntry ID | UUID 문자열 |
| `variant_term` | string | Y | 변형 또는 동의어 표현 | `AI` 또는 `랭그래프` |
| `variant_type` | string | N | 변형 유형(alias, typo, abbreviation 등) | `alias` \| `typo` |
| `sort_order` | int | Y | 정렬 순서 | 0, 1, 2, ... |
| `enabled` | boolean | Y | 사용 여부 | `true` |
| `created_at` | datetime | Y | 생성일시 | `2026-07-10T13:00:00Z` |

## 4. 사전 버전 관리 (Dictionary Version Tracking)

사전은 워크플로우 실행 시 특정 버전으로 고정되어 전처리 결과의 재현성을 보장합니다.

- **DictionaryRevision**: 사전 항목이 추가/수정/삭제될 때마다 버전 번호가 증가합니다.
- **WorkflowRun.dictionary_version**: 각 워크플로우 실행은 시작 시점의 dictionary 버전을 기록합니다.
- **DocumentChunk.dictionary_version**: 각 청크가 생성될 때 적용된 사전 버전을 기록합니다.

이를 통해:
- 동일한 문서를 같은 사전 버전으로 재처리할 수 있습니다.
- 사전 변경 전후의 전처리 결과 차이를 추적할 수 있습니다.
- 부분 재처리 시 사전 버전을 고정하거나 최신으로 업데이트할 수 있습니다.

## 5. 통합 사전 관리 스키마 (Deprecated)

> **⚠ 실제 구현과 차이**: 설계서의 "통합 사전 관리 스키마"는 참고용이며, 실제 구현에서는 DictionaryEntry의 `entry_type` 필드 하나로 불용어/동의어/사용자사전을 모두 관리합니다. 따라서 아래의 통합 스키마는 구현되지 않으며, DictionaryEntry와 DictionaryEntryVariant 두 테이블만 사용합니다.

세 종류의 사전을 하나의 사전 관리 단위로 묶는 상위 스키마입니다(설계 참고용).

```json
{
  "dictionaryId": "DICT-0001",
  "dictionaryName": "공통 문서 처리 사전",
  "dictionaryType": "USER",
  "version": "1.0.0",
  "description": "요구사항 및 기술 문서 처리용 사전",
  "ownerId": "USER-0001",
  "scope": {
    "workspaceIds": ["WS-0001"],
    "documentTypes": [
      "REQUIREMENT",
      "TECHNICAL_DESIGN"
    ]
  },
  "priority": 100,
  "enabled": true,
  "entries": [],
  "createdAt": "2026-07-10T13:00:00Z",
  "updatedAt": "2026-07-10T13:00:00Z"
}
```

### `dictionaryType` 권장 값

```text
STOPWORD
SYNONYM
USER
```

```text
단어 | 일치방식 | 대소문자구분 | 언어 | 적용범위 | 제외사유 | 사용여부

```

### 동의어 사전

```text
대표용어 | 동의어 | 적용방향 | 처리방식 | 대소문자구분 | 언어 | 적용범위 | 사용여부
```

```text

```

## 7. 설계 원칙

동의어 사전과 사용자 사전의 역할은 명확히 구분해야 합니다.

- **동의어 사전**: 의미적으로 동일하거나 유사한 표현을 대표 용어로 통합
- **사용자 사전**: 도메인 용어의 인식, 보존, 추출, 태깅, 치환 규칙을 관리
- **불용어 사전**: 분석이나 검색에서 의미 기여도가 낮은 표현을 제외

공통 스키마를 사용하되, 사전 유형별로 필요한 속성만 활성화하는 방식이 관리와 확장에 유리합니다.
