# 문서 처리 사전 스키마

**최종 갱신**: 2026-11-17 (HEAD 0f38033 코드 기준으로 점검했다. 각 절에 근거가 되는 코드 위치를 적었다.)

문서 처리용 사전은 불용어 사전, 동의어 사전, 사용자 사전으로 구분한다. 세 종류는 `dictionary_entries` 테이블 하나에 `entry_type` 값으로 구분해 저장하고, 공통 필드 구조를 함께 쓴다. 사전 변경 이력과 문서별 적용 기록은 별도 테이블에 남는다.

이 문서는 설계 기준과 현재 구현을 함께 적는다. 설계 기준과 구현이 다른 부분은 "실제 구현"이라고 표시했다. 설계 기준만 있고 구현하지 않은 항목은 그렇게 명시했다.

---

## 1. 불용어 사전 스키마

불용어는 문서 처리와 검색에서 의미 기여도가 낮아 제외할 단어나 표현이다.

실제 구현은 `DictionaryEntry` 모델(`backend/app/db/models/dictionary_entry.py`)에서 `entry_type="stopword"`인 행이다. 불용어는 변형 표현을 쓰지 않으므로 `variants`는 비어 있다. 같은 `entry_type` 안에서 `term`은 유일하며, 중복으로 만들면 409 응답이 온다.

| 필드명 | 타입 | 필수 | 설명 | 예시 |
|---|---|---:|---|---|
| `id` | UUID | 서버 생성 | 사전 항목 식별자 | UUID 문자열 |
| `entry_type` | enum | Y | 항목 유형. 불용어는 `stopword` | `"stopword"` |
| `term` | string | Y | 제외할 단어 또는 표현 (1~255자) | `그리고` |
| `match_type` | enum | N (기본 `EXACT`) | 일치 방식 | `EXACT` |
| `case_sensitive` | boolean | N (기본 `false`) | 대소문자 구분 여부 | `false` |
| `language` | string | N (기본 `ko`) | 언어 코드 (10자 이하) | `ko` |
| `scope` | JSON 배열 | N (기본 `["ALL"]`) | 적용 범위. 블록 설정의 `scope_filter`를 줄 때만 적용된다 | `["ALL"]` |
| `description` | text | N | 항목 설명이나 제외 사유 | `접속사` |
| `enabled` | boolean | N (기본 `true`) | 사용 여부. 끄면 처리와 검색 모두에서 빠진다 | `true` |
| `created_by` | UUID | 서버 기록 | 생성자 사용자 ID | UUID 문자열 |
| `created_at` | datetime | 서버 기록 | 생성일시 | `2026-11-17T09:00:00Z` |
| `updated_at` | datetime | 서버 기록 | 수정일시 | `2026-11-17T09:00:00Z` |
| `variants` | 문자열 배열 | 없음 | 불용어는 항상 빈 배열이다 | `[]` |

### JSON 예시 (API 요청 형태)

관리자 API `POST /api/v1/admin/dictionary`에 보내는 본문이다. 응답에는 `id`, `created_at`, `updated_at`이 더해진다.

```json
{
  "entry_type": "stopword",
  "term": "그리고",
  "match_type": "EXACT",
  "case_sensitive": false,
  "language": "ko",
  "scope": ["ALL"],
  "description": "접속사",
  "enabled": true,
  "variants": []
}
```

### `match_type` 값과 동작

| 값 | 설명 |
|---|---|
| `EXACT` | 단어가 정확히 일치하면 제외한다. 본문에서 찾을 때는 앞쪽 경계만 확인하므로 조사가 뒤에 붙은 형태("그리고는")도 찾는다 |
| `CONTAINS` | 해당 문자열을 포함하면 제외한다 |
| `PREFIX` | 해당 문자열로 시작하면 제외한다 |
| `SUFFIX` | 해당 문자열로 끝나면 제외한다 |
| `REGEX` | `term`을 정규식으로 보고 일치하면 제외한다. 잘못된 정규식은 건너뛴다 |

본문 처리(`stopword` 블록)와 검색용 토큰 판정(`dictionary_service._is_stopword`)은 같은 값을 다르게 판정한다. 본문에서는 `normalization_blocks._find_spans`가 문자열 구간을 찾고, 검색에서는 형태소 토큰 단위로 비교한다. 따라서 `CONTAINS`나 `PREFIX`를 쓰면 두 경로의 결과가 다를 수 있다.

### 불용어 처리 블록의 동작 (실제 구현)

표준 전처리 워크플로우의 `stopword` 블록(`normalization_blocks.py`의 `StopwordBlock`)은 블록 설정 `action`에 따라 다음처럼 동작한다.

| `action` 값 | 동작 |
|---|---|
| `mark` (기본) | 일치한 위치를 적용 기록(`DictionaryApplication`)으로만 남기고 본문은 바꾸지 않는다 |
| `exclude_from_analysis` | 설정값으로만 존재한다. 현재 구현은 `mark`와 같이 기록만 남긴다 |
| `remove` | 일치한 구간을 본문에서 잘라낸다 |

추가로 다음 규칙이 적용된다.

- 블록 설정 `scope_filter`를 주면 항목의 `scope`와 겹칠 때만 적용한다. 설정이 없으면 `scope`는 무시된다.
- 사용자 사전의 보호 구간(`protected_spans`, 아래 3절 참고)과 겹치는 위치는 제외한다.
- 문서별로 끈 항목(`DocumentDictionaryExclusion`)은 건너뛴다.
- 되돌린 적용(`DictionaryApplication.reverted`)과 같은 원문 표현은 다시 적용하지 않는다.

### 검색에서의 동작 (실제 구현)

활성(`enabled=true`) 불용어는 BM25 토큰과 키워드 색인 토큰에서 제외된다(`dictionary_service.tokenize_batch`). 이 경로는 사전 항목의 `scope`와 무관하게 모든 활성 불용어를 쓴다.

## 2. 동의어 사전 스키마

서로 다른 표현을 하나의 대표 용어로 정규화하거나, 검색할 때 같은 의미의 다른 표현도 함께 찾기 위한 사전이다.

실제 구현에서는 `DictionaryEntry`(`entry_type="synonym"`)를 쓴다. `term`이 대표 용어이고 `variants`가 동의어 목록이다. 동의어는 최소 1개 있어야 하며, 하나도 없으면 생성 요청이 검증 오류로 거부된다.

| 필드명 | 타입 | 필수 | 설명 | 예시 |
|---|---|---:|---|---|
| `id` | UUID | 서버 생성 | 사전 항목 식별자 | UUID 문자열 |
| `entry_type` | enum | Y | 항목 유형. 동의어는 `synonym` | `"synonym"` |
| `term` | string | Y | 대표 용어 (1~255자) | `인공지능` |
| `variants` | 문자열 배열 | Y (1개 이상) | 동의어 목록 | `["AI", "A.I.", "인공 지능"]` |
| `direction` | enum | N (기본 `ONE_WAY`) | 동의어 적용 방향 | `ONE_WAY` |
| `processing_mode` | enum | N (기본 `NORMALIZE`) | 처리 방식 | `NORMALIZE` |
| `case_sensitive` | boolean | N (기본 `false`) | 대소문자 구분 여부 | `false` |
| `language` | string | N (기본 `ko`) | 언어 코드 | `ko` |
| `scope` | JSON 배열 | N (기본 `["ALL"]`) | 적용 범위 (불순물 제외 규칙은 3절 참고) | `["ALL"]` |
| `description` | text | N | 동의어 그룹 설명 | `AI 관련 표현 통합` |
| `enabled` | boolean | N (기본 `true`) | 사용 여부 | `true` |
| `created_by`, `created_at`, `updated_at` | | 서버 기록 | 생성자와 시각 | |

### JSON 예시 (API 요청 형태)

```json
{
  "entry_type": "synonym",
  "term": "인공지능",
  "variants": ["AI", "A.I.", "인공 지능", "Artificial Intelligence"],
  "direction": "ONE_WAY",
  "processing_mode": "NORMALIZE",
  "case_sensitive": false,
  "language": "ko",
  "scope": ["ALL"],
  "description": "인공지능 관련 표현을 대표 용어로 통합",
  "enabled": true
}
```

### `direction` 값

| 값 | 설명 |
|---|---|
| `ONE_WAY` | 동의어가 나오면 대표 용어를 함께 쓴다. 대표 용어가 나와도 동의어는 추가하지 않는다 |
| `BIDIRECTIONAL` | 대표 용어가 나오면 동의어도 함께 쓴다. 그룹 안의 용어는 서로 찾을 수 있다 |

### `processing_mode` 값과 실제 동작

처리 방식은 항목을 어디에서 어떻게 쓸지 정한다. 실제 동작은 다음과 같다.

| 값 | 문서 본문 (`synonym` 블록) | 검색 토큰 (BM25, 키워드 색인) | 검색어 확장 |
|---|---|---|---|
| `NORMALIZE` | 블록 설정 `processing_mode`가 `normalize`(기본)면 동의어를 대표 용어로 치환한다 | 동의어가 나오면 대표 용어를 더한다 | 적용하지 않는다 |
| `REPLACE` | `NORMALIZE`와 같이 치환한다 | 같은 방식으로 반영된다 | 적용하지 않는다 |
| `SEARCH_EXPAND` | 치환하지 않고 적용 위치만 기록한다 | 같은 방식으로 반영된다 | 검색어에 대표 용어 또는 동의어를 덧붙인다 |
| `TAGGING` | 치환하지 않고 적용 위치만 기록한다 | 같은 방식으로 반영된다 | 적용하지 않는다 |

> **실제 구현 참고**: 검색 토큰 반영은 `processing_mode`와 관계없이 모든 활성 동의어에 적용된다(`dictionary_service._install_entries`). 블록 설정 `processing_mode`를 `tag_only`로 두면 `NORMALIZE`와 `REPLACE` 항목도 치환하지 않고 기록만 한다(`SynonymBlock`).

`SEARCH_EXPAND`의 검색어 확장(`dictionary_service.expand_query`)은 다음 순서로 동작한다.

1. 질의에 변형 표현이 부분 문자열로 나오면 대표 용어를 덧붙인다. 대표 용어가 이미 질의에 있으면 덧붙이지 않는다.
2. `BIDIRECTIONAL` 항목의 대표 용어가 질의에 나오면 동의어 목록을 덧붙인다.
3. 확장된 질의는 임베딩과 키워드 점수 계산에 쓰인다. 채팅의 재순위(교차 인코더)에는 사용자가 입력한 원래 질문을 쓴다.

### 한국어 조사가 붙은 표현 (실제 구현)

2026-11-13 커밋 cd32ac6에서 치환 방식을 고쳤다. 예전에는 사전이 찾은 위치를 다시 정규식으로 찾아 치환해서, "에이아이는"처럼 조사가 붙은 변형은 기록에만 남고 실제 본문은 바뀌지 않았다. 지금은 사전이 찾은 위치를 그대로 치환하므로 조사가 붙은 형태도 바뀐다.

## 3. 사용자 사전 스키마

도메인 전문용어, 기관명, 제품명, 약어, 고유명사처럼 사용자가 직접 정의한 용어를 관리한다.

실제 구현에서는 `DictionaryEntry`(`entry_type="custom_word"`)와 `DictionaryEntryVariant`를 쓴다. `term_type`은 용어의 분류이고, `processing_rule`은 이 항목을 문서 처리에서 어떻게 다룰지 정한다.

| 필드명 | 타입 | 필수 | 설명 | 예시 |
|---|---|---:|---|---|
| `id` | UUID | 서버 생성 | 사용자 용어 식별자 | UUID 문자열 |
| `entry_type` | enum | Y | 항목 유형. 사용자 사전은 `custom_word` | `"custom_word"` |
| `term` | string | Y | 표준 용어 (1~255자) | `LangGraph` |
| `variants` | 문자열 배열 | N | 오탈자, 띄어쓰기, 별칭 | `["랭그래프", "Lang Graph"]` |
| `term_type` | enum | N (기본 `CUSTOM`) | 용어 분류 | `PRODUCT` |
| `processing_rule` | enum | N (기본 `KEEP`) | 처리 규칙 | `KEEP` |
| `pronunciation` | string | N | 발음 또는 읽기 정보 (255자 이하). 저장과 엑셀 입출력에만 쓰이고 처리에는 쓰이지 않는다 | `랭그래프` |
| `case_sensitive` | boolean | N (기본 `false`) | 대소문자 구분 여부 | `true` |
| `language` | string | N (기본 `ko`) | 언어 코드 | `en` |
| `scope` | JSON 배열 | N (기본 `["ALL"]`) | 적용 범위 | `["요구사항 정의서", "기술 설계서"]` |
| `description` | text | N | 용어 정의 | `그래프 기반 AI 워크플로우 프레임워크` |
| `enabled` | boolean | N (기본 `true`) | 사용 여부 | `true` |

### JSON 예시 (API 요청 형태)

```json
{
  "entry_type": "custom_word",
  "term": "LangGraph",
  "variants": ["랭그래프", "Lang Graph"],
  "term_type": "PRODUCT",
  "processing_rule": "KEEP",
  "pronunciation": "랭그래프",
  "case_sensitive": true,
  "language": "en",
  "scope": ["요구사항 정의서", "기술 설계서"],
  "description": "그래프 기반 AI 에이전트 및 워크플로우 구성 프레임워크",
  "enabled": true
}
```

### `term_type` 값

| 값 | 설명 |
|---|---|
| `TECHNICAL_TERM` | 전문용어 |
| `ABBREVIATION` | 약어 |
| `ORGANIZATION` | 기관명 |
| `PERSON` | 인명 |
| `PRODUCT` | 제품 또는 서비스명 |
| `PROJECT` | 프로젝트명 |
| `POLICY` | 정책 또는 제도명 |
| `CUSTOM` | 사용자 정의 유형 (기본값) |

`term_type`은 문서 처리 블록 `user_dict`의 `term_types` 설정으로 대상을 고를 때만 쓰인다. 설정이 없으면 모든 유형을 처리한다.

### `processing_rule` 값과 실제 동작

아래 표는 문서 처리 블록 `user_dict`(`UserDictBlock`)의 동작을 정리한 것이다.

| 값 | 실제 동작 |
|---|---|
| `KEEP` | 표준 용어가 나온 위치를 보호 구간으로 등록한다. 변형 표현은 바꾸지 않는다 |
| `NORMALIZE` | 변형 표현을 표준 용어로 치환한다. 치환한 위치도 보호 구간에 넣는다 |
| `REPLACE` | `NORMALIZE`와 같이 치환한다 |
| `TAG` | 적용 위치만 기록한다. 본문은 바꾸지 않으며, 태그를 따로 붙이지는 않는다 |
| `EXTRACT` | 적용 위치만 기록한다. 개체 목록으로 따로 뽑지는 않는다 |
| `MASK` | 적용 위치만 기록한다. 마스킹하지 않는다. 민감정보 마스킹은 `pii_detect` 블록이 맡는다 |
| `IGNORE` | 문서 처리와 검색 토큰 모두에서 제외한다 |

보호 구간(`protected_spans`)은 불용어 블록이 같은 위치를 지우지 못하게 막는다. 블록 설정 `protect_from_stopwords`가 기본으로 켜져 있다.

검색 쪽에서는 `IGNORE`를 뺀 모든 사용자 사전 항목의 표준 용어와 변형 표현을 형태소 분석기에 고유명사(NNP)로 등록한다. 그래서 등록된 용어가 여러 낱말로 쪼개지지 않는다. `NORMALIZE` 항목의 변형 표현은 검색 토큰에서 표준 용어로 바뀐다.

## 3.1 DictionaryEntryVariant 스키마

각 항목(`DictionaryEntry`)은 여러 변형 표현(variant)을 가질 수 있다. 동의어 사전은 동의어 문자열을, 사용자 사전은 별칭, 약어, 오탈자, 표기 변형을 variant로 저장한다. 불용어는 variant를 쓰지 않는다.

실제 구현은 `backend/app/db/models/dictionary_entry_variant.py`의 `dictionary_entry_variants` 테이블이다.

| 필드명 | 타입 | 설명 | 예시 |
|---|---|---|---|
| `id` | UUID | 변형 항목 식별자 (서버 생성) | UUID 문자열 |
| `entry_id` | UUID | 상위 `DictionaryEntry` ID. 항목을 지우면 함께 지워진다 (cascade) | UUID 문자열 |
| `variant_term` | string (255자) | 변형 또는 동의어 표현 | `AI`, `랭그래프` |
| `sort_order` | int | 정렬 순서 (0부터) | `0`, `1` |
| `created_at` | datetime | 생성일시 | |

설계 초안의 `variant_type`(alias, typo 등)과 variant 단위 `enabled`는 구현하지 않았다. 변형 표현을 고치려면 항목 전체의 `variants` 목록을 보낸다. 수정 요청의 `variants`는 기존 목록을 **교체**하며, 병합하지 않는다.

## 4. 사전 버전 관리 (Dictionary Version Tracking)

사전은 워크플로우 실행 시 특정 버전으로 고정되어 전처리 결과의 재현성을 보장한다.

### 4.1 기록되는 테이블과 필드 (실제 구현)

- **DictionaryRevision** (`dictionary_revisions`): 사전 쓰기 한 번마다 한 행을 추가한다. `version`은 자동 증가하는 전역 번호다. `change_type`은 `CREATE`, `UPDATE`, `DELETE`, `IMPORT` 중 하나다. `changed_entry_id`는 항목이 지워지면 빈 값이 된다. `created_by`와 `created_at`을 함께 남긴다. `snapshot_key` 컬럼은 있으나 현재 기록하지 않는다.
- 엑셀 가져오기는 여러 행을 바꿔도 `IMPORT` 행 하나만 남긴다. 몇 행이 바뀌었는지는 리비전에 남지 않는다.
- **WorkflowRun.dictionary_version**: 실행을 만들 때 최신 리비전 번호를 기록한다. 사전이 한 번도 바뀌지 않았으면 빈 값이며, 그때는 활성 항목 전부를 그대로 읽는다.
- **DocumentChunk.dictionary_version**: 청크를 저장할 때의 실행 사전 버전을 기록한다.
- **DictionaryApplication.dictionary_version**: 적용 기록마다 실행 사전 버전을 기록한다.

이를 통해 다음을 할 수 있다.

- 같은 문서를 같은 사전 버전 기준으로 다시 확인할 수 있다.
- 사전 변경 전후의 처리 결과 차이를 실행 기록으로 비교할 수 있다.
- 재처리 실행은 실행 시점의 최신 사전 버전을 새로 고정한다. 기존 실행의 사전 버전은 바뀌지 않는다.

### 4.2 버전 기준 읽기의 한계 (실제 구현)

문서 처리 블록은 실행의 사전 버전 시각(`DictionaryRevision.created_at`) 이전에 `updated_at`이 찍힌 활성 항목만 읽는다(`normalization_blocks._load_entries_as_of`). 항목별 이력을 저장하지 않는 현재 구조에서 쓰는 근사 방식이다.

확인된 한계는 다음과 같다.

- 컷오프 이후에 삭제된 항목은 과거 실행 기준으로 다시 만들 수 없다.
- 항목의 값은 바뀌었지만 그 뒤에 만들어진 항목의 `updated_at`이 갱신되지 않은 경우, 과거 실행 기준이 최신 값을 읽을 수 있다. 변형 표현만 바꾸면 항목 행이 갱신되지 않아 이 경우에 해당할 수 있다.

### 4.3 버전 이력 조회

관리자 API `GET /api/v1/admin/dictionary/revisions`가 최근 200건을 돌려준다. 누가, 언제, 어떤 항목을 어떤 방식으로 바꿨는지만 보여준다. 필드 단위의 이전 값과 이후 값(diff)은 저장하지 않으므로 보여주지 않는다.

### 4.4 사전 변경의 후속 처리 (실제 구현)

사전 쓰기가 성공하면 다음이 자동으로 이어진다.

1. 검색에 쓰는 사전 캐시를 다시 만든다. API 프로세스는 시작할 때와 쓰기 뒤에 다시 읽는다. 워커는 리비전 번호가 바뀌었을 때 다시 읽는다(`ensure_dictionary_cache_sync`).
2. 골든쿼리가 있는 컬렉션마다 골든 평가를 예약한다(`trigger="dictionary"`). 평가 실패는 사전 변경을 되돌리지 않는다.

키워드 색인(Qdrant의 `_lex` 보조 컬렉션)은 자동으로 다시 만들지 않는다. 사전을 크게 바꾼 뒤에는 `backend/scripts/backfill_lexical_index.py`를 실행해야 검색 토큰이 새 사전을 따른다.

## 6. 엑셀 업로드 형식

관리자는 사전을 엑셀(.xlsx)로 내려받고 올릴 수 있다. 화면에서 쓰는 API는 다음과 같다.

- `GET /api/v1/admin/dictionary/export?entry_type=stopword|synonym|custom_word`: 데이터 시트와 "스키마 안내" 시트가 든 파일을 내려준다. 파일 이름은 `dictionary_{entry_type}.xlsx`다.
- `POST /api/v1/admin/dictionary/import?entry_type=...`: 첫 번째 시트의 2행부터 읽는다. 첫 행은 헤더로 건너뛴다. 한 번에 최대 5,000행까지 가져올 수 있다.

가져오기는 `term`이 같은 항목이 있으면 갱신하고, 없으면 새로 만든다. 필수 값이 빠진 행은 건너뛰고 행 번호를 결과에 적는다. 완전히 빈 행은 세지 않는다. 결과는 `created`, `updated`, `skipped`, `skipped_rows`로 돌아온다. 가져오기가 하나라도 반영되면 `IMPORT` 리비전을 한 개 남긴다.

### 불용어 사전

```text
단어 | 일치방식 | 대소문자구분 | 언어 | 적용범위 | 제외사유 | 사용여부
그리고 | EXACT | N | ko | ALL | 접속사 | Y
```

- 단어는 필수 입력 값이다.
- 일치방식은 비워 두면 `EXACT`, 대소문자구분은 비워 두면 `N`, 언어는 비워 두면 `ko`, 적용범위는 비워 두면 `ALL`로 본다.

### 동의어 사전

```text
대표용어 | 동의어 | 적용방향 | 처리방식 | 대소문자구분 | 언어 | 적용범위 | 사용여부
인공지능 | AI;A.I.;인공 지능 | ONE_WAY | NORMALIZE | N | ko | ALL | Y
```

- 대표용어와 동의어는 필수 입력 값이다. 동의어는 1개 이상 있어야 한다.
- 동의어는 세미콜론(`;`)으로 구분한다.
- 적용방향은 비워 두면 `ONE_WAY`, 처리방식은 비워 두면 `NORMALIZE`로 본다.

### 사용자 사전

```text
표준용어 | 변형표현 | 용어유형 | 처리규칙 | 정의 | 대소문자구분 | 언어 | 적용범위 | 사용여부 | 발음
LangGraph | 랭그래프;Lang Graph | PRODUCT | KEEP | AI 워크플로우 프레임워크 | Y | en | 기술설계서 | Y | 랭그래프
```

- 표준용어는 필수 입력 값이다.
- 변형표현은 세미콜론(`;`)으로 구분한다.
- 용어유형은 비워 두면 `CUSTOM`, 처리규칙은 비워 두면 `KEEP`으로 본다.
- 발음 열은 설계 초안에 없던 열이다. 엑셀 열 순서는 구현을 따른다.

### 공통 규칙

- 대소문자구분, 사용여부는 `Y`, `YES`, `TRUE`, `1`을 참으로 보고, 그 밖의 값은 거짓으로 본다. 사용여부가 비어 있으면 참으로 본다.
- 적용범위는 **쉼표(`,`)**로 구분한다. 내보내기와 가져오기 파서가 모두 쉼표를 기준으로 나눈다.

> **코드 불일치 (확인 필요)**: 내려받은 파일의 "스키마 안내" 시트와 사용자 사전 예시 행은 적용범위를 세미콜론(`;`)으로 구분하라고 적는다(`backend/app/api/v1/endpoints/dictionary.py`의 `_FIELD_GUIDES`, `_EXAMPLE_ROWS`). 그러나 파서(`_split_list(..., ",")`)는 쉼표로만 나눈다. 세미콜론으로 적은 적용범위는 한 개의 값으로 들어간다. 이 불일치는 코드 수정으로 맞춰야 하며, 그 전까지 적용범위는 쉼표로 적는다.

## 7. 설계 원칙

동의어 사전과 사용자 사전의 역할은 명확히 구분해야 한다.

- **동의어 사전**: 의미적으로 같거나 비슷한 표현을 대표 용어로 통합한다.
- **사용자 사전**: 도메인 용어의 인식, 보존, 치환 규칙을 관리한다. 개체 추출과 마스킹은 구현하지 않았으며, 각각 개체 추출 블록과 `pii_detect` 블록의 몫이다.
- **불용어 사전**: 분석이나 검색에서 의미 기여도가 낮은 표현을 제외한다.

공통 스키마를 사용하되, 사전 유형별로 필요한 속성만 쓰는 방식이 관리와 확장에 유리하다. 실제 구현도 이 방식을 따르며, 쓰지 않는 속성은 `NULL`로 둔다.

### 적용 범위(`scope`)의 실제 동작

항목의 `scope`는 저장만 되고 대부분의 경로에서 적용 범위를 제한하지 않는다. 불용어 블록은 설정 `scope_filter`를 줄 때만 `scope`를 본다. 동의어 블록과 사용자 사전 블록은 `scope`를 보지 않는다. 문서 유형별로 사전을 나누려면 블록 설정이나 다른 방법을 써야 하며, 현재는 그 기능을 제공하지 않는다.
