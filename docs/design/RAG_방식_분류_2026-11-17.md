# RAG 방식 분류 (2026-11-17)

이 문서는 docvec v3(Project_3)의 RAG가 어떤 방식인지 세 가지 기준으로 정의한다. 기준은 작동 방식(아키텍처), 구현 도구(프레임워크), 데이터 저장소(검색 엔진)다. 내용은 커밋 `cb33d7c` 시점의 코드를 직접 확인해 적었다. 각 단계의 알고리즘과 수식은 `docs/기술문서_시스템_아키텍처.md` 11절에 있으므로, 이 문서는 분류와 그 근거만 다룬다.

## 요약

이 시스템은 프레임워크 없이 직접 구현한 권한 인지형 하이브리드 RAG다. Qdrant에서 의미 벡터(dense)와 키워드 벡터(sparse)로 함께 찾고, 교차 인코더로 재순위한다. 여기에 상위 절 문맥과 답변 자기검증을 더했다. 질문을 나눠 찾는 심층 검색은 선택 모드로 두었고, MCP 서버로 외부 에이전트에도 검색 기능을 내놓는다.

| 기준 | 분류 |
|---|---|
| 작동 방식 | Advanced RAG를 바탕으로 라우팅과 자기검증을 더한 Modular RAG. 선택 모드로 통제된 Agentic RAG(심층 검색)를 둔다. GraphRAG는 아니다. |
| 구현 도구 | RAG 프레임워크(LangChain, LlamaIndex, Haystack)를 쓰지 않은 자체 구현. 부품마다 전용 라이브러리를 쓴다. |
| 데이터 저장소 | Qdrant 하나에서 dense와 sparse 검색을 함께 한다. 하이브리드 검색형이다. 원본과 메타데이터는 PostgreSQL, MinIO, Redis가 나눠 맡는다. |

## 1. 작동 방식(아키텍처)에 따른 분류

### 1.1 정의

기본 흐름은 Advanced RAG다. 검색 전에 질의를 다듬고, 검색 후에 재순위를 한다. 그 위에 질문 의도에 따라 검색 경로를 고르는 라우팅과, 답이 근거에 기대는지 확인하는 자기검증 단계를 모듈로 끼웠다. 이 점에서 Modular RAG에 해당한다. 사용자가 심층 검색을 고르면 LLM이 질문을 하위 질문으로 나누고, 하위 질문마다 찾은 뒤 종합한다. 이 모드는 Agentic RAG에 해당한다.

지식 그래프를 만들거나 엔티티 관계를 따라 찾지는 않으므로 GraphRAG는 아니다.

### 1.2 단계별 구성

| 단계 | 구현 | 해당 유형 | 코드 위치 |
|---|---|---|---|
| 검색 전 | 사전의 동의어로 검색어를 넓힌다. 재순위는 원래 질문으로 판단한다. | 질의 확장 | `dictionary_service.expand_query` |
| 검색 전 | LLM이 질문 의도를 문서 검색, 표 조회, 요약 조회 가운데 하나로 분류한다. 요약 조회는 요약 색인을 쓴다. 표 조회도 청크 검색을 먼저 쓰고, 결과가 없을 때만 표 목록을 찾는다. | 라우팅 | `tasks/chat.py`의 `_classify_intent`, `generate_answer` |
| 검색 | 의미 검색과 키워드 검색(BM25 방식)의 후보를 합친다. | 하이브리드 검색 | `tasks/chat.py`의 `_retrieve_chunks`, `qdrant_service.search` |
| 검색 | 보안등급과 ACL로 검색 단계에서 거르고, 재순위와 LLM에 넣기 전에 PostgreSQL 기준으로 다시 확인한다. 확인하지 못하면 근거에서 뺀다. | 권한 인지형 RAG | `access_policy` |
| 검색 후 | 벡터 점수와 BM25 점수를 섞는다. 선택하면 MMR로 비슷한 근거를 덜 뽑는다. 교차 인코더가 질문과 본문을 함께 읽어 최종 근거를 고른다. | 재순위 | `_rank_candidates`, `reranker.py`, `mmr_service.py` |
| 문맥 구성 | 작은 청크로 찾고, 답변에는 그 청크가 속한 절의 앞뒤 청크를 함께 넘긴다. | Parent Document Retrieval | `parent_context.py` |
| 색인 | 키워드 색인용 텍스트에 절 경로 같은 문맥을 덧붙인다. 인용과 화면 표시는 원문을 쓴다. | Contextual Retrieval | `storage_blocks.py`의 `index_text` |
| 생성 후 | 검증 모델이 답이 근거에 기대는지 판정한다. 근거가 없다고 보면 범위를 넓혀 한 번만 다시 찾고 답한다. | 자기검증형 RAG(Self-RAG나 CRAG의 단순형) | `_is_answer_grounded`, `generate_answer` |
| 심층 검색(선택) | LLM이 질문을 하위 질문으로 나눈다. 하위 질문마다 찾고, 근거가 약하면 한 번 보강한 뒤 근거를 합쳐 종합한다. | Agentic RAG | `services/agentic/planner.py`, `deep_search.py` |
| 외부 연동 | MCP 서버가 `list_collections`, `search_documents`, `read_chunk`, `read_document`, `ask` 도구를 내놓는다. 외부 에이전트가 이 시스템을 검색 도구로 쓴다. | 도구형 RAG | `app/mcp/` |

### 1.3 에이전틱 단계의 범위

이 시스템의 에이전틱 단계는 LLM이 도구를 마음대로 반복해 부르는 방식이 아니다. LLM은 질문을 나누는 일과 답을 종합하는 일만 맡는다. 근거가 충분한지는 코드가 판단한다. 기준은 찾은 근거 수(2건 이상)와 재순위 최고 점수(0.5 이상)다. 보강 검색과 범위를 넓힌 재검색은 각각 한 번으로 묶여 있어, 답이 늦어지는 상한이 정해져 있다. 하위 질문이 무엇이든 모든 검색은 같은 권한 필터를 지나므로, 사용자가 볼 수 없는 문서는 근거가 될 수 없다. 그래서 이 방식은 "통제된(bounded) Agentic RAG"라고 부르는 것이 정확하다.

### 1.4 기본 검색 설정

컬렉션마다 검색 설정을 바꿀 수 있다. 저장된 설정이 없으면 채팅은 아래 기본값을 쓴다(`search_settings.py`).

| 항목 | 기본값 |
|---|---|
| 검색 방식 | 하이브리드 |
| 근거 수 | 5 |
| 교차 인코더 재순위 | 켬 |
| MMR(다양화) | 끔 |
| 벡터 점수 비중 | 0.6(BM25 0.4) |

검색 방식을 "벡터"로 바꾸면 키워드 색인을 쓰지 않고 의미 검색만 한다. 검색 API는 방식을 넘기지 않고 컬렉션 설정도 없으면 예전처럼 의미 검색을 쓴다.

## 2. 구현 도구(프레임워크)에 따른 분류

### 2.1 정의

LangChain, LlamaIndex, Haystack 같은 RAG 프레임워크를 쓰지 않았다. 검색, 재순위, 생성 단계를 Python 코드로 직접 엮은 자체 구현이다. 권한 재확인, 답변 캐시의 권한 지문, 외부 모델 차단처럼 거버넌스가 단계 사이사이에 끼어야 해서, 흐름을 프레임워크에 맡기지 않고 직접 다룬다.

### 2.2 역할별 도구

| 역할 | 도구 |
|---|---|
| API 서버 | FastAPI |
| 작업 실행 | Celery와 Redis(문서 처리, 답변 생성, 임베딩, 추출 큐로 나뉜다) |
| 문서 처리 파이프라인 | 자체 워크플로 블록 엔진. 텍스트 추출, 구조 분석, 정제, 사전, PII, 청크 분할, 품질 검사, 색인을 블록으로 잇는다. |
| 문서 파서 | Docling(PDF 표), pyhwp(구형 HWP), HWPX XML 직접 해석, Tesseract(OCR) |
| 임베딩 | FlagEmbedding의 `bge-m3`(기본값). sentence-transformers 모델과 OpenAI `text-embedding-3-small`도 고를 수 있다. |
| 재순위 | FlagEmbedding의 `BAAI/bge-reranker-v2-m3`(교차 인코더) |
| 키워드 검색 | kiwipiepy(한국어 형태소 분석), rank-bm25(후보 재점수), 자체 sparse 벡터 생성(`lexical_index.py`) |
| 생성 LLM | 사내 추론 서버 Ollama를 HTTP로 부른다(`qwen2.5` 3B와 7B, 4비트 양자화). 보안등급이 허용하는 문서에 한해 OpenAI와 Anthropic SDK도 쓴다. |
| 그림 설명(선택) | Ollama의 그림 모델(`LOCAL_VISION_MODEL`). 기본값은 꺼짐이다(설계 문서 9.4절). |
| 외부 에이전트 연동 | 자체 구현 MCP 서버(Streamable HTTP, JSON-RPC, 개인 접근 토큰 인증) |

## 3. 데이터 저장소(검색 엔진)에 따른 분류

### 3.1 정의

벡터 DB인 Qdrant 하나에서 의미 검색과 키워드 검색을 모두 처리하는 하이브리드 검색형이다. Elasticsearch, OpenSearch, pgvector는 쓰지 않는다. 키워드 검색은 Qdrant의 sparse 벡터로 구현했고, 드문 낱말의 가중치(IDF)는 Qdrant가 컬렉션 통계로 곱한다. 원문, 권한, 파일은 다른 저장소가 맡는다.

### 3.2 저장소별 역할

| 저장소 | 담는 것 | 검색에서의 역할 |
|---|---|---|
| Qdrant 청크 컬렉션 | 청크의 dense 벡터(bge-m3)와 페이로드(원문, 문맥이 붙은 색인 텍스트, 문서 id, 컬렉션 id, 권한 정보) | 의미 검색을 하고, 검색 단계에서 권한 필터를 적용한다. |
| Qdrant 키워드 컬렉션 | 청크의 sparse 벡터(형태소 토큰의 BM25 단어 빈도 항) | 키워드 검색. 조항 번호, 품번, 고유명사처럼 글자가 그대로 맞아야 하는 질의를 찾는다. |
| Qdrant 요약 컬렉션 | 문서마다 요약 벡터 하나 | 요약 조회 의도일 때 문서 단위로 찾는다. |
| PostgreSQL | 문서, 청크 원문, 상위 절, 표 행, 권한과 보안등급, 사전, 답변 추적, 감사 기록 | 검색 결과의 권한을 다시 확인하고, 상위 절 문맥을 구성하며, 표 목록 대체 검색에 쓰인다. |
| MinIO | 원본 파일, 쪽 그림, 추출한 그림 | 원문 대조와 인용 위치 표시에 쓰인다. |
| Redis | 작업 큐, 답변 캐시, 진행 상황 | 같은 질문의 답을 캐시에서 낸다. 캐시 키에 권한 지문을 넣어 등급이 다른 사용자에게 답이 새지 않게 한다. |

## 4. 해당하지 않는 유형

분류를 분명히 하려고, 흔히 함께 거론되지만 이 시스템이 하지 않는 것을 적는다.

| 유형 | 상태 |
|---|---|
| GraphRAG | 지식 그래프를 만들지 않는다. |
| LLM 자율 도구 호출 루프(ReAct형) | 시스템 안에서는 쓰지 않는다. 외부 에이전트가 MCP로 이 시스템을 부를 때만 그 에이전트 쪽에서 일어난다. |
| 질의 재작성 LLM(HyDE 등) | 쓰지 않는다. 질의 확장은 사전 기반이다. |
| 멀티모달 검색 | 그림은 글(OCR, 선택 시 그림 모델 설명)로 바꿔 색인한다. 그림 벡터로 직접 찾지는 않는다. |
