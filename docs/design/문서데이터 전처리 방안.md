# 문서 데이터 전처리 상세 설계서

**최종 갱신**: 2026-11-17. 아래 내용은 2026-11-17 기준 코드(HEAD 0f38033)를 점검해 실제 구현 상태를 반영함. 구현하지 않은 항목은 해당 절에 미구현으로 표시함

## 1. 문서 개요

### 1.1 목적

본 문서는 문서 기반 AI 플랫폼에서 사용되는 **문서 데이터 전처리 기능의 상세 설계 기준**을 정의한다.

문서 데이터 전처리는 PDF, DOCX, HWP, TXT, XLSX, 이미지 등의 원본 파일을 다음과 같은 후속 기능에서 활용할 수 있도록 표준화된 데이터로 변환하는 과정이다.

- 문서 검색
- 키워드 추출
- 문서 분류
- 문서 요약
- 질의응답
- RAG 검색
- 임베딩 생성
- 엔티티 추출
- 문서 비교
- 문서 품질 분석
- 업무 자동화

전처리 단계에서는 단순히 문서의 텍스트만 추출하는 것이 아니라, 문서의 구조와 위치 정보, 적용된 사전, 처리 이력, 오류 정보, 품질 지표를 함께 관리해야 한다.

---

### 1.2 핵심 설계 원칙

문서 데이터 전처리 기능은 다음 원칙을 기준으로 설계한다.

1. **원본 보존**
   - 원본 파일은 변경하지 않는다.
   - 추출본, 정제본, 정규화본을 별도 데이터로 관리한다.

2. **처리 이력 추적**
   - 어떤 블록이 어떤 설정으로 실행되었는지 기록한다.
   - 입력과 출력의 해시값을 저장한다.
   - 사전, 모델, 규칙의 버전을 기록한다.

3. **부분 재처리 지원**
   - 전체 문서를 처음부터 다시 처리하지 않고 특정 단계 이후만 다시 실행할 수 있어야 한다.

4. **문서 구조 보존**
   - 페이지, 섹션, 제목, 문단, 표, 목록, 각주 등의 구조를 가능한 한 유지한다.

5. **검증 가능성**
   - 전처리 결과가 원문의 어느 위치에서 생성되었는지 역추적할 수 있어야 한다.

6. **블록 기반 실행**
   - 전처리 기능은 고정된 실행 블록으로 구성한다.
   - AI는 블록을 직접 대체하는 것이 아니라, 블록 구성과 설정을 보조한다.

7. **확장 가능성**
   - 신규 파일 형식, 신규 사전, 신규 정제 규칙, 신규 분할 정책을 추가할 수 있어야 한다.

## 2. 전체 처리 흐름

```text
문서 업로드
→ 파일 검증
→ 파일 형식 판별
→ 악성 파일 및 보안 검사
→ 텍스트 및 객체 추출
→ OCR 수행
→ 문서 구조 분석
→ 텍스트 정제
→ 사전 기반 정규화
→ 개인정보 및 민감정보 탐지
→ 문서 분할
→ 품질 검증
→ 전처리 결과 저장
→ 임베딩 또는 후속 AI 처리
```

플랫폼 내부에서는 각 단계를 독립적인 워크플로우 블록으로 관리한다. 표준 전처리 워크플로우(시스템 기본값)의 실제 블록 순서는 다음과 같다.

```text
[문서 입력]              업로드 API가 문서를 등록하고 워크플로우를 시작함
    ↓
[파일 검증]              file_validate
    ↓
[형식 판별]              format_detect
    ↓
[텍스트 추출]            text_extract (OCR 포함)
    ↓
[문서 구조 분석]         structure_analyze
    ↓
[텍스트 정제]            text_clean
    ↓
[사용자 사전 적용]       user_dict
    ↓
[동의어 정규화]          synonym
    ↓
[불용어 처리]            stopword
    ↓
[민감정보 탐지]          pii_detect
    ↓
[문서 분할]              chunk_split
    ↓
[품질 검증]              quality_check (검토 게이트)
    ↓
[RAG 저장]               rag_store (임베딩, 벡터 DB 색인, 청크 저장)
```

사용자 사전을 동의어와 불용어보다 먼저 적용하는 이유는 사용자 사전 용어가 불용어 규칙으로 잘못 지워지지 않게 하기 위해서다(9.5절). 독립된 OCR 블록(ocr)은 표준 워크플로우에 넣지 않는다. OCR은 텍스트 추출 블록 안에서 쪽 단위로 수행한다(5.2.1절, 6절). 악성 파일 검사는 구현하지 않았다(3.2절).

모든 문서에 동일한 블록을 적용할 필요는 없다. 예를 들어 텍스트 레이어가 정상적으로 존재하는 PDF에는 OCR 단계를 생략할 수 있다. 실제로는 텍스트 추출 블록이 쪽마다 OCR 필요 여부를 정하므로, 텍스트 레이어가 충분한 쪽에는 OCR을 적용하지 않는다(6.1절).

## 3. 입력 문서 관리

## 3.1 지원 파일 형식

초기 지원 형식은 다음과 같이 구성할 수 있다.

| 분류 | 파일 형식 | 처리 방식 (2026-11-17 구현 기준) |
|---|---|---|
| 문서 | PDF | 텍스트 레이어가 있으면 Docling 엔진(기본 auto), 없으면 쪽 단위 전면 OCR(Tesseract) 엔진 |
| 문서 | DOCX | 문단과 표를 문서 순서대로 추출함. 쪽수는 미리보기 PDF로 셈 |
| 문서 | HWP/HWPX | 문단, 표(병합 칸 포함), 글자 서식과 개요 스타일을 추출함. 쪽은 미리보기 PDF로 배정함 |
| 문서 | TXT, MD | 인코딩을 판별(utf-8-sig, cp949, utf-16 순)한 뒤 로드함. 마크다운 제목과 파이프 표를 인식함 |
| 웹 문서 | HTML, HTM | h1부터 h6까지의 제목과 table 태그를 표로 추출함 |
| 스프레드시트 | XLSX | 시트 하나를 한 쪽으로 보고, 빈 행으로 나뉜 구역을 표로 추출함. 수식은 저장된 계산값을 씀 |
| 프레젠테이션 | PPTX | 슬라이드 하나를 한 쪽으로 보고 제목, 본문, 표, 발표자 노트를 추출함 |
| 이미지 | PNG, JPG, TIFF, BMP, WEBP | 쪽마다 한 장짜리 PDF로 바꾼 뒤 스캔 PDF와 같은 전면 OCR 경로로 처리함 |

RTF, XLS(구형 엑셀), CSV, JSON, XML은 지원하지 않는다. 지원 형식 목록은 `app/pipeline/formats.py`에 있으며, 업로드 API와 커넥터 동기화, 파일 검증 블록이 같은 목록을 쓴다. 이 목록에 없는 확장자는 업로드 단계에서 거부된다.

## 3.2 업로드 시 검증 항목

문서 업로드 시 다음 항목을 검증한다.

- 허용된 확장자인지 확인
- 실제 MIME Type과 확장자가 일치하는지 확인
- 최대 파일 크기 초과 여부
- 암호화 또는 비밀번호 설정 여부
- 파일 손상 여부
- 압축 폭탄 가능성
- 악성 코드 포함 가능성
- 중복 파일 여부
- 빈 파일 여부
- 페이지 수 또는 시트 수 제한 초과 여부

**구현 현황 (2026-11-17)**

- 허용 확장자: 업로드 API가 `SUPPORTED_SUFFIXES`로 거부하고, `file_validate` 블록이 같은 목록을 다시 확인한다. MIME 타입과 파일 시그니처는 대조하지 않으며, 업로드 MIME 타입은 확장자에서 정한다.
- 최대 크기: 업로드 API는 200MB(`max_upload_size_bytes`)를 넘으면 거부한다. `file_validate` 블록의 기본 상한은 100MB라서, 그 사이 크기의 파일은 블록에서 `FILE_UNSUPPORTED`로 실패한다. 두 값은 설정에서 따로 조정한다.
- 암호화 여부: PDF만 열어 판정한다. DOCX와 HWP는 암호 여부를 확인하지 않으며, 열지 못하면 텍스트 추출 실패로 처리된다.
- 파일 손상: 어댑터가 열지 못하면 `TEXT_EXTRACTION_FAILED`로 실패한다. 별도의 무결성 검사는 없다.
- 압축 폭탄: ZIP 업로드에서만 항목 수(200개), 항목 크기(200MB), 전체 압축 해제 크기(2GB), 압축 파일 크기(1GB) 상한을 둔다. 문서 내부의 압축 해제 크기는 검사하지 않는다.
- 악성 코드: 미구현이다. `file_validate`의 `scan_malware` 설정은 검사 엔진이 없어서 항상 건너뜀으로 기록한다.
- 중복 파일: 업로드 API가 같은 사용자의 같은 컬렉션 안에서 SHA-256이 같은 파일을 409로 거부한다. `file_validate`의 중복 검사는 결과에 기록만 하고 실패시키지 않는다.
- 빈 파일: 별도로 검사하지 않는다.
- 페이지 수: PDF만 쪽수를 미리 세어 `max_pages`(기본 1,000쪽)를 넘으면 거부한다. 다른 형식에는 적용하지 않는다.

## 3.3 문서 메타데이터

문서 업로드 시 최소한 다음 메타데이터를 저장한다.

```json
{
  "documentId": "DOC-20260714-000001",
  "fileName": "사업계획서.pdf",
  "originalFileName": "사업계획서_최종_v3.pdf",
  "fileExtension": "pdf",
  "mimeType": "application/pdf",
  "fileSize": 10485760,
  "pageCount": 42,
  "checksum": "sha256:...",
  "uploadedBy": "USER-1001",
  "uploadedAt": "2026-07-14T10:00:00+09:00",
  "documentStatus": "UPLOADED",
  "sourceType": "LOCAL_UPLOAD",
  "version": 1
}
```

위 JSON은 설계 예시다. 실제 값은 `Document` 모델의 열에 저장된다. `documentId`는 `id`, `fileName`은 `filename`, `originalFileName`은 `original_filename`, `mimeType`은 `mime_type`, `checksum`은 `file_hash`(SHA-256), `uploadedBy`는 `created_by`, `uploadedAt`은 `created_at`, `version`은 `version_number`에 해당한다. `documentStatus`는 `status` 열이며, 업로드 직후에는 `QUEUED` 값을 가진다. `pageCount`는 `page_count` 열이고, 쪽수를 알 수 없는 HWP와 HWPX에서는 비어 있다(21.1.1절).

## 4. 파일 형식 판별

## 4.1 판별 목적

파일 확장자만으로 처리 방식을 결정하면 확장자 위조, 형식 불일치, 손상 파일 등의 문제가 발생할 수 있다.

따라서 다음 정보를 함께 사용한다.

- 파일 확장자
- MIME Type
- 파일 시그니처
- 내부 구조
- 압축 패키지 구조
- 인코딩 정보

---

## 4.2 판별 결과 예시

```json
{
  "documentId": "DOC-20260714-000001",
  "detectedFileType": "PDF",
  "detectedMimeType": "application/pdf",
  "isScannedDocument": false,
  "hasTextLayer": true,
  "isEncrypted": false,
  "confidence": 0.99
}
```

## 4.3 구현 현황

형식 판별 블록(`format_detect`)은 확장자와 MIME 타입으로 어댑터를 고른다(`get_adapter`, `app/pipeline/adapters/__init__.py`). 파일 시그니처, 내부 구조, 압축 패키지 구조, 인코딩은 판별에 쓰지 않는다. 출력의 `detected_file_type`은 어댑터 이름에서 얻은 값이다(`pdf`, `docx`, `hwp`(HWP와 HWPX 공통), `sheet`, `slide`, `text`, `html`, `image`).

PDF만 텍스트 레이어 유무를 따로 본다. 앞쪽 3쪽의 글자 수를 세고, 20자 이상이면 텍스트 레이어가 있다고 본다. 그보다 적으면 글자 수에 비례해 확신도를 낮게 준다. 암호가 걸린 PDF는 열 때 나는 예외 문구로 판정한다. DOCX, HWP, HWPX, 텍스트, 이미지는 텍스트 레이어가 있는 것으로 간주한다. 이미지는 전면 OCR 경로로 처리한다.

## 5. 텍스트 추출

## 5.1 텍스트 추출 목적 및 엔진

> **⚠ 실제 구현 상태**: Docling 도입(2026-07-23 Phase 1)이 완료되어 PDF 처리 방식이 이원화되었습니다.

텍스트 추출 단계에서는 문서의 내용을 단순 문자열로만 반환하지 않고, 문서 객체와 위치 정보를 함께 추출합니다. 실제 구현에서는 다음 두 가지 엔진을 지원합니다:

1. **Legacy Engine** (PDF 스캔본, DOCX, HWP/HWPX, XLSX, PPTX, 텍스트, HTML, 이미지): 형식별 어댑터를 사용합니다.
   - 파일: `backend/app/pipeline/adapters/pdf_adapter.py`, `docx_adapter.py`, `hwp_adapter.py`, `sheet_adapter.py`, `slide_adapter.py`, `text_adapter.py`, `image_adapter.py`

2. **Docling Engine** (PDF 전용):
   - 파일: `backend/app/pipeline/adapters/docling_adapter.py`
   - `TextExtractConfig.engine`의 기본값은 `auto`다. 텍스트 레이어가 있는 PDF는 Docling으로, 텍스트 레이어가 없는 스캔 PDF는 Legacy 엔진(전면 OCR)으로 보낸다(2026-11-17 기준 블록 버전 1.18.0부터).
   - `docling`을 고르면 스캔 PDF에도 Docling을 쓰고 경고를 남긴다. `legacy`를 고르면 PDF도 Legacy 엔진으로 처리한다.
   - DOCX, HWP, HWPX는 설정과 무관하게 항상 Legacy 엔진을 쓴다.
   - 추출 결과에 통합 요소 JSON을 추가로 저장한다(Document.elements 필드). 스캔 PDF는 Legacy 엔진이 표와 그림을 찾지 못하므로, 기본값으로 켜진 `scan_layout` 설정이 Docling으로 표와 그림의 위치만 찾아 덧붙인다(5.2.1절).

## 5.1.1 텍스트 추출 목적

텍스트 추출 단계에서는 문서의 내용을 단순 문자열로만 반환하지 않고, 문서 객체와 위치 정보를 함께 추출한다.

추출 대상은 다음과 같다.

- 제목
- 본문
- 문단
- 표
- 목록
- 머리말
- 꼬리말
- 각주
- 미주
- 캡션
- 텍스트 박스
- 슬라이드 노트
- 셀 데이터
- 링크
- 이미지 설명
- 문서 속성

**구현 현황 (2026-11-17)**: 제목, 본문, 표, 목록, 그림(그림 인식 결과를 `[그림 N]` 블록으로 본문에 넣음), 캡션(Docling 경로), 발표자 노트(PPTX), 셀 값(XLSX, 계산된 표시값), 문서 속성(제목, 작성일, 쪽수)을 추출한다. 머리말과 꼬리말은 PDF에서 쪽 가장자리에 반복되는 줄로 판정하고, 나머지 형식은 구조 분석의 반복 줄 판정으로 처리한다. 각주는 PDF 하단의 번호 표기를 기준으로 판정한다. 미주, 텍스트 박스, 하이퍼링크, DOCX의 머리말과 꼬리말과 각주는 추출하지 않는다. XLSX의 셀 주소와 수식 문자열, 숨김 시트 정보도 저장하지 않는다.

## 5.2 PDF 텍스트 추출 (Docling Engine)

> **실제 구현**: Docling 어댑터(backend/app/pipeline/adapters/docling_adapter.py)는 다음을 제공합니다:
> - IBM Docling DocumentConverter 기반 추출
> - 통합 요소 JSON 생성 (page/type/bbox/content/metadata)
> - 각 요소의 신뢰도와 감지 방식 추적
> - Document.elements 필드에 저장

### Docling PDF 처리 특성

1. **통합 요소 추출**
   - 각 문서 요소(heading, paragraph, table, picture 등)를 JSON으로 저장
   - 요소별 bbox, confidence, section_path 정보 포함
   - Structure analyze(Phase 2)가 이 정보를 활용하여 정규식 폴백 경로 개선

2. **OCR 처리 (EasyOCR + 한국어 명시)**
   - 기본 RapidOCR은 한글을 의미 없는 한자 형태로 오인식하는 문제 실제 확인 (2026-07-23)
   - **반드시 EasyOCR을 한국어로 명시 설정** (docling_adapter.py의 `_get_converter()`)
   - 설정: `pipeline_options.ocr_options = EasyOcrOptions(lang=["ko"])`
   - 한글 문서의 OCR 품질 보장

3. **표 처리**
   - Docling이 추출한 표를 행/열 기반 Markdown으로 변환
   - 표는 element_spans 계산 시 이전 갭을 보정하기 위해 text_blocks에도 저장 (phase 1 검증 중 발견)

4. **그림/이미지 처리**
   - `generate_picture_images=True` 설정으로 실제 PNG bytes 추출
   - PIL Image 형식으로 저장하고 SVG/RGBA 모드를 PNG로 변환

5. **표 머리글**: Docling이 열 이름을 알아보지 못하면 열 이름이 `0, 1, 2…`로 나온다. 이때는 본문의 첫 행을 머리글로 쓴다(`_table_rows`). 병합 칸 정보는 Docling 표에 대해 저장하지 않는다.
6. **변환기 재사용**: `DocumentConverter`는 프로세스마다 한 번만 만든다. 텍스트 추출은 `worker-extract` 프로세스에서만 돌기 때문에 레이아웃, 표, OCR 모델은 한 벌만 올라간다.
7. **저커버리지 쪽 보강**: OpenAI 또는 Anthropic 키가 등록되어 있고 문서의 보안 등급이 외부 모델 사용을 허용할 때만, 글자가 적은 쪽을 클라우드 VLM으로 읽어 VLM 텍스트를 별도 블록으로 덧붙인다. 키가 없으면 실행되지 않는다. Docling 자체 VLM 파이프라인(granite-docling)은 한국어 문서에서 반복 출력이 나와 쓰지 않는다(2026-07-29 조사).

### 5.2.1 PDF 텍스트 추출 (Legacy Engine)

PDF 문서는 다음 유형으로 구분한다.

### 텍스트 PDF

텍스트 레이어가 존재하는 PDF이다.

처리 항목:

- 페이지별 텍스트 추출
- 텍스트 블록 좌표 추출
- 읽기 순서 복원
- 글자 크기 및 스타일 추출
- 표 후보 탐지
- 이미지 객체 추출
- 페이지 회전 정보 확인(미구현)

### 스캔 PDF

페이지가 이미지로 구성된 PDF이다.

처리 항목:

- 페이지 이미지 렌더링(300dpi)
- 이미지 보정(회색조 변환만 적용함)
- OCR 수행(Tesseract, 한국어와 영어)
- OCR 신뢰도 저장(쪽 평균과 단어 수. 글자 위치는 저장하지 않음)
- 표와 그림 찾기(`scan_layout`, Docling 레이아웃 인식을 사용함). 본문 구조는 구조 분석 블록이 정함

### 혼합 PDF

일부 페이지에는 텍스트 레이어가 있고 일부 페이지는 이미지인 PDF이다.

페이지별로 텍스트 추출 방식과 OCR 방식을 선택한다.

### 구현 현황 (2026-11-17)

- OCR 대상 쪽: 그림이 쪽 면적의 절반을 넘거나, 글자 밀도로 구한 덮개율이 0.3 미만이면서 쪽 글자가 50자 미만인 쪽이다. 글자가 50자 이상이면 덮개율과 상관없이 OCR하지 않는다.
- 렌더링과 인식: 쪽을 300dpi PNG로 그린다. 클라우드 VLM 키가 있으면 먼저 VLM으로 읽고, 실패하면 Tesseract(`--oem 1 --psm 4`)로 읽는다.
- 채택 규칙: OCR 결과는 원래 글자보다 길다는 이유만으로 채택하지 않는다. 원래 글자가 50자 이상이면 OCR로 바꾸지 않는다. 길이만으로 고르면 잘못 읽은 OCR이 정확한 글자를 덮을 수 있기 때문이다.
- 표 영역의 글자는 본문에서 빼고 표 후보로 따로 남긴다.
- 스캔 문서의 표와 그림: `scan_layout`이 기본으로 켜져 있다. 27쪽 보고서에서 Legacy 엔진은 표와 그림을 하나도 찾지 못했고, Docling 레이아웃은 표 9개와 그림 10개를 찾았다(2026-11-16 실측). 찾은 표는 쪽 끝에 `[표 N]`으로 덧붙이고, 그림은 그림 인식 대상이 된다. 표 안의 글자는 Docling의 OCR로 읽은 것이라 본문보다 오독이 많다.

## 5.3 DOCX/HWP 추출

문서 편집기 형식에서는 다음 정보를 보존한다.

- 제목 스타일
- 문단 스타일
- 들여쓰기
- 번호 목록
- 글머리 기호
- 표 셀 병합 정보
- 머리말 및 꼬리말
- 각주
- 페이지 구분
- 이미지 위치
- 텍스트 박스
- 하이퍼링크

**구현 현황 (2026-11-17)**

- DOCX: 문단과 표를 본문 순서대로 내보낸다(텍스트 추출 블록 1.5.0). 스타일 이름과 글꼴 이름을 문단 서식으로 남기고, 작성일은 파일 속성에서 읽는다. 쪽수는 LibreOffice로 만든 미리보기 PDF의 쪽수이며, 변환에 실패하면 Word가 저장한 쪽수(docProps/app.xml)를 쓴다. 병합 칸 정보, 머리말과 꼬리말, 각주, 하이퍼링크, 목록 번호와 글머리 기호, 텍스트 박스는 추출하지 않는다.
- HWPX: 문단과 표를 문서 순서대로 내보낸다. 표는 칸의 주소와 합친 크기로 격자를 만들어 열을 맞추고, 합친 칸의 위치와 크기를 `spans`로 남긴다. 셀 안의 여러 문단은 ` / `로 잇는다. 글자 크기, 굵기, 개요 스타일을 읽어 제목 판정에 쓴다. 그림은 BinData에서 읽는다.
- HWP(구형 이진 형식): pyhwp가 만든 XML에서 같은 방식으로 표 격자와 글자 서식을 읽는다(텍스트 추출 블록 1.26.0). 2026-11-17부터 적용했다.
- 쪽 배정(HWP, HWPX): 미리보기 PDF의 쪽별 글자에서 문단과 표의 앞쪽 60자를 문서 순서대로 찾아 쪽을 정한다. 찾지 못하면 직전 쪽에 머문다. 미리보기를 만들지 못하면 모든 블록이 1쪽으로 남고 쪽수는 비운다.

## 6. OCR 처리

> **실제 구현 참고**: Docling 엔진은 내부의 EasyOCR(한국어)을, Legacy 엔진은 Tesseract(한국어와 영어)를 쓴다. 독립된 `ocr` 블록(`OcrBlock`)은 자리표시자이며 표준 워크플로우에 넣지 않는다.

## 6.1 OCR 적용 조건

다음 조건 중 하나 이상을 만족하면 OCR을 수행한다.

- PDF에 텍스트 레이어가 없음
- 텍스트 추출량이 임계값보다 적음
- 추출된 문자의 깨짐 비율이 높음
- 이미지 문서가 입력됨
- 사용자가 OCR 강제 실행을 선택함
- 표 또는 도장이 이미지 형태로 존재함

**구현 현황**

- Legacy 엔진: 쪽의 그림 비율이 0.5를 넘거나, 덮개율이 0.3 미만이면서 쪽 글자가 50자 미만이면 OCR을 수행한다(5.2.1절). 이미지 파일은 항상 OCR을 쓴다.
- Docling 엔진: 자동 선택에서 텍스트 레이어가 없는 PDF는 Legacy 엔진으로 넘어가 전면 OCR을 쓴다. 텍스트 레이어가 있는 PDF에서 그림 영역으로 잡힌 곳은 원본 텍스트 레이어를 먼저 읽고, 10자 이상일 때만 그 글자를 쓴다.
- 미구현: 깨짐 비율에 따른 OCR 재실행, 표와 도장을 이미지로 판단하는 OCR, 사용자의 OCR 강제 실행. `OcrConfig`의 `force_ocr` 값은 자리표시자 블록에만 있어 효과가 없다.

---

## 6.2 OCR 전처리

OCR 정확도를 높이기 위해 다음 이미지 보정 기능을 사용할 수 있다.

- 기울기 보정
- 회전 보정
- 노이즈 제거
- 대비 조정
- 흑백 변환
- 해상도 조정
- 여백 제거
- 그림자 제거
- 문서 영역 탐지
- 다단 문서 영역 분리

**구현 현황**: Legacy 경로는 회색조 변환만 적용한다. 이진화(Otsu)는 벤치마크에서 이득이 없어 쓰지 않는다(F1 0.628에서 0.621로 떨어짐). Tesseract 설정은 `--oem 1 --psm 4`이며, psm 3은 한글 스캔에서 글자 사이가 벌어져 채택하지 않았다. 기울기, 회전, 노이즈, 대비, 여백, 그림자, 문서 영역 탐지, 다단 분리는 구현하지 않았다. `OcrConfig`의 `deskew`, `denoise`, `contrast` 값은 자리표시자 블록에만 있고 실제 처리에 쓰이지 않는다.

## 6.3 OCR 결과 데이터

```json
{
  "pageNumber": 3,
  "text": "문서 데이터 전처리",
  "confidence": 0.94,
  "boundingBox": {
    "x": 120,
    "y": 340,
    "width": 450,
    "height": 42
  },
  "language": "ko",
  "engine": "OCR_ENGINE_A",
  "engineVersion": "2.1.0"
}
```

위 JSON은 설계 예시다. 실제로는 쪽 단위 목록이 `Document.ocr_page_confidence`에 저장된다. 각 항목은 `{"page_number": 3, "confidence": 0.94, "word_count": 58}` 형태다. `confidence`는 Tesseract가 단어마다 준 신뢰도(`image_to_data`)의 평균이다. 클라우드 VLM으로 읽은 쪽은 단어 신뢰도가 없으므로 기록하지 않는다. 글자 위치(bbox)와 OCR 엔진 버전은 저장하지 않는다.

---

## 6.4 OCR 품질 기준

OCR 결과에 대해 다음 지표를 산출한다.

- 평균 인식 신뢰도
- 저신뢰 문자 비율
- 숫자 인식 오류 비율
- 한글 조합 오류 비율
- 비정상 특수문자 비율
- 빈 페이지 비율
- 문장 완결성
- 사전 미등록 토큰 비율

**구현 현황**: 구현된 지표는 쪽 평균 인식 신뢰도(기준 0.5 미만인 쪽은 실패 쪽으로 기록함), 한 글자 한글 토큰 비율(기준 25% 초과이면 글자가 벌어진 것으로 보고 점수를 깎음), 빈 쪽 비율, 깨진 문자 비율(추출 텍스트 전체 기준)이다. 숫자 인식 오류 비율, 한글 조합 오류 비율, 비정상 특수문자 비율, 문장 완결성, 사전 미등록 토큰 비율은 구현하지 않았다.

## 6.5 OCR 결과 후처리 (구현)

- **그림 인식 잡음 제거**: 그림 인식 결과에서 줄마다 한글 단어, 숫자, 영문 단어가 차지하는 글자 비율이 절반 미만인 줄은 본문에서 뺀다. 남은 글자가 10자 미만이면 그림 텍스트 전체를 본문에 넣지 않는다. 인식 원문은 그림 기록(`Document.images`)에 그대로 남는다(`app/pipeline/ocr_cleanup.py`).
- **% 오인식 보정**: OCR이 `%`를 `9`나 `96`으로 읽어 생긴 소수 셋째 자리 숫자(예: 87.00%가 87.009, 94.30%가 94.3096)를 고친다. 같은 표나 문단에 비율을 뜻하는 말이 있고, 제대로 찍힌 `%`가 없으며, 소수 셋째 자리 이상의 숫자가 두 개 이상이고 모두 같은 모양일 때만 고친다. p값처럼 진짜 소수가 섞인 문서는 고치지 않는다. 고친 개수는 텍스트 추출 경고로 남는다.
- **그림 글의 위치**: 그림 글은 그림 바로 앞 문단 뒤에 넣는다. 위치를 알 수 없으면 쪽 끝에 붙인다.
- **미구현**: 띄어쓰기 복원과 문장부호 앞 공백 제거는 하지 않았다(전처리 성능 검토 보고서 3절의 권고 4, 5가 남아 있다).

## 7.1 구조 분석 목적

```text
문서

 │   │   ├─ 제목
 │   │   ├─ 문단
 │   │   ├─ 목록
 │   │   ├─ 표
 │   │   └─ 이미지
 │   └─ 각주

```


위 JSON은 설계 예시다. 실제 노드는 `document_nodes` 행으로 저장되며, 열은 `id`, `node_type`, `level`, `sort_order`, `parent_node_id`, `page_number`, `span_start`, `span_end`, `text`(최대 2,000자), `style`, `source_table_id`, `element_id`, 보정 기록(`user_corrected`, `correction_type`, `correction_notes`)이다. `style`에는 `font_size`, `is_bold`, `is_italic`, `style_name`, `font_name`이 들어가며, 정렬(`alignment`)은 저장하지 않는다.

## 7.5 구현 현황 (2026-11-17)

구조 분석 블록(`structure_analyze`, 버전 1.15.0)은 두 경로 가운데 하나로 트리를 만든다.

1. **요소 경로**: `Document.elements`가 있으면(Docling으로 처리한 PDF) 요소의 유형을 노드 유형으로 옮긴다. `document_index`는 TOC, `section_header`와 `title`은 HEADING, `table`은 TABLE, `list_item`은 LIST_ITEM, `picture`와 `figure`는 IMAGE, `caption`은 CAPTION, `footnote`는 FOOTNOTE, `page_header`와 `page_footer`는 HEADER와 FOOTER이고, 나머지는 PARAGRAPH다. 이어서 `structure_refine.py`가 bbox로 제목 수준을 다시 정하고, 목차 쪽의 제목을 목차로 바꾸고, 쪽 가장자리에서 세 쪽 이상 반복되는 문구를 머리말이나 꼬리말로 바꾸고, 한 글자 문단을 버린다.
2. **정규식 경로**: 요소가 없는 문서(HWP, HWPX, DOCX, 스캔 PDF, Legacy로 처리한 PDF)는 줄 단위로 분류한다.
   - 번호 제목: `1.`, `1.1`처럼 점의 개수로 수준을 정한다. `1)`은 수준 3이다. 번호 뒤 글이 50자를 넘거나, 번호가 99보다 크거나, 글자보다 숫자가 많거나, 칸이 넓게 벌어져 있거나(표 행), 인용 연도가 있으면 제목으로 보지 않는다.
   - `제N장`, `제N절`, `제N조`, `제N편`과 `□`로 시작하는 줄은 수준 1이다.
   - 목록: `-`, `*`, `•`, `1.`, `1)`로 시작하는 줄이다.
   - 스타일 제목: HWPX와 HWP에서 "개요 N" 스타일을 쓴 짧은 문단은 수준 N의 제목이다.
   - 글자 신호: 굵고 본문 대표 크기보다 2pt 이상 큰 줄은 제목이다. 본문 대표 크기의 1.3배 이상이면 수준 1, 아니면 수준 2다. 정규식이 이미 분류한 줄은 바꾸지 않는다.
   - 목차: 앞쪽 60줄(빈 줄 제외) 안에서 점선 리더와 쪽 번호로 끝나는 줄이 세 줄 이상 이어지면 목차로 본다.
   - 머리말과 꼬리말: 쪽의 처음과 끝 두 줄 안에 있고, 숫자를 뺀 내용이 같은 줄이 세 쪽 이상에서 나오면 HEADER로 둔다. 글머리표 줄과 목록 줄은 제외한다.
   - 날짜만 적힌 줄(예: "2025년 12월")은 굵어도 제목이 아니다.
   - 제목 상자: 번호 표시로 시작하는 한 줄짜리 짧은 표는 제목으로 올리고, 그 아래 줄 제목의 수준을 한 단계 내린다(`title_box.py`).
3. **공통 규칙**: 제목 수준이 `heading_max_level`(기본 3)을 넘으면 문단으로 바꾼다. 노드의 쪽 번호는 요소의 쪽을 쓰고, 요소가 없으면 쪽 맵으로 시작 위치의 쪽을 찾는다. DOCX는 쪽 구분이 없어 비워 둔다.
4. **문서 제목**: `Document.title`은 `title_resolver.py`가 정한다. 원본 파일의 제목 속성, 1쪽 표지 줄(글자 크기 신호가 있는 줄 우선), OCR 문서의 파일명, 장 제목이 아닌 첫 제목, 정리한 파일명 순서다. 사용자가 고친 제목은 재처리가 덮어쓰지 않는다.
5. **글자 서식**: Docling 경로는 글꼴 정보를 주지 않으므로 `style`의 값이 비어 있다. 나머지 경로는 글자 크기, 굵기, 기울기, 스타일 이름을 채우고, 글꼴 이름은 DOCX와 PDF(Legacy)에서만 채운다(`메타 정보 생성.txt` 2절 참고).
6. **사용자 보정**: `PATCH /documents/{id}/nodes/{node_id}`로 수준(`level`), 유형(`node_type`), 서식(`style`)을 고칠 수 있다. 보정 기록은 `correction_type`과 `correction_notes`에 남는다. 문단 경계나 표 경계를 나누거나 합치는 편집은 지원하지 않는다.

**객체 유형 구현 현황**: 실제로 만드는 유형은 DOCUMENT, TOC, HEADING, PARAGRAPH, LIST_ITEM, TABLE, IMAGE, CAPTION, FOOTNOTE, HEADER, FOOTER다. COVER, SECTION, SENTENCE, LIST, TABLE_ROW, TABLE_CELL, PAGE_NUMBER, FORM_FIELD는 DB enum에만 있고 아직 만들지 않는다. 표의 행과 셀은 노드로 나누지 않고, 표 전체를 마크다운 텍스트 한 노드로 둔다.

## 8. 텍스트 정제

## 8.1 정제 목적

텍스트 정제는 분석 품질을 저해하는 불필요한 문자와 반복 요소를 제거하고, 문장 구조를 안정적으로 만드는 과정이다.

원문을 직접 수정하지 않고 다음 세 가지 값을 구분하여 저장한다.

```text
원문 텍스트
추출 텍스트
정제 텍스트
```

구현에서 원문은 `Document.parsed_text`로 남고, 정제 결과는 `DocumentTextRevision`(source=CLEAN), 청크 입력이 되는 정규화 텍스트는 `DocumentTextRevision`(source=NORMALIZED)으로 남는다. 텍스트 정제 블록은 원문을 바꾸지 않는다.

---

## 8.2 기본 정제 규칙

각 규칙 뒤의 괄호는 2026-11-17 기준 구현 여부다.

### 공백 정규화

- 연속 공백 제거(구현)
- 탭을 공백으로 변환(구현)
- 문장 내부 불필요한 줄바꿈 제거(미구현. 줄바꿈은 그대로 둔다)
- 문단 간 줄바꿈 유지(구현. 빈 줄이 세 줄 이상이면 한 줄로 줄인다)
- 줄 시작 및 종료 공백 제거(구현)
- 문장부호 앞의 공백 제거(미구현)

### 문자 정규화

- 유니코드 정규화(구현. NFC)
- 깨진 문자 치환(미구현. 사용자 정의 규칙으로만 가능하다)
- 제어문자 제거(구현)
- 비표준 따옴표 통일(구현. 곡선 따옴표를 직선 따옴표로 바꾼다)
- 전각 문자와 반각 문자 통일(구현. U+FF01부터 U+FF5E까지와 전각 공백)
- 하이픈 및 대시 문자 통일(일부 구현. en dash와 em dash를 하이픈으로 바꾼다)

### 반복 요소 제거

- 반복 머리말, 반복 꼬리말(구현. 구조 분석이 HEADER와 FOOTER로 표시하고, 구조 기반 청크 분할이 그 글자를 청크 본문에서 뺀다. 텍스트 정제의 `remove_repeated_headers` 설정은 기본으로 꺼져 있다)
- 페이지 번호(구현. 번호가 달라 줄이 같지 않아도 구조 분석이 숫자를 무시하고 반복을 판정한다)
- 보안 문구, 워터마크 텍스트, 출력 시스템 메시지(자동 제거는 미구현. 사용자 정의 규칙으로 등록해야 한다)
- 반복된 문서 제목(`remove_repeated_headers`가 여러 쪽에 반복되는 줄을 지우며, 기본으로 꺼져 있다)

### OCR 오류 보정

- 숫자와 문자 혼동(일부 구현. `%`를 `9`나 `96`으로 읽은 값만 고친다. 6.5절)
- 자모 분리(미구현)
- 비정상 띄어쓰기(미구현)
- 동일 문자의 반복(미구현)
- 줄바꿈으로 분리된 단어 결합(일부 구현. 하이픈으로 끝난 줄만 붙인다. `fix_ocr_errors` 설정이며 기본으로 꺼져 있다)
- 문맥 기반 오탈자 후보 탐지(미구현)

## 8.3 정제 규칙 데이터 모델

```json
{
  "ruleId": "CLEAN-RULE-001",
  "ruleName": "연속 공백 제거",
  "ruleType": "REGEX_REPLACE",
  "pattern": "\\s{2,}",
  "replacement": " ",
  "scope": "PARAGRAPH",
  "priority": 10,
  "enabled": true,
  "version": 3
}
```

실제 규칙은 `cleaning_rules` 테이블에 저장한다. 규칙 종류(`rule_type`)는 `REGEX_REPLACE`, `EXACT_REMOVE`, `LINE_FILTER` 셋이며, `BUILTIN`은 내장 규칙을 표시하는 값으로 사용자가 만들거나 고칠 수 없다. 규칙은 우선순위(`priority`) 내림차순으로 적용하고, 정규식이 잘못된 규칙은 건너뛴다. 실제 열 이름은 `id`, `rule_name`, `rule_type`, `pattern`, `replacement`, `scope`, `priority`, `enabled`, `version`이다. 위 JSON의 `ruleId`는 설계 예시다.

## 9. 사전 기반 정규화

## 9.1 사전 구성

전처리 플랫폼에서는 다음 세 가지 사전을 기본으로 관리한다.

1. 불용어 사전
2. 동의어 사전
3. 사용자 사전

각 사전은 버전 단위로 관리하며, 워크플로우 실행 시 특정 버전을 고정하여 사용한다.

**구현 현황**: 사전 항목의 종류는 `stopword`(불용어), `synonym`(동의어), `custom_word`(사용자 사전) 세 가지다. 버전은 전역 `DictionaryRevision` 번호로 매기며, 워크플로우 실행은 `WorkflowRun.dictionary_version`에 그 번호를 고정한다. 실행 시점의 사전 적용은 리비전 시각 이전에 갱신된 활성 항목을 쓰는 근사다. 항목별 이력 테이블이 없어서, 리비전 이후에 삭제된 항목은 되살리지 못한다.

---

## 9.2 불용어 사전

불용어 사전은 분석에 불필요하거나 의미 기여도가 낮은 표현을 제거 또는 제외하기 위해 사용한다.

예시:

- 페이지 번호
- 반복되는 보안 문구
- 문서 출력 시스템 문구
- 일반적인 접속 표현
- 분석에 불필요한 기호
- 조직별 상용 문구

```json
{
  "dictionaryId": "STOPWORD-001",
  "term": "대외비",
  "matchType": "EXACT",
  "action": "EXCLUDE_FROM_ANALYSIS",
  "scope": "ALL",
  "enabled": true,
  "version": 2
}
```

불용어는 원문에서 삭제하지 않고, 분석 대상에서 제외하는 방식이 기본이다.

구현에서 항목의 `match_type`은 `EXACT`, `PREFIX`, `SUFFIX`, `CONTAINS`, `REGEX` 가운데 하나다. 불용어 블록의 `action`이 `mark`(기본값)이면 본문은 그대로 두고 적용 기록만 남긴다. `remove`일 때만 본문에서 지운다. 사용자 사전 블록이 보호한 구간은 불용어로 잡지 않는다. 위 JSON의 `matchType`과 `action`은 설계 예시다.

---

## 9.3 동의어 사전

동의어 사전은 여러 표현을 하나의 대표어로 통합한다.

```text
AI
인공지능
Artificial Intelligence
A.I.
→ 인공지능
```

```json
{
  "dictionaryId": "SYNONYM-001",
  "canonicalTerm": "인공지능",
  "synonyms": [
    "AI",
    "Artificial Intelligence",
    "A.I."
  ],
  "caseSensitive": false,
  "domain": "GENERAL",
  "version": 4
}
```

동의어 처리 시 다음 값을 모두 유지해야 한다.

- 원문 표현
- 대표 표현
- 적용 위치
- 적용 사전 ID
- 사전 버전
- 적용 신뢰도

**구현 현황**: 적용 기록(`DictionaryApplication`)에는 원문 표현, 대표 표현, 시작과 끝 위치, 사전 항목 id, 사전 버전, 앞뒤 40자의 문맥이 남는다. 적용 신뢰도 열은 없다. 변형어는 글자를 그대로 맞춘다. 앞쪽 경계는 같은 글자 체계에서만 따진다. 한글로 시작하는 항목은 앞 글자가 한글이 아닐 때, 영문이나 숫자로 시작하는 항목은 앞 글자가 영문이나 숫자가 아닐 때만 매치한다. 뒤쪽에는 경계를 요구하지 않는다. 한국어는 조사와 어미가 공백 없이 붙기 때문이다. 그래서 "에이아이는"처럼 조사가 붙은 말도 "인공지능"으로 바뀐다(커밋 cd32ac6).

---

## 9.4 사용자 사전

사용자 사전은 일반 언어 모델이나 형태소 분석기가 정확히 인식하기 어려운 도메인 용어를 등록하는 기능이다.

대상:

- 기관명
- 제품명
- 서비스명
- 인명
- 지명
- 약어
- 전문 용어
- 프로젝트 코드
- 계약 번호
- 법령명
- 사내 용어

```json
{
  "dictionaryId": "USER-DICT-1024",
  "term": "국토부",
  "normalizedTerm": "국토교통부",
  "termType": "ORGANIZATION",
  "aliases": [
    "국토부",
    "MOLIT"
  ],
  "description": "대한민국 국토교통부",
  "domain": "PUBLIC_SECTOR",
  "enabled": true,
  "version": 7
}
```

**구현 현황**: 사용자 사전 항목은 `entry_type`이 `custom_word`인 항목이다. 용어 유형(`term_type`)은 `ORGANIZATION`, `PERSON` 등이다. 사전 항목의 대표 용어(`term`)와 변형어 목록(`variants`)을 쓴다. 처리 규칙(`processing_rule`)의 동작은 9.1.1절과 같다. 사용자 사전 블록이 보호한 구간은 다음의 불용어 블록이 잘못 지우지 않도록 넘긴다. 같은 사전 항목은 개인정보 탐지의 이름 탐지(`PERSON`)에도 쓰인다(10.3절). 위 JSON의 `normalizedTerm`과 `aliases`는 설계 예시이고, 실제로는 `term`과 `variants`를 쓴다.

---

## 9.5 사전 적용 순서

사전 적용 순서는 결과 품질에 영향을 줄 수 있다.

표준 워크플로우의 실제 순서는 다음과 같다.

```text
사용자 사전 적용(user_dict, 보호 구간 생성)
→ 동의어 정규화(synonym)
→ 불용어 처리(stopword, 보호 구간은 제외)
```

사용자 사전 용어가 불용어 규칙으로 잘못 제거되지 않도록 우선 보호해야 한다는 원칙은 구현에 반영되어 있다. 형태소 분석은 처리 시점 블록에서 쓰지 않고, 검색 시점의 토큰화에서만 쓴다(9.7절). 처리 시점 블록은 문자열 위치를 찾아 적용한다.

---

## 9.6 사전 적용 결과

```json
{
  "originalText": "국토부는 AI 정책을 발표했다.",
  "normalizedText": "국토교통부는 인공지능 정책을 발표했다.",
  "appliedEntries": [
    {
      "dictionaryType": "USER_DICTIONARY",
      "entryId": "USER-DICT-1024",
      "original": "국토부",
      "normalized": "국토교통부",
      "startOffset": 0,
      "endOffset": 3
    },
    {
      "dictionaryType": "SYNONYM",
      "entryId": "SYNONYM-001",
      "original": "AI",
      "normalized": "인공지능",
      "startOffset": 5,
      "endOffset": 7
    }
  ]
}
```

위 JSON은 설계 예시다. 구현에서 `dictionaryType` 값은 `STOPWORD`, `SYNONYM`, `USER_DICT` 가운데 하나다. 적용 기록은 원문 위치(`start_offset`, `end_offset`)와 앞뒤 40자 문맥을 가진다. 문맥은 개인정보를 가린 상태로 저장한다. 사용자는 적용을 되돌릴 수 있다(`reverted`). 되돌림은 위치가 아니라 사전 항목과 원문 표현의 쌍으로 적용하므로, 재처리로 위치가 바뀌어도 유지된다.

## 9.7 검색 시점 사전 (구현)

검색 시점의 토큰화(`app/services/dictionary_service.py`)는 kiwipiepy 형태소 분석기로 조사와 어미를 떼고, 불용어 규칙(EXACT, CONTAINS, PREFIX, SUFFIX, REGEX)으로 토큰을 거른다. 동의어는 변형어를 대표어로 바꾼 토큰을 추가해서, 어느 표현으로 질의해도 같은 문서가 맞도록 한다(BM25 키워드 색인). `direction`이 `BIDIRECTIONAL`인 동의어는 대표어에서 변형어 쪽으로도 확장한다. 처리 방식이 `SEARCH_EXPAND`인 동의어는 질의에 변형어나 대표어가 들어 있으면 나머지 표현을 질의에 덧붙인다. 사전을 저장하면 검색 캐시를 다시 만든다. 이 경로는 처리 시점의 사전 적용과 별개다.

## 11. 문서 분할

## 11.1 분할 목적

긴 문서를 AI 모델이나 검색 시스템에서 처리하기 위해 의미 있는 단위로 나눈다.

문서 분할 단위를 일반적으로 **청크(Chunk)**라고 한다.

구현에서 청크 크기 설정(`max_tokens`, `min_tokens`, `overlap_tokens`)의 단위는 토큰이 아니라 글자 수다. 이름만 토큰일 뿐이다. 토큰 수(`token_count`)는 따로 근사해서 기록한다(11.5절).

---

## 11.2 분할 방식

구현된 분할 방식과 설정 값은 다음과 같다. 아래 절의 설명은 설계 원안이며, 각 방식의 구현 범위는 표에 따른다.

| 분할 방식 | 설정 값 | 구현 내용 |
|---|---|---|
| 고정 길이 | `fixed` | 글자 수 기준이다. 문단 경계, 문장 끝, 줄바꿈, 공백 순으로 자를 곳을 찾고, `overlap_tokens`만큼 겹친다. 마지막 조각이 최소 길이보다 짧으면 앞 조각과 합친다 |
| 문장 기준 | `sentence` | 문장 끝에서만 자르고 최대 길이까지 채운다. 겹침은 없다 |
| 문단 기준 | `paragraph` | 구조 노드 트리를 따라 문단을 모은다. `preserve_heading`이 켜져 있으면 제목마다 청크를 닫는다 |
| 섹션 기준 | `section_aware` | 제목마다 청크를 닫는다. 조상 제목 경로를 `section_path`에 저장한다 |
| 의미 기반 | `semantic` | 문장 임베딩의 인접 유사도가 하위 25% 지점에서 자른다. 임베딩 모델을 호출한다 |
| 표 단위 | `table_unit` | 표 노드만 청크로 만든다. 최대 길이를 넘는 표는 행 그룹으로 나누고 헤더를 반복한다 |

컬렉션의 기본 전략 `size`는 구조를 보지 않는 글자 수 기준(`fixed`)이다. 다만 구조 노드가 본문의 80% 이상을 덮으면 `section_aware`로 바꾼다(11.5절). 블록에서 `strategy`를 명시하면 그 값을 따른다.

### 고정 길이 분할

- 문자 수 기준
- 토큰 수 기준
- 일정 길이의 중첩 적용

장점:

- 구현이 단순함
- 처리량 예측이 쉬움

단점:

- 문장이 중간에 끊길 수 있음
- 문서 구조가 손상될 수 있음

---

### 문장 기준 분할

문장 경계를 기준으로 청크를 생성한다.

장점:

- 문장 단위 의미 보존

단점:

- 문장 길이 편차가 큼

---

### 문단 기준 분할

문단 단위로 청크를 생성한다.

장점:

- 원문 구조 보존
- 출처 확인이 쉬움

단점:

- 지나치게 긴 문단 처리 필요

---

### 섹션 기준 분할

제목과 하위 문단을 하나의 단위로 묶는다.

장점:

- 문서의 논리적 구조 유지
- RAG 검색 품질 향상 가능

단점:

- 문서 구조 분석 정확도에 의존

---

### 의미 기반 분할

문장 간 의미 유사도를 분석하여 주제가 전환되는 지점을 기준으로 분할한다.

장점:

- 의미 단위 보존

단점:

- 계산 비용이 높음
- 결과 재현성을 위해 모델 버전 고정 필요

---

### 표 단위 분할 (Table Unit Chunking with Row Groups)

> **실제 구현**: backend/app/pipeline/blocks/chunk_strategies.py에서 테이블 기반 청킹 구현.
> 
> 표는 일반 텍스트와 별도로 처리해야 합니다. 문자 수 기반 컷 대신 **행 그룹 + 헤더 반복** 방식으로 오버사이즈 표를 처리합니다.

표 처리 전략:
1. 전체 표는 하나의 청크로 유지하되, 너무 크면 행 그룹으로 분할
2. 각 행 그룹이 max_chars을 초과하면 새 청크로 분할
3. 분할된 각 청크마다 테이블 헤더를 반복해서 포함

설정 예시:
- `table_chunk_max_rows`: 행 그룹의 최대 행 수 (설정값으로 조정 가능)
- 헤더(첫 번째 행)는 모든 분할 청크에 반복 포함

예시:

```text
[표 N: 데이터 1-50행]
| 열1 | 열2 | 열3 |
|---|---|---|
| 데이터... |

[표 N: 데이터 51-100행]  
| 열1 | 열2 | 열3 |  ← 헤더 반복
| 데이터... |
```

---

## 11.3 분할 설정 예시

```json
{
  "strategy": "section_aware",
  "max_tokens": 512,
  "min_tokens": 50,
  "overlap_tokens": 64,
  "preserve_table": true,
  "preserve_heading": true,
  "include_previous_heading": false,
  "split_long_paragraph": true,
  "table_chunk_max_rows": null
}
```

위 설정은 실제 `chunk_split` 블록의 설정 키다. `strategy`를 `null`로 두면 컬렉션 설정을 따른다. `max_tokens`, `min_tokens`, `overlap_tokens`를 `null`로 두면 컬렉션의 값을 쓴다. 컬렉션의 기본값은 최대 512, 최소 50, 겹침 64(글자 수)다. `include_previous_heading`을 켜면 청크 본문 앞에 조상 제목 경로가 `[제목 > 절]` 형태로 붙는다. 위 예시의 `maxTokens` 계열 이름은 설계 예시다.

위 JSON은 설계 예시다. 실제 청크는 `document_chunks` 행이며, `chunk_text`에 정리한 본문을, `original_text`에 원문 구간을 저장한다. 나머지 열의 의미는 메타 정보 생성.txt 3절에 정리되어 있다.

## 11.5 구현 현황 (2026-11-17)

- **컬렉션 기본값**: 최대 512, 최소 50, 겹침 64(글자 수), 전략 `size`다. 컬렉션 화면은 `size`와 `semantic`만 고른다.
- **size 전략의 구조 전환**: 이 실행에 구조 노드가 있고, 노드가 본문의 비공백 글자 80% 이상을 덮을 때만 `section_aware`로 바꾼다. 이때 최소 길이보다 짧은 구획은 이웃과 합친다(표와 표 제목 줄은 제외). 블록에서 `strategy`를 명시하면 그대로 따른다.
- **표**: 표는 다른 노드와 섞지 않는다(`preserve_table`). 최대 길이를 넘는 표는 헤더를 포함한 행 그룹으로 나누고, 조각은 `[표 N] (부분 i/K)`로 표시한다. `table_chunk_max_rows`가 없으면 그룹 길이는 최대 길이를 기준으로 정한다.
- **꼬리 병합**: 구조 기반 전략에서는 마지막 청크가 최소 길이보다 짧으면, 같은 절이고 표가 아닐 때만 앞 청크와 합친다. 고정 길이 전략은 마지막 조각을 앞 조각에 바로 합친다.
- **청크 본문에서 빼는 글자**: 머리말, 꼬리말, 목차 노드의 글자는 청크 본문에서 뺀다. 위치 정보는 그대로 둔다. 구조 기반 전략에서만 적용된다.
- **본문 정리**: 제어문자를 지우고, 줄 안의 연속 공백을 한 칸으로 줄이며, 세 줄 이상의 빈 줄을 한 줄로 줄인다(`_clean_rag_text`). 원문(`original_text`)은 그대로 둔다.
- **쪽 번호**: 청크의 시작과 끝 위치를 원문 기준으로 옮긴 뒤 쪽 맵에서 찾는다(`page_alignment.py`).
- **token_count**: 한글 음절 하나를 토큰 하나로, 그 밖의 글자 네 자를 토큰 하나로 근사한다. 임베딩 모델의 실제 토큰 수와는 다르다.
- **char_count**: 정리한 뒤 본문의 글자 수다.
- **부모 청크(parent)**: 같은 상위 절의 연속 child를 묶는다. 절 경로가 없는 구간은 다섯 개씩 묶는다. 절 경로가 있으면 같은 상위 절 안에서 묶고, 상위 절이 바뀌거나 묶음 길이가 최대 길이의 4배를 넘으면 끊는다. parent는 임베딩하지 않고, 답변 문맥을 넓힐 때만 쓴다(`services/parent_context.py`, 한도 1,200자).
- **의미 기반(semantic)**: 문장을 임베딩해서 인접 문장 유사도가 하위 25%인 지점을 자른다. 최소 길이 전에는 자르지 않는다. 문장이 세 개 미만이면 고정 길이로 처리한다.
- **keywords**: 분석 워크플로우의 출력 블록이 문서 키워드 가운데 청크 본문에 들어 있는 것을 골라 저장한다. 표준 전처리 워크플로우에는 출력 블록이 없어서 비어 있다.
- **chunk_type과 element_id**: 청크를 만든 첫 노드의 유형과 요소 id를 옮긴다. 노드를 쓰지 않는 전략(`fixed`, `sentence`, `semantic`)에서는 비어 있다.

## 12. 품질 검증 (Quality Check Block)

> **실제 구현**: backend/app/pipeline/blocks/quality_blocks.py에서 QualityCheckBlock이 구현되었습니다. 이는 품질 검증(automatic check) + 검토 게이트(review gate)를 통합하는 블록입니다.

## 12.1 품질 검증 목적 및 메커니즘

전처리 결과가 검색, 분석, RAG, 임베딩 생성에 사용 가능한 수준인지 평가합니다.

실제 구현에서는:
- 이 실행(WorkflowRun)이 만든 데이터(Document, DocumentNode, DocumentChunk, DictionaryApplication)에서 지표를 직접 계산합니다. 점수 항목은 텍스트, OCR, 구조, 분할, 원문 재현율이다. OCR 점수는 OCR을 쓴 문서에만, 원문 재현율은 텍스트 레이어가 있는 PDF에만 넣는다. 사전 적용 건수는 정보성으로 metrics에만 남기고 점수에는 넣지 않는다.
- QualityReport 행 1개를 쓰며, 이는 run_id로 유일합니다.
- QualityReport.status 값이 review gate의 결정을 내립니다 (WAITING_REVIEW로 전환 여부).

---

## 12.2 품질 검증 항목 (5가지 수준)

> **Phase 3/4 업그레이드**: QualityCheckBlock은 이제 다음 4개의 새로운 메트릭을 계산합니다:
> - `Document.ocr_page_confidence`: 페이지 단위 OCR 신뢰도 (Phase 3, Tesseract word-level confidence)
> - `Document.tables[*]["detected_as"]`: 암시적 표 탐지 (선 없이 정렬로만 검출, Phase 3)
> - `DocumentNode` TOC/HEADING 노드: 목차-제목 일치율 (Phase 4)
> - `failed_pages`: OCR 신뢰도 미달 페이지 목록 (Phase 4)
> 
> 이들은 이전에 데이터 소스가 없어 계산 불가능했으나, 이제 PARTIAL_FAILURE 판정이 실제로 가능합니다.

각 항목 뒤의 괄호는 2026-11-17 기준 구현 여부다.

### 파일 수준

- 파일 열기 성공 여부(미구현. 열지 못하면 앞 단계의 실패로 대신한다)
- 페이지 수 확인(구현. 쪽 맵으로 빈 쪽 비율을 계산한다)
- 암호화 여부(미구현. 형식 판별 블록이 검사한다)
- 손상 여부(미구현. 추출 단계의 실패로 대신한다)
- 처리 완료 여부(미구현. 실행 상태로 관리한다)

### 텍스트 수준

- 추출 문자 수(구현. 50자 미만이면 감점한다)
- 쪽당 실질 글자 수(구현. 쪽당 30자 미만이면 실패로 판정한다)
- 빈 페이지 비율(구현. 구조 수준에서 계산한다)
- 깨진 문자 비율(구현. U+FFFD와 제어문자를 센다)
- 비정상 특수문자 비율(미구현)
- 중복 문단 비율(미구현)
- OCR 신뢰도(구현. OCR을 쓴 문서에만 적용한다)
- 문장 완결성(미구현)
- 언어 판별 결과(구현. 한글 비중으로 `Document.language`에 기록하며, 점수에는 넣지 않는다)

### 구조 수준

- 제목 탐지 여부(구현. 제목 노드가 하나도 없으면 경고한다. 탐지율이 아니라 유무로 점수를 준다)
- 문단 탐지 여부(구현. 문단이나 목록 항목이 있는지로 점수를 준다)
- 표 탐지율(미구현. 표 수는 기록하고, 선 없이 검출한 표의 비율로 대신한다)
- 페이지 순서 정상 여부(미구현)
- 목차와 제목 일치율(구현. 기준 50%)
- 읽기 순서 신뢰도(미구현)

### 사전 수준

- 사전 적용 건수(구현. 정보성 지표로 점수에 넣지 않는다)
- 미등록 도메인 용어 수, 충돌 규칙 수, 중복 사전 항목 수, 사전 적용 실패 수(미구현)

### 분할 수준

- 평균 청크 크기(미구현. 짧은 청크와 긴 청크의 id 목록으로 대신한다)
- 최소 및 최대 청크 크기(구현. 50자 미만과 2,000자 초과 청크의 id를 남긴다)
- 허용 토큰 초과 청크 수(구현. 2,000자를 넘는 청크 수로 대신한다)
- 너무 짧은 청크 수(구현. 50자 미만)
- 중복률(미구현)
- 제목 누락률(미구현)
- 원문 역추적 가능 여부(미구현. 청크에 원문 구간 위치는 저장한다)

분할 수준 점검은 `chunk_tier`가 `child`인 청크만 센다. parent 청크는 일부러 길기 때문에 포함하지 않는다.

## 12.4 품질 상태 및 검토 게이트

| 상태 | 의미 | 자동 진행 | 검토 필수 |
|---|---|:---:|:---:|
| **SUCCESS** | 정상 처리 완료 | O | X |
| **SUCCESS_WITH_WARNING** | 경고가 있으나 사용 가능 | O* | O* |
| **REVIEW_REQUIRED** | 사용자 또는 관리자 검토 필요 | X | O |
| **PARTIAL_FAILURE** | 일부 페이지 또는 블록 실패 | X | O |
| **FAILURE** | 전처리 실패(치명적 오류) | X | O |

*review_policy 설정에 따라 결정 (auto_pass / review_on_warning / always_review)

### 청크 0개 및 사용 불가 텍스트의 강제 FAILURE (2026-07-28 검증, 2026-11-17 코드 점검)

> **⚠ 중요 버그 수정**: overall_score는 5개 지표 평균이라, 청크 0개는 다른 지표(예: 표 문법만으로 min_extraction_chars 충족)에 희석돼 SUCCESS_WITH_WARNING으로 조용히 넘어갈 수 있었습니다. 
> 
> **실제 구현** (`backend/app/pipeline/blocks/quality_blocks.py`, `_determine_status`): 청크 0개이거나 쪽당 실질 글자 수가 `min_usable_chars_per_page`(30자) 미만이면 평균과 무관하게 **먼저 FAILURE로 확정**합니다.
> ```python
> if chunk_count == 0 or unusable_text:
>     return "FAILURE"
> ```
> 
> 이는 2026-07-28 test_data E2E 검증 중 "서울시 도시 범죄 취약지 분석 PDF"에서 실제 재현된 버그였습니다.

### FAILURE/PARTIAL_FAILURE 강제 검토

> review_policy와 무관하게 FAILURE/PARTIAL_FAILURE는 **항상 검토가 필수**입니다. 
> "검토 없이 진행" 옵션(skip_review)은 review_policy를 이 run에 한해 auto_pass로 낮출 뿐,
> 실제로 실패한 문서까지 조용히 통과되지는 않습니다 (9항목 펀치리스트 #1, 2026-07-24).

## 12.5 판정 순서와 기준값 (구현, 2026-11-17 점검)

상태는 `backend/app/pipeline/blocks/quality_blocks.py`의 `_determine_status`가 다음 순서로 정한다. 앞 조건에 걸리면 뒤 조건은 보지 않는다.

1. 자식 청크(`chunk_tier == "child"`)가 0개이거나 쪽당 실질 글자 수가 `min_usable_chars_per_page` 미만이면 FAILURE
2. `overall_score`가 `fail_below_score`(기본 30.0) 미만이면 FAILURE
3. 실패 쪽(`failed_pages`)이 있고 OCR 쪽 전체 수보다 적으면 PARTIAL_FAILURE
4. 경고가 하나라도 있으면 SUCCESS_WITH_WARNING
5. 그 외에는 SUCCESS

이후 `_decide_review`가 `review_policy`와 업로드 옵션 `skip_review`를 반영해 최종 상태를 정한다. FAILURE와 PARTIAL_FAILURE는 항상 검토 대상이다. SUCCESS_WITH_WARNING은 `review_on_warning` 또는 `always_review`일 때 REVIEW_REQUIRED가 된다. SUCCESS는 `always_review`일 때만 REVIEW_REQUIRED가 된다. `skip_review`가 켜지면 정책은 `auto_pass`로 취급된다. 따라서 12.4 표의 SUCCESS_WITH_WARNING 행은 기본 설정에서 실제로는 REVIEW_REQUIRED로 저장된다.

`overall_score`는 `scores`에 들어간 항목의 단순 평균이다. `sourceRecall`은 원본 PDF 텍스트 레이어가 있을 때만 포함되고, `ocr`은 OCR을 쓴 문서에서만 계산된다. 정규화 점수는 측정 값이 없어 평균에서 뺀다(quality_check 1.5.0).

| 설정 (`QualityCheckConfig`) | 기본값 | 쓰이는 곳 |
|---|---|---|
| `min_extraction_chars` | 50 | 추출 텍스트 길이 하한 (textExtraction) |
| `max_broken_char_ratio` | 0.05 | 깨진 문자 비율 상한 (textExtraction) |
| `min_ocr_confidence` | 0.5 | OCR 페이지 신뢰도 하한 (ocr, failed_pages) |
| `max_ocr_single_char_ratio` | 0.25 | 한 글자 토큰 비율 상한 (ocr) |
| `min_usable_chars_per_page` | 30 | 쪽당 실질 글자 수 하한 (FAILURE 조건) |
| `max_empty_page_ratio` | 0.2 | 빈 쪽 비율 상한 (structure) |
| `min_toc_heading_match_ratio` | 0.5 | 목차와 제목 일치율 하한 (structure) |
| `max_implicit_table_ratio` | 0.2 | 선 없는 표 비율 상한 (table) |
| `min_chunk_chars_warning` | 50 | 짧은 청크 기준 (chunking) |
| `max_chunk_chars_warning` | 2000 | 긴 청크 기준 (chunking) |
| `min_source_recall` | 0.8 | 원본 PDF 대비 재현율 하한 (sourceRecall) |
| `review_policy` | review_on_warning | auto_pass, review_on_warning, always_review |
| `fail_below_score` | 30.0 | 종합 점수 FAILURE 기준 |

## 13. 워크플로우 블록 설계

## 13.1 블록 공통 속성

모든 전처리 블록은 다음 공통 속성을 가진다.

```json
{
  "blockId": "BLOCK-TEXT-CLEAN-001",
  "blockType": "TEXT_CLEANING",
  "blockName": "텍스트 정제",
  "version": "1.3.0",
  "inputSchema": "TextDocument",
  "outputSchema": "CleanedTextDocument",
  "timeoutSeconds": 300,
  "retryCount": 2,
  "enabled": true
}
```

위 JSON은 설계 예시다. 실제 코드에서 블록의 식별 정보는 `BaseBlock`(`backend/app/pipeline/blocks/base.py`)의 `block_type`, `block_version`, `category`, `config_schema` 속성으로 정해진다. `block_version`은 캐시 무효화 기준이므로 출력 형태가 바뀌면 올린다. `blockId`, `inputSchema`, `outputSchema`, `enabled` 키는 코드가 읽지 않는다. 시간 제한과 재시도는 블록 config의 `timeoutSeconds`(기본 1800초)와 `retryCount`(기본 2회)로 정하며, `backend/app/pipeline/tasks/workflow.py`가 이 값을 읽는다. 영구 오류(`BlockExecutionError`의 `permanent=True`, 예: FILE_UNSUPPORTED, FILE_ENCRYPTED)는 재시도하지 않는다.

## 13.2 주요 블록 목록

| 블록 | 입력 | 출력 | 주요 기능 |

| 텍스트 정제 | 구조 텍스트 | 정제 텍스트 | 공백, 문자, 반복 제거 |

구현 현황(2026-11-17): 블록 레지스트리(`backend/app/pipeline/blocks/registry.py`)에는 24개 블록 타입이 등록되어 있다. 이 중 전처리 표준 체인에 들어가는 블록은 file_validate, format_detect, text_extract, structure_analyze, text_clean, user_dict, synonym, stopword, pii_detect, chunk_split, quality_check, rag_store의 12개다. 위 표의 OCR 블록은 `ocr` 자리표시자로, 상류 출력을 그대로 통과시키며 표준 체인에 없다. OCR은 `text_extract`가 호출하는 어댑터 안에서 수행된다. "문서 입력"은 업로드 API(`documents/upload.py`)가 맡고, "결과 저장"은 표준 체인에서 `rag_store` 블록이 맡는다. 불용어 처리, 동의어 정규화, 사용자 사전 적용은 `user_dict`, `synonym`, `stopword` 순서로 실행되며 정확한 순서는 2절과 9.5절을 따른다.

## 14. AI 활용 범위

## 14.1 AI가 담당하는 기능

AI는 전처리 블록 자체를 실시간으로 임의 생성하는 역할보다 다음 기능을 담당하는 것이 적절하다.

- 문서 유형 분석
- 적합한 워크플로우 추천
- 블록 순서 추천
- OCR 필요 여부 추천
- 문서 분할 전략 추천
- 청크 크기 추천
- 불필요한 블록 감지
- 누락된 블록 감지
- 정제 규칙 초안 생성
- 동의어 및 사용자 사전 후보 추천
- 품질 경고 원인 설명
- 실패 블록 원인 분석
- 부분 재처리 범위 추천
- 사용자 요청을 블록 설정으로 변환

구현 현황(2026-11-17): LLM을 쓰는 기능은 문서 요약, 키워드, 카테고리 생성과 태그 추천(`tasks/summary.py`, `tasks/metadata.py`, 분석 블록 `summarize`, `extract_keywords`, `classify`)이다. 그림 설명은 선택 기능으로 클라우드 VLM(사용자 키, BYOK)이나 로컬 VLM(`LOCAL_VISION_MODEL`, 기본값 비어 있어 꺼짐)으로 수행한다. 위 목록의 나머지 항목(문서 유형 분석, 워크플로우와 블록 순서 추천, OCR 필요 여부 추천, 분할 전략과 청크 크기 추천, 불필요 블록과 누락 블록 감지, 정제 규칙 초안, 사전 후보 추천, 품질 경고 원인 설명, 실패 원인 분석, 재처리 범위 추천, 자연어 설정 변환)은 코드에서 확인되지 않았으며 미구현이다.

---

## 14.2 AI 요청 예시

사용자 요청:

```text
이 문서는 법률 계약서이므로 조항 번호를 유지하고,
회사명과 계약 번호는 분리해서 인식해줘.
표는 분할하지 말고 하나의 청크로 유지해줘.
```

AI 변환 결과:

```json
{
  "documentType": "LEGAL_CONTRACT",
  "structureOptions": {
    "preserveClauseNumber": true,
    "detectOrganization": true,
    "detectContractNumber": true
  },
  "chunkOptions": {
    "preserveTable": true,
    "splitTable": false,
    "strategy": "CLAUSE_AWARE"
  }
}
```

AI는 자연어 요청을 고정된 블록의 파라미터로 변환한다.

위 JSON은 설계 예시이며 현재 코드에는 자연어를 블록 설정으로 바꾸는 기능이 없다. `documentType`과 `CLAUSE_AWARE` 전략은 구현되지 않았다. 분할 전략은 11.2절의 fixed, sentence, paragraph, section_aware, semantic, table_unit 중에서 블록 설정으로 직접 고른다.

## 14.3 AI가 직접 수행하지 않는 기능

기본 설계에서는 AI가 다음 기능을 직접 통제하지 않도록 한다.

- 원본 파일 삭제
- 임의의 코드 실행
- 검증되지 않은 블록 생성
- 승인되지 않은 외부 API 호출
- 원문 영구 변경
- 사전 항목 자동 확정
- 개인정보 원문 외부 전송
- 관리자 승인 없는 워크플로우 배포

구현 현황(2026-11-17): AI가 실행하는 기능이 없으므로 위 항목은 대부분 해당하지 않는다. 원본 파일은 전처리 과정에서 변경하지 않으며 보정 내용은 별도 계층에 저장한다(19.3절). 사전 항목이 자동으로 확정되는 경로는 확인하지 못했다. 사전 항목은 사용자가 등록하거나 수정한다.

## 15. 수정 및 재처리 설계

## 15.1 수정 시나리오

사용자가 전처리 결과를 검토한 뒤 다음과 같이 요청할 수 있다.

```text
3장에서는 'PM'을 프로젝트 관리자가 아니라 예방정비로 처리해줘.
```

이 경우 전체 문서를 처음부터 처리하지 않고 다음 범위만 재처리할 수 있어야 한다.

```text
사용자 사전 수정
→ 해당 용어가 포함된 노드 탐색
→ 동의어/사용자 사전 적용 블록부터 재실행
→ 문서 분할 재실행
→ 품질 검증 재실행
→ 변경 결과 저장
```

구현 현황(2026-11-17): 재처리는 `POST /api/v1/documents/{id}/reprocess`로 시작한다. 요청 본문의 `start_block_type` 또는 `start_block_instance_id`(둘 중 하나만 지정)로 시작 블록을 정하고, `reason`에 사유를 적는다. 노드 단위 대상 지정(`targetNodeIds`)은 요청 스키마에 없다. 시작 블록부터 하류 블록을 다시 실행하고, 상류 블록은 부모 실행(`parent_run_id`)의 결과를 재사용한다(`reprocess_service.start_partial_reprocess`). 사용자 사전을 고친 뒤 재처리하는 흐름은 사전 적용 블록(`user_dict`, `synonym`, `stopword`)을 시작 블록으로 지정하면 된다.


---

## 15.2 재처리 범위 결정

재처리 범위는 블록 의존성을 기준으로 계산한다.

예시:

```text
텍스트 추출 수정
→ 구조 분석 이후 모든 단계 재실행

동의어 사전 수정
→ 동의어 정규화 이후 단계 재실행

청크 크기 수정
→ 문서 분할과 품질 검증만 재실행

품질 기준 수정
→ 품질 검증만 재실행
```

구현 현황(2026-11-17): 하류 범위는 `reprocess_service.downstream_closure`가 블록 간선(`WorkflowEdge`)을 따라 계산한다. 위 예시의 청크 크기 수정은 시작 블록을 `chunk_split`으로 지정하면 같은 범위가 된다. 텍스트 추출 블록을 시작 블록으로 지정하면 그 뒤 블록 전체가 다시 실행된다. 품질 기준 수정은 시작 블록을 `quality_check`로 지정한다.

```json
{
  "changeRequestId": "CR-001",
  "changeType": "DICTIONARY_UPDATE",
  "changedEntityId": "USER-DICT-1024",
  "affectedBlocks": [
    "USER_DICTIONARY",
    "CHUNKING",
    "QUALITY_VALIDATION"
  ],
  "affectedNodeCount": 14,
  "affectedChunkCount": 8,
  "fullReprocessingRequired": false
}
```

구현 현황(2026-11-17): 위 JSON은 설계 예시다. 실제 영향도는 `reprocess_service.compute_reprocess_impact`가 계산하며, `GET /api/v1/documents/{id}/reprocess/impact` 미리보기와 실제 재처리 실행이 같은 계산을 쓴다. 응답의 `impact` 필드는 `reason`, `changeType`(수동 재처리는 MANUAL), `affectedBlocks`, `affectedNodeCount`, `affectedChunkCount`, `fullReprocessingRequired`다. `changeRequestId`와 `changedEntityId`는 없다. 청크 수는 자식 청크(`chunk_tier == "child"`)만 센다. 사전 항목 하나가 바뀌었을 때의 영향은 `GET /api/v1/admin/dictionary/entries/{entry_id}/impact`에서 따로 조회한다.

## 16. 버전 관리

## 16.1 버전 관리 대상

다음 항목은 모두 버전 관리가 필요하다.

- 원본 문서
- 워크플로우
- 블록
- 블록 설정
- 정제 규칙
- 불용어 사전
- 동의어 사전
- 사용자 사전
- OCR 엔진
- AI 모델
- 문서 분할 정책
- 품질 기준
- 전처리 결과

구현 현황(2026-11-17): 버전이 기록되는 위치는 다음과 같다. 워크플로우 버전은 `WorkflowRun.version_id`와 `version_snapshot`, 사전 버전은 `WorkflowRun.dictionary_version`과 `DictionaryRevision`, 정제 규칙 버전은 `CleaningRule.version`, 블록 버전은 각 블록의 `block_version`(캐시 키에 포함), 원본 교체는 `Document.file_hash`로 구분한다. 문서 버전 번호는 `Document.version_number`와 `lineage_id`로 관리한다. 전처리 결과 버전은 `DocumentTextRevision`(출처 `source`)에 쌓인다. OCR 엔진 버전과 AI 모델 버전은 별도로 기록하지 않으며, 캐시 키에도 들어 있지 않다.

## 16.2 처리 버전 예시

```json
{
  "documentVersion": 2,
  "workflowVersion": 5,
  "textExtractionVersion": "2.0.1",
  "cleaningRuleVersion": 3,
  "stopwordDictionaryVersion": 2,
  "synonymDictionaryVersion": 4,
  "userDictionaryVersion": 7,
  "chunkPolicyVersion": 6,
  "qualityRuleVersion": 3
}
```

위 JSON은 설계 예시다. 실제 값은 `WorkflowRun` 행(`version_id`, `dictionary_version`, `version_snapshot`)과 각 실행 단계(`WorkflowRunStep`)의 캐시 키 구성 요소에 남는다. `Document.pipeline_version` 컬럼은 모델에 정의되어 있으나 코드 어디에서도 값을 쓰지 않는다. 따라서 파서 버전을 추적하는 필드는 현재 없다(`메타 정보 생성.txt` 1절 참고).

## 18. 오류 처리

## 18.1 오류 유형

| 오류 코드 | 설명 |
|---|---|
| FILE_UNSUPPORTED | 지원하지 않는 파일 형식 |
| FILE_CORRUPTED | 손상된 파일 |
| FILE_ENCRYPTED | 암호화된 파일 |
| TEXT_EXTRACTION_FAILED | 텍스트 추출 실패 |
| OCR_FAILED | OCR 실패 |
| STRUCTURE_ANALYSIS_FAILED | 구조 분석 실패 |
| CLEANING_RULE_ERROR | 정제 규칙 오류 |
| DICTIONARY_CONFLICT | 사전 규칙 충돌 |
| CHUNK_SIZE_EXCEEDED | 청크 최대 크기 초과 |
| QUALITY_THRESHOLD_FAILED | 품질 기준 미달 |
| STORAGE_FAILED | 결과 저장 실패 |
| WORKFLOW_TIMEOUT | 실행 시간 초과 |

구현 현황(2026-11-17): 위 표의 코드는 `backend/app/pipeline/blocks/base.py`의 `ERROR_CODES` 집합에 정의되어 있다. 블록이 실제로 발생시키는 코드는 FILE_UNSUPPORTED(영구 오류), FILE_ENCRYPTED(영구 오류), TEXT_EXTRACTION_FAILED이다. 실행 시간 초과는 WORKFLOW_TIMEOUT 대신 `TIMEOUT_EXCEEDED`로 기록한다(`workflow.py`, `reprocess_service.py`의 `reconcile_stuck_run`). 나머지 코드는 집합에만 있고 발생 지점을 확인하지 못했다. 품질 기준 미달은 오류 코드가 아니라 QualityReport의 상태(12.5절)로 표현한다.

## 18.2 재시도 정책

- 일시적 오류만 자동 재시도
- 동일 오류 반복 시 중단
- 블록 단위 재시도 지원
- 재시도 횟수 제한

- 수동 재실행 지원

구현 현황(2026-11-17): 블록 실행은 `retryCount`(기본 2회)까지 재시도한다(`workflow.py`). 영구 오류(FILE_UNSUPPORTED, FILE_ENCRYPTED)는 재시도하지 않고 즉시 실패한다. 그 밖의 오류는 모두 재시도 대상이며, 재시도 간격은 별도 countdown 없이 Celery 기본 지연을 따른다. 일시적 오류만 골라 재시도하는 분류는 없다. 시간 초과 run은 `reconcile_stuck_run`이 TIMEOUT_EXCEEDED로 정리하며, 재처리 요청의 `timeout_overrides`로 더 긴 제한을 줄 수 있다. 재처리 단위는 블록이고 페이지 또는 노드 단위 선택 재처리는 없다. 수동 재실행은 `POST /api/v1/documents/{id}/reprocess`와 `POST /api/v1/documents/{id}/retry`가 지원한다.

> **실제 구현 (2026-11-17 점검)**: 모든 경로는 `/api/v1` 아래에 있다. 문서 API는 `backend/app/api/v1/endpoints/documents/` 패키지(업로드 `upload.py`, 처리 `processing.py`, 청크 `chunks.py`, 메타데이터 `metadata.py`, 목록 `listing.py` 등)에, 워크플로우 API는 `backend/app/api/v1/endpoints/workflows/` 패키지(`definitions.py`, `versions.py`, `runs.py`)에 있다. 아래 경로와 필드는 코드 기준이다. 설계 초안의 `/documents/{id}/preprocess` 계열 경로는 구현되지 않았다.

## 20.1 문서 업로드 및 PREPROCESS 시작

```http
POST /api/v1/documents/upload
Content-Type: multipart/form-data

file: <원본 파일>
collection_id: (선택)
skip_review: false (true이면 "검토 없이 진행")
workflow_version_id: (선택)
```

응답은 `DocumentUploadResponse`이며 문서 ID와 상태를 담는다. 처음 상태는 QUEUED다.

워크플로우 선택 순서(`upload.py`)는 다음과 같다.

1. 요청에서 `workflow_version_id`를 명시하면 그 버전을 쓴다. PREPROCESS 종류인지 확인한다.
2. 그렇지 않으면 컬렉션의 기본 워크플로우(`default_workflow_id`)를 쓴다. 컬렉션에 버전 고정값이 없으면 그 워크플로우의 최신 발행 버전을 쓴다.
3. 그 외에는 시스템 표준 PREPROCESS 워크플로우의 최신 발행 버전을 쓴다.

선택된 버전으로 `WorkflowRun`(trigger가 UPLOAD)을 만들고 진입 블록을 큐에 넣는다. 실행 시점의 사전 버전은 `WorkflowRun.dictionary_version`에 남는다.

`skip_review`는 `WorkflowRun.skip_review`에 저장된다. quality_check 블록은 이 값을 보고 review_policy를 auto_pass로 바꾼다. FAILURE와 PARTIAL_FAILURE는 이 옵션과 무관하게 검토 대상이다(12.5절).

`POST /api/v1/documents/upload-zip`은 ZIP 묶음을 올린다. ZIP 제한은 3.2절을 따른다.

## 20.2 검토 후 진행 및 워크플로우 재개

```http
POST /api/v1/documents/{documentId}/proceed
{ "edited_text": "(선택, 최대 200,000자)" }
```

REVIEW_PENDING 상태의 문서를 CHUNKING으로 바꾸고 `continue_processing` 태스크를 호출한다(`processing.py`). `edited_text`가 있으면 추출 텍스트를 그 값으로 바꾸고, 원문은 `DocumentTextRevision`(출처 REVIEW_EDIT)에 남긴다. 상태가 REVIEW_PENDING이 아니면 409를 반환한다.

워크플로우 run이 WAITING_REVIEW 상태이면 다음 API로 재개한다.

```http
POST /api/v1/workflows/runs/{runId}/resume
```

WAITING_REVIEW가 아니면 409를 반환한다. 성공하면 `{"status": "RESUME_QUEUED"}`를 돌려주고, `resume_workflow_run` 태스크가 run을 이어서 실행한다. PREPROCESS run이 끝난 뒤 기본 분석 워크플로우가 없으면 요약과 메타데이터 태스크가 실행된다(`_dispatch_default_analysis`).

설계 초안의 `POST /api/v1/documents/{id}/preprocess`(워크플로우 지정과 options)는 구현되지 않았다. 워크플로우 실행은 `POST /api/v1/workflows/{workflowId}/run`(`RunCreate`)을 쓴다.

## 20.5 특정 단계 재처리

```http
POST /api/v1/documents/{documentId}/reprocess
```

요청 본문(`DocumentReprocessRequest`)의 예는 다음과 같다.

```json
{
  "start_block_type": "user_dict",
  "reason": "사용자 사전 의미 수정",
  "timeout_overrides": { "text_extract": 3600 },
  "use_latest_version": false
}
```

- `start_block_type` 또는 `start_block_instance_id` 중 하나를 지정한다. 같은 타입의 블록이 여럿이면 `start_block_instance_id`를 써야 한다.
- `use_latest_version`이 true이면 이전 실행의 버전을 물려받지 않고 최신 게시 버전으로 처음부터 처리한다. `start_block_type`과만 함께 쓴다.
- `timeout_overrides`는 이 재처리 run에만 적용된다.
- `edited_text`는 레거시 경로다. 텍스트를 통째로 바꿔 기존 방식으로 재실행하며, 블록 지정과 함께 쓸 수 없다.

재처리 영향도 미리보기는 `GET /api/v1/documents/{documentId}/reprocess/impact`다. 여러 문서를 한 번에 재처리하는 `POST /api/v1/documents/batch-reprocess`도 있다.

## 21. 성능 및 확장성

## 21.1 비동기 처리 및 타임아웃 관리

> **실제 구현**: 블록은 Celery 태스크로 실행된다. 블록별 시간 제한은 블록 config의 `timeoutSeconds`(기본 1800초)이다. 재처리 run에는 `WorkflowRun.timeout_overrides`로 블록 타입별 제한을 따로 줄 수 있다. 대용량 PDF가 기본 제한을 넘을 때 이 값으로 해당 run만 늘린다. 블록의 공유 config는 바뀌지 않으므로 다른 문서에는 영향이 없다.

대용량 문서 처리 방식의 구현 현황은 다음과 같다.

- 작업 큐 사용(Celery): 구현. 블록 종류에 따라 큐가 나뉜다(21.1.2절).
- 블록 단위 실행: 구현. 각 블록은 `WorkflowRunStep`으로 기록된다.
- 작업 우선순위: 부분 구현. 블록 실행은 normal, extract, embed 세 큐 중 하나를 쓴다. critical, high, low 큐는 블록 실행에 쓰이지 않는다. 우선순위를 블록마다 지정하는 기능은 없다.
- 병렬 페이지 처리: 미구현. 페이지 단위 병렬 처리 코드를 확인하지 못했다.
- 처리 상태 이벤트 발행: 확인하지 못함. 상태는 조회 API로 확인한다.
- 중간 결과 저장: 부분 구현. 블록 출력이 단계마다 저장되고, 재처리는 상류 결과를 재사용한다. 블록 내부의 페이지 단위 중간 저장은 없다.
- 실패 시 재개: 부분 구현. 실패한 지점부터 다시 실행하는 부분 재처리가 있다. 검토 대기 run은 resume API로 이어서 실행한다.
- 타임아웃 오버라이드: 구현.

## 21.1.1 알려진 제약사항

| 파일 형식 | 제약사항 | 현재 처리 |
|---|---|---|
| HWP/HWPX | 파서가 쪽 경계를 주지 않아 추출 결과가 한 쪽으로 나온다 | 추출 후 LibreOffice 미리보기 PDF로 쪽을 나눠 쪽 번호를 부여한다(`_repaginate_hwp_like`). 쪽 번호는 미리보기 렌더링 기준이다 |
| DOCX | 쪽 수를 원본만으로 얻지 못할 수 있다 | 미리보기 PDF의 쪽 수를 쓰고, 없으면 문서 속성(app.xml)의 값을 쓴다 |
| PDF (대용량) | 기본 시간 제한을 넘을 수 있다 | `timeout_overrides`로 해당 run만 제한을 늘린다. 쪽 수가 `max_pages`(기본 1000쪽)를 넘으면 FILE_UNSUPPORTED로 영구 실패한다 |

## 21.1.2 큐와 동시 실행 (구현)

블록은 `step_queue_for_block`(`backend/app/pipeline/tasks/workflow.py`)이 고른 큐로 보낸다. 워커 설정은 `docker-compose.yml`에 있다.

| 큐 | 실행하는 블록 | 워커 | 동시성 | 메모리 재시작 기준 |
|---|---|---|---|---|
| normal | 위 두 큐에 없는 블록 | 메인 워커(critical, high, normal, low 큐) | 4 | 4,000,000 KB |
| extract | `text_extract`(Docling 레이아웃과 표 모델, EasyOCR 포함) | worker-extract | 1 | 8,000,000 KB |
| embed | `rag_store`, `summarize`, `extract_keywords`, `classify`, `extract_entities`, `output`, 전략이 semantic인 `chunk_split` | worker-embed(llm, embed 큐) | 1 | 지정 없음 |

GPU 모델을 쓰는 블록을 동시성 1인 워커로 모은 이유는 프로세스마다 모델 사본을 올려 GPU 메모리가 경합하는 것을 막기 위해서다. 개발용 `docker-compose.dev.yml`은 한 워커(동시성 2)가 모든 큐를 처리한다.

## 21.2 캐시

블록 실행 결과는 `BlockExecutionCache`에 캐시 키와 함께 저장되고, 같은 키의 실행이 오면 결과를 다시 쓴다(`_compute_cache_key`, `workflow.py`). 구현된 캐시 키 구성은 다음과 같다.

```text
document_id
+ input_hash (상류 블록 출력의 해시)
+ block_type
+ block_version
+ 블록 설정 해시
+ 사전 버전 (stopword, synonym, user_dict, pii_detect에만 포함)
+ skip_review (quality_check에만 포함)
+ file_hash (원본 파일 해시)
```

`document_id`를 키에 넣은 이유는 진입 블록처럼 상류 출력이 없는 블록의 입력 해시가 모든 문서에서 같아지기 때문이다. 설계 초안에 있던 모델 버전은 캐시 키에 들어 있지 않다.

## 21.3 대용량 문서 대응

- 페이지 단위 병렬 처리: 미구현
- 시트 단위 병렬 처리: 미구현
- 중간 결과 스트리밍 저장: 미구현. 저장은 블록 단위로만 한다.
- 메모리 사용량 제한: 구현. 워커의 max-memory-per-child 설정(21.1.2절)

- 최대 OCR 해상도 정책: 구현. Tesseract는 300dpi 흑백 입력을 쓴다(5.2.1절).
- 긴 표 분할 정책: 구현. 행 묶음, 헤더 반복, `table_chunk_max_rows`(11.5절)

## 24.1 워크플로우 실행 상태 전환 (Workflow Run States)

> **실제 구현**: `WorkflowRun.status`는 QUEUED, RUNNING, WAITING_REVIEW, COMPLETED, FAILED, CANCELLED 여섯 값이다(`backend/app/db/models/workflow_run.py`). PENDING과 SKIPPED는 실행 단계(`WorkflowRunStep`)의 상태다.

**PREPROCESS 워크플로우 상태 전환**:

```
QUEUED → RUNNING → COMPLETED
            │
            ├→ WAITING_REVIEW (quality_check가 검토 필요로 판정)
            │      │
            │      └ POST /workflows/runs/{id}/resume → RUNNING → COMPLETED
            │
            ├→ FAILED
            └→ CANCELLED (취소 API)
```

**WorkflowRun.trigger 값** (기본값 MANUAL):
- `UPLOAD`: 업로드로 시작
- `MANUAL`: 수동 실행
- `REPROCESS`: 부분 재처리
- `COLLECTION_REPROCESS`: 컬렉션 일괄 재처리
- `AUTO_ANALYSIS`: 기본 분석 워크플로우 실행(`_dispatch_default_analysis`)

**Document.status와 active_run_id**:
- `Document.active_run_id`: 현재 또는 가장 최근 워크플로우 실행 ID
- `Document.status`: 마지막으로 시작된 블록 종류에 대응하는 상태(17.3절)
- `Document.quality_status`: 마지막 QualityReport의 상태 스냅샷(SUCCESS, SUCCESS_WITH_WARNING, REVIEW_REQUIRED, PARTIAL_FAILURE, FAILURE)

## 25. 최종 설계 정리

문서 데이터 전처리 플랫폼의 핵심은 단순 텍스트 변환이 아니다.

다음 세 가지 데이터가 반드시 함께 관리되어야 한다.

```text
원본 데이터
전처리 결과
변경 및 실행 이력
```

또한 전처리 과정은 다음 구조를 유지해야 한다.

```text
고정된 실행 블록
+ 버전 관리된 설정
+ 사전 기반 정규화
+ 원문 위치 추적
+ 부분 재처리
+ 품질 검증
+ AI 기반 설정 보조
```

AI는 전처리 엔진을 대체하기보다 사용자의 자연어 요구사항을 해석하여 적절한 워크플로우와 블록 설정으로 변환하는 역할을 담당한다.

이 구조를 적용하면 다음 요구사항을 충족할 수 있다.

- 전처리 결과의 재현성
- 문서 원문과 결과 간 추적성
- 사용자 수정 반영
- 부분 재처리
- 도메인 사전 적용
- RAG 및 검색 품질 개선
- 운영 중 오류 분석
- 워크플로우 확장
