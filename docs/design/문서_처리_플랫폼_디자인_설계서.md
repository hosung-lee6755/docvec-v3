# 문서 처리 플랫폼 디자인 설계서

**최종 갱신**: 2026-11-17. 2026-07-28 설계 본문을 2026-11-17 코드 점검(HEAD 0f38033) 결과에 맞춰 고쳤다. 각 절은 현재 구현된 화면과 구현되지 않은 설계를 구분해 적는다. 미구현 항목은 "미구현"으로 표시했다.

## 1. 문서 개요

### 1.1 목적

본 문서는 문서 업로드, 전처리 워크플로우 구성, 사전 관리, 문서 처리 결과 검토와 수정, 검색과 채팅을 제공하는 **문서 처리 플랫폼**의 화면 구조와 사용자 경험을 정의한다. 전처리 워크플로우의 처리 로직은 `전처리_워크플로우_통합_설계서.md`가 정본이다.

### 1.2 설계 목표

- 문서 처리 과정을 단계별로 이해할 수 있게 한다.
- 등록된 처리 블록을 조합해 워크플로우를 구성할 수 있게 한다.
- 불용어, 동의어, 사용자 사전을 같은 방식으로 관리할 수 있게 한다.
- 처리 결과의 검토 대기와 실패를 한눈에 확인하고, 필요한 부분만 고칠 수 있게 한다.
- 업무용 B2B 웹 서비스에 맞는 명확하고 안정적인 인터페이스를 제공한다.

### 1.3 주요 사용자

| 사용자 유형 | 주요 목적 | 현재 권한 모델 |
|---|---|---|
| 일반 사용자 | 문서 업로드, 처리 결과 확인, 채팅과 검색 | 프로젝트 또는 컬렉션의 viewer 권한 |
| 편집자 | 워크플로우 구성과 실행, 재처리, 청크 수정, 검토 승인과 반려 | 프로젝트 또는 컬렉션의 editor 권한 |
| 관리자 | 사전, 정제 규칙, 사용자와 그룹, 원천 연결, 감사 로그, 민감정보 원문 열람 | 전역 admin 역할 |

## 2. 플랫폼 구조

### 2.1 전체 정보 구조

좌측 메뉴는 `frontend/src/components/navigation.ts`의 `NAV_GROUPS`에서 정의한다. 관리 그룹은 관리자에게만 보인다.

```text
문서 처리 플랫폼
├─ 대시보드 (홈)
├─ 계정 설정 (하단 메뉴)
│
├─ 워크스페이스
│  ├─ 프로젝트 (프로젝트별 컬렉션, 문서, 검색, 채팅, 워크플로우 탭)
│  └─ 컬렉션
│
├─ 문서 처리
│  ├─ 문서 (목록, 업로드, 상세)
│  ├─ 검토 대기 (배지: 검토 대기 문서 수)
│  ├─ 실패 (배지: 실패 문서 수)
│  └─ 처리 현황
│
├─ 지식 활용
│  ├─ 검색
│  └─ 채팅
│
├─ 파이프라인 설정
│  ├─ 워크플로우 (목록, 편집, 실행 이력)
│  ├─ 검색 사전 (관리자)
│  └─ 정제 규칙 (관리자)
│
└─ 관리 (관리자)
   ├─ 사용자
   ├─ 그룹
   ├─ 문서 원천 연결
   ├─ 외부 에이전트 토큰
   ├─ 감사 로그
   ├─ 답변 추적
   ├─ AI 기본법 근거 자료
   └─ 사용량
```

설계 초안의 "문서 유형", "모델 설정", "프롬프트 템플릿", "사전 그룹" 메뉴는 구현되지 않았다(§4.13).

### 2.2 기본 레이아웃

- 좌측에 고정된 내비게이션(폭 240px, 토큰 `--sidebar-w`)이 있다.
- 메인 영역에 페이지 제목과 본문이 들어간다. 페이지 헤더에 제목, 부제, 상태 배지, 작업 버튼이 놓인다.
- 문서 상세에서는 좌측 보조 패널(RAG 현황, 문서 정보)과 탭 본문으로 나뉜다.
- 워크플로우 편집기는 좌측 블록 팔레트, 가운데 캔버스, 우측 속성 패널의 3열 구조다.
- 설계 초안의 우측 AI 채팅 패널과 실행 로그 패널은 구현되지 않았다.

### 2.3 레이아웃 원칙

- 주요 작업은 메인 영역에서 끝난다. 보조 정보는 탭이나 패널에 둔다.
- 검토 대기와 실패 같은 조치 필요 항목은 좌측 메뉴 배지로 상시 알린다.
- 편집 중 이탈하면 저장되지 않은 변경을 확인하는 대화 상자를 띄운다(워크플로우 편집기).

## 3. 주요 사용자 흐름

### 3.1 문서 처리 기본 흐름

```text
문서 업로드 (전처리 워크플로우 선택 또는 컬렉션 기본값)
→ 워크플로우 자동 실행 (파일 검증 → 텍스트 추출 → 구조 분석 → 정제 → 사전 → 민감정보 → 분할 → 품질 검증)
→ 품질 검증 결과에 따라 검토 대기 (WAITING_REVIEW) 또는 자동 진행
→ 검토 승인 또는 반려 (검토 대기 화면 또는 문서 품질 탭)
→ 필요하면 구조, 사전, 민감정보, 청크를 고치고 부분 재처리
→ 색인 완료 (INDEXED), 검색과 채팅에서 사용
```

### 3.2 검토 흐름

```text
품질 검증 판정이 검토 필요
→ 검토 대기 메뉴 배지 증가, 문서 업로더에게 알림
→ 검토 대기 화면에서 문서를 열거나 바로 승인과 반려
→ 승인: 다음 블록부터 재개 / 반려: 런 취소, 문서 실패 처리
```

설계 초안의 AI 수정 흐름(AI 채팅으로 결과를 고쳐 변경 전후를 비교한 뒤 승인)은 구현되지 않았다(§4.12).

### 3.3 워크플로우 구성 흐름

```text
워크플로우 생성 (빈 워크플로우 또는 복제)
→ 팔레트에서 블록 추가 (카테고리별 목록, 검색 가능)
→ 블록 연결 (에지 추가와 삭제)
→ 블록 설정 입력 (하드코딩 폼 또는 백엔드 스키마 기반 폼)
→ 그래프 검증 (오류 목록과 빨간 강조 표시)
→ 저장 (초안) → 게시 (검증 통과 시에만 가능, 게시된 버전은 수정 불가)
→ 실행 (문서 1건 또는 컬렉션 최대 50건) 또는 컬렉션 기본 워크플로우로 지정
```

### 3.4 사전 등록 흐름

```text
사전 종류 선택 (불용어, 동의어, 사용자 사전)
→ 항목 추가 또는 엑셀 가져오기
→ 입력 검증 (필수 항목, 일치 방식, 처리 방식)
→ 저장 (사전 버전 증가)
→ 영향 문서 수 확인 (영향 문서 재처리는 사용자가 실행)
```

설계 초안의 "중복 및 충돌 확인", "사전 그룹", "사전 버전 생성" 단계 중 충돌 검사와 사전 그룹은 구현되지 않았다. 버전은 항목 변경마다 자동으로 생성된다.

## 4. 화면 설계

## 4.1 대시보드

### 목적

로그인한 사용자가 프로젝트, 최근 검색과 문서, 빠른 실행을 한곳에서 시작하도록 한다.

### 구현된 영역

- 시간대에 따라 달라지는 인사말과 사용자 이름을 보여준다.
- 총 문서, 처리 중, 색인 완료, 컬렉션 수를 숫자 카드로 요약한다.
- 내 프로젝트 목록을 보여준다.
- 최근 문서와 최근 검색 기록을 보여준다.
- 검색, 채팅, 문서 묶음 관리로 이어지는 빠른 실행 버튼을 둔다.

### 미구현

- 상태별 도넛 차트, 일별 처리 건수 라인 차트, 기간 필터(7일, 30일, 사용자 지정)는 구현되지 않았다. 프로젝트에 차트 라이브러리가 없다.
- 별도 알림 영역은 없다. 알림은 헤더의 알림 벨에서 본다(§4.14).
- 관리자 대시보드의 처리 지표 위젯은 없다. 처리 지표는 별도의 "처리 현황" 화면이 맡는다(§4.9).

## 4.2 문서 목록과 업로드

### 목적

문서를 찾고, 상태를 확인하고, 새 문서를 업로드한다.

### 문서 목록 (`/documents`, 프로젝트 안에서는 `/projects/:id/documents`)

- 목록에는 파일명, 컬렉션, 상태, 품질, 크기, 생성일 열이 나온다. 정렬 기준은 생성일, 파일명, 파일 크기, 상태다.
- 파일명으로 검색하고, 상태(전체, 처리 중, 검토 대기, 실패, 경고와 부분 실패 등), 컬렉션, 처리 품질, 버전과 보관 상태로 거를 수 있다. 기본은 이전 버전을 숨긴다.
- 검토 대기 문서가 있으면 상단에 안내와 "검토 대기만 보기" 필터 버튼이 나타난다.
- 행 선택 후 일괄 삭제와 선택 재처리(`batch-reprocess`, 실패한 블록부터)를 할 수 있다.
- 처리 중인 문서가 있으면 목록을 주기적으로 다시 불러온다.
- 품질 열은 종합 점수 대신 품질 판정 라벨(품질 경고, 품질 실패, 부분 실패, 검토 필요 등)을 보여준다.
- 문서를 보관하고 복원하며 만료일을 설정할 수 있다. 보관된 문서는 검색과 답변에 쓰이지 않는다.

### 업로드 모달

- 파일 선택 버튼으로 여러 파일을 고른다. 끌어다 놓기는 지원하지 않는다.
- 지원 형식은 PDF, DOCX, HWP, HWPX, XLSX, PPTX, TXT, MD, HTML(HTM), 이미지(PNG, JPG, JPEG, TIFF, BMP, WEBP)다. 목록은 `backend/app/pipeline/formats.py`가 정본이다.
- 다음 항목을 입력한다.
  - 컬렉션을 고른다.
  - 전처리 워크플로우는 "컬렉션 기본값 사용" 또는 PREPROCESS 워크플로우 중 하나다. 워크플로우를 고르면 이번 업로드에만 그 버전이 지정된다.
  - "같은 이름이 있어도 새 문서로 올리기" 옵션을 끄면 같은 이름의 문서를 새 버전으로 잇는다.
  - "검토 없이 자동 진행" 옵션은 파일이 2개 이상이면 자동으로 켜지며 끌 수 없다.
- ZIP 일괄 업로드 탭이 따로 있다. 결과는 등록됨, 중복, 건너뜀, 실패 건수로 집계된다.
- 업로드 결과는 파일별로 성공 또는 실패를 표시한다.
- 설계 초안의 문서명, 설명, 문서 유형, 태그 입력은 구현되지 않았다. 문서 메타데이터는 문서 상세의 메타데이터 편집에서 고친다.

## 4.3 전처리 설정

### 설계 대비 현재 구성

설계 초안은 문서별 전처리 규칙 목록과 미리보기 화면을 제안했다. 이 화면은 구현되지 않았다. 전처리 설정은 다음 화면으로 나뉘어 있다.

- 처리 순서와 블록 설정은 워크플로우 편집기에서 한다(§4.5).
- 컬렉션의 기본 워크플로우와 재처리는 컬렉션 설정 모달에서 한다(§4.4).
- 정제 규칙(정규식 치환, 문자열 제거, 라인 필터)은 정제 규칙 화면에서 관리한다(§4.8).
- 사전 적용 설정(불용어, 동의어, 사용자 사전)은 검색 사전 화면에서 관리한다(§4.7).

### 정제 규칙 화면 (`/cleaning-rules`, 관리자)

- 목록에는 이름, 유형, 적용 범위, 우선순위, 활성 여부 열이 나온다.
- 규칙 유형은 정규식 치환, 문자열 제거, 라인 필터 세 가지다.
- 적용 범위는 문서 전체, 문단, 라인 중에서 고른다.
- 규칙을 등록할 때 이름, 유형, 패턴, 치환 결과(비우면 제거), 우선순위, 범위, 활성 여부를 입력한다.
- 텍스트 정제 블록이 `apply_custom_rules` 설정이 켜져 있을 때 활성 규칙을 적용한다.

### 미구현

- 문서별 전처리 미리보기와 설정 항목의 체크박스 목록(머리글, 바닥글, 중복 문장, 페이지 번호 제거 등)은 구현되지 않았다. 이 항목들은 워크플로우 블록 설정으로 구현되었다(`text_clean`, `text_extract`).

## 4.4 컬렉션 설정

### 목적

컬렉션이 어떤 워크플로우로 문서를 처리할지 정하고, 기존 문서를 다시 처리한다.

### 구현된 항목 (컬렉션 설정 모달)

- 기본 정보로 이름, 프로젝트, 보안 등급 기본값, 검색 설정을 입력한다.
- 문서 처리 섹션에서는 다음을 정한다.
  - 기본 워크플로우는 "표준 전처리(시스템 기본값)" 또는 프로젝트의 PREPROCESS 워크플로우 중에서 고른다. 개인 컬렉션은 시스템 기본값만 고를 수 있다.
  - 고정할 버전은 항상 최신 게시 버전을 쓰는 방식과 특정 버전을 고정하는 방식 중에서 고른다.
  - 기본 분석 워크플로우는 "표준 분석(시스템 기본값)" 또는 프로젝트의 분석 워크플로우 중에서 고른다. 고른 워크플로우는 전처리가 끝난 직후 문서마다 자동으로 실행된다. 워크플로우에 요약, 추천 태그, 분류 단계가 없으면 그 항목은 비워지며, 고를 때 경고로 알린다.
  - 재처리 버튼은 두 개다.
    - "처음부터 다시 처리" 버튼은 원본 파싱부터 다시 해 추출, 표, 쪽 번호 개선을 반영한다. 확인 후 실행하며 결과로 요청 건수와 건너뛴 건수를 알린다. 진행률 막대는 없다.
    - "청크·임베딩만 다시 만들기" 버튼은 이미 추출된 텍스트로 청크와 임베딩만 다시 만든다.

### 제거된 항목

- 청크 크기와 전략을 정하는 입력란은 이 화면에서 없어졌다. 청크 설정은 워크플로우의 문서 분할 블록에서 정하고, 블록 값이 없으면 컬렉션의 기본값을 쓴다.

### 미구현

- 컬렉션 재처리의 진행률 표시와 "예상 시간" 안내는 구현되지 않았다.

## 4.5 워크플로우 목록과 편집

### 4.5.1 워크플로우 목록 (`/workflows`)

- 목록에는 이름, 종류(전처리, 분석), 버전, 상태(초안, 활성, 비활성), 수정자, 수정일, 작업 열이 나온다.
- 시스템 기본 워크플로우는 ★ 시스템 기본 표시가 붙고 삭제와 비활성화가 막힌다.
- 검색어, 종류, 상태로 거를 수 있다.
- 작업 메뉴에는 편집, 실행 이력, 복제(프로젝트 선택), 상태 변경, 삭제, 기본 지정(컬렉션 선택)이 있다. 삭제할 때는 모든 버전과 실행 이력이 함께 삭제된다고 경고한다.
- 버전 비교는 편집기의 버전 비교 대화 상자에서 한다(`VersionCompareModal`).

### 4.5.2 워크플로우 편집기 (`/workflows/:id/edit`)

화면 구조

```text
┌──────────────┬─────────────────────────────┬────────────────────┐
│ 블록 팔레트   │ 캔버스                       │ 블록 또는 연결 속성  │
│ 검색          │ 블록 노드와 에지              │ 이름, 설정 폼         │
│ 카테고리별 목록│ 검증 실패 블록은 빨간 테두리  │ 설정 저장 과 삭제     │
│              │ 검증 실패 에지는 빨간 선       │                    │
└──────────────┴─────────────────────────────┴────────────────────┘
  상단: 워크플로우 이름, 종류, 버전 선택, 초안 저장, 게시, 실행, 버전 삭제
  하단: 검증 오류 목록
```

- 팔레트: 블록을 카테고리별로 묶어 보여준다. 전처리 종류는 입력·추출, 정제·정규화, 구조·보호, 분할·저장, 품질·제어 카테고리를, 분석 종류는 분석 카테고리를 쓴다. 블록 이름으로 검색할 수 있다. 팔레트 항목을 누르면 캔버스에 추가된다.
- 캔버스: 블록을 옮기고 에지를 이어 연결한다. 연결 속성 패널에서 에지 조건을 설정할 수 있다. 조건부 에지는 "조건부" 라벨로 표시된다.
- 설정 폼: 블록에 하드코딩된 설정 필드가 있으면 그것을 쓰고, 없으면 백엔드 `config_schema`에서 만든 필드를 쓴다. 불리언은 체크박스, 선택지는 셀렉트, 숫자는 숫자 입력, 목록은 태그 입력으로 나온다. 고급 JSON 편집 영역은 없다.
- 검증: 검증 실패 블록과 에지를 빨간색으로 강조하고, 오류 메시지를 목록으로 보여준다. 예를 들어 "'RAG 저장' 블록은 상류에 품질 검증 블록이 필요합니다" 같은 메시지를 보여준다.
- 게시: 검증 오류가 남아 있으면 게시할 수 없고, "아래 검증 오류를 먼저 고쳐야 게시할 수 있습니다."라는 메시지가 나온다. 게시된 버전은 수정할 수 없고, 수정하려면 새 버전을 만든다.
- 실행: 게시된 버전만 실행할 수 있다. 대상은 문서 1건 또는 컬렉션이다. 컬렉션을 고르면 파싱이 끝난 문서마다 실행을 만들며 최대 50건이다. 대상 문서의 기존 RAG 데이터를 대체한다는 경고가 나온다.
- 저장하지 않은 변경이 있으면 페이지를 떠날 때 확인 대화 상자를 띄운다.

### 4.5.3 실행 이력 (`/workflows/:id/runs`)

- 워크플로우의 실행 목록을 보여준다. 런을 선택하면 블록별 타임라인이 나온다(§4.6.3과 같은 스텝 타임라인 컴포넌트).

### 미구현

- AI 블록 추천, 순서 개선 제안, 설정 초안 생성은 구현되지 않았다(설계 초안 §4.5의 "AI의 역할"). 블록은 사람이 직접 조합한다.
- 샘플 문서로 미리 돌려 보는 테스트 실행은 없다. 실행은 실제 문서 대상으로만 한다.
- 사용자 사전이 불용어보다 뒤에 있을 때 경고하는 기능은 없다.

## 4.6 문서 상세

### 4.6.1 헤더와 보조 패널

- 헤더에는 파일명, 상태 배지, 보안 등급 배지가 나온다. 작업 버튼으로 원본을 내려받을 수 있다(처리가 끝난 문서). 재처리 버튼도 있다.
- 검토 대기 문서는 헤더 아래에 "이 문서는 검토 대기 중입니다" 안내와 "품질 탭으로 이동" 버튼이 나온다.
- 실패 문서는 오류 메시지를 보여준다. 재시도 요청 버튼이 있다.
- 좌측 보조 패널에는 RAG 현황(청크 수, 임베딩 상태 등), 문서 정보, 태그, 추천 태그가 나온다. 추천 태그는 추가하거나 무시할 수 있다.

### 4.6.2 탭

탭은 `DocumentDetailPage`의 `TABS`에 정의되어 있다. 설계 초안의 여덟 탭에서 요소, 표, 그림, RAG 데이터 수정 탭이 더해졌다.

| 탭 | 내용 | 표시 조건 |
|---|---|---|
| 원문 대조 | 원본 페이지 미리보기와 쪽별 추출 텍스트 | 처리 완료 또는 검토 대기 |
| 구조 | 구조 트리와 노드 상세. 노드 유형, 레벨, 글꼴 스타일 보정 | 항상 |
| 요소 | Docling 요소 목록과 마크다운 보정 | PDF이고 처리 완료 |
| 정제 비교 | 정제 전후 변경 내역과 규칙별 표본 | 항상 |
| 사전 적용 | 사전 적용 내역, 문서 단위 항목 제외, 개별 적용 취소 | 항상 |
| 민감정보 | 탐지 목록, 승인, 해제, 원문 보기(관리자) | 항상 |
| 청크 | 청크 목록, 검색 제외, 텍스트 수정(재임베딩), 상위 청크 보기 | 항상 |
| 표 | 추출된 표 | 처리 완료 |
| 그림 | 추출된 그림 | 처리 완료 |
| RAG 데이터 수정 | 텍스트 리비전 이력과 원문 편집 | 처리 완료 |
| 품질 | 종합 점수, 항목별 점수 막대, 판정 기준, 경고 목록, 승인과 반려 | 항상 |
| 처리 이력 | 런 목록, 블록 타임라인, 스텝 상세, 이 블록부터 재처리 | 항상 |

- 검토 대기 문서를 열면 품질 탭이 먼저 열린다. 이후 원문 대조 탭으로 가도 품질 탭으로 되돌아가지 않는다.
- 탭 상태는 URL의 `tab` 쿼리로 지정할 수 있다(예: 검토 대기 화면의 "문서 열기" 링크).

### 4.6.3 처리 이력과 스텝 타임라인

- 런 목록에서 런을 고르면 블록별 스텝이 순서대로 나온다. 스텝마다 상태, 소요 시간, 캐시 여부("캐시" 배지), 경고 수를 보여준다.
- 실패한 스텝은 오류 코드에 맞는 한글 안내를 보여준다.
- "이 블록부터 재처리" 버튼으로 재처리 대화 상자를 시작점이 고정된 상태로 연다.

### 4.6.4 재처리 대화 상자 (`ReprocessModal`)

- 시작 지점은 "전체(파일 검증부터)"와 "특정 블록부터" 중에서 고른다. 특정 블록부터를 고르면 블록을 따로 선택한다.
- 전체를 고르면 "최신 게시 버전으로 처리" 체크박스가 나온다. 워크플로우를 고쳐 새 버전을 게시했을 때 켠다.
- 영향 범위 미리보기에는 재실행 블록 목록, 캐시로 재사용되는 블록, 영향 노드 수, 영향 청크 수, 전체 재처리 필요 여부가 나온다.
- 이번 런에만 적용할 블록 시간 제한을 조정할 수 있다(선택).
- 사유를 적을 수 있다(선택). 재처리 시작 버튼으로 실행한다.

### 4.6.5 탭별 기능

- **원문 대조**: 원본 미리보기와 추출 텍스트를 나란히 본다. 쪽을 넘긴다.
- **구조**: 노드 트리에서 노드를 고르면 상세가 나온다. 노드 유형, 레벨, 글꼴 이름, 글꼴 크기, 스타일 이름을 고치고 메모를 남길 수 있다. 보정한 노드는 "사용자 보정됨" 표시가 붙는다. 보정하면 재처리 제안 배너가 나온다. 문단과 표의 경계를 고치는 기능은 없다.
- **정제 비교**: 정제 변경 내역을 전후 문장으로 보여준다.
- **사전 적용**: 적용된 항목을 원문과 적용 결과로 보여준다. 항목별로 이 문서에서 제외할 수 있다. 개별 적용 취소는 `reverted` 표시만 바꾼다. 재처리해야 반영된다.
- **민감정보**: 탐지 목록(유형, 마스킹 값, 쪽, 신뢰도, 조치, 승인 여부)을 보여준다. 승인과 해제를 할 수 있다. 원문 보기는 관리자에게만 보인다. 원문을 열 때는 감사 로그가 남는다.
- **청크**: 청크를 순서대로 보여준다. 청크를 고르면 텍스트를 고치고 저장할 수 있다. 저장하면 재임베딩이 실행된다. 검색 제외 토글은 해당 청크를 검색에서 뺀다. 원문 쪽과 이전 또는 다음 청크로 이동하는 링크가 있다. 품질 경고 대상 청크는 따로 강조된다.
- **품질**: 종합 점수를 크게 보여주고, 항목별 점수 막대(텍스트 추출, OCR, 구조, 청크, 원문 재현율)를 보여준다. 점수 산정 기준을 펼쳐 볼 수 있다. 경고마다 "구조 탭에서 대상 확인", "원문 대조 탭에서 확인", "청크 탭에서 확인" 링크가 있다. 검토 대기 상태이면 하단에 "반려"와 "승인 후 계속 진행" 버튼이 나온다. 검토 의견 입력란은 없다.
- **처리 이력**: 4.6.3절 참고.

### 미구현

- 청크 경계 수정과 문단, 표 경계 수정은 구현되지 않았다.
- 검토 승인과 반려에 메모를 남기는 검토 의견 입력은 구현되지 않았다.
- 문서를 고친 뒤 승인할 때 자동 재처리를 확인하는 대화 상자는 구현되지 않았다.

## 4.7 검색 사전 관리 (`/dictionary`, 관리자)

### 목적

검색 시 불용어 제외, 동의어 정규화, 사용자 용어를 관리한다. 항목을 저장하면 사전 리비전이 올라가고, 검색어 확장(`SEARCH_EXPAND`)에는 다음 질문부터 바로 쓰인다(`dictionary_service.ensure_dictionary_cache_sync`). 문서 본문의 정규화(불용어, 동의어, 사용자 사전 블록)는 문서를 새로 처리하거나 재처리할 때 반영된다.

### 화면 구조

- 상단에는 불용어, 동의어, 사용자 사전 탭이 있다. 여기에 "버전 이력" 보기가 더해진다.
- 상단 도구로 검색어를 입력하고, 엑셀로 내려받거나 가져오며, 항목을 추가할 수 있다.
- 본문에는 항목 표가 나온다(종류에 따라 열이 다르다). 행마다 수정, 삭제, 사용 여부 전환을 할 수 있다.
- 항목 추가와 수정은 대화 상자에서 한다.

### 종류별 입력 항목

- 불용어는 단어, 일치 방식(정확히 일치, 포함, 시작 문자열, 끝 문자열, 정규식), 대소문자 구분, 언어, 적용 범위, 제외 사유, 사용 여부를 입력한다.
- 동의어는 대표 용어, 동의어 목록(Enter로 추가), 적용 방향(단방향, 양방향), 처리 방식(정규화, 치환, 검색 확장, 태깅), 대소문자 구분, 언어, 적용 범위, 설명을 입력한다.
- 사용자 사전은 표준 용어, 변형 표현(Enter로 추가), 용어 유형(전문용어, 약어, 기관명, 인명, 제품 또는 서비스명, 프로젝트명, 정책명, 기타), 처리 규칙(원문 유지, 표준어로 정규화, 치환, 태그 부여, 주요 개체 추출, 민감정보 마스킹, 처리 대상에서 제외), 발음, 정의, 적용 범위를 입력한다.

적용 범위는 쉼표로 구분한 문자열(예: ko, en, all)이다. 설계 초안의 "문서 유형" 범위는 구현되지 않았다.

### 저장 후 영향 확인

항목을 저장하면 영향받는 문서 수를 보여주는 대화 상자(`ImpactModal`)가 뜬다. 재처리는 사용자가 문서별로 실행한다. 자동 재처리는 없다.

### 버전 이력

"버전 이력" 보기에서 사전 리비전 목록(번호, 시각, 변경 종류, 변경 항목, 작성자)을 본다. 항목별 실행 이력 연결은 없다.

### 검색 적용 범위의 한계 (화면에 안내됨)

화면 상단 안내는 다음을 밝힌다. 치환, 태깅, 개체 추출, 마스킹 규칙은 저장되지만 검색 토큰화 단계에는 아직 적용되지 않는다. 검색에 실제로 적용되는 규칙은 정규화(KEEP, NORMALIZE)다.

### 미구현

- 사전 그룹, 항목별 충돌 검사(중복 등록 경고, 변형 표현 충돌 표시), 저장 전 충돌 요약은 구현되지 않았다.
- 일괄 업로드 화면의 충돌 미리보기는 없다. 가져오기는 된다.

## 4.8 정제 규칙 (`/cleaning-rules`, 관리자)

4.3절에 적었다.

## 4.9 처리 현황 (`/processing-status`)

- 제목은 "문서 처리 현황"이고 부제는 "최근 24시간"이다.
- 지표 카드는 처리 문서, 평균 품질, 실패율, 재처리율, 검토 대기, 큐 대기 시간을 보여준다.
- 블록별 성능 표에는 블록, 실행 수, 실패율, 평균 시간이 나온다.
- 최근 실패 목록에는 문서명과 오류 원인이 나오며, 각 문서로 이동할 수 있다.
- 관리자 전용이 아니다. 문서 처리 권한이 있는 사용자가 볼 수 있다.

### 미구현

- 시간당 처리 문서 수 차트와 일별 처리 추이 차트는 구현되지 않았다.
- 실패율 임계치 알림은 구현되지 않았다.

## 4.10 검토 대기와 실패 큐

### 4.10.1 검토 대기 (`/review-queue`)

- 제목은 "검토 대기"다. 처리 도중 사람의 확인이 필요해 멈춘 문서를 오래 기다린 순서대로 보여준다.
- 요약 카드는 전체, 품질 검토 건수, 개인정보 검토 건수, 하루 넘게 대기한 건수를 보여준다.
- 사유별(품질, 민감정보 등)로 거를 수 있다.
- 행에는 파일명, 대기 시간, 사유 배지, 품질 범주 배지가 나온다.
- 행에서는 "문서 열기"(사유에 맞는 탭으로 이동), "승인하고 계속", "반려"를 할 수 있다.

### 4.10.2 실패 (`/failures`)

- 제목은 "실패"다. 처리에 실패한 문서를 원인별로 본다.
- 요약 카드는 실패 문서 수, 바로 다시 처리할 수 있는 문서 수, 반복 실패 수, 원인 종류 수를 보여준다.
- 원인별로 거르는 도구가 있다.
- 행에는 파일명, 실패 횟수, 원인 설명, 처리 이력 보기, 다시 처리 버튼이 나온다.
- 실패 단계를 기록하지 못한 문서는 다시 처리 버튼이 막히고, 문서 상세에서 전체 재처리를 하라는 안내가 나온다.
- 여러 문서를 고르는 일괄 재처리는 문서 목록의 "선택 재처리"에서 한다.

### 메뉴 배지

좌측 메뉴의 "검토 대기"와 "실패" 항목에는 건수 배지가 있다. 배지는 주기적으로 갱신된다.

## 4.11 문서 처리 결과 검토

설계 초안의 "분석 결과 목록(개체, 키워드, 분류, 검증)과 결과 상태(신규, 사전 일치, 수정됨, 무시됨, 승인됨)" 화면은 구현되지 않았다. 처리 결과는 다음 방식으로 검토한다.

- 검토 대기 화면과 문서 품질 탭에서 품질 근거를 확인하고 승인 또는 반려한다.
- 구조, 정제, 사전, 민감정보, 청크 탭에서 세부 결과를 확인하고 고친다.
- 요약과 추천 태그는 문서 메타데이터 영역에서 확인하고 고친다. 추천 태그는 추가하거나 무시한다.

## 4.12 채팅 (`/chat`)

설계 초안의 "AI 수정 채팅"(결과를 자연어로 고치고 변경 전후를 비교한 뒤 승인)은 구현되지 않았다. 현재 채팅은 컬렉션 문서를 근거로 답하는 질의응답 화면이다.

- 대화 목록을 보고, 대화를 열거나 이름을 바꾸거나 삭제할 수 있다.
- 답변은 스트리밍으로 나온다. 진행 상황(에이전트 단계)과 근거 인용을 함께 보여준다.
- 심층 검색 토글을 켜면 복합 질문을 하위 질문으로 나눠 찾은 뒤 종합한다.
- 답변에 피드백을 남길 수 있다.
- 근거가 없으면 답하지 않는다. 답변 추적 기록은 관리자 메뉴에서 본다(§4.13).

- 프로젝트 (`/projects`, `/projects/:id`): 프로젝트 안에 컬렉션, 문서, 검색, 채팅, 워크플로우 탭이 있다.

## 4.15 부분 재처리 (Partial Reprocessing)

### 목적

전체 문서를 처음부터 다시 처리하지 않고, 수정한 단계부터만 다시 실행한다.

### 재처리 흐름 (구현)

1. 문서 상세 또는 처리 이력에서 재처리를 연다.
2. 시작 지점을 고른다(전체 또는 특정 블록).
3. 영향 범위 미리보기가 자동으로 계산되어 나온다.
4. 사유를 적고 시작한다. 상류 단계는 원본 실행의 결과를 재사용하고, 시작 블록부터 새로 실행한다.

### 수정 내용과 시작 블록 (블록 이름은 실제 block_type 기준)

| 수정 내용 | 시작 블록 | 재실행 범위 |
|---|---|---|
| 파일을 처음부터 다시 처리 | file_validate (전체) | 전체 |
| 텍스트 추출 설정 변경 (워크플로우 게시 후 "최신 게시 버전으로 처리") | file_validate (전체) | 전체 |
| 구조 분석 설정 변경 | structure_analyze | 구조 분석 이후 전체 |
| 정제 규칙 변경 | text_clean | 정제 이후 전체 |
| 사용자 사전 변경 | user_dict | 사용자 사전 이후 전체 |
| 동의어 변경 | synonym | 동의어 이후 전체 |
| 청킹 전략 또는 크기 변경 | chunk_split | 문서 분할, 품질 검증, RAG 저장 |
| 품질 기준 변경 | quality_check | 품질 검증, RAG 저장 |

- 재실행 범위는 워크플로우 DAG에서 시작 블록의 하류에 있는 블록 전체로 자동 계산된다. 설계 초안의 "청킹 전략 변경은 품질 검증만 재실행" 항목은 잘못된 내용이었다. 청크가 바뀌면 품질 검증과 RAG 저장도 다시 실행되어야 한다.
- 노드 단위 재처리는 구현되지 않았다. 블록 단위만 가능하다.

### 캐시와 복사

- 시작 블록의 상류 단계는 원본 실행의 스텝 상태와 출력을 새 실행에 복사해 "cached"로 표시한다.
- 캐시 테이블은 세 블록(파일 검증, 형식 판별, 텍스트 추출)에만 쓰인다.
- 시간 제한이 부족하면 이번 실행에만 적용되는 시간 제한을 설정한다.

## 5. 디자인 시스템

디자인 시스템은 세 층으로 이루어진다. 공통 토큰(`styles/tokens.css`), KRDS 기반 테마(`styles/krds-theme.css`, `krds-uiux` 라이브러리를 재정의), 그리고 화면 공통 클래스(`styles/components.css`의 `ds-` 접두사 클래스)와 화면별 스타일(`styles/screens/*.css`)이다. 현재 라이트 테마만 제공하며 다크 모드 토큰은 없다.

## 5.1 시각 방향

- 배경은 흰색과 밝은 회색을 쓰고, 텍스트는 짙은 남색으로 하며, 주요 액션 색상은 파란색이다.
- 정보 밀도를 높이고 계층을 분명하게 나타낸다.
- 상태는 색과 텍스트를 함께 표시한다(배지에 라벨 문구가 들어간다)
- 장식보다 가독성과 작업 효율을 우선한다

## 5.2 색상 토큰 (`tokens.css`의 `:root`)

| 토큰 | 값 | 용도 |
|---|---|---|
| `--color-bg` | #f5f6f8 | 전체 배경 |
| `--color-surface` | #ffffff | 카드, 패널, 표 |

| `--color-primary-subtle` | #edf2fc | 선택 배경 |
| `--color-success` | #146c43 | 완료, 정상 (배경 #e7f5ee) |

## 5.3 타이포그래피

- 글꼴: Pretendard GOV를 우선하고, 없으면 시스템 기본 글꼴을 쓴다. Pretendard GOV는 KRDS 패키지에서 직접 싣는다(외부 글꼴 서버를 쓰지 않는다).
- 고정폭 글꼴은 Consolas, D2Coding 등을 쓴다(`--font-mono`).
- 크기 토큰은 xs 12px, sm 13px, base 14px(본문), md 15px, lg 16px, xl 20px, 2xl 24px이다.
- 두께 토큰은 400, 500, 600이다.
- 줄 간격 토큰은 tight 1.35, normal 1.55다.

## 5.4 간격 체계

`--space-1`부터 `--space-10`까지 4, 8, 12, 16, 20, 24, 32, 40px을 쓴다.

## 5.5 모서리, 그림자, 크기

- 반경 토큰은 sm 6px(입력, 버튼), md 8px(카드), lg 12px, pill 999px이다.
- 컨트롤 높이 토큰은 28px(sm), 32px(md), 36px(lg)이다.
- 그림자 토큰은 xs, sm, lg이며 모두 깊이가 낮은 그림자다.
- 포커스 링은 파란색 3px 링이다(`--focus-ring`).
- 모션 시간은 빠름 120ms, 보통 200ms이고, 감속 곡선은 `cubic-bezier(0.16, 1, 0.3, 1)`를 쓴다. `prefers-reduced-motion`에서는 움직임을 줄인다.

## 6. 컴포넌트 정의

컴포넌트는 `frontend/src/components/ui/`에 있다(Button, Badge, Field, Page, Data, Modal, ErrorAlert, Spinner). KRDS 클래스(`krds-btn`, `krds-input` 등)와 `ds-` 클래스가 함께 쓰인다.

## 6.1 버튼

- 변형은 primary, secondary, ghost, danger, danger-solid다.
- 크기는 sm, md, lg다.
- 상태는 기본, 마우스 올림, 누름, 비활성, 로딩(작업 중 아이콘 회전)이다.
- 아이콘만 쓰는 버튼(`IconButton`)에는 라벨을 붙인다.
- 저장과 실행 중에는 같은 버튼을 다시 누를 수 없다(비활성 처리).

## 6.2 입력 컴포넌트

- 입력 컴포넌트는 `Field`(라벨과 입력 묶음), `Input`, `Select`, `Textarea`, `SearchInput`이 있다.
- 태그 입력은 Enter로 항목을 추가한다. 사전의 동의어, 변형 표현, 워크플로우 목록 입력에 쓴다.
- 체크박스는 자동 진행, 새 문서 올리기 등에 쓴다.
- 파일 선택은 버튼 방식이며 끌어다 놓기는 없다.
- 입력 상태는 기본, 포커스, 오류(`ErrorText`), 비활성이다.

## 6.3 데이터 표

- 열 정렬은 문서 목록의 정렬 기준에 쓴다.
- 필터와 검색 도구 모음(`Toolbar`, `FilterChip`, `Segmented`)을 갖춘다.
- 행을 선택하고 일괄 작업 막대(`BulkActionBar`)로 작업한다.
- 페이지마다 표시할 건수를 고를 수 있다.
- 빈 상태(`EmptyState`)와 로딩 표시(`Spinner`)를 보여준다.

## 6.4 카드와 통계

- `Card`는 제목과 본문이 있는 패널이다.
- `Stat`와 `StatStrip`은 숫자 지표 카드 묶음이다. 톤(기본, 경고, 위험)을 지정할 수 있다.
- 문서 카드 형태의 목록은 없다. 문서는 표로 나온다.

## 6.5 상태 배지

| 상태 | 배지 톤 | 예시 |
|---|---|---|
| 색인 완료, 정상 | success | INDEXED, 품질 정상 |
| 처리 중 | info | 파싱, 청크 분할, 임베딩 등 |
| 검토 필요 | warning | WAITING_REVIEW, 품질 경고 |
| 실패 | danger | FAILED, 품질 실패 |
| 대기, 보관, 비활성 | neutral | QUEUED, 보관됨, INACTIVE |

- 배지는 `StatusBadge`가 문서 상태를 톤과 라벨로 바꿔 그린다. 보안 등급은 `SecurityLevelBadge`를 쓴다.
- 건수 배지는 `CountBadge`다(메뉴의 검토 대기와 실패).

## 6.6 패널

- `SidePanel`은 문서 상세의 보조 정보(RAG 현황, 문서 정보)와 워크플로우 편집기의 속성 패널에 쓴다.
- 접기나 크기 조절 기능은 없다.

## 7. 상태 및 예외 설계

## 7.1 빈 상태

- `EmptyState`에 제목과 설명을 함께 쓴다. 예: "업로드된 문서가 없습니다", "조건에 맞는 문서가 없습니다. 필터를 바꾸거나 초기화해 보세요."
- 가능하면 다음 행동 버튼을 함께 둔다(문서 업로드, 필터 초기화).

## 7.2 로딩 상태

- 페이지를 불러올 때는 "로딩 중..." 문구 또는 `Spinner`를 보여준다.
- 버튼을 실행하면 버튼 안에 작은 회전 아이콘이 나타난다.
- 문서 처리: 문서 상세의 "전처리 단계" 타임라인이 블록별 상태를 보여준다. 목록은 주기적으로 다시 불러온다.
- 채팅 응답: 스트리밍으로 답변과 진행 단계를 표시한다.

## 7.3 오류 상태

- 오류 메시지는 `ErrorAlert`와 `ErrorText`로 표시한다. 작업이 실패하면 무엇을 하지 못했는지 한 문장으로 쓴다. 예: "사전 항목을 저장하지 못했습니다."
- 가능하면 원인을 함께 쓴다. 워크플로우 실패는 오류 코드를 한글 안내로 바꾸고, 알 수 없는 원인은 예외 종류와 원문 일부를 덧붙인다.
- 재시도 가능 여부는 실패 큐의 "다시 처리" 버튼 활성 여부로 알린다.

## 7.4 저장되지 않은 변경

- 워크플로우 편집기는 저장하지 않은 변경이 있으면 페이지를 떠날 때 확인 대화 상자를 띄운다.
- 자동 저장은 없다. 설계 초안의 충돌 병합 기능은 구현되지 않았다.

## 8. 권한 설계

현재 권한은 두 층으로 나뉜다. 프로젝트와 컬렉션 권한(viewer, editor)과 전역 역할(admin, 일반 사용자)이다. 설계 초안의 "일반 사용자, 실무 담당자, 검토자, 관리자"는 별도 역할로 구현되지 않았다.

| 기능 | 권한 | 근거 |
|---|---|---|
| 문서 조회, 원문 대조, 검색, 채팅 | viewer 이상 | 문서 접근 검사 (`check_document_access`) |
| 문서 업로드, 메타데이터 수정, 청크 수정과 삭제, 재처리, 검토 승인과 반려 | editor 이상 | `min_role="editor"` |
| 워크플로우 실행, 워크플로우 실행 검토 승인과 반려 | editor 이상 | `workflows/runs.py` |
| 컬렉션 재처리 (두 종류) | editor 이상 | `collections.py` |
| 워크플로우 생성, 편집, 게시, 복제 | 프로젝트 또는 워크플로우 접근 권한 | `workflows/definitions.py` |
| 시스템 기본 워크플로우 삭제와 비활성화 | 막음 (모든 사용자) | 409 응답 |
| 검색 사전 관리, 정제 규칙 관리 | 전역 admin | `require_admin` |
| 민감정보 원문 열람 | 전역 admin | `structure.py`의 reveal |
| 사용자, 그룹, 원천 연결, 감사 로그 | 전역 admin | 관리 메뉴 |

- 권한이 없는 메뉴는 숨기고, 권한이 없는 버튼은 비활성 처리한다.
- 원문 열람과 미리보기는 감사 로그에 남긴다.

## 9. 반응형 기준

- 화면 폭 기준으로 CSS 미디어 쿼리는 860px과 960px 두 곳에 있다(`components.css`, `documents.css`, `pipeline.css`).
- 본격적인 태블릿, 모바일 전용 레이아웃(드로어 메뉴, 카드형 목록 전환)은 구현되지 않았다.
- 워크플로우 편집기는 넓은 화면을 기준으로 한다. 좁은 화면에서는 블록 편집이 불편할 수 있다.

## 10. 접근성 기준

다음은 목표 기준이다. 전체 화면을 감사한 결과는 아니다.

- 텍스트와 배경의 명도 대비를 확보한다. 토큰 값을 기준으로 삼는다.
- 포커스 상태를 파란색 링으로 표시한다.
- 아이콘 버튼에는 접근성 라벨을 붙인다(`IconButton`).
- 상태를 색으로만 구분하지 않는다. 배지에 라벨 문구를 쓴다.
- 대화 상자는 열리면 포커스를 가둔다(`Modal`).
- 움직임은 `prefers-reduced-motion`에서 줄인다.
- 표와 폼에는 제목과 라벨을 붙인다. 파일 선택과 체크박스 목록에 aria 라벨이 있다.

## 11. 생성형 AI 상호작용 원칙

설계 초안의 "AI 수정 제안과 승인 후 반영" 원칙은 구현되지 않았다. 현재 AI 기능은 다음과 같다.

- 채팅 답변 생성: 근거가 없으면 답하지 않는다. 근거 인용을 함께 보여준다.
- 요약과 추천 태그 생성: 추천 태그는 사용자가 수락하거나 무시한다. 자동 반영하지 않는다.
- 답변 추적 기록: 관리자가 답변의 근거를 추적할 수 있다.

## 13. 우선 구현 화면 (현재 상태)

|---:|---|---|
| 1 | 문서 업로드와 처리 설정 | 구현됨. 설정은 워크플로우와 컬렉션 기본값으로 나뉜다. |

| 4 | AI 수정 채팅 | 미구현. 채팅은 질의응답 화면이다. |

## 14. 핵심 설계 원칙 요약

1. 문서 처리 과정을 블록 단위로 보여준다. 블록별 상태, 캐시 여부, 소요 시간을 함께 본다.
2. 자동 처리 결과는 검토 게이트에서 사람이 확인한다. 검토 대기 문서는 메뉴 배지와 알림으로 알린다.
3. 원본 데이터는 바꾸지 않고 정제 결과와 이력을 따로 남긴다.
4. 부분 재처리와 변경 이력을 기본 기능으로 제공한다.
5. 사전은 종류별로 나누되 관리 화면은 하나로 통일한다.
6. 상태는 색과 텍스트를 함께 표시한다.
7. AI가 결과를 자동으로 고치지 않는다. 추천은 사용자가 수락하거나 무시한다.
