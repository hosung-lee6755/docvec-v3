# 문서 처리 플랫폼 디자인 설계서

**최종 갱신**: 2026-07-28 — 아래 내용은 실제 구현 완료 상태를 반영함

## 1. 문서 개요

### 1.1 목적

본 문서는 문서 업로드, 전처리, 워크플로우 구성, 사전 적용, AI 분석, 결과 검토 및 수정 기능을 제공하는 **문서 처리 플랫폼**의 화면 구조와 사용자 경험을 정의한다.

### 1.2 설계 목표

- 복잡한 문서 처리 과정을 단계별로 이해할 수 있도록 구성
- 사용자가 고정된 처리 블록을 조합하여 워크플로우를 구성할 수 있도록 지원
- 불용어, 동의어, 사용자 사전을 일관된 방식으로 관리
- AI 분석 결과를 검토하고 필요한 부분만 수정할 수 있도록 지원
- 문서 처리 상태, 오류, 검토 필요 항목을 한눈에 확인
- 업무용 B2B SaaS에 적합한 명확하고 안정적인 인터페이스 제공

### 1.3 주요 사용자

| 사용자 유형 | 주요 목적 |
|---|---|
| 일반 사용자 | 문서 업로드, 처리 실행, 결과 확인 |
| 실무 담당자 | 워크플로우 구성, 사전 적용, 결과 수정 |
| 검토자 | 분석 결과 검토, 승인, 반려 |
| 관리자 | 사용자, 권한, 문서 유형, 모델, 시스템 설정 관리 |

### 2.2 기본 레이아웃

```text
┌──────────────┬─────────────────────────────┬────────────────────┐
│ 좌측 내비게이션 │ 메인 작업 영역               │ 우측 보조 패널       │
│              │                             │                    │
│ 대시보드      │ 문서 또는 워크플로우 캔버스   │ 속성 설정           │
│ 문서 처리     │ 처리 단계 및 결과             │ AI 수정 채팅         │
│ 워크플로우    │ 문서 미리보기                 │ 실행 로그            │
│ 사전 관리     │ 데이터 테이블                 │ 변경 이력            │
│ 관리자        │                             │                    │
└──────────────┴─────────────────────────────┴────────────────────┘
```

### 2.3 레이아웃 원칙

- 좌측 내비게이션은 플랫폼의 주요 메뉴를 제공한다.
- 중앙 영역은 문서, 워크플로우, 테이블 등 핵심 작업을 수행하는 공간이다.
- 우측 패널은 속성 설정, AI 채팅, 실행 로그, 변경 이력 등 보조 작업을 제공한다.
- 사용자의 주요 작업은 중앙에서 완료되며, 우측 패널은 문맥을 유지한 채 보조 기능을 제공한다.
- 작업 컨텍스트가 없는 화면에서는 우측 패널을 접을 수 있다.



```text

→ 각 블록 속성 설정
→ 입력/출력 검증
→ 테스트 실행

```

### 3.4 사전 등록 흐름

```text

→ 항목 등록 또는 파일 업로드

→ 중복 및 충돌 확인
```

## 4. 화면 설계

## 4.1 대시보드

### 목적

사용자가 플랫폼의 문서 처리 현황, 오류, 검토 필요 항목, 최근 활동을 한눈에 확인할 수 있도록 한다.

### 주요 영역

#### 상단 요약 카드

| 항목 | 설명 |
|---|---|
| 전체 문서 | 등록된 전체 문서 수 |
| 처리 완료 | 정상 처리된 문서 수 |
| 처리 중 | 현재 실행 중인 문서 수 |
| 검토 필요 | 사용자 검토가 필요한 문서 수 |
| 오류 | 처리 실패 문서 수 |

#### 처리 현황 차트

- 상태별 도넛 차트
- 일별 처리 건수 라인 차트
- 기간 필터: 7일, 30일, 사용자 지정

#### 최근 문서

| 컬럼 | 설명 |
|---|---|
| 문서명 | 업로드된 문서 이름 |
| 문서 유형 | 요구사항, 기술 설계서 등 |
| 상태 | 완료, 처리 중, 검토 필요, 오류 |
| 수정자 | 최근 수정 사용자 |
| 수정일 | 최종 수정 일시 |

#### 알림 영역

- 처리 완료
- 검토 요청
- 사전 버전 변경
- 워크플로우 오류
- 시스템 공지

### 주요 액션

- 새 문서 처리
- 검토 필요 문서 열기
- 오류 상세 보기
- 전체 활동 보기

## 4.2 문서 업로드

### 목적

사용자가 처리할 문서를 업로드하고 문서 유형과 처리 옵션을 지정한다.

### 입력 항목

| 항목 | 필수 | 설명 |
|---|---:|---|
| 문서 파일 | Y | PDF, DOCX, HWPX, TXT 등 |
| 문서 유형 | Y | 요구사항, 기술 문서, 정책 문서 등 |
| 문서명 | Y | 기본값은 파일명 |
| 설명 | N | 문서에 대한 부가 설명 |
| 컬렉션 | Y | 문서를 저장할 공간(또는 워크스페이스) |
| 태그 | N | 검색 및 분류용 태그 |
| 워크플로우 버전 | N | 전처리 파이프라인 버전(명시하지 않으면 컬렉션 기본값 또는 시스템 표준 사용) |
| 검토 없이 진행 | N | 체크 시 품질 검토 게이트를 `auto_pass`로 설정(실패 시엔 여전히 검토 필수) |

### 업로드 상태

- 대기
- 업로드 중
- 업로드 완료
- 형식 오류
- 용량 초과
- 암호화 문서
- 손상된 파일

### UX 원칙

- 드래그 앤 드롭 지원
- 다중 업로드 지원
- 파일별 상태 표시
- 형식 오류 발생 시 즉시 안내
- 업로드 후 문서 유형 자동 추천 가능

## 4.5 워크플로우 편집

### 목적

사용자가 고정된 처리 블록을 조합하여 문서 처리 흐름을 설계한다.

### 화면 구조

```text
┌──────────────┬─────────────────────────────┬────────────────────┐
│ 블록 목록     │ 워크플로우 캔버스             │ 블록 속성           │
│              │                             │                    │
│ 입력          │ [입력]                      │ 이름                │
│ 전처리        │    ↓                        │ 설명                │
│ 분석          │ [전처리]                    │ 입력/출력            │
│ 후처리        │    ↓                        │ 적용 사전            │
│ 출력          │ [분석]                      │ 모델 설정            │
│ 조건 분기     │    ↓                        │ 오류 처리            │
│ 병합          │ [출력]                      │                    │
└──────────────┴─────────────────────────────┴────────────────────┘
```

### 블록 유형

| 블록 | 역할 |
|---|---|
| 입력 | 문서 또는 데이터 입력 |
| 전처리 | 텍스트 정제 및 사전 적용 |
| 분류 | 문서 유형 또는 범주 분류 |
| 개체 추출 | 인명, 기관명, 제품명 등 추출 |
| 키워드 추출 | 핵심 키워드 추출 |
| 요약 | 문서 또는 섹션 요약 |
| 검증 | 규칙 기반 또는 AI 기반 검증 |
| 조건 분기 | 결과에 따른 분기 |
| 병합 | 여러 결과 통합 |
| 후처리 | 결과 정규화 및 포맷팅 |
| 출력 | 저장, 내보내기, API 전달 |

### 편집 규칙

- 사용자는 블록의 생성, 삭제, 순서 변경, 연결 변경이 가능하다.
- 플랫폼은 허용되지 않는 연결을 차단한다.
- 필수 입력이 없는 블록은 오류 상태로 표시한다.
- 저장 전 워크플로우 유효성 검사를 수행한다.
- 활성 버전은 직접 수정하지 않고 새 버전으로 저장한다.

### AI의 역할

- 사용자의 자연어 요청을 기반으로 적절한 블록 조합 추천
- 기존 워크플로우의 순서 및 연결 개선 제안
- 누락된 단계 감지
- 블록 속성 초안 생성
- 실행 오류 원인 설명
- 전체 블록 자체를 자유 생성하기보다, 등록된 블록을 조합하고 설정하는 방식으로 제한

## 4.9 사용자 사전

### 목적

도메인 전문용어, 기관명, 제품명, 프로젝트명, 약어, 고유명사 등을 등록하고 처리 규칙을 지정한다.

### 목록 컬럼

| 컬럼 | 설명 |
|---|---|
| 표준 용어 | 시스템에서 인식할 기준 용어 |
| 변형 표현 | 별칭, 띄어쓰기, 오탈자 |
| 용어 유형 | 제품명, 약어, 전문용어 등 |
| 처리 규칙 | KEEP, NORMALIZE, REPLACE 등 |

## 4.10 품질 검토 게이트 (Quality Check & Review)

### 목적

문서 전처리 완료 후, 자동 품질 검증과 사용자 검토를 통해 문서를 임베딩/검색 단계로 진행할지 결정한다.

### 품질 검증 (Automatic Quality Check)

품질 검증 블록은 다음 5개 수준의 지표를 계산한다:
- **textExtraction**: 추출 문자 수, 깨진 문자 비율, 빈 페이지 비율
- **ocr**: OCR 신뢰도(OCR 사용 문서만), 페이지별 실패 여부 추적
- **structure**: 제목 탐지율, 목차-제목 일치율
- **normalization**: 사전 적용 건수, 미등록 용어, 충돌 규칙
- **chunking**: 평균 청크 크기, 너무 짧은/긴 청크 비율

> **⚠ 실제 구현과 차이**: 설계서는 청킹 수준 지표만 언급했으나, 실제로는 파일/텍스트/구조/사전/분할 5개 수준을 모두 계산하고 있다.

### 품질 검증 상태 (Quality Report Status)

`QualityReport.status`는 다음 5가지 상태를 가진다:

| 상태 | 의미 | 자동 진행 | 검토 필요 |
|---|---|:---:|:---:|
| **SUCCESS** | 모든 지표가 기준 충족 | O | X |
| **SUCCESS_WITH_WARNING** | 경고는 있으나 사용 가능 | O* | O* |
| **REVIEW_REQUIRED** | 사용자 검토 필요 | X | O |
| **PARTIAL_FAILURE** | 일부 페이지 처리 실패 | X | O |
| **FAILURE** | 치명적 오류(청크 0개 등) | X | O |

*review_policy 설정에 따라 결정 (auto_pass / review_on_warning / always_review)

### 검토 게이트 (Review Gate)

품질 검증 완료 후:

1. **SUCCESS 또는 SUCCESS_WITH_WARNING (auto_pass)**: 자동으로 다음 단계(AUTO_ANALYSIS 워크플로우) 진행
2. **SUCCESS_WITH_WARNING 또는 SUCCESS (review_required)**: `WAITING_REVIEW` 상태로 일시정지 → 사용자 검토 필요
3. **PARTIAL_FAILURE 또는 FAILURE**: `WAITING_REVIEW` 상태로 일시정지 → 항상 검토 필수

업로드 시 **"검토 없이 진행"** 옵션을 체크하면, 이 run의 review_policy를 `auto_pass`로 강제 설정한다. 단, PARTIAL_FAILURE/FAILURE는 그대로 검토가 필수다.

WorkflowRun 상태:
- `QUEUED` → `RUNNING` → `COMPLETED` (검토 필요 없을 때)
- `QUEUED` → `RUNNING` → `WAITING_REVIEW` → (사용자 승인) → `COMPLETED`

## 4.12 AI 수정 채팅

### 목적

### 기본 구조

```text
┌────────────────────────────┬──────────────────────┐
│ AI 채팅                     │ 변경 미리보기         │
│                            │                      │

│ AI 응답                     │ 변경 후              │
│ 수정 제안                   │ 변경 근거            │
│                            │ 영향 범위            │
│ [입력창]                    │ [반영] [취소]         │
└────────────────────────────┴──────────────────────┘
```

### 컨텍스트 유지 범위

AI는 다음 정보를 함께 참조한다.

- 현재 문서
- 사용자가 선택한 결과 항목
- 기존 분석 결과
- 적용된 사전
- 사용한 워크플로우
- 이전 수정 이력
- 동일 세션의 대화 내용

### 수정 요청 예시

- “LangGraph 설명을 더 정확하게 수정해줘.”
- “이 문단의 요약만 다시 작성해줘.”
- “이 항목은 제품명이 아니라 기술 용어로 변경해줘.”
- “신뢰도가 0.8 이하인 항목만 다시 검토해줘.”

### 변경 반영 규칙

- AI 수정 결과는 즉시 원본에 반영하지 않는다.
- 변경 전후 비교를 제공한다.
- 사용자의 명시적 승인 후 반영한다.
- 반영된 변경은 이력으로 저장한다.
- 변경 취소 및 이전 버전 복원이 가능해야 한다.

## 4.14 부분 재처리 (Partial Reprocessing)

### 목적

전체 문서를 처음부터 다시 처리하지 않고, 사용자 수정 이후 해당 단계부터만 다시 실행한다.

### 재처리 흐름

1. 사용자가 검토 결과에서 사용자 사전, 청킹 전략 등을 수정
2. "재처리" 버튼으로 시작 블록(start_block_type)과 이유(reason) 입력
3. **영향도 계산 (Impact Preview)**:
   - 시작 블록의 상류 블록들이 영향받을지 분석
   - 영향받는 청크/노드 개수 표시
   - 전체 재처리 필요 여부 판정
4. 사용자 확인 후 재처리 실행
5. 상류 단계는 원본 런의 완료된 결과를 캐시에서 재사용, 시작 블록부터 새로 실행

### 재처리 범위 결정 (Block Dependencies)

재처리 범위는 블록 의존성으로 자동 계산된다:

| 수정 내용 | 시작 블록 | 영향 범위 |
|---|---|---|
| 텍스트 추출 방식 | format_detect | 전체 재처리 |
| 구조 분석 설정 | structure_analyze | 분할 이후 재실행 |
| 사용자 사전 추가 | apply_custom_dictionary | 분할 이후 재실행 |
| 청킹 전략 변경 | chunk_split | 품질 검증만 재실행 |
| 청킹 크기만 변경 | chunk_split | 품질 검증만 재실행 |

### 캐시 메커니즘

- 부분 재처리 시 시작 블록 상류의 완료된 WorkflowRunStep을 새 WorkflowRun으로 복사
- `BlockExecutionCache`에 저장된 이전 실행 결과 재사용 (구현: app/pipeline/tasks/workflow.py)
- 타임아웃 길어짐이 필요한 경우 `timeout_overrides` 설정으로 해결

- 데이터 테이블은 카드형 목록으로 전환 가능

## 10. 접근성 기준

- 텍스트와 배경의 충분한 명도 대비
- 키보드만으로 주요 기능 사용 가능
- 포커스 상태 명확히 표시

- 오류 메시지와 입력 필드 연결
- 모달 열림 시 포커스 고정
- 표와 폼에 명확한 제목 제공

## 11. AI 인터랙션 원칙

### 설명 가능성

AI가 수정 또는 제안을 할 때 다음 정보를 함께 제공한다.

- 변경한 내용
- 변경 이유
- 적용된 규칙 또는 사전
- 영향을 받는 영역
- 신뢰도 또는 주의 사항

### 사용자 통제

- 자동 반영 금지
- 변경 전후 비교 필수
- 승인 후 적용
- 이력 저장
- 이전 버전 복원 가능

### 문맥 유지

AI 대화는 작업 단위로 세션을 유지한다.

```text
워크스페이스
└─ 문서
   └─ 처리 실행
      └─ 검토 세션
         └─ AI 대화 및 수정 이력
```

### 부분 수정

AI는 전체 결과를 재생성하기보다, 선택된 항목 또는 사용자가 지정한 범위만 수정할 수 있어야 한다.

## 14. 핵심 설계 원칙 요약

1. 문서 처리 과정을 단계적으로 보여준다.
2. AI는 등록된 블록의 조합과 설정을 지원한다.
3. AI 결과는 사용자 승인 전까지 자동 반영하지 않는다.
4. 부분 수정과 변경 이력을 기본 기능으로 제공한다.
5. 사전은 유형별로 분리하되 관리 경험은 통일한다.
6. 중앙 작업 영역과 우측 보조 패널 구조를 유지한다.
7. 오류, 검토 필요, 신뢰도 정보를 명확히 표현한다.
8. 업무 효율과 정보 가독성을 시각적 장식보다 우선한다.
