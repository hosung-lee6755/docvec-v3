# 전처리 워크플로우 성능 검토 보고서

- 검토일: 2026-11-13
- 대상: `test_data` 로컬 연결(컬렉션 "로컬 폴더 점검")로 들어온 문서를 "표준 전처리 워크플로우"로 처리한 결과
  - 블록 순서: file_validate → format_detect → text_extract → structure_analyze → text_clean → user_dict → synonym → stopword → pii_detect → chunk_split → quality_check → rag_store
  - 컬렉션 청크 설정: `size` 전략, 최대 512토큰, 겹침 64토큰(기본값)
- 방법: 화면의 품질 점수는 보지 않았다. 원본 PDF·HWPX의 텍스트 레이어와 페이지 이미지를 직접 뽑아 파싱 결과(`documents.parsed_text`), 구조 노드, 청크, 개인정보 탐지 결과와 나란히 비교했다.
  - 텍스트 재현율은 원본 텍스트의 글자 4-gram이 파싱 결과에 얼마나 남았는지로 쟀다.
  - 이미지로만 된 페이지는 페이지를 그림으로 렌더링해 눈으로 대조했다.
  - 속도는 run의 블록별 소요 시간, 워커 로그의 Docling 변환 시간, 같은 문서를 단독으로 돌린 시간을 함께 봤다.
- 아래 건수와 시간은 이번 실행에서 잰 값이다. 문서 구성이나 동시 실행 상황이 바뀌면 달라진다.

## 2. 처리 속도

**관찰**
- 텍스트 추출 블록이 문서당 시간의 대부분을 차지한다. 세원화성 사업계획서(82쪽) 1668초, 정부 가이드라인(988쪽) 1790초, AX 사례(22쪽) 666초였다. 워커 로그의 Docling 변환 시간도 1655초, 652초로 같은 수준이다.
- 8쪽짜리 디에스아이 문서를 컨테이너에서 단독으로 돌리면 모델 적재 7초, OCR을 켠 변환 18초였다. 변환기를 재사용하면 11초, OCR을 끄면 9초다. 같은 문서가 운영 실행에서는 143초 걸렸다. 동시 4건 처리와 메모리 압박이 겹쳐 약 8배 느려진 것으로 본다.
- 문서마다 `DocumentConverter`를 새로 만들어 레이아웃·표·OCR 모델을 매번 다시 적재한다.
- 워커 자식 프로세스가 쉬는 동안에도 13.7GB, 5.4GB를 쥐고 있다. `--max-tasks-per-child`, `--max-memory-per-child` 설정이 없어 메모리가 돌려지지 않는다. GPU 메모리도 12GB 가운데 11.7GB를 쓰고 있었다.
- rag_store가 10초에서 345초까지 크게 흔들린다. 같은 시간대의 추출 작업과 자원을 다툰 결과로 보인다.
- 검토 도중 Docker VM 전체가 40분 가까이 응답을 멈춰 재시작했다. 원인을 따라가 보니 GPU 모델을 쓰는 작업이 메인 워커(`--concurrency=4`)에서 돈다는 점이 핵심이었다. 텍스트 추출(Docling, EasyOCR)과 답변 생성(로컬 LLM, 임베딩, 재순위)이 여기에 해당한다. 자식 프로세스 4개가 모델을 저마다 따로 올린다.
  - 3B 모델(fp16 약 6GB)을 4개가 올리면 24GB, 7B 모델(fp16 약 15GB)은 하나만으로도 12GB GPU를 넘는다. 넘친 몫은 Windows의 공유 시스템 메모리로 흘러가 매우 느려지고, WSL VM의 메모리를 바닥낸다. 실제로 같은 시각 api가 `OSError: [Errno 12] Cannot allocate memory`로 커넥터 삭제에 실패했다.
  - 같은 워커를 자식 프로세스 1개로 줄이자 답변 하나가 모델 적재를 포함해 37초에 끝났고, GPU 6.9GB, 메모리 4.2GB로 안정됐다. 4개일 때는 같은 3B 답변이 215초 뒤 시간 초과로 실패하기도 했다.
  - 이미 임베딩 블록은 이 문제 때문에 `concurrency=1`인 `worker-embed`(`embed` 큐)로 분리돼 있다(2026-07-21). 추출과 답변 생성은 아직 분리되지 않았다.
  - 채팅 화면은 12GB GPU에 들어가지 않는 7B 모델도 "사용 가능"으로 보여 준다.

**권고**
0. GPU 모델을 쓰는 작업(텍스트 추출, 답변 생성, 골든 평가)을 `concurrency=1` 전용 큐로 옮긴다. `embed` 큐와 같은 방식이다. 이 항목이 가장 급하다. 메인 워커는 DB·파일 작업만 병렬로 맡는다. 장기적으로는 LLM을 별도 추론 서버(vLLM 등)로 빼는 것이 맞다.
1. 워커 프로세스마다 Docling 변환기를 한 번만 만들어 재사용한다(옵션 조합별 캐시).
2. 추출 전용 큐를 두고 동시성을 1~2로 낮춘다. 다른 블록은 지금처럼 병렬로 둔다.
3. 워커에 `--max-memory-per-child`(예: 8GB)와 `--max-tasks-per-child`를 둔다.
4. 텍스트 레이어가 충분한 페이지는 OCR을 끈다. 그림 OCR은 아래 5절의 판정으로 대체한다.

## 3. 텍스트 추출 정확도

**텍스트 레이어 PDF**: 대부분 4-gram 재현율 0.90~0.98로 본문은 잘 들어온다. 정부 가이드라인만 0.871인데, 2~6쪽 목차의 점선 리더와 쪽 번호가 흐트러진 탓이다. Docling은 문장부호 앞에 공백을 넣는다(" ,"). 검색에는 영향이 작지만 화면 표시와 인용에는 거슬린다.

**스캔 PDF(범죄 취약지 연구)**: 텍스트 레이어가 없어 Tesseract로 처리됐다. 단어 오류가 약 5%다. "범죄"→"Wal", "영향을"→"SSS", "관계를"→"WAS"처럼 한글이 영문 잡음으로 바뀌고, 저자 이름이 숫자로 바뀐다. 문서의 핵심 용어("범죄")가 깨져 검색에서 놓칠 수 있다.

**이미지 슬라이드(AX 사례, EasyOCR)**
- 숫자가 깨진다. 0.90%→0.909, 87.00%→87.009, 94.30%→94.3096처럼 `%`가 숫자 `9`나 `96`으로 읽힌다. 수치를 묻는 질문에 틀린 답을 줄 수 있어 가장 위험하다.
- 슬라이드 제목과 목록 첫 항목이 빠진다.
- "일치율"→"일치울", "모델링"→"모델림", "검증"→"검종"처럼 받침이 틀린다.

**전면 이미지 페이지(심야버스)**: 표지와 뒤표지에서 글자가 하나도 나오지 않았다. 제목은 "넥데이터 기반 심아버스 노선 수립올"로 읽혔다.

**띄어쓰기 없는 원본(개인하수처리 사례집)**: 원본 PDF에 공백 문자가 없고 글자 위치로만 띄어쓰기를 표현한다. 파싱 결과가 붙어 나와 단어 검색과 토큰 수 계산이 모두 틀어진다.

**권고**
1. 스캔 PDF도 Tesseract 대신 한국어 OCR(EasyOCR 등)로 보내고, 결과에서 한글 비율이 낮은 줄을 다시 인식한다.
2. OCR 결과의 `%` 오인식(숫자 뒤 `9`, `96`)을 후처리 규칙으로 보정한다. 규칙만으로 확신할 수 없는 경우는 검토 대기로 보낸다.
3. 텍스트가 전혀 나오지 않은 페이지는 해상도를 올려 다시 인식하고, 그래도 비면 "이미지 페이지"로 표시한다.
4. PDF 글자 사이 간격을 보고 공백을 복원한다(글자 폭 대비 간격이 임계값보다 크면 공백).
5. 문장부호 앞 공백을 정제 단계에서 지운다.

## 4. 페이지 번호 귀속(버그)

**원인**: `process._build_page_map`이 블록 원문 길이로 페이지 시작 위치를 쌓는데, `parsed_text`는 머리말·꼬리말 줄을 지운 텍스트다. 지운 만큼 위치가 어긋나고, 페이지가 넘어갈수록 어긋남이 쌓인다.

**영향**
- 정부 가이드라인은 페이지 맵 끝 위치가 263,663인데 파싱 텍스트 길이는 261,077이다. 청크 719개 가운데 페이지가 맞는 것은 130개였고, 중앙값으로 6쪽 차이가 났다.
- 짧은 문서도 조금씩 틀린다. 세원화성 158/172, D01 22/24, AX 6/8이 맞았다.
- 답변의 출처 페이지와 문서 뷰어의 이동 위치가 틀어진다.

**권고**: 머리말·꼬리말을 지운 뒤의 블록으로 페이지 맵을 만들거나, 지운 구간만큼 위치를 보정한다. 페이지 경계가 `parsed_text`의 실제 위치와 맞는지 검사하는 회귀 테스트를 함께 둔다. 가장 먼저 고칠 항목으로 권한다.

## 5. 표와 그림

**Docling 표**: 87개 표가 `| 0 | 1 | 2 |` 같은 번호 머리글로 시작하고, 실제 머리글은 본문 첫 줄로 밀려 있다. 표를 마크다운으로 바꿀 때 열 이름 대신 열 번호를 쓴 결과다. 첫 행을 머리글로 승격하면 된다.

**HWPX 표**
- 어댑터가 모든 문단을 먼저 내보내고 표를 문서 끝에 모은다. 표가 설명 문단과 떨어져 청크에서 맥락을 잃는다.
- 셀 안 줄바꿈이 사라져 "사업계획서- 국세…"처럼 항목이 붙는다.
- HWP 블록이 모두 1쪽으로 기록된다.
- 권고: 본문 순서대로 문단과 표를 섞어 내보내고, 셀 안 줄바꿈은 `<br>`이나 ` / `로 남긴다.

**그림 OCR**: 그림 173개 가운데 74개는 텍스트가 비었고, 나머지 99개 가운데 35개는 의미 없는 글자였다. 이것이 "[그림 N]" 본문으로 들어가 색인을 오염시킨다. 한글·영문 단어 비율과 길이로 쓸모를 판정해 기준에 못 미치면 본문에 넣지 않도록 권한다. 그림의 존재만 메타데이터로 남기면 된다.

## 6. 청크 분할

- 컬렉션이 `size` 전략이라 구조 노드가 있어도 쓰지 않는다. 모든 청크의 `section_path`가 비어 있고, 약 절반이 문장 중간에서 끝난다.
- 청크 길이는 중앙값 약 500자에서 최대 약 2000자까지다. 표가 섞인 구간에서 길어진다.
- 권고: 새 컬렉션의 기본 전략을 구조 기반(제목·문단 경계 우선, 크기 상한)으로 바꾸고, 크기로 자를 때도 문장 경계에서 자른다. 기존 컬렉션은 설정을 바꾼 뒤 재처리해야 반영된다.

## 7. 개인정보 탐지

- `2026-06-08`, `2026-07-13` 같은 날짜가 계좌번호(ACCOUNT)로 가려졌다. 공고문의 일정이 청크에서 사라져 "언제 접수하느냐" 같은 질문에 답하지 못한다.
- 공고문에 실린 공공기관 대표 전화와 이메일, 사업자등록번호, 한전 고객번호도 가려진다. 공개된 기관 연락처는 개인정보가 아니다.
- 탐지 결과의 `start_offset`이 `parsed_text`의 위치와 맞지 않는다. 4절과 같은 계열의 위치 어긋남으로 보인다.
- 권고: 계좌 패턴에서 날짜 형식(`YYYY-MM-DD`, `YYYY.MM.DD`)을 먼저 제외하고, 기관 대표번호·도메인 허용 목록을 둔다. 위치는 정제 뒤 텍스트 기준으로 맞춘다.

## 8. 정제·사전·불용어

정제 규칙, 사용자 사전, 동의어 치환은 원본 대비 의도대로 바뀌었다. 불용어는 표시만 하고 본문에서 지우지 않는다. 지금 설정에서는 문제가 없다.

## 9. 답변으로 본 영향(일반 답변과 심층 답변 비교)

원문에서 정답을 확인한 질문 10개를 Qwen2.5 3B로 일반 모드와 심층 모드에 한 번씩 물었다. 워커를 프로세스 1개로 줄여 한 건씩 돌렸고, 답에 원문 사실 조각이 들어 있는지 셌다.

| 모드 | 사실 포함 | 평균 소요(브라우저 기준) |
|---|---|---|
| 일반 | 24개 가운데 22개 | 약 10초(첫 건은 모델 적재 포함 38초) |
| 심층 | 24개 가운데 20개 | 약 11초 |

- OCR 오류가 그대로 답이 됐다. 두 모드 모두 운임 일치율을 "87.009%", "94.3096%"로 답했다(원문 87.00%, 94.30%). 일반 모드는 평균 운임 차이를 "0원"이라고 답했다(원문 2,165원 이내). 3절의 `%` 오인식 보정이 필요한 이유다.
- 심층 모드는 비교 질문에서 나았다. "R&D성과확산과 디지털협업공장의 지원 한도 비교"에 일반 모드는 "같다"고 틀리게 답했고, 심층 모드는 5억원과 2억원(동일수준 0.5억원)을 옳게 나눠 답했다.
- 심층 모드는 하위 질문으로 나누다가 다른 문서로 새는 경우가 있었다. "(유)정민산업의 주요 생산품과 대표자"에 다른 문서를 근거로 "조개탄, 김윤수"라고 답했다(원문은 선박임가공, 전재현). "AIDE 1단계 비용"에서는 4.5M/M(인월)을 "4억 5천만 원"으로 잘못 풀었다.
- 같은 문서 안에서 답이 나오는 단순 사실 질문은 두 모드 모두 대체로 맞혔다.

**고친 내용**
- GPU 작업 분리: 텍스트 추출은 `worker-extract`(`extract` 큐), 임베딩·답변 생성·골든 평가는 `worker-embed`(`embed`, `llm` 큐)가 하나씩 처리한다. 메인 워커에는 GPU 모델이 올라가지 않는다. Docling 변환기는 프로세스마다 한 번만 만들고, 재순위 모델은 GPU에서 fp16으로 올린다. 메인 워커는 자식 프로세스 메모리가 4GB, 추출 워커는 8GB를 넘으면 교체된다.
- 쪽 번호: 페이지 맵을 실제로 조립한 텍스트 기준으로 만들고, 정제·치환·마스킹 뒤 위치를 원문 위치로 옮겨 쪽을 정한다(`app/pipeline/page_alignment.py`).
- 개인정보: 날짜, 사업자번호, 고객번호는 계좌나 전화로 보지 않는다. 계좌는 앞에 은행·계좌 단서가 있거나 그런 계좌에 이어 적힌 경우만 잡는다. 문의처·기관명 바로 뒤의 유선번호와 공공기관 도메인 메일은 기관 연락처로 본다. 휴대전화는 어떤 문맥이어도 개인정보로 본다.
- 표: Docling 표의 실제 머리글 행을 살리고, HWP/HWPX 표를 문서 순서 자리에 두며, 셀 안 문단을 ` / `로 구분한다.
- 청크: 컬렉션 기본값(`size`)이고 구조 노드가 본문의 80% 이상을 덮으면 구조 기준으로 자른다. 블록에서 전략을 명시하면 그대로 따른다. 이때 50자 미만 조각은 이웃과 합치고, 표 바로 앞의 짧은 줄은 그 표의 제목으로 붙인다. 크기 기준으로 자를 때도 문단, 문장 끝, 공백 순으로 자를 곳을 찾는다.
- OCR: 그림 인식 결과에서 의미 없는 줄을 본문에서 뺀다(원문은 그림 기록에 남는다). `%`를 `9`·`96`으로 읽은 값은 비율 문맥이 있고, 같은 범위에 제대로 찍힌 %가 없으며, 소수 셋째 자리 이상인 숫자가 모두 그 모양일 때만 고친다. p값이 섞인 연구 보고서의 숫자 12개는 일부러 고치지 않았다.
- 텍스트 추출 블록 버전을 1.22.0으로 올려 이전 캐시를 쓰지 않게 했다.

**남은 문제**
- `worker-embed`에 LLM(3B), 임베딩, 재순위 모델이 함께 올라가면 GPU를 약 10.1GB 쓴다. 이 상태에서 추출이 함께 돌면(약 4GB) 12GB를 넘어 공유 메모리로 흘러간다. 대량 재처리 중에는 채팅을 피하거나, LLM을 별도 추론 서버로 빼야 한다. 채팅 화면은 여전히 12GB에 들어가지 않는 7B 모델을 "사용 가능"으로 보여 준다.
- 품질 검사는 50자 미만 청크가 하나라도 있으면 검토 대기로 멈춘다. 지금 남은 짧은 청크는 큰 표 앞의 제목 줄처럼 따로 두는 것이 맞는 경우라 승인해서 마무리했다.
- 컬렉션 일괄 재처리(`POST /collections/{id}/reprocess`)는 예전 고정 파이프라인으로 청크와 임베딩만 다시 만들고 추출은 다시 하지 않는다. 추출 개선을 반영하려면 문서별 재처리(최신 버전으로 처음부터)를 써야 한다.
- 스캔 PDF의 한글 OCR 오류와 띄어쓰기가 없는 PDF의 띄어쓰기 복원은 손대지 않았다.
- 실행을 취소한 문서는 부분 재처리를 할 수 없다. "최신 버전으로 처음부터" 재처리는 이번에 허용했다.
