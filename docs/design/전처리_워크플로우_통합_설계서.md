## 1. 현황 진단

### 1.1 두 개의 분리된 처리 경로

현재 시스템에는 문서 처리 경로가 2개 병존하며 서로 연결되지 않는다.

**경로 A — 고정 파이프라인** (`tasks/pipeline.py`, `tasks/process.py`)

```
업로드 → ingest_document → parse_document → [REVIEW_PENDING 게이트]
       → continue_processing (청크 분할 → _clean_rag_text 정제 → 임베딩 → Qdrant)
       → generate_summary / extract_metadata (비동기 후속)
```

- 사용자가 순서·설정을 구성할 수 없는 하드코딩 체인
- 정제는 제어문자/공백 정규화 최소한만 수행 (`_clean_rag_text`)
- 사전(불용어/동의어/사용자사전)은 BM25 토크나이저에만 쓰이고 **RAG 저장 데이터에는 미적용**

**경로 B — 워크플로우** (`pipeline/blocks/`, `tasks/workflow.py`)

- 입력→전처리→분류/요약/키워드/개체→검증→출력 DAG
- 이미 파싱 완료된 문서의 `parsed_text`를 읽어 요약/태그를 문서 메타데이터에 기록
- **청크·임베딩·Qdrant에는 전혀 개입하지 않음** — 워크플로우의 전처리 블록에서 텍스트를 정제해도 RAG 검색 결과는 변하지 않는다

### 1.2 이미 존재하는 자산 (재사용 대상)

| 자산 | 위치 | 통합 후 역할 |
|---|---|---|
| 파일 어댑터 (PDF/DOCX/HWP) | `pipeline/adapters/` | 텍스트추출 블록 내부 구현 |
| OCR (Tesseract + 클라우드 VLM) | `pdf_adapter.py`, `process.py::_recognize_*` | OCR 블록 내부 구현 |
| 페이지 매핑 (`page_map`) | `process.py::_build_page_map` | 원문 위치 추적의 기반 |
| HWP 재페이지네이션 | `process.py::_repaginate_hwp_like` | 텍스트추출 블록 내부 |
| 청크 분할 (크기/의미 기준) | `process.py::_chunk_text*` | 문서분할 블록 내부 |
| 기본 정제 | `process.py::_clean_rag_text` | 텍스트정제 블록의 기본 규칙 |
| 사전 시스템 | `dictionary_service.py`, `DictionaryPage` | 불용어/동의어/사용자사전 블록의 데이터 소스 |
| 원문 대조 미리보기 | `preview_service.py` | 검토 화면 원문 패널 |
| 파싱 이력 | `DocumentTextRevision` | 추출본 버전 관리로 확장 |
| 청크 단위 재임베딩 | `tasks/chunks.py::update_chunk_text` | 청크 수정 기능의 기반 |
| DAG 실행기 (분기/병합) | `tasks/workflow.py` | 그대로 재사용 + 확장 |
| 워크플로우 버전 불변성 | `WorkflowVersion.published_at` | 그대로 재사용 |
| 잡 트래커 | `job_tracker.py` | WorkflowRunStep 상태 전이로 대체 |
| 감사 로그 | `services/audit.py`, `AuditLog` | 22장 감사 요구사항의 기반 |

### 1.3 설계서 대비 결핍 (신규 구축 대상)

- 파일 검증(3.2) / 형식 판별(4장)이 업로드 엔드포인트에 산재하거나 부재
- 문서 구조 분석(7장): 구조 트리(DocumentNode) 부재 — 어댑터가 blockType 정도만 가짐
- 정제 규칙 관리(8.3)·정제 이력(8.4) 부재 — 정제가 코드에 하드코딩
- 사전 버전 관리(9장, 16장) 부재 — `dictionary_entries`에 version 개념 없음
- 민감정보 탐지(10장) 전체 부재
- 청크가 DB 엔티티가 아님(11.4) — Qdrant payload에만 존재, sourceNode/sectionPath/전후 링크 없음
- 품질 검증(12장) 전체 부재
- 부분 재처리(15장) 부재 — 전체 재처리만 가능
- 실행 캐시(21.2) / 입출력 해시(13.3) 부재

## 2. 목표 아키텍처

### 2.1 전체 흐름

```
문서 업로드 (POST /api/v1/documents)
  → 원본 저장 (MinIO originals) + Document 행 생성        [엔드포인트 책임]
  → 컬렉션의 기본 전처리 워크플로우 결정                    [엔드포인트 책임]
  → WorkflowRun 생성 + 첫 블록 enqueue                    [이후 전부 워크플로우 책임]

워크플로우 (기본 제공 "표준 전처리" 예시):
  [파일 검증] → [형식 판별] → [텍스트 추출] → [OCR(조건)] → [구조 분석]
  → [텍스트 정제] → [불용어 처리] → [동의어 정규화] → [사용자 사전 적용]
  → [민감정보 탐지] → [문서 분할] → [품질 검증(검토 게이트)] → [RAG 저장]
  → (선택) [요약] [키워드 추출] [분류] …
```

- `tasks/pipeline.py::create_processing_chain`, `tasks/process.py`의 `parse_document`/`continue_processing`, `tasks/ingest.py`는 **블록 구현으로 분해·이관 후 제거**한다.
- `tasks/summary.py`/`tasks/metadata.py`의 자동 트리거도 제거 — 요약/키워드가 필요하면 워크플로우에 해당 블록을 넣는다(기본 워크플로우에 포함해 현재 동작을 보존).
- Document.status는 더 이상 태스크가 직접 조작하지 않고, **실행 중인 WorkflowRun의 현재 블록에서 파생**된다(17.3 상태 매핑 — §7.2).

### 2.2 컬렉션 ↔ 워크플로우 바인딩

```
Collection
  + default_workflow_id        (FK workflow_definitions, nullable)
  + default_workflow_version   (int | null — null이면 실행 시점의 최신 published 버전)
```

- 컬렉션에 지정이 없으면 **시스템 기본 워크플로우**(마이그레이션 시 시드되는 "표준 전처리", ACTIVE)를 사용한다.
- 업로드 API는 `workflow_id`/`workflow_version` 파라미터로 1회성 오버라이드를 허용한다.
- 시스템 기본 워크플로우는 비활성화·삭제할 수 없다(다른 워크플로우를 기본으로 승격한 뒤에만 가능).
- 컬렉션 설정 변경 후 "이 컬렉션 전체 재처리" 액션 제공(기존 reprocess 동작 대체).

### 2.3 실행 데이터 흐름 — 아티팩트 저장소

현재 실행기는 블록 출력 JSON 전체를 `WorkflowRunStep.output`에 저장한다. 전문 텍스트·구조 트리·청크 목록이 13개 블록을 통과하면 DB가 비대해지므로:

- **`WorkflowRunStep.output`에는 요약 메타데이터만** 저장: 처리 건수, 경고 수, 입력/출력 해시, 아티팩트 참조 키.
- **대용량 산출물은 MinIO artifacts 버킷**에 저장: `runs/{run_id}/{step_id}/output.json` (구조 트리, 정제 텍스트, 청크 목록 등).
- 블록 간 전달: 실행기가 상류 스텝의 아티팩트 참조를 `BlockContext.upstream_outputs`로 로드해 넘긴다(작으면 인라인, 크면 lazy 로드 — `BlockContext`에 `load_artifact(ref)` 헬퍼 추가).

```json
// WorkflowRunStep.output (DB) — 예: 텍스트정제 블록 (합성 예시)
{
  "artifact": "runs/RUN-1/STEP-7/output.json",
  "input_hash": "sha256:…",
  "output_hash": "sha256:…",
  "stats": {"changes": 182, "rules_applied": 6, "chars_before": 51200, "chars_after": 49810},
  "warnings": 0
}
```

### 2.4 실행 캐시 (설계서 21.2)

캐시 키 = `원본 파일 해시 + 블록 타입 + 블록 버전 + 블록 설정 해시 + 사전 버전(사전 블록만) + 모델 버전(LLM/임베딩 블록만)`.

- `block_execution_cache` 테이블(§4.9)에 캐시 키 → 아티팩트 참조를 기록.
- 재처리·재실행 시 동일 키가 있으면 블록 실행을 건너뛰고 아티팩트를 재사용(스텝 상태 `COMPLETED`, `cached: true` 표시).
- 부분 재처리(§8)의 상류 재사용도 이 캐시로 구현한다.

## 3. 블록 카탈로그 (전면 재편)

### 3.1 카테고리 구성

| 카테고리 | 블록 | 비고 |
|---|---|---|
| 입력·추출 | 파일 검증, 형식 판별, 텍스트 추출, OCR | 신규 4종 |
| 정제·정규화 | 텍스트 정제, 불용어 처리, 동의어 정규화, 사용자 사전 적용 | 신규 4종 |
| 구조·보호 | 구조 분석, 민감정보 탐지 | 신규 2종 |
| 분할·저장 | 문서 분할, RAG 저장 | 신규 2종 |
| 품질·제어 | 품질 검증, 조건 분기, 병합 | 품질 신규 / 분기·병합 기존 |
| 분석 (선택) | 분류, 개체 추출, 키워드 추출, 요약, 검증, 후처리, 출력 | 기존 유지 |

기존 `input`(입력) 블록은 **텍스트 추출 블록으로 흡수·폐기**한다(입력 = 파일 검증이 시작점). 기존 `preprocess` 블록은 **텍스트 정제 블록으로 대체·폐기**한다.

### 3.2 블록 공통 규격 (설계서 13.1)

`BaseBlock`에 다음을 추가한다:

```python
class BaseBlock(ABC):
    block_type: str                 # 기존
    block_version: str              # 신규 — 캐시 키·이력 기록용 (예: "1.0.0")
    category: str                   # 신규 — 팔레트 그룹핑
    config_schema: type[BaseModel]  # 신규 — Pydantic 설정 스키마(저장 전 검증 + UI 폼 자동 생성)
    def run(self, context: BlockContext) -> BlockResult: ...
```

- `GET /workflows/block-types` 응답에 `category`, `block_version`, `config_schema`(JSON Schema)를 포함해 **프론트 팔레트/설정 폼이 백엔드 스키마에서 자동 생성**되도록 한다. (`frontend/src/lib/workflowBlocks.ts`의 수동 configFields 정의는 아이콘/색/도움말 등 표현 메타만 남기고, 필드 목록은 API 주도로 전환.)
- `BlockResult`에 `warnings: list[str]`, `metrics: dict`를 추가한다(품질 검증·모니터링 집계용).
- 타임아웃/재시도(`timeoutSeconds`, `retryCount`)는 블록 설정 공통 필드로 노출하고 실행기(Celery task)가 적용한다.

### 3.3 블록별 상세 규격

각 블록의 **입력/출력/설정(UI 폼 필드)/내부 구현 이관원**을 정의한다.

#### ① 파일 검증 (`file_validate`)
- **입력**: Document(원본 파일 참조)
- **출력**: 검증 리포트 `{passed, checks: [{name, ok, detail}]}` — 실패 시 블록 실패로 런 종료, Document.status=FAILED, 오류코드 매핑(§6)
- **설정**: `max_file_size_mb`(number), `allowed_extensions`(list), `reject_encrypted`(bool), `reject_duplicates`(bool — file_hash 중복), `max_pages`(number), `scan_malware`(bool, ClamAV 연동 여지)
- **구현 이관**: 현재 `documents.py` 업로드 엔드포인트의 확장자/크기 검사 + 신규(시그니처 대조, 암호화·손상·압축폭탄·빈파일 검사)

#### ② 형식 판별 (`format_detect`)
- **출력**: `{detected_file_type, detected_mime_type, is_scanned_document, has_text_layer, is_encrypted, confidence}` (설계서 4.2)
- **설정**: 없음(자동)
- **구현**: 확장자+MIME+파일 시그니처(magic bytes)+내부 구조 검사. `has_text_layer`/`is_scanned_document`는 PDF 첫 N페이지 샘플링으로 판정 — **후속 OCR 블록의 조건 분기 근거**

#### ③ 텍스트 추출 (`text_extract`)
- **출력**: 추출 텍스트 + 페이지/블록 구조 + 표 후보 + 이미지 영역 + page_map (아티팩트)
- **설정**: `extract_tables`(bool), `extract_images`(bool), `recognize_figures`(bool — VLM/Tesseract 그림 인식), `max_figures`(number)
- **구현 이관**: `parse_document`의 어댑터 호출부, `_repaginate_hwp_like`, `_recognize_document_images`, `_build_page_map`. Document에 `parsed_text`/`page_map`/`tables`/`images` 기록 + `DocumentTextRevision(source="PARSE")` 생성은 이 블록이 수행

#### ④ OCR (`ocr`)
- **출력**: OCR 텍스트 블록(좌표·신뢰도·엔진·버전 포함, 설계서 6.3) — 텍스트 추출 결과에 병합
- **설정**: `force_ocr`(bool), `engine`(select: tesseract/cloud_vlm/auto), `language`(select: ko/en/ko+en), 이미지 보정 토글(`deskew`, `denoise`, `contrast`, `grayscale`), `min_confidence`(number — 미달 페이지는 경고)
- **구현 이관**: `pdf_adapter.py`의 OCR 경로 + `_resolve_vision_credentials`
- **연결 규칙**: 표준 워크플로우에서 형식판별→조건분기(`has_text_layer == false` 또는 `force_ocr`)→OCR로 구성. 설계서 6.1의 "추출량 미달/깨짐 비율" 조건은 텍스트추출 블록이 출력에 지표를 실어 분기 조건으로 사용

#### ⑤ 구조 분석 (`structure_analyze`)
- **출력**: DocumentNode 트리(§4.2) — DB 저장 + 아티팩트
- **설정**: `detect_headings`(bool), `heading_max_level`(number), `detect_lists`(bool), `detect_toc`(bool), `use_font_signals`(bool — 글자 크기/굵기 기반), `preserve_clause_number`(bool — 법률문서용)
- **구현**: 신규. 어댑터의 blockType(paragraph/table/image) + 스타일 신호(글꼴 크기·굵기·번호 체계·들여쓰기)로 HEADING/PARAGRAPH/LIST/TABLE/… 노드 생성, parsed_text 문자 오프셋(span)을 노드마다 기록해 **원문 역추적의 근간**으로 삼는다

#### ⑥ 텍스트 정제 (`text_clean`)
- **출력**: 정제 텍스트(아티팩트) + 노드 단위 변경 이력(CleaningChange, §4.3)
- **설정**: `collapse_whitespace`(bool), `normalize_unicode`(bool — NFC), `normalize_quotes`(bool), `normalize_width`(bool — 전각/반각), `remove_control_chars`(bool, 항상 권장), `remove_repeated_headers`(bool — 페이지 반복 머리말/꼬리말/페이지번호 제거), `fix_ocr_errors`(bool — 자모분리/줄바꿈 단어 결합), `custom_rules`(정제 규칙 테이블 참조 — §4.3의 CleaningRule 중 enabled 항목 적용)
- **원칙**: 원문(`parsed_text`)은 불변. 정제 결과는 별도 아티팩트 + `DocumentTextRevision(source="CLEAN")`. 노드 span 오프셋은 정제 전 기준으로 유지하고, 정제 후 텍스트에는 노드별 재계산 span을 병기(원문 대조 하이라이트용)

#### ⑦ 불용어 처리 (`stopword`)
- **출력**: 불용어 마킹 결과(위치·사전항목ID·사전버전) — 기본 동작은 **삭제가 아닌 분석 제외 표시**(설계서 9.2)
- **설정**: `action`(select: mark/exclude_from_analysis/remove), `scope_filter`(list — dictionary scope 필터)
- **데이터 소스**: `dictionary_entries(entry_type=stopword)` + 사전 버전(§5)

#### ⑧ 동의어 정규화 (`synonym`)
- **출력**: 정규화 텍스트 + 적용 항목 목록(원문 표현/대표 표현/오프셋/사전ID/버전 — 설계서 9.6)
- **설정**: `processing_mode`(select: normalize/tag_only — dictionary의 processing_mode 존중 여부), `case_sensitive_default`(bool)
- **데이터 소스**: `dictionary_entries(entry_type=synonym)` + variants

#### ⑨ 사용자 사전 적용 (`user_dict`)
- **출력**: 도메인 용어 인식·정규화 결과(적용 이력 동일 구조)
- **설정**: `term_types`(multiselect — ORGANIZATION/PRODUCT/…), `protect_from_stopwords`(bool, 기본 true)
- **적용 순서 강제**: 표준 워크플로우는 설계서 9.5 순서(사용자 사전 보호 → 동의어 → 불용어)를 기본 배치로 제공. 그래프 검증(§7.3)이 순서 위반 시 경고

#### ⑩ 민감정보 탐지 (`pii_detect`)
- **출력**: PiiDetection 레코드(§4.5) + 정책 적용된 텍스트(마스킹 시)
- **설정**: `entity_types`(multiselect: 주민등록번호/전화번호/이메일/계좌번호/카드번호/주소/이름/사번/…), `action`(select: mark_only/mask/tokenize/remove/exclude_from_embedding), `mask_char`(text), `require_admin_approval`(bool — REVIEW_REQUIRED로 격상)
- **구현**: 1차 정규식 엔진(주민번호/전화/이메일/계좌/카드 등 한국형 패턴) + 검증 로직(체크섬), 이름/주소는 사용자 사전 termType + NER(로컬 LLM) 보조. 탐지 신뢰도 기록

#### ⑪ 문서 분할 (`chunk_split`)
- **출력**: DocumentChunk 행(§4.6) + 아티팩트
- **설정**: `strategy`(select: fixed/sentence/paragraph/section_aware/semantic/table_unit — 설계서 11.2 전체), `max_tokens`/`min_tokens`/`overlap_tokens`(number), `preserve_table`(bool), `preserve_heading`(bool), `include_previous_heading`(bool), `split_long_paragraph`(bool)
- **구현 이관**: `_chunk_text`(fixed), `_chunk_text_semantic`(semantic) + 신규(sentence/paragraph/section_aware — 구조 트리 기반, table_unit). 컬렉션의 기존 chunk 설정(`chunk_strategy`, `chunk_*_tokens`)은 **블록 설정의 기본값 소스**로만 쓰고, 실제 실행값은 블록 config가 우선
- **section_aware**: 구조 분석 블록의 노드 트리를 소비 — sectionPath/sourceNodeIds를 청크에 기록

#### ⑫ 품질 검증 (`quality_check`) — 검토 게이트 겸용
- **출력**: QualityReport(§4.7) — 파일/텍스트/구조/사전/분할 수준 지표(설계서 12.2) + 상태(SUCCESS/SUCCESS_WITH_WARNING/REVIEW_REQUIRED/PARTIAL_FAILURE/FAILURE)
- **설정**: 임계값 세트(`min_extraction_chars`, `max_broken_char_ratio`, `min_ocr_confidence`, `max_empty_page_ratio`, `min_chunk_tokens_warning`, …), `review_policy`(select: **auto_pass / review_on_warning / always_review**), `fail_below_score`(number)
- **검토 게이트**: `review_policy` 결과가 검토 필요이면 **런 상태를 `WAITING_REVIEW`로 전환하고 후속 블록을 enqueue하지 않는다.** 사용자가 검토 화면(§9)에서 승인(또는 수정 후 승인)하면 다음 블록부터 재개. — 기존 `REVIEW_PENDING` + `continue_processing(edited_text)` 게이트를 일반화하여 대체

#### ⑬ RAG 저장 (`rag_store`)
- **출력**: 저장 결과 `{points_upserted, collection, embedding_model, dimension}`
- **설정**: `embedding_model`(select — 컬렉션 기본값 상속), `exclude_pii`(bool — pii action=exclude_from_embedding 청크 제외), `store_masked_text`(bool)
- **구현 이관**: `continue_processing`의 임베딩·Qdrant 업서트부. **선행 삭제(delete_by_document) 포함.** Qdrant payload에 `chunk_id`(DB FK), `workflow_run_id`, `dictionary_version`, `pipeline_version`을 추가해 추적성 확보. Document.status=INDEXED 전환도 이 블록이 담당

#### ⑭~⑳ 분석 블록 (기존 유지)
- `classify`/`extract_entities`/`extract_keywords`/`summarize`/`validate`/`postprocess`/`output` — 현행 유지하되:
  - 입력을 "가장 가까운 상류 텍스트"에서 **정제·정규화 텍스트 아티팩트 우선**으로 변경(전처리 뒤에 붙으면 정제본을 분석)
  - `output` 블록의 문서 메타데이터 기록(요약/추천태그) 동작 유지 — 표준 워크플로우 후미에 요약+키워드+출력을 포함해 기존 자동 요약/태그 동작을 보존

#### 제어 블록 (기존 유지)
- `branch`/`merge` — 현행 유지. 표준 워크플로우의 OCR 분기에 사용

## 5. 사전 버전 관리 설계

- `dictionary_entries` 모든 쓰기 경로(`dictionary_service`, API)가 트랜잭션 내에서 `dictionary_revisions`에 1행을 추가하고 전역 버전을 +1 한다.
- 워크플로우 런 시작 시 현재 전역 버전을 `workflow_runs.dictionary_version`에 고정. 사전 블록은 이 버전 시점 기준으로 항목을 읽는다.
  - 구현 단순화: 항목별 이력 테이블 대신 **"버전 N 시점 유효 항목" 판정을 `dictionary_entries.updated_at ≤ revision N.created_at ∧ (삭제 이력 없음)`으로 근사**하되, DELETE는 soft-delete(`enabled=false` + revision 기록)로 전환해 재현성을 보장한다.
- 사전 수정 → 영향받는 문서 탐지: `dictionary_applications`에서 entry_id 역참조 → 부분 재처리 제안(§8).
- BM25 토크나이저(`dictionary_service`)는 현행 유지 — 같은 테이블을 공유하되 항상 최신 버전 사용(검색측은 재현성 불요).

## 6. 오류 처리 (설계서 18장)

- 오류 코드 체계 도입: `FILE_UNSUPPORTED / FILE_CORRUPTED / FILE_ENCRYPTED / TEXT_EXTRACTION_FAILED / OCR_FAILED / STRUCTURE_ANALYSIS_FAILED / CLEANING_RULE_ERROR / DICTIONARY_CONFLICT / CHUNK_SIZE_EXCEEDED / QUALITY_THRESHOLD_FAILED / STORAGE_FAILED / WORKFLOW_TIMEOUT` — `WorkflowRunStep.error_code` 컬럼, 프론트는 코드별 한국어 안내문 매핑.
- 재시도 정책: 블록 설정 `retryCount`(기본 2)·`timeoutSeconds`(기본 300)를 실행기가 적용. **영구 오류(FILE_UNSUPPORTED/FILE_ENCRYPTED)는 즉시 실패** — 현재 `parse_document`의 UnsupportedFileTypeError 즉시 실패 패턴을 일반화.
- 실패 격리(18.3): 페이지 단위 처리 블록(OCR/추출)은 페이지별 오류를 `metrics.failed_pages`로 수집하고 블록 자체는 성공 처리 → 품질 검증이 `PARTIAL_FAILURE` 판정 → 검토 게이트에서 실패 페이지만 선택 재처리(§8) 가능.

## 7. 실행기 확장

### 7.1 기존 유지
`tasks/workflow.py`의 DAG 워커(블록 실행 → 출력 조건으로 에지 평가 → 다음 블록 enqueue, 병합 카운터) 구조는 그대로 쓴다.

### 7.2 Document.status 파생 매핑

실행기가 스텝 시작 시 문서 상태를 갱신한다 (설계서 17.3):

| 실행 중 블록 | Document.status |
|---|---|
| file_validate, format_detect | VALIDATING |
| text_extract | PARSING |
| ocr | PARSING (job 메시지로 구분) |
| structure_analyze | STRUCTURING |
| text_clean | REFINING |
| stopword/synonym/user_dict | NORMALIZING |
| pii_detect | MASKING |
| chunk_split | CHUNKING |
| quality_check | VALIDATING → (게이트 시) WAITING_REVIEW |
| rag_store | EMBEDDING → UPLOADING → INDEXED |
| 분석 블록 | (상태 변경 없음 — INDEXED 유지) |

### 7.3 그래프 검증 확장 (`workflow_service.validate_graph`)

기존 검증(사이클/고아 블록/필수 설정)에 추가:
- **전처리 워크플로우 필수 규칙**: 컬렉션 기본으로 지정하려면 `file_validate`로 시작하고 `rag_store`를 정확히 1개 포함해야 한다(분석 전용 워크플로우는 제약 없음 — `workflow_definitions.kind ENUM(PREPROCESS/ANALYSIS)` 컬럼으로 구분).
- 순서 제약: `text_extract`는 `format_detect` 하류, `chunk_split`은 `text_clean` 하류, `rag_store`는 `chunk_split`+`quality_check` 하류 등 — 블록별 `requires_upstream: set[str]` 선언으로 일반화.
- 사전 순서 경고(§3.3⑨): user_dict가 stopword보다 하류이면 경고(오류 아님).

### 7.4 검토 게이트 재개 프로토콜

```
quality_check 판정 REVIEW_REQUIRED
  → run.status = WAITING_REVIEW, document.status = WAITING_REVIEW
  → 알림(§12) 발행, 후속 enqueue 중단

사용자 검토 화면에서:
  a) 승인               → POST /workflows/runs/{id}/resume            → 다음 블록부터 재개
  b) 수정 후 승인       → (텍스트/노드/청크 수정 API로 보정 레이어 기록)
                        → resume 시 영향 블록부터 재실행(§8 재처리 로직 재사용)
  c) 반려(폐기)         → POST /workflows/runs/{id}/cancel            → run CANCELLED, document FAILED(사유 기록)
```

## 8. 부분 재처리 설계 (설계서 15장)

### 8.1 재처리 범위 계산

- 블록 의존성 = 발행된 버전의 DAG에서 시작 블록의 **하류 폐포(downstream closure)**.
- 요청: `POST /documents/{id}/reprocess {start_block_type | start_block_instance_id, reason}` 또는 사전/규칙 수정 이벤트에서 영향 문서 일괄 제안.
- 매핑 규칙(설계서 15.2)은 별도 하드코딩 없이 DAG로 자연 도출된다:
  - 사전 수정 → 해당 사전 블록부터 하류 재실행 (동의어 수정이면 synonym→…→chunk_split→quality_check→rag_store)
  - 청크 설정 수정 → chunk_split부터
  - 품질 기준 수정 → quality_check부터

### 8.2 실행 방식

- 새 `WorkflowRun(trigger=REPROCESS, parent_run_id=원본, started_block_id=시작점)` 생성.
- 시작점 상류 스텝들은 원본 런의 아티팩트/해시를 복사해 `cached=true`로 즉시 COMPLETED 처리(§2.4 캐시로 구현).
- 시작점부터 정상 실행. rag_store는 문서 단위 delete→재업서트(전체) 또는 영향 청크만 갱신(노드 범위 지정 시).
- `targetNodeIds` 지정 시(설계서 20.5): 사전/정제 블록이 해당 노드만 재처리하고 나머지는 이전 결과 병합 — chunk_split은 영향 노드가 속한 청크 경계만 재계산.

## 13. 구현 순서 (의존성 기준 — 범위 축소 아님)

전 범위를 구축하되, 의존성이 강제하는 빌드 순서만 정의한다.

1. **데이터 모델 + 마이그레이션** (§4 전체, 사전 revision §5) — 모든 것의 토대
2. **블록 공통 규격 확장** (config_schema/block_version/category, 아티팩트 저장, BlockContext 확장) + 실행기 확장(상태 파생, 캐시, WAITING_REVIEW, error_code)
3. **입력·추출 블록 4종** (기존 parse_document 분해 이관) — 이 시점에 업로드→워크플로우 전환 스위치 온, 고정 파이프라인 제거
4. **정제·정규화 블록 4종** + 정제 규칙 CRUD + 사전 버전 연동
5. **구조 분석·민감정보 블록**
6. **분할·저장 블록** (document_chunks 승격, rag_store) + 기존 청크 수정 재배선
7. **품질 검증 블록 + 검토 게이트** (기존 REVIEW_PENDING 게이트 대체)
8. **부분 재처리** (§8) + 영향도 API
9. **프론트엔드**: 에디터 팔레트/폼 재편 → 문서 상세 탭 재편(원문대조/구조/정제/사전/민감정보/청크/품질/이력) → 컬렉션 설정 → 업로드 흐름 → 사전 영향 제안 → 관리 대시보드
10. **표준 워크플로우 시드 + 기존 문서 마이그레이션**(§14) + 버그 3종 검증(§11)
11. **테스트**: 블록 단위(설정 조합), 실행기(게이트/캐시/부분 재처리), E2E(업로드→검토→INDEXED→검색)

각 단계는 TDD(테스트 선행) + 코드 리뷰 후 다음 단계 진행.

## 14. 기존 데이터 마이그레이션

- **표준 전처리 워크플로우 시드**: 마이그레이션에서 시스템 소유 `PREPROCESS` 워크플로우 v1 published 생성 — 블록: 파일검증→형식판별→텍스트추출→분기(has_text_layer=false→OCR)→병합→구조분석→텍스트정제→사용자사전→동의어→불용어→민감정보(마킹만)→문서분할(컬렉션 기본값)→품질검증(review_on_warning)→RAG저장→요약→키워드→출력. 현재 자동 동작과 최대한 등가.
- **기존 INDEXED 문서**: parsed_text/page_map/tables/images 유지. Qdrant payload를 스캔해 `document_chunks` 역생성(chunk_id=point id, chunk_text=payload.text, page 정보 이전). 구조 트리/정제 이력/품질 리포트는 없음(null) — 재처리 시 생성됨을 UI에 안내.
- **진행 중 문서**: 마이그레이션 시점에 QUEUED/PARSING 등 중간 상태 문서는 FAILED(사유: 시스템 전환)로 마킹하고 일괄 재처리 제안.
- 기존 `processing_jobs` 테이블·job 타임라인 UI는 스텝 타임라인으로 대체 후 테이블 유지(과거 이력 열람용, 신규 기록 중단).

## 15. 리스크

| 리스크 | 대응 |
|---|---|
| 고정 파이프라인 제거 → 회귀 범위 큼 | 표준 워크플로우를 현행 동작과 등가로 시드하고, 전환 직후 기존 E2E(업로드→INDEXED→검색) 통과를 게이트로 삼음 |
| 아티팩트 저장 도입으로 실행기 복잡도 상승 | BlockContext에 로드/저장 헬퍼로 캡슐화, 블록 코드는 dict 입출력 유지 |
| 사전 버전 근사 방식의 재현성 한계 | soft-delete + updated_at 기준 근사를 명시하고, 필요 시 항목 스냅샷(revision.snapshot_key)로 보강 |
| 의미 분할·NER 등 모델 의존 블록의 비용 | 캐시(§2.4)로 동일 입력 재계산 방지, 블록 설정으로 opt-in |
| 문서·청크·노드 대량 행 증가 | 노드 text는 요약 저장+아티팩트 원본, cleaning_changes 표본화, 인덱스 설계(document_id, run_id) |
