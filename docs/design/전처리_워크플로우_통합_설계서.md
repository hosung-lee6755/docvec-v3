## 0. 결정 사항 (2026-07-16 확정)

| 항목 | 결정 |
|---|---|
| 통합 방식 | 고정 파이프라인을 워크플로우 실행으로 대체한다. 업로드 시 컬렉션에 지정된 전처리 워크플로우가 자동 실행된다. 다만 청크와 임베딩만 다시 만드는 레거시 경로(`continue_processing`)는 일부 API에 남아 있다(§2.1). |

## 1. 현황 진단

> 이 절은 설계 착수 시점(2026-07-16)의 진단이다. 현재 구현 상태는 §1.4를 본다.

### 1.1 두 개의 분리된 처리 경로

설계 착수 당시 문서 처리 경로는 2개였고 서로 연결되어 있지 않았다.

**경로 A: 고정 파이프라인** (`tasks/pipeline.py`, `tasks/process.py`)

```
업로드 → ingest_document → parse_document → [REVIEW_PENDING 게이트] (설계 당시 흐름. 현재 워크플로우 경로의 검토 게이트는 WAITING_REVIEW다)
       → continue_processing (청크 분할 → _clean_rag_text 정제 → 임베딩 → Qdrant)
       → generate_summary / extract_metadata (비동기 후속)
```

- 사용자가 순서나 설정을 구성할 수 없는 하드코딩 체인이었다.
- 정제는 제어 문자와 공백 정규화 정도만 수행했다.
- 사전(불용어, 동의어, 사용자 사전)은 BM25 토크나이저에만 쓰였고 RAG 저장 데이터에는 적용되지 않았다.

**경로 B: 워크플로우** (`pipeline/blocks/`, `tasks/workflow.py`)

- 입력에서 전처리, 분류, 요약, 키워드, 개체 추출, 검증, 출력으로 이어지는 DAG였다.
- 이미 파싱된 문서의 `parsed_text`를 읽어 요약과 태그를 문서 메타데이터에 기록했다.
- 청크, 임베딩, Qdrant에는 전혀 개입하지 않았다. 워크플로우의 전처리 블록에서 텍스트를 정제해도 RAG 검색 결과는 변하지 않았다.

- 부분 재처리(15장)가 없었다. 전체 재처리만 가능했다.

## 2. 목표 아키텍처

### 2.1 전체 흐름

```
문서 업로드 (POST /api/v1/documents/upload, ZIP은 POST /api/v1/documents/upload-zip)
  → 원본 저장 (MinIO originals) + Document 행 생성                  [엔드포인트 책임]
  → 컬렉션의 기본 전처리 워크플로우 결정 (요청의 workflow_version_id가 있으면 우선)   [엔드포인트 책임]
  → WorkflowRun 생성 + 첫 블록 enqueue                             [이후 블록 실행은 워크플로우 책임]

워크플로우 (시스템 기본 "표준 전처리"의 현재 구성):
  [파일 검증] → [형식 판별] → [텍스트 추출] → [구조 분석] → [텍스트 정제]
  → [사용자 사전 적용] → [동의어 정규화] → [불용어 처리] → [민감정보 탐지]
  → [문서 분할] → [품질 검증(검토 게이트)] → [RAG 저장]
```

표준 워크플로우에는 OCR 블록과 조건 분기가 없다. OCR은 텍스트 추출 어댑터가 페이지 단위로 자동 수행한다(§3.3④). 요약, 키워드, 출력 블록은 표준 워크플로우에서 제외되었다(마이그레이션 `f1a3c5e7b9d1`). 분석은 §7.5의 분석 워크플로우 또는 기본 요약, 태그 태스크가 맡는다.

설계에서 제거하기로 한 항목의 현재 상태는 다음과 같다.

- `tasks/pipeline.py`와 `tasks/ingest.py`는 제거되었다.
- `tasks/process.py`는 제거되지 않았다. `parse_document`만 사라졌다. `continue_processing`(청크 분할, 정제, 임베딩, Qdrant 업서트를 한 번에 수행하는 레거시 경로)과 청크, 표, 그림 처리용 헬퍼 함수는 남아 있다. 블록 구현은 이 헬퍼를 가져다 쓴다.
- 레거시 `continue_processing`은 다음 API에서 여전히 호출된다. `POST /collections/{id}/reprocess`(청크와 임베딩만 다시 만들기), `POST /documents/{id}/proceed`(검토 대기 상태 문서의 진행), `POST /documents/{id}/reprocess`(시작 블록 없이 edited_text만 보낸 경우), 문서 버전 복원(`POST /documents/{id}/revisions/{revision_id}/restore`).
- `tasks/summary.py`와 `tasks/metadata.py`의 자동 트리거는 2026-11-20에 제거되었다. 분석 워크플로우가 지정되지 않은 컬렉션의 문서는 시스템 표준 분석 워크플로우로 분석한다(§7.5). 워크플로우 밖의 레거시 처리(`continue_processing`: 컬렉션의 청크와 임베딩만 다시 만들기, 검토 대기 문서 진행, 버전 복원)도 끝나면 같은 함수(`start_auto_analysis`)로 분석한다. 두 태스크를 부르는 코드는 더 이상 없다.
- Document.status는 워크플로우 실행기가 블록 시작 시점에 갱신한다(§7.2). 레거시 경로는 여전히 상태를 직접 기록한다.

### 2.2 컬렉션 ↔ 워크플로우 바인딩

```
Collection
  + default_workflow_id        (FK workflow_definitions, nullable)
  + default_workflow_version   (int | null, null이면 실행 시점의 최신 게시 버전)
  + default_analysis_workflow_id, default_analysis_workflow_version
                               (설계 이후 추가. 전처리 완료 뒤 자동 실행할 분석 워크플로우)
```

- 컬렉션에 지정이 없으면 시스템 기본 워크플로우(마이그레이션으로 시드된 "표준 전처리", ACTIVE)를 쓴다.
- 업로드 API는 `workflow_version_id` 폼 필드로 1회성 버전 오버라이드를 받는다. 설계의 `workflow_id`, `workflow_version` 파라미터는 이 이름으로 구현되었다. 오버라이드 대상은 PREPROCESS 종류 워크플로우여야 한다(`upload.py`).
- 시스템 기본 워크플로우는 삭제(409)와 비활성화(409)가 모두 막혀 있다(`workflows/definitions.py`). 다른 워크플로우를 기본으로 지정한 뒤에만 가능하다는 설계 의도와 같다.
- 컬렉션 설정 화면에는 재처리 동작이 두 개 있다. "처음부터 다시 처리"(`POST /collections/{id}/reprocess-from-start`)는 문서마다 워크플로우 최신 게시 버전으로 새 실행을 만든다. "청크·임베딩만 다시 만들기"(`POST /collections/{id}/reprocess`)는 이미 추출된 텍스트를 레거시 경로로 다시 자른다. 설계의 "기존 reprocess 동작 대체"는 아직 완료되지 않았고, 레거시 동작이 그대로 남아 있다.

### 2.3 실행 데이터 흐름: 아티팩트 저장소

실행기는 블록 출력을 `WorkflowRunStep.output`에 저장한다. 출력의 직렬화 크기가 16,000바이트(`_ARTIFACT_INLINE_THRESHOLD_BYTES`) 이하이면 출력 전체를 그대로 저장한다. 초과하면 MinIO artifacts 버킷에 `runs/{run_id}/{step_id}/output.json`으로 올리고 DB에는 참조만 남긴다.

```json
// 인라인 저장 (16,000바이트 이하): output에 블록 출력 전체가 들어간다.
// 아티팩트 저장 (초과): output에는 참조만 들어가고 artifact_key 컬럼에도 같은 키가 기록된다.
{"artifact": "runs/RUN-1/STEP-7/output.json", "output_hash": "sha256:…", "_artifact_only": true}
```

- 모든 스텝은 `input_hash`와 `output_hash`(SHA-256)를 기록한다.
- 블록 간 전달은 실행기가 상류 스텝의 출력을 모두 읽어 `BlockContext.upstream_outputs`에 넣는 방식이다. 아티팩트는 이때 바로 내려받아 복원하므로 lazy 로드가 아니다.
- `BlockContext.load_artifact(ref)` 헬퍼는 다른 런의 아티팩트를 명시적으로 읽기 위해 준비되었지만, 현재 블록 코드에서 호출하는 곳은 없다.

### 2.4 실행 캐시 (설계서 21.2)

캐시 키는 다음 값을 이어 붙인 SHA-256 해시다.

- 문서 ID (`document_id`)
- 상류 스텝 입력 해시 (`input_hash`)
- 블록 타입과 블록 버전
- 블록 설정 해시
- 원본 파일 해시 (`file_hash`). 같은 문서의 원본이 교체되어도 이전 내용의 캐시를 쓰지 않게 한다.

여기에 두 값이 조건부로 더해진다. 사전 버전(`dictionary_version`)은 사전 블록(stopword, synonym, user_dict, pii_detect)에만 포함되고, 검토 생략 여부(`skip_review`)는 quality_check에만 포함된다. **모델 버전은 캐시 키에 포함되지 않는다.** 설계서의 "모델 버전(LLM, 임베딩 블록만)" 항목은 구현되지 않았다.

캐시 대상은 화이트리스트(`_CACHE_SAFE_BLOCK_TYPES`)로 제한된다. 현재는 `file_validate`, `format_detect`, `text_extract` 세 블록만 캐시한다. 이유는 다음과 같다. 나머지 블록은 실행 런 ID로 범위가 정해진 행(DocumentNode, CleaningChange, PiiDetection, DocumentChunk 등)을 만든다. 캐시 히트 시 이전 런의 아티팩트를 재사용하면서도 현재 런의 행은 만들지 않아, 구조, 정제 비교, 사전 적용, 민감정보 탭이 비는 버그가 있었다(2026-07-25 확인). 새 블록 타입은 명시적으로 추가하기 전까지 캐시되지 않는다(기본 차단 원칙).

- 캐시 히트 시 스텝은 `COMPLETED`, `cached: true`로 기록되고 블록은 실행되지 않는다.
- 캐시 엔트리에는 `requires_review` 값도 저장되며, 히트 시에도 검토 게이트 판정에 쓰인다.
- 부분 재처리의 상류 재사용은 이 캐시를 거치지 않는다. 재처리 시작 시 원본 런의 상류 스텝 상태, 출력, 아티팩트 키를 새 런에 복사하고 `cached=true`로 표시한다(§8.2).

## 3. 블록 카탈로그

### 3.1 카테고리 구성

| 카테고리 | 블록 | 구현 상태 |
|---|---|---|
| 입력·추출 | 파일 검증, 형식 판별, 텍스트 추출, OCR | 파일 검증, 형식 판별, 텍스트 추출은 구현됨. OCR은 자리표시자다(§3.3④). |
| 정제·정규화 | 텍스트 정제, 불용어 처리, 동의어 정규화, 사용자 사전 적용 | 구현됨 |
| 구조·보호 | 구조 분석, 민감정보 탐지 | 구현됨. 민감정보 탐지의 NER 보조는 미구현이다. |
| 분할·저장 | 문서 분할, RAG 저장 | 구현됨 |
| 품질·제어 | 품질 검증, 조건 분기, 병합 | 품질 검증은 구현됨. 조건 분기와 병합은 기존 구현을 유지하며 표준 워크플로우에는 포함되지 않는다. |
| 분석 (선택) | 분류, 개체 추출, 키워드 추출, 요약, 검증, 후처리, 출력 | 기존 구현을 유지한다. |

기존 `input`(입력) 블록은 설계에서 텍스트 추출 블록으로 흡수하기로 했다. 현재 `input`과 `preprocess` 블록은 레지스트리에 레거시 카테고리로 남아 있고, 전처리 팔레트에는 표시되지 않는다.

### 3.2 블록 공통 규격 (설계서 13.1)

`BaseBlock`의 현재 구조는 다음과 같다.

```python
class BaseBlock(ABC):
    block_type: str                              # 블록 타입 이름
    block_version: str                           # 캐시 키와 이력에 쓰인다. 기본값 "1.0.0"이며 블록이 재정의한다.
    category: str                                # 팔레트 그룹. 구체 블록은 반드시 정의한다.
    config_schema: type[BaseModel] | None        # Pydantic 설정 스키마(저장 전 검증, UI 폼 생성에 사용)
    def run(self, context: BlockContext) -> BlockResult: ...
```

- `GET /workflows/block-types` 응답에는 `block_type`, `block_version`, `category`, `label`, `config_schema`(JSON Schema)가 포함된다.
- 프론트엔드 설정 폼은 두 방식이 공존한다. `frontend/src/lib/workflowBlocks.ts`에 하드코딩된 `configFields`가 있으면 그것을 쓰고, 없는 블록은 API의 `config_schema`를 `lib/blockConfigSchema.ts`로 변환해 쓴다. 필드 목록을 API 주도로 완전히 전환하지는 않았다.
- `BlockResult`는 `output`, `warnings`, `metrics`, `requires_review`를 가진다. `requires_review`가 참이면 실행기가 런을 WAITING_REVIEW로 전환한다.
- 블록 설정의 `retryCount`(기본 2)와 `timeoutSeconds`를 실행기가 적용한다. 시간 제한의 기본값은 설계 초안의 300초가 아니라 1800초다(`tasks/workflow.py`). 런마다 시간 제한을 덮어쓰는 `timeout_overrides`도 있다.

### 3.3 블록별 상세 규격

각 블록의 입력, 출력, 설정, 구현 내용을 코드 기준으로 정리한다. 설정 기본값은 블록의 Config 클래스를 따른다.

#### ① 파일 검증 (`file_validate`)

- **입력**: Document(원본 파일 참조)
- **출력**: 검증 리포트 `{passed, checks: [{name, ok, detail}]}`. 검사에 실패하면 블록이 실패하여 런이 종료되고 문서가 FAILED가 된다.
- **설정**: `max_file_size_mb`(기본 100), `allowed_extensions`(허용 확장자 목록), `reject_encrypted`(기본 참), `reject_duplicates`(기본 참), `max_pages`(기본 1000), `scan_malware`(기본 거짓)
- **실제 검사 항목**: 확장자(`extension`), 파일 크기(`file_size`), 중복(`duplicate`, 파일 해시 기준), 쪽 수(`max_pages`, PDF만 해당), 악성코드(`malware_scan`). 암호화 여부는 이 블록이 아니라 형식 판별 블록이 검사한다.
- **미구현**: `scan_malware`는 자리표시자라서 켜도 항상 통과한다. ClamAV 연동은 없다. 시그니처 대조, 손상 파일, 압축 폭탄, 빈 파일 검사는 구현되지 않았다.

#### ② 형식 판별 (`format_detect`)

- **출력**: `detected_file_type`, `detected_mime_type`, `is_scanned_document`, `has_text_layer`, `is_encrypted`, `confidence`
- **설정**: 없음(자동)
- **구현**: 형식은 어댑터 선택 결과(확장자 기준)로 정하고, MIME 타입은 업로드 때 저장된 값을 그대로 쓴다. 파일 시그니처(magic bytes) 대조는 하지 않는다. PDF는 첫 몇 쪽을 pdfplumber로 샘플링해 텍스트 층 유무, 스캔 여부, 암호화 여부를 판정한다. DOCX, HWP, HWPX는 텍스트 층이 있는 것으로 간주한다.
- **OCR 분기 근거**: `has_text_layer`는 설계상 OCR 분기 조건이다. 표준 워크플로우에는 분기가 없어 현재는 분기 근거로 쓰이지 않는다.

#### ③ 텍스트 추출 (`text_extract`)

- **출력**: 추출 텍스트(`parsed_text`), 쪽 매핑(`page_map`), 표, 그림 정보를 Document에 기록한다. `DocumentTextRevision(source="PARSE")`도 이 블록이 만든다.
- **설정**: `extract_tables`(기본 참), `extract_images`(기본 참), `recognize_figures`(기본 참), `max_figures`(기본 40), `exclude_headers_footers`(기본 참), `detect_implicit_tables`(기본 참), `extract_font_signals`(기본 참), `engine`(기본 auto), `scan_layout`(기본 참)
- **구현**: `TextExtractBlock`(block_version 1.38.0). 어댑터 호출, HWP 재페이지네이션, 그림 인식, page_map 생성을 포함한다. 쪽 단위 OCR도 이 어댑터 안에서 페이지별 텍스트 커버리지를 기준으로 자동 수행된다. Docling 레이아웃과 EasyOCR이 GPU를 쓰므로 `extract` 큐에서 실행된다. 버전별 변경 이유는 `block_version` 주석에 적는다.
- **그림 글의 저신뢰 줄 제외**(1.38.0, 2026-11-23): Tesseract로 읽은 그림 글은 줄마다 단어 신뢰도 평균을 `image_to_data`로 재고, 40 미만인 줄을 뺀다(`ocr_cleanup.drop_low_confidence_lines`). `image_to_string`의 빈 줄이 아닌 줄과 `image_to_data`의 줄은 순서대로 1:1로 맞는다(표본 그림 67개 모두 일치). 줄 수가 다르면 맞댈 수 없으므로 그대로 둔다. 기존 낱말·숫자 비율 기준(`figure_text_for_body`)은 "wise waso22 45"처럼 실제 영어 낱말과 숫자가 섞인 잡음을 통과시켰다. 전체 문서 그림 1,871줄을 다시 재 보니 40 미만이면서 비율 기준을 통과한 264줄은 거의 모두 잡음이었고, 40~50 구간은 정상 줄과 섞여 있었다. 그래서 기준을 40으로 잡았다. 영어 낱말 최소 길이를 5자로 올리는 방법도 시험했지만 "Step 1", "Card", "SLAB" 같은 정상 글자까지 빠져 쓰지 않았다.
- **2026-11-20 감사 반영**
  - Word 문서는 제목 스타일("Heading N", "Title", "제목 N")과 개요 수준으로 제목 단계를 넘긴다. 글자 크기를 직접 주지 않은 Word 제목이 본문 문단이 되던 문제를 고쳤다.
  - HTML은 "맨 위로" 같은 쪽 안 이동 링크를 버리고, 접는 영역 제목(`<summary>`)의 칸 사이를 띄운다.
  - Docling PDF는 본문 글을 원본 글자 층(pdfplumber)의 같은 영역 글과 견준다(`native_spacing.choose_spacing`). 두 글의 글자가 같으면 띄어쓰기가 덜 깨진 쪽을 쓴다("텅레 일의", "V oluntary"). 한글은 같은 순서로 모두 같은데 Docling이 숫자와 기호를 옮기거나 빠뜨렸으면 원본 글을 쓴다("가 에너지원별 사용량 ." → "가. 에너지원별 사용량", "대 가" → "2대(75HP/1, 30HP/1)가"). 옆 글이 섞여 한글이 늘거나 순서가 바뀐 경우, 수식 글꼴 글리프(유니코드 사용자 정의 영역)가 있는 경우, Docling 글의 "CO2" 같은 영문+숫자 묶음이 원본에 그대로 없는 경우(원본 글자 층이 아래첨자를 줄 뒤로 보낸다)에는 Docling 글을 둔다. 원본 글자 층의 글자 위치는 PyMuPDF로 읽고 글 조립(공백, 줄 나눔)은 pdfplumber 방식을 따른다. 처음에는 pdfplumber로 요소마다 영역을 읽었는데, 쪽 해석 비용 때문에 기계설비 매뉴얼(글 요소 6천여 개)의 추출이 430초에서 시간 제한 1800초를 넘겼다. 다섯 문서 표본에서 대조 결과는 같았고, 이 문서의 대조 시간은 약 320초에서 5초로 줄었다.
  - Docling 그림 영역은 그림 요소와 같은 id를 갖는다. 그림 인식 글("[그림 N] …") 블록이 이 id를 이어받아, 그림 요소가 본문 위치와 글을 얻고 구조 노드를 거쳐 청크에 들어간다. 예전에는 그림 요소에 위치가 없어 그림 속 글이 본문에는 있어도 청크에서 빠졌다(디지털협업공장 공고문).

#### ④ OCR (`ocr`)

- **현재 상태**: 자리표시자다. 블록은 레지스트리에 등록되어 있고 설정 폼도 있지만, 실행하면 상류 출력을 그대로 넘긴다. 표준 워크플로우에 포함되지 않는다.
- **OCR 설정 값의 위치**: `force_ocr`, `engine`, `language`, `deskew`, `denoise`, `contrast`, `grayscale`, `min_confidence` 값은 `OcrConfig`에 정의되어 있지만 실행 결과에 연결되어 있지 않다. OCR의 실제 동작은 텍스트 추출 어댑터가 정한다.
- **미구현**: 형식 판별 결과에 따라 OCR로 분기하는 구성은 구현되지 않았다.

#### ⑤ 구조 분석 (`structure_analyze`)

- **출력**: DocumentNode 트리(런 단위 행)와 아티팩트. 노드마다 `parsed_text` 기준 문자 오프셋(`span_start`, `span_end`)을 기록해 원문 역추적에 쓴다.
- **설정**: `detect_headings`(기본 참), `heading_max_level`(기본 5), `detect_lists`(기본 참), `detect_toc`(기본 참), `use_font_signals`(기본 참), `preserve_clause_number`(기본 참)
- **구현**: `StructureAnalyzeBlock`(block_version 1.22.0). 추출 레이아웃이 있으면 글꼴 신호, 목차, 각주 분류에 쓴다. TABLE 노드에는 `source_table_id`도 채운다. 노드 종류는 §4.2를 따른다.
- **2026-11-20 감사 반영**
  - 같은 크기의 제목은 기호 순서로 단계를 나눈다. "Ⅰ."·"1." 아래에 "가.", 그 아래에 "(1)"·"1)", 그 아래에 □, ○, - 순서다. 한글 기호와 괄호 번호가 □·○와 함께 쓰일 때의 앞뒤는 정해진 규칙이 없어 번호 체계를 먼저 둔다. 예전에는 "2. 에너지 사용현황"과 "가. 에너지원별 사용량"이 같은 단계가 되어 "2." 제목이 구획 경로에서 빠졌다(세원화성 에너지진단보고서).
  - "○○○ 귀하" 같은 수신인 줄은 굵고 커도 제목으로 보지 않는다(제안요청서).
  - Docling이 장 구분 쪽의 "PART 01"과 장 이름을 일반 글로 읽으면, 같은 쪽에서 바로 이어지는 40자 이하의 장 이름과 합쳐 1단계 제목 하나("PART 01 분석개요")로 만든다. 예전에는 장 제목이 구조에 없어 그 장 본문의 구획 경로에서 장 이름이 빠졌다(경기도 데이터분석 사례집).
  - 위치 정보가 없는 경로(HWP/HWPX, 스캔 PDF)의 머리말·꼬리말은 쪽 처음과 끝 두 줄에서 반복되는 줄로 찾는다. 쪽 끝을 셀 때는 표 줄("[표 N]", 칸 구분선 "|"가 두 개 이상인 행, 표시 바로 다음의 표 제목)을 건너뛴다. 스캔 PDF는 쪽의 표 글을 OCR 글 뒤에 붙여서, 예전에는 표가 있는 쪽의 꼬리말이 본문 청크로 남았다(서울 데이터 펠로우십 보고서). 쪽 머리는 모든 줄을 그대로 센다. 쪽 머리의 표 다음에 오는 본문 소제목이 머리말로 잡히지 않게 하려는 것이다.

#### ⑥ 텍스트 정제 (`text_clean`)

- **출력**: 정제 텍스트(아티팩트), 노드 단위 변경 이력(CleaningChange), `DocumentTextRevision(source="CLEAN")`
- **설정**: `collapse_whitespace`(기본 참), `normalize_unicode`(기본 참, NFC), `normalize_quotes`(기본 참), `normalize_width`(기본 참, 전각을 반각으로), `remove_control_chars`(기본 참), `remove_repeated_headers`(기본 거짓), `fix_ocr_errors`(기본 거짓), `apply_custom_rules`(기본 참, `cleaning_rules`의 활성 규칙을 적용)
- **원칙**: 원문(`parsed_text`)은 바꾸지 않는다. 정제 결과는 아티팩트와 CLEAN 리비전으로 따로 보관한다.
- **구현**: `TextCleanBlock`. 설계서의 `custom_rules` 항목은 `apply_custom_rules`라는 이름으로 구현되었다.

#### ⑦ 불용어 처리 (`stopword`)

- **출력**: 불용어 표시 결과(위치, 사전 항목 ID, 사전 버전). 기본 동작은 삭제가 아니라 표시다.
- **설정**: `action`(mark 기본, exclude_from_analysis, remove), `scope_filter`(사전 범위 필터, 없으면 전체)
- **데이터 소스**: `dictionary_entries`의 stopword 항목. 런의 `dictionary_version` 시점 기준으로 읽는다(§5). 적용 내역은 `dictionary_applications`에 기록한다.

#### ⑧ 동의어 정규화 (`synonym`)

- **출력**: 정규화 텍스트와 적용 항목 목록(원문 표현, 대표 표현, 오프셋, 사전 ID, 버전)
- **설정**: `processing_mode`(normalize 기본, tag_only. 사전 항목의 processing_mode를 따를지 정한다), `case_sensitive_default`(기본 거짓. 항목마다 대소문자 설정이 채워져 있어 사실상 쓰이지 않는다.)
- **데이터 소스**: `dictionary_entries`의 synonym 항목과 그 variants

#### ⑨ 사용자 사전 적용 (`user_dict`)

- **출력**: 도메인 용어 인식과 정규화 결과. 적용 이력은 ⑦, ⑧과 같은 구조로 남긴다.
- **설정**: `term_types`(없으면 전체 유형), `protect_from_stopwords`(기본 참)
- **적용 순서**: 표준 워크플로우는 사용자 사전, 동의어, 불용어 순서로 배치되어 있다(설계 9.5). 순서가 틀리면 경고하는 검사는 구현되지 않았다(§7.3).

#### ⑩ 민감정보 탐지 (`pii_detect`)

- **출력**: PiiDetection 행과 마스킹을 적용한 텍스트
- **설정**: `entity_types`(없으면 사업자등록번호를 제외한 전체 유형), `action`(mask 기본, mark_only, mask, tokenize, remove, exclude_from_embedding), `mask_char`(기본 "*"), `require_admin_approval`(기본 거짓)
- **구현**: 정규식 탐지와 검증을 쓴다. 주민등록번호는 체크섬으로, 카드번호는 Luhn 검사로 확인한다. 원문 값은 `crypto.encrypt_secret`으로 암호화해 `original_encrypted`에 저장하고, 열람은 전역 admin 역할만 할 수 있다.
- **이전 결정 이어받기**(block_version 1.3.0, 2026-11-20): 재처리하면 탐지를 새로 만든다. 이때 같은 문서에서 사람이 승인하거나 해제한 탐지가 있는 가장 최근 실행의 결정을 (유형, 원문) 기준으로 이어받는다. 해제(오탐 처리)한 값은 글에서 가리지 않고 '해제됨'으로 기록하고, 승인한 값은 승인자와 승인 시각을 그대로 옮긴다. 같은 값에 승인과 해제가 섞여 있으면 가리는 쪽을 따른다. `require_admin_approval`을 켰더라도 모든 탐지가 이전 결정으로 정해졌으면 검토를 다시 기다리지 않는다. 예전에는 재처리할 때마다 결정이 사라지고 해제한 값도 다시 가려져, 해제가 글에 반영될 길이 없었다.
- **이름 재등장 가리기**(block_version 1.4.0, 2026-11-21): 사전·표지·호칭으로 잡은 이름이 같은 문서의 다른 자리에 표지 없이 다시 나오면 그 자리도 같은 이름으로 탐지해 가린다. 정민산업 에너지진단보고서에서 "대표자 ○○○"은 가렸지만 표 칸("| 담당자 / 직위 | ○○○ / 대표 |")에 같은 이름이 그대로 남은 것을 고쳤다. 다른 낱말 속에 든 경우("정민수"와 "정민수산")까지 번지지 않도록, 앞 글자는 한글이 아니어야 하고 뒤 글자는 한글이 아니거나 조사 한 글자여야 한다. 이전 결정은 (유형, 원문) 기준이라 새로 잡힌 자리도 같은 값의 승인·해제를 그대로 따른다. 같은 버전에서 "지하주차장"을 "지하주 차장"으로 읽던 호칭 오탐도 막았다. 1.4.1에서는 잡은 이름 1건당 다시 나온 자리가 20곳을 넘으면 그 값은 번지지 않게 했다. 기계설비 매뉴얼에서 "| 담당자 | 기계설비 |"로 잘못 잡힌 "기계설비"가 문서 전체 930곳으로 번졌기 때문이다. 사람 이름은 한 문서에 그렇게 자주 나오지 않는다. 전체 문서를 측정했을 때 예시 이름("홍길동")은 3건 잡혀 13번 다시 나왔다.
- **국제 표기와 띄어 쓴 휴대전화**(block_version 1.4.3, 2026-11-23): "+82 10-1234-5678", "+82 (0)10-…", "010 1234 5678", "010 - 1234 - 5678"도 휴대전화로 찾는다. 휴대전화는 어떤 문맥이어도 개인정보로 보는 기존 규칙을 따른다. 같은 형식의 유선번호("053) 256-4413", "(061) 464 - 7009", "+82-33-811-2001")와 해외 번호(Pub120의 "689-87-757547 (mobile)")는 넓히지 않았다. 전체 문서를 조사해 보니 이 형식으로 나온 번호는 모두 협회, 업체, 구조센터, 도선사 회사 같은 기관 연락처였고, 기관 연락처는 가리지 않는다는 규칙에 맞지 않기 때문이다.
- **탐지 쪽 번호**(block_version 1.4.2, 2026-11-21): 탐지마다 원문 쪽 번호(`pii_detections.page_number`)를 남긴다. 탐지 위치는 정제와 치환을 거친 글 기준이므로, 청크와 같은 방법(`PageLocator`)으로 원문 위치로 되돌린 뒤 `page_map`에서 쪽을 찾는다. 예전에는 이 값을 채우지 않아 민감정보 탭의 "위치"가 모든 문서에서 "-"였다. 쪽 정보가 없는 형식(HWP, DOCX, HTML 등)은 계속 비어 있다.
- **미구현**: 이름과 주소를 찾는 NER 보조(로컬 LLM)는 아직 구현되지 않았다. 사용자 사전의 termType으로 보조하는 부분도 없다.

#### ⑪ 문서 분할 (`chunk_split`)

- **출력**: DocumentChunk 행과 아티팩트. 청크에는 `section_path`, `source_node_ids`, 쪽 범위, 토큰 수가 기록된다.
- **설정**: `strategy`(없으면 컬렉션의 `chunk_strategy`), `max_tokens`, `min_tokens`, `overlap_tokens`(없으면 컬렉션 값), `preserve_table`(기본 참), `preserve_heading`(기본 참), `include_previous_heading`(기본 거짓), `split_long_paragraph`(기본 참), `table_chunk_max_rows`(없음)
- **전략**: `fixed`(문자 수 기준, 기존 `_chunk_text`), `semantic`(문장 임베딩 유사도), `sentence`, `paragraph`, `section_aware`, `table_unit`을 구현했다. 컬렉션 기본값 `size`는 전략을 명시하지 않았을 때 쓰인다. 이때 구조 노드가 본문의 80% 이상을 덮으면 `section_aware`로 바뀌고, 그렇지 않으면 문자 수 기준으로 나뉜다.
- **구현**: `ChunkSplitBlock`(block_version 1.11.0). 구조 기반 전략은 노드 트리를 쓴다.
- **긴 문단의 문장 경계**(1.10.0, 2026-11-23): 최대 길이를 넘는 문단은 `_chunk_text`로 나눈다. 예전에는 끝 1/4 구간에서만 문장 끝을 찾고, 없으면 띄어쓰기에서 잘랐다. 긴 문장이 그 구간을 다 덮으면 다음 청크가 "in fog; it is lighted ..."처럼 문장 중간에서 시작했다(Pub120). 이제 띄어쓰기로 내려가기 전에 청크가 최대 길이의 1/4보다 짧아지지 않는 곳까지 문장 끝을 한 번 더 찾는다. 그래도 문장 끝이 없으면, 남은 문장 꼬리가 최대 길이의 1/8 안일 때 청크를 그만큼 늘려 문장을 끝까지 담는다. 전체 문서의 큰 문단 487개로 견주어 보니 문장 중간에서 시작하는 조각이 102개에서 13개로 줄었다. 남은 것은 최대 길이보다 긴 문장, 명령어 줄, OCR 표 잔해다.
- **노드 경계에서 끊긴 문장**(1.11.0, 2026-11-23): 원본의 쪽이나 단이 넘어가는 자리에서 한 문장이 두 문단 노드로 나뉘면("... with all procedures specified" / "in the vessel security plan ...", "Is-" / "land are dry"), 청크가 그 노드 경계에서 닫혀 다음 청크가 문장 중간에서 시작했다. 이제 앞 글이 문장 끝 없이 끝나고 다음 노드가 영문 소문자로 시작하면 이어지는 문장으로 본다. 이때 청크를 버퍼 안의 마지막 문장 끝에서 닫고, 끝나지 않은 문장은 다음 노드와 함께 담는다. 합쳐도 최대 길이를 넘으면 두 노드를 한 구간으로 보고 `_chunk_text`로 나눈다. 큰 문단을 나눈 마지막 조각이 문장 중간에서 끝나면 다음 노드를 기다렸다가, 이어지는 문장이 아니면 예전처럼 따로 청크로 낸다. 목록 기호("b. "), 주소("http", "www."), 띄어쓰기가 없는 글은 이어 붙이지 않는다. 표는 늘 따로 둔다.
- **2026-11-20 감사 반영**
  - 큰 표는 `Document.tables`의 칸으로 행 묶음을 만든다. 이때 같은 실행의 민감정보 탐지 가운데 글에서 가린 값을 칸에도 똑같이 가린다(`mask_table_cells`). 원문은 메모리에서만 복호화한다. 예전에는 가리기로 한 전화번호와 이메일이 큰 표 조각에 그대로 들어갔다(기계설비 매뉴얼 232건, Pub120bk 306건).
  - 가로로 합친 긴 설명 행처럼 첫 열 글이 100자를 넘으면, 첫 열을 되풀이할 행 이름으로 보지 않고 그 글도 나눠 담는다. 예전에는 나머지 열이 빈 설명 행이 통째로 빠졌다.
  - 아래에 본문 없이 같은 수준 이상의 제목이 바로 오는 제목(한 줄짜리 조문, 제목으로 분류된 번호 줄)은 구획 경로에 들어갈 곳이 없으므로 문단처럼 청크에 담는다. 구조 트리의 제목 노드는 그대로다.
  - 큰 표를 나눈 조각은 같은 parent 청크에 묶는다. 예전에는 조각마다 표 전체를 담은 parent가 따로 생겼다.
  - parent 청크 글에서도 머리말·꼬리말·목차 노드의 글을 지운다(child와 같은 `strip_ranges`). parent는 원문 연속 구간이라 그 사이의 쪽 꼬리말이 답변 문맥에 따라 들어갔다(서울 데이터 펠로우십 보고서). 위치(span)는 그대로다.

#### ⑫ 품질 검증 (`quality_check`, 검토 게이트 겸용)

- **출력**: QualityReport(`scores`, `metrics`, `warnings`, `warning_categories`, `status`). 최종 상태는 `documents.quality_status`에도 복사된다.
- **점수 항목**: `textExtraction`, `ocr`(OCR을 쓴 문서만), `structure`, `chunking`, `sourceRecall`(원본을 그대로 그린 PDF와 비교할 수 있을 때만). PDF는 원본 파일을, DOCX, HWP, HWPX, PPTX, XLSX, HTML은 원문 대조 탭과 같은 미리보기 PDF를 쓴다(1.11.0, 2026-11-23). 미리보기가 원본을 직접 열지 못해 우리가 읽은 글로 다시 만든 것이면 대조가 되지 않으므로 `unsupported_format`으로 남기고 재지 않는다. CSV, TXT, MD는 비교할 PDF가 없어 재지 않는다. 원본 재현율은 쪽마다 PDF 저장 순서와 위치 정렬 두 읽기 순서 가운데 본문과 더 잘 맞는 쪽으로 잰다(1.9.0). 저장 순서에서 기호가 줄 뒤로 밀린 PDF는, 보이는 순서로 바로잡은 본문이 누락으로 잘못 잡혔다(세원화성 에너지진단보고서, 0.673 → 0.868). 목차-제목 대조는 점선 없이 공백 하나 뒤에 붙은 쪽 번호("분석개요 06")를 뗀 형태와, 합친 장 제목("PART 01 분석개요")의 "PART 01"과 장 이름도 열쇠로 쓴다. 이 변경으로 KR S-03010 규격의 대조 비율이 0에서 0.861로, Pub120bk는 0.130에서 0.300으로 실제에 가깝게 올랐다. `normalization`은 항상 100점이라 평균에서 제외되었고 점수 항목에서도 빠졌다(`quality_blocks.py` 주석).
- **종합 점수**: 항목 점수의 산술 평균이다. 청크가 0개이면 평균과 무관하게 FAILURE로 확정한다.
- **상태 판정** (`_determine_status`)
  - 청크가 0개이거나 쓸 수 있는 텍스트가 없으면 FAILURE
  - 종합 점수가 `fail_below_score`(기본 30) 미만이면 FAILURE
  - 쪽 단위 OCR 실패가 일부 있으면 PARTIAL_FAILURE (전부 실패한 경우는 FAILURE 쪽으로 판정된다)
  - 경고가 있으면 SUCCESS_WITH_WARNING
  - 그 밖에는 SUCCESS
- **검토 판정** (`_decide_review`)
  - FAILURE와 PARTIAL_FAILURE는 항상 검토가 필요하다.
  - SUCCESS_WITH_WARNING은 `review_policy`가 review_on_warning 또는 always_review이면 REVIEW_REQUIRED로 바뀌어 검토가 필요하다.
  - SUCCESS는 `review_policy`가 always_review일 때만 검토가 필요하다.
  - "검토 없이 진행"(`skip_review`)을 켜면 정책은 auto_pass로 취급된다. 단, FAILURE와 PARTIAL_FAILURE는 여전히 검토가 필요하다.
- **설정**: `min_extraction_chars`(50), `max_broken_char_ratio`(0.05), `min_ocr_confidence`(0.5), `max_empty_page_ratio`(0.2), `min_chunk_chars_warning`(50), `max_chunk_chars_warning`(2000), `max_implicit_table_ratio`(0.2), `min_toc_heading_match_ratio`(0.5), `min_source_recall`(0.8), `min_usable_chars_per_page`(30), `max_ocr_single_char_ratio`(0.25), `review_policy`(기본 review_on_warning), `fail_below_score`(기본 30.0)
- **구현**: `QualityCheckBlock`(block_version 1.10.0). 1.10.0(2026-11-23)에서 목차 대조가 세 가지를 더 알아본다. ". . . ." 점선 뒤의 로마 숫자 쪽 번호("Preface. . . . II"), 한 줄에 붙은 두 단 목차("AUSTRALIA . . . 1 NEW CALEDONIA . . . 229", 점선 없는 영문 "General 1 Routes 22"), 쪽 번호 열 머리글("Page")이다. 두 단 항목은 나누어 각각 센다. 한글 "제 2 장"을 나누지 않도록 점선 없는 나누기는 영문자 뒤의 번호와 대문자로 시작하는 다음 항목 사이에서만 한다. Pub120bk의 대조 비율이 0.300에서 0.575로 올랐고 다른 목차 문서 다섯 개는 그대로다. 남은 미대조 항목은 나라별 쪽의 목차 단과 본문 단이 한 줄로 합쳐진 것으로, 추출 단계의 문제다. 설계서의 `min_chunk_tokens_warning`은 `min_chunk_chars_warning`(문자 수 기준)으로 구현되었다.
- **검토 게이트**: 판정이 검토 필요이면 런을 `WAITING_REVIEW`로 바꾸고 후속 블록을 디스패치하지 않는다. 사용자가 승인하면 다음 블록부터 재개한다(§7.4).

#### ⑬ RAG 저장 (`rag_store`)

- **출력**: 저장 결과(업서트한 포인트 수 등 metrics). 청크의 `embedded` 값을 갱신한다.
- **설정**: `embedding_model`(없으면 컬렉션 값), `exclude_pii`(기본 참, `exclude_from_embedding` 조치 구간을 임베딩에서 뺀다), `store_masked_text`(기본 거짓), `enable_llm_context`(기본 거짓)
- **구현**: `RagStoreBlock`(block_version 1.4.0). 문서 단위로 기존 포인트를 모두 지운 뒤 새 청크를 업서트한다(`delete_by_document` 후 `upsert_points`). 포인트 ID는 청크 ID와 같다.
- **Qdrant payload**: `document_id`, `collection_id`, `chunk_index`, `text`, `index_text`, `filename`, `page_number`, `tags`, `chunk_id`, `workflow_run_id`와 권한 사본 필드(`sec_rank`, `acl`, `owner_id` 등)가 들어간다. 설계서에 있던 `dictionary_version`과 `pipeline_version`은 payload에 들어가지 않고 DocumentChunk 행에만 기록된다.
- **상태**: 저장을 마치면 Document.status를 INDEXED로 설정한다(`storage_blocks.py`).

#### ⑭~⑳ 분석 블록 (기존 유지)

`classify`, `extract_entities`, `extract_keywords`, `summarize`, `validate`, `postprocess`, `output`은 분석 카테고리에 속하며 기존 구현을 유지한다. `output` 블록은 `save_to_document`(기본 참)이 켜져 있으면 요약과 추천 태그를 문서 메타데이터에 기록한다. 설계서는 분석 블록의 입력을 정제 아티팩트로 우선 바꾸기로 했으나, 이번 점검에서 그 규칙이 구현되었는지는 확인하지 못했다(§16). 표준 워크플로우에는 이 블록들이 포함되지 않는다.

- **요약의 금액 단위**(`SummarizeBlock` block_version 1.1.0, 2026-11-23): 3B 요약 모델은 "7,500[천원]"(750만 원)을 "7500원"이나 "7,500만 원"으로, "9,000[백만원]"(90억 원)을 "9,000만원"으로 옮겼다. 프롬프트에 단위를 옮기라고 지시해도 나아지지 않았다. 그래서 모델에 넘기는 글에서만 천원, 백만원, 천만원 금액을 "750만 원", "90억 원"처럼 원 단위로 풀어 쓴다(`app/pipeline/money_units.py`). 바꾸는 곳은 숫자 바로 뒤의 단위, 표 머리글의 단위("투자비 [백만원]" 열의 숫자 칸), 표 바로 위의 단위 안내("(단위 : 백만원)" 다음 표)다. 빈 줄 없이 붙은 표는 중간의 머리글 줄을 새 머리글로 본다. 단위 표기는 그 열에서 숫자를 하나라도 바꿨을 때만 "원"으로 고친다. 숫자를 못 바꿨는데 단위만 바뀌면 원문보다 틀린 정보가 되기 때문이다. 모델이 그대로 옮기는 만원과 억원은 두고, 단위가 여럿인 안내("(단위 : ha, 기, 백만원)")는 어느 열의 단위인지 알 수 없어 두며, 저장된 본문도 바꾸지 않는다.

#### 제어 블록 (기존 유지)

`branch`(조건 분기)와 `merge`(병합)는 기존 구현을 그대로 쓴다. 병합은 원자적 카운터로 상류 에지가 모두 도착했을 때만 실행된다. 표준 워크플로우에는 포함되지 않는다.

## 5. 사전 버전 관리 설계

- 사전 항목을 만들거나 고치거나 지우거나 가져올 때 모두 같은 트랜잭션에서 `dictionary_revisions`에 1행을 추가한다(`bump_revision`을 생성, 수정, 삭제, 가져오기 경로 모두에서 호출한다). 전역 버전은 이 행의 번호다.
- 워크플로우 런을 시작할 때 현재 전역 버전을 `workflow_runs.dictionary_version`에 고정한다. 사전 블록(stopword, synonym, user_dict, pii_detect)은 이 버전 시점 기준으로 항목을 읽는다.
- 시점 판정은 설계의 근사식을 따른다. 항목이 활성이고 `updated_at`이 리비전의 생성 시각 이하이면 그 시점에 유효했던 것으로 본다(`normalization_blocks.py`, `_dictionary_version_cutoff`).
- **삭제 방식은 설계와 다르다.** 설계는 DELETE를 soft-delete(`enabled=false`)로 바꾸기로 했으나, 현재 구현은 `dictionary.py`의 `delete_dictionary_entry`가 `db.delete`로 항목을 물리 삭제한다(hard delete). 삭제 사실은 리비전에만 남는다. 삭제된 항목은 과거 버전의 재현에 포함되지 않으므로, 재현성에는 한계가 있다(§15 참조).
- 사전 수정 후 영향 문서 탐지: `GET /api/v1/admin/dictionary/entries/{id}/impact`가 영향 문서 수를 돌려준다. 재처리는 사용자가 문서별로 실행한다. 자동 실행은 없다.
- BM25 토크나이저(`dictionary_service`)는 같은 테이블을 쓰되 항상 최신 버전을 사용한다. 검색 쪽은 재현성이 필요 없다.

> **구현 추가 사항**: `skip_review`도 캐시 키에 포함된다(§2.4). 이 값은 런이 시작할 때 고정되고 런마다 다를 수 있으므로, 같은 입력이라도 검토 판정이 다르면 캐시를 공유하면 안 된다.

## 6. 오류 처리 (설계서 18장)

- **오류 코드 체계**: 설계의 전체 목록은 `ERROR_CODES`로 정의되어 있다(FILE_UNSUPPORTED, FILE_CORRUPTED, FILE_ENCRYPTED, TEXT_EXTRACTION_FAILED, OCR_FAILED, STRUCTURE_ANALYSIS_FAILED, CLEANING_RULE_ERROR, DICTIONARY_CONFLICT, CHUNK_SIZE_EXCEEDED, QUALITY_THRESHOLD_FAILED, STORAGE_FAILED, WORKFLOW_TIMEOUT). 실제로 발생시키는 코드는 다음 네 개다. `FILE_UNSUPPORTED`, `FILE_ENCRYPTED`, `TEXT_EXTRACTION_FAILED`, 그리고 sweeper가 기록하는 `TIMEOUT_EXCEEDED`다. 나머지 코드는 정의만 있고 발생 경로가 없다. 시간 초과 코드는 설계의 `WORKFLOW_TIMEOUT`이 아니라 `TIMEOUT_EXCEEDED`다.
- **재시도 정책**: 블록 설정의 `retryCount`(기본 2)와 `timeoutSeconds`(기본 1800)를 실행기가 적용한다. `BlockExecutionError`의 `permanent` 플래그가 참이면 재시도 없이 즉시 실패한다. `FILE_UNSUPPORTED`와 `FILE_ENCRYPTED`가 이 플래그로 발생한다.
- **사용자 안내 문구**: 워커 안에서 잡힌 라이브러리 예외 문구는 `_localize_error_message`가 한글 안내로 바꾸어 `Document.error_message`와 스텝 오류 메시지에 남긴다. 알 수 없는 예외는 예외 종류와 원문 일부를 덧붙여 진단 단서를 남긴다.
- **실패 격리(18.3)**: 쪽 단위 처리에서 실패한 쪽은 `failed_pages`로 모으고 블록은 성공으로 처리한다. 품질 검증이 실패한 쪽의 수에 따라 PARTIAL_FAILURE를 판정하고, 검토 게이트에서 해당 문서를 다시 처리할 수 있다.

## 7. 실행기 확장

### 7.1 기존 유지

`tasks/workflow.py`의 DAG 워커 구조(블록 실행, 출력 조건으로 에지 평가, 다음 블록 디스패치, 병합 카운터)는 그대로 쓴다. 큐는 셋으로 나뉜다. 일반 블록은 `normal`, GPU 모델 블록은 `embed`, Docling 추출은 `extract` 큐를 쓴다(§0 운영 변경 (1)).

### 7.2 Document.status 파생 매핑

실행기는 스텝 시작 시 문서 상태를 갱신한다(설계서 17.3). 현재 매핑은 다음과 같다.

| 실행 중 블록 | Document.status |
|---|---|
| file_validate, format_detect | VALIDATING |
| text_extract, ocr | PARSING |
| structure_analyze | STRUCTURING |
| text_clean | REFINING |
| stopword, synonym, user_dict | NORMALIZING |
| pii_detect | MASKING |
| chunk_split | CHUNKING |
| quality_check | VALIDATING (검토 게이트에서는 WAITING_REVIEW) |
| rag_store | EMBEDDING, 저장이 끝나면 INDEXED |
| 분석 블록 | 분석 런이 시작될 때 ANALYZING, 런이 끝나면 INDEXED |

- 워크플로우 경로는 UPLOADING 상태를 설정하지 않는다. UPLOADING은 레거시 `continue_processing`만 쓴다.
- 런이 완료될 때 그 런이 문서의 `active_run_id`인 경우에만 INDEXED로 바꾼다. 늦게 끝난 이전 런이 최신 상태를 덮어쓰지 않게 하려는 장치다.

### 7.3 그래프 검증 (`workflow_service.validate_graph`)

현재 검증은 다음과 같다.

- **순환 검사**: 그래프에 사이클이 있으면 오류다.
- **설정 검사**: 블록의 `config`가 `config_schema`와 맞지 않으면 첫 번째 문제를 한글로 알려준다. 스키마에 없는 키(에디터의 `timeoutSeconds` 등)는 무시한다.
- **연결 순서 제약**: `_REQUIRES_UPSTREAM` 표(`workflow_service.py`)가 블록별 상류 요구를 정의한다. `text_extract`는 `format_detect`의 하류, `structure_analyze`, `text_clean`, `pii_detect`는 `text_extract`의 하류, `chunk_split`은 `text_clean`의 하류, `quality_check`는 `chunk_split`의 하류, `rag_store`는 `chunk_split`과 `quality_check`의 하류여야 한다. 설계서의 블록별 `requires_upstream` 속성 대신 중앙 표로 구현했다.
- **PREPROCESS 종류 규칙**: 진입 블록은 `file_validate` 정확히 1개여야 하고, `rag_store`는 정확히 1개여야 한다. 분석 종류 워크플로우에는 이 규칙이 적용되지 않는다. 종류는 `workflow_definitions.kind`(PREPROCESS, ANALYSIS)로 구분한다.
- **미구현**: 사전 순서 경고(사용자 사전이 불용어보다 뒤에 있으면 경고)는 구현되지 않았다.

### 7.4 검토 게이트 재개 프로토콜

```
quality_check 판정이 검토 필요
  → run.status = WAITING_REVIEW, document.status = WAITING_REVIEW
  → 알림 발행(업로더에게), 후속 블록 디스패치 중단

사용자 검토 화면에서:
  a) 승인      → POST /workflows/runs/{id}/resume → resume_workflow_run이 멈춘 블록의 다음 블록부터 재개
  b) 수정 후 승인 → 구조 보정(PATCH /documents/{id}/nodes/{nodeId}) 같은 수정 API로 기록만 남긴다.
                  승인하면 멈춘 지점부터 이어 달린다. 수정한 블록을 자동으로 다시 실행하지는 않는다.
                  수정을 반영하려면 사용자가 부분 재처리(§8)를 따로 실행해야 한다.
  c) 반려      → POST /workflows/runs/{id}/cancel → run CANCELLED, document FAILED(사유 기록)
```

- 승인과 반려는 검토 대기 화면(`/review-queue`)의 버튼과 문서 품질 탭의 버튼에서 같은 API를 호출한다.
- 설계서의 검토 의견(`review_note`) 입력은 현재 UI에 없다. 승인, 반려 API에도 메모 필드가 없다.

### 7.5 분석 워크플로우 자동 실행 (설계 이후 추가)

- 업로드할 때 문서에 분석 워크플로우를 골랐으면(`documents.analysis_workflow_id`, 마이그레이션 `e4a6c8b0d2f5`, 2026-11-24) 그 워크플로우의 최신 게시 버전이 가장 먼저다. 문서에 남기므로 재처리 뒤의 분석도 같은 워크플로우를 따른다. 그 워크플로우가 지워졌거나, 지금 컬렉션의 프로젝트에서 쓸 수 없거나, 게시된 버전이 없으면 아래 컬렉션 기준으로 넘어간다(`workflow._document_analysis_version`).
- PREPROCESS 런이 완료되면 해당 문서의 컬렉션에 `default_analysis_workflow_id`가 있는지 확인한다.
- 지정이 있으면 그 워크플로우의 지정 버전(없으면 최신 게시 버전)으로 `AUTO_ANALYSIS` 런을 만들고 문서를 ANALYZING으로 설정한다. 분석 런이 끝나면 문서는 INDEXED로 돌아간다.
- 지정이 없으면 시스템 표준 분석 워크플로우(`00000000-0000-0000-0000-0000000000e1`, 마이그레이션 `b9d1f3a5c7e9`)의 최신 게시 버전으로 `AUTO_ANALYSIS` 런을 만든다. 사슬은 입력, 요약, 키워드, 분류, 출력이고 출력은 분류를 추천 태그에 넣지 않는다(`category_as_tag: false`). 표준 분석 워크플로우도 없으면 분석하지 않고 경고만 남긴다.
  - 예전(2026-11-16~11-20)에는 지정이 없으면 워크플로우 밖에서 `generate_summary`와 `extract_metadata`를 보냈다(`_dispatch_default_analysis`). 처리 이력에 남지 않았고, 분석 워크플로우를 지정하지 않은 컬렉션 문서에도 분석 결과가 생겨 화면 안내와 어긋났다(사용자 검토). 그래서 표준 분석 워크플로우로 바꿨다.
- 분석은 사용자 워크플로우를 그대로 따른다(2026-11-20 사용자 결정). 워크플로우에 없는 단계를 시스템이 채우지 않고, 그 단계가 만들 항목은 분석 런을 시작할 때 비운다(`app/pipeline/analysis_outputs.py`).
  - 요약은 요약 블록과 출력 블록(문서에 저장)이 함께 있을 때 남는다. 없으면 요약을 지우고 `summary_status`를 `SKIPPED`로 두며 요약 검색 색인에서도 뺀다.
  - 추천 태그는 키워드나 개체 블록이 있거나, 분류 블록이 있고 출력이 분류를 태그로 넣을 때 남는다. 없으면 추천 태그를 비운다.
  - 분류는 분류 블록이 있을 때 남는다. 없으면 분류를 비우되, 사용자가 직접 고친 분류(`user_edited_fields`)는 그대로 둔다.
  - 추천 태그를 만드는 단계가 있으면 추천 태그는 이번 실행 결과로 바꿔 넣는다. 이전 실행 값과 합치지 않는다(출력 블록 1.7.0). 예전에는 합쳐서 예전 워크플로우나 예전 작업이 만든 태그가 계속 쌓였다. 같은 글을 같은 워크플로우로 다시 분석하면 모델이 temperature 0이라 결과가 거의 같고, 추천 태그가 바뀌는 것은 글이나 워크플로우가 바뀐 경우다.
  - 사용자가 무시한 추천 태그는 `documents.dismissed_tags`에 기록하고(마이그레이션 `c1e3a5b7d9f2`), 다음 분석부터 제안하지 않는다. 이미 단 태그(`tags`)도 제안하지 않는다. 대소문자는 구분하지 않는다.
  - 태그와 분류를 모두 만들지 않으면 `metadata_status`를 `SKIPPED`로 둔다. 사용자가 단 태그(`tags`)는 어떤 경우에도 건드리지 않는다.
  - 문서 화면은 `SKIPPED`일 때 "이 컬렉션의 분석 워크플로우에는 요약 단계가 없어 요약을 만들지 않았습니다"처럼 이유를 보여 준다.
  - 컬렉션 생성, 수정 화면과 워크플로우 목록의 "컬렉션 기본으로 지정" 창은 고른 워크플로우(고정 버전이면 그 버전)에 없는 항목을 경고로 알린다. 규칙은 `frontend/src/lib/analysisOutputs.ts`가 백엔드와 같게 판정한다.
- 분석 런은 또 다른 분석 런을 시작하지 않는다. 자동 실행은 PREPROCESS 런의 완료에서만 일어난다.

## 8. 부분 재처리 설계 (설계서 15장)

### 8.1 재처리 범위 계산

- 블록 의존성은 게시된 버전의 DAG에서 시작 블록의 하류 폐포(`downstream_closure`)로 계산한다.
- 요청은 `POST /api/v1/documents/{id}/reprocess`로 보낸다. 본문은 다음 필드를 가진다.
  - `start_block_type` 또는 `start_block_instance_id`: 재처리를 시작할 블록을 지정한다.
  - `reason`: 재처리 사유를 적는다(선택).
  - `timeout_overrides`: 이 런에만 적용할 시간 제한을 준다.
  - `use_latest_version`: 최신 게시 버전으로 처음부터 처리할지 정한다.
  - `edited_text`: 레거시 경로 전용. 시작 블록과 함께 쓸 수 없다.
- 영향도는 `GET /api/v1/documents/{id}/reprocess/impact`로 미리 본다. 응답은 §4.10의 구조다.
- 시작 블록의 상류 스텝이 모두 COMPLETED 또는 SKIPPED여야 한다. 원본 런이 진행 중(QUEUED, RUNNING)이거나 검토 대기(WAITING_REVIEW)이면 409로 거절한다.
- 매핑 규칙(설계서 15.2)은 별도 표 없이 DAG에서 자연스럽게 도출된다. 예를 들어 사용자 사전을 고치면 `user_dict` 블록부터 하류 전체가 다시 실행된다.
- **미구현**: 노드 단위 재처리(`targetNodeIds`)는 없다. 재처리는 항상 블록 단위다.

### 8.2 실행 방식

- 새 WorkflowRun을 만든다. `trigger=REPROCESS`, `parent_run_id`는 원본 런, `started_block_id`는 시작 블록이다. `dictionary_version`은 현재 전역 버전으로 고정하고, `skip_review`는 원본 값을 복사한다. `timeout_overrides`는 요청값을 쓴다.
- 시작 블록의 상류 스텝은 원본 런의 상태, 입력 해시, 출력, 아티팩트 키를 복사하고 `cached=true`로 표시한다. 이 복사는 BlockExecutionCache를 거치지 않는다. 캐시는 세 블록 타입에만 적용되기 때문이다.
- 시작 블록부터 정상 실행한다. rag_store는 문서 전체를 지운 뒤 다시 업서트하며, 노드나 청크 범위만 갱신하지 않는다.
- `use_latest_version`이 참이면 상류 복사 없이 진입 블록부터 새 버전으로 실행한다. 설정이 같은 `file_validate`, `format_detect`, `text_extract`는 캐시로 재사용된다.
- 문서의 활성 런이 분석 런이면 원본 전처리 런을 찾아 그 런을 기준으로 재처리한다(`resolve_reprocess_parent`).
- 재처리 시작 전에 멈춘 런이 있으면 `reconcile_stuck_run`으로 먼저 확정한다(§10.5).

## 9. 화면 설계 (설계서 19장)

### 9.1 문서 상세 페이지 (`DocumentDetailPage`)

탭은 다음과 같다. 설계 초안의 여덟 탭에 요소, 표, 그림, RAG 데이터 수정 탭이 추가되었다.

| 탭 (화면 표시명) | 내용 | 표시 조건 |
|---|---|---|
| 원문 대조 | 원본 페이지 미리보기와 추출 텍스트의 쪽별 대조 | 처리 완료 또는 검토 대기 |
| 구조 | DocumentNode 트리와 노드 상세. 노드 유형, 레벨, 글꼴 스타일을 보정한다. | 항상 |
| 요소 | Docling 요소 목록과 요소 마크다운 보정 | PDF이고 처리 완료 |
| 정제 비교 | 정제 변경 내역(CleaningChange)과 규칙별 표본 | 항상 |
| 사전 적용 | 사전 적용 내역, 문서 단위 항목 제외 토글, 개별 적용 취소 | 항상 |
| 민감정보 | 탐지 목록, 승인, 반려, 원문 보기(전역 admin) | 항상 |
| 청크 | 청크 목록, 검색 제외, 텍스트 수정(재임베딩), 상위 청크 보기 | 항상 |
| 표 | 추출된 표 | 처리 완료 |
| 그림 | 추출된 그림 | 처리 완료 |
| RAG 데이터 수정 | 수정 이력과 원문 편집 | 처리 완료 |
| 품질 | 종합 점수, 항목별 점수 막대, 판정 기준, 경고 목록, 승인과 반려 | 항상 (검토 대기 문서는 이 탭이 먼저 열린다) |
| 처리 이력 | 런 목록, 블록 타임라인, 스텝 상세, 이 블록부터 재처리 | 항상 |

- "항상"으로 표시한 탭은 처리 상태와 무관하게 보인다. 나머지 탭은 INDEXED 또는 ANALYZING일 때 보이고, 검토 대기 상태에서는 원문 대조 탭만 추가로 보인다.
- 검토 대기 문서를 열면 품질 탭이 기본으로 열린다. 원문 대조 탭을 눌러도 다시 품질 탭으로 돌아가지 않는다. 검토 대기 화면에서 들어올 때는 `?tab=` 쿼리로 탭을 지정한다.
- 헤더에는 상태 배지와 보안 등급 배지가 표시된다. 원본 다운로드와 재처리 버튼이 있다. 품질 상태는 품질 탭에서 확인한다.
- **구조 탭 보정**: 노드의 유형, 레벨, 글꼴 스타일(style_name, font_size, font_name)과 보정 메모를 고칠 수 있다. 문단 경계와 표 경계를 고치는 기능은 없다.
- **청크 탭**: 청크 텍스트를 고치면 재임베딩되고, 검색 제외 토글은 Qdrant payload의 `disabled` 값을 바꾼다. 청크 경계를 고치는 기능은 없다.
- **원문 대조 탭의 원본 보기**(2026-11-23): PDF는 원본 파일을 그대로 보여 준다. DOCX, PPTX, XLSX, HWP, HWPX, HTML은 서버의 LibreOffice가 원본을 PDF로 그린다. 한글 파일은 LibreOffice 확장 H2Orestart(0.8.0, sha256 고정)로 연다. 이미지는 PDF로 감싸고, CSV와 TXT는 원본 글을 그대로 적은 HTML로 보여 준다. 예전에는 한글 파일과 HTML이 추출한 글로 다시 만든 미리보기였고, XLSX와 PPTX도 LibreOffice 구성 요소가 없어 같은 처지였다. 원본을 직접 그리지 못하면 예전처럼 다시 만든 미리보기로 내려가고 "원본과 다를 수 있음" 표시를 남긴다(`preview/v2/{id}.approximate`). 미리보기는 `preview/v2/` 아래에 캐시하므로 예전 재구성 미리보기는 쓰이지 않는다.
- **올린 HTML의 안전 처리**: LibreOffice는 HTML 안의 외부 주소(이미지, 스타일시트, CSS url)를 서버에서 불러온다. 그러면 올린 사람이 서버로 하여금 내부 주소에 요청을 보내게 할 수 있다. 그래서 그리기 전에 남길 것만 고르는 허용 목록으로 다듬는다(`preview_html.py`). 글과 표를 그리는 태그와 모양 속성만 남기고, 이름에 다른 문자가 섞인 태그와 속성은 버린다. src는 내장 래스터 이미지(data:image/png 등, base64)만 남긴다. CSS 선언에 url, image-set, 역슬래시 이스케이프, 주석이 있으면 그 선언을 버린다. DOCTYPE, 주석, 스크립트, 프레임, SVG도 버린다. 변환은 실행마다 임시 프로필을 쓰고, 120초를 넘기면 soffice 프로세스 그룹 전체를 끝낸다. 컨테이너의 외부 통신을 막는 일은 배포 설정의 몫으로 남아 있다.
- **원본 대조로 드러난 추출 누락**(텍스트 추출 1.40.0, 2026-11-23): PDF가 아닌 형식을 원본과 처음 대조하자 두 가지 누락이 나왔다. HWPX는 `<hp:t>` 안의 줄바꿈, 전각 공백, 탭 뒤 글이 XML에서 그 요소의 tail이라 읽히지 않았다(스마트공장 공고의 "중소벤처기업부 장관"에서 "장관", "② AAS (IEC 63278)"). 이제 요소 자리에 공백을 두고 뒤 글을 이어 읽는다. PDF 표는 Docling이 칸 안의 한 줄을 어느 칸에도 넣지 않거나(자율형공장 공고 17쪽), 바깥 세로 테두리 없는 선 표에서 양 끝 열이 통째로 빠졌다(UIUX 가이드라인 80쪽). 표마다 표 영역의 원본 글자 줄과 견줘 빠진 줄을 같은 열의 가장 가까운 칸에 붙이고, 선 표가 Docling 표보다 많이 빠뜨렸으면 Docling 표를 쓴다. Docling 칸 글의 띄어쓰기는 본문과 같은 규칙(`choose_spacing`)으로 원본에 맞춘다(`table_text_coverage.py`). 1.41.0에서 두 가지를 바로잡았다. 빠진 줄 판정은 글자와 숫자만 견준다. 글자 층에 괄호가 따로 그려진 쪽(세원화성 진단보고서 34쪽 "가격원")에서 1.40.0이 이미 있는 줄을 한 번 더 붙였기 때문이다. 선 표와 Docling 표의 선택은 빠진 줄을 되돌려 넣기 전의 Docling 칸 글로 견준다. 넣은 뒤 글로 견주면 Docling 쪽이 늘 이겨 칸 순서를 지킨 선 표 대신 글 순서가 뒤섞인 표가 골라졌고, 그 문서의 본문이 3천여 자 줄었다.
- **HWP·HWPX 그림 자리**(텍스트 추출 1.42.0, 2026-11-23): 어댑터가 BinData 그림을 위치 없이 읽어 모든 그림 글([그림 N])이 1쪽 표지 뒤에 붙었다(NS-AM 검사매뉴얼). 본문을 읽는 순서대로 그림 컨트롤이 가리키는 BinData 를 남긴다. HWP는 PictureInfo `bindata-id`가 DocInfo BinData 순번이고 그 `storage-id`가 스트림 이름이며, HWPX는 `hc:img binaryItemIDRef`가 content.hpf 매니페스트 id다. 그림은 들어 있던 문단 뒤(칸 안 그림은 그 표 뒤)에 두고, 미리보기 쪽 나눔에서 그 문단이 놓인 쪽으로 보낸다. 머리말처럼 본문 밖에 있는 그림은 예전처럼 첫 쪽에 둔다(`hwp_pictures.py`).
- **HWP·HWPX 원본 보기의 쪽 나눔**(텍스트 추출 1.43.0, 2026-11-23): H2Orestart로 바로 PDF를 그리면 NS-AM 검사매뉴얼(원본 19쪽)이 34쪽이 되고 3쪽은 빈 쪽이었다. 원인은 두 가지였다. 첫째, 한글은 머리말·꼬리말 영역 높이만큼만 본문을 비우는데, H2Orestart는 그 높이를 최소 높이로 둔 머리말·꼬리말에 빈 문단을 넣는다. 그래서 LibreOffice가 문단 높이만큼 본문을 더 줄였고, 높이 0인 꼬리말이 쪽마다 약 32pt를 차지해 서식마다 마지막 줄이 다음 쪽으로 넘어갔다. 둘째, 한글에서 표는 문단 안에 글자처럼 들어가 그 문단이 표 높이만 차지하는데, H2Orestart는 표 뒤에 남은 문단을 빈 줄로 남긴다. 쪽을 거의 채운 표 뒤에서는 이 줄이 다음 쪽으로 밀려 빈 쪽이 생겼다. 이제 원본을 먼저 ODT로 열고, 내용이 없는 머리말·꼬리말을 지운 뒤 그 최소 높이와 간격을 쪽 여백에 더한다. 같은 쪽 모양을 쓰는 마스터 페이지가 모두 비어 있을 때만 지운다. 표 바로 뒤의 빈 문단은 1pt 문단 모양으로 바꾸며, 쪽을 넘기는 문단 모양은 그대로 둔다. 그다음 PDF로 그린다(`preview_odt_fix.py`). H2Orestart를 쓴 변환은 결과를 다 쓴 뒤 끝내는 중에 비정상 종료(rc=134)할 때가 있으므로, 결과 파일이 온전하면(PDF는 머리와 끝 표시, ODT는 압축이 온전하고 본문·스타일이 있음) 종료 코드와 상관없이 그 결과를 쓴다. ODT 단계가 실패하면 원본을 바로 PDF로 그린다. HWP 쪽 나눔은 이 미리보기를 따르므로, 블록 코드가 같아도 쪽 결과가 달라진다. 그래서 텍스트 추출 버전을 올려 이전 실행 캐시를 다시 쓰지 않게 했다. 한글이 저장해 둔 줄 배치로 센 원본 쪽 수와 비교한 결과는 다음과 같다. NS-AM은 34쪽에서 19쪽(원본 19쪽), UIUX 보고서는 29쪽(원본 29쪽), 과업지시서는 4쪽(원본 4쪽)이 되었다. 조사료 지침 2021은 42쪽에서 39쪽(원본 36쪽), 2022는 49쪽에서 46쪽(원본 40쪽), 제안요청서는 80쪽에서 78쪽이 되었고, 빈 쪽은 모두 없어졌다. 남은 차이는 한컴 글꼴(굴림, 바탕, 휴먼명조 등)이 없어 나눔고딕으로 바꿔 그린 데서 오는 글자 폭 차이로 본다. 원문 대조 탭이 파싱 본문을 미리보기 쪽에 맞춰 자를 때, 경계 바로 앞 줄이 "[표 N]"이나 "[그림 N]" 머리표뿐이면 머리표 줄부터 다음 쪽으로 넘긴다(`page_text_align.py`). 미리보기 쪽은 표 칸 글로 시작하므로, 예전에는 머리표만 앞 쪽 끝에 남았다(NS-AM 3쪽 끝의 "[표 4]").
- **제목 상자와 긴 □ 문장**(구조 분석 1.23.0·1.23.1, 2026-11-24): 공공 문서는 절 제목을 한 줄짜리 표(제목 상자)에 넣는 일이 많다. 예전에는 번호로 시작하는 상자("① | 조사료…", "Ⅱ | 사업 개요")만 제목으로 읽었다. 그래서 정부 보도자료(d1)의 "참고1 | 법령체계 개편(안)" 같은 부록 머리와 " | 제명을 바꾼다! (…)" 같은 표어 상자가 표로 남았고, 그 아래 내용이 어느 절에 속하는지 청크의 절 경로에 드러나지 않았다. 이제 붙임·참고·별첨·별표·별지·첨부·부록 표시로 시작하는 상자를 1단계 제목으로 읽는다. 번호 없이 한 칸만 든 상자도 낱말이 셋 이상이거나 느낌표로 끝나면 1단계 제목으로 읽는다. 단, 번호·붙임 제목 상자를 이미 쓴 문서에서는 이런 표어 상자를 제목으로 올리지 않는다. 장 안에서 할 일의 주체를 표시한 상자("시·도(시·군), 농협경제지주(일선조합), 축산단체")가 1단계 제목이 되면 장 밖으로 튀어나오기 때문이다(1.23.1). 다만 문장으로 끝나거나("…다.", "…함"), 글머리표(◈, ☞ 등)로 시작하거나, 칸 안 문단이 여럿이거나, 괄호로 감싼 소제목 표시("< 부적격 사항 >")인 상자는 표로 둔다. 흐름도의 기관 이름 상자도 낱말이 적어 표로 남는다(`title_box.py`). 제목 상자 아래의 줄 제목은 지금처럼 상자 수준만큼 내린다. 또 □ 로 시작하는 줄이 제목 길이(50자)를 넘으면 문단으로 둔다. 보도자료와 지침은 "□ 행정안전부는 … 개정하기로 하고 …" 같은 본문 문장도 □ 로 시작해, 150자가 넘는 문장이 1단계 제목이 되어 절 경로를 채웠다. 짧은 강조 글 상자(◈ 문단 여럿)는 지금처럼 표 노드로 두고 혼자 청크가 된다.
- **DOCX 표의 합친 칸**(텍스트 추출 1.44.0, 2026-11-24): python-docx 의 `row.cells`는 가로로 합친 칸을 열 수만큼 되풀이해 돌려준다. 그래서 견적표의 "직접인건비 소계 - ①"이 한 줄에 세 번 들어가 청크와 표 탭에 그대로 실렸다. 이제 칸(`w:tc`)을 직접 훑어 가로로 합친 칸(`w:gridSpan`)은 한 번만 적고, 세로로 이어지는 칸(`w:vMerge`)은 위 칸의 줄 수를 늘린다. 격자와 합친 칸 목록은 HWP와 같은 규칙(`grid_from_cells`)으로 만든다. 세로로 합친 칸의 글은 아래 줄에도 되풀이해 줄마다 뜻이 통하게 하고, 표 탭은 합친 칸 목록(`spans`)으로 원래 모양을 그린다(`docx_adapter._table_grid`). 격자가 너무 커서 만들지 못한 표는 예전 방식으로 읽는다.
- **HWP 쪽 번호**: 텍스트 추출 블록(1.39.0)이 HWP와 HWPX의 쪽을 원본을 그대로 그린 미리보기 PDF로 매긴다. 예전에는 다시 만든 PDF의 쪽이라 실제 한글 문서의 쪽과 달랐다.
- **사전 적용 탭**: 개별 적용 취소는 `reverted` 표시만 바꾼다. 재처리를 해야 반영된다.

### 9.2 워크플로우 에디터 (`WorkflowEditorPage`)

- **팔레트**: 블록을 §3.1의 카테고리별로 묶어 나열하고, 블록 이름으로 검색할 수 있다. 전처리 종류는 전처리 카테고리를, 분석 종류는 분석 카테고리를 보여준다.
- **블록 설정 폼**: 하드코딩된 설정 필드가 있으면 그것을 쓰고, 없으면 백엔드 `config_schema`에서 만든 필드를 쓴다(§3.2).
- **순서 제약 표시**: 검증에서 걸린 블록은 빨간 테두리로, 걸린 에지는 빨간 선으로 표시한다. 검증 오류 문구는 에디터에 목록으로 보인다.
- **발행**: 검증 오류가 남아 있으면 발행할 수 없다. 메시지는 "아래 검증 오류를 먼저 고쳐야 게시할 수 있습니다."이다.
- **기본 지정**: 에디터에는 기본 지정 기능이 없다. 워크플로우 목록(`/workflows`)의 "기본 지정" 동작에서 `SetCollectionDefaultModal`로 컬렉션을 고른다.
- **실행**: 에디터 상단의 실행 버튼으로 `RunWorkflowModal`을 연다. 게시된 버전만 실행할 수 있다. 대상은 문서 1건 또는 컬렉션이다. 컬렉션을 고르면 파싱이 끝난 문서마다 실행이 만들어지며 최대 50건이다. 모달에는 "이 워크플로우를 실행하면 대상 문서의 기존 RAG 데이터를 대체합니다."라는 경고가 있다. "업로드와 동시에 실행" 옵션은 없다.
- **실행 이력**: 워크플로우별 실행 이력 화면(`/workflows/:id/runs`)에서 런 목록을 본다.
- **버전**: 버전 선택, 버전 삭제, 게시, 버전 비교(`VersionCompareModal`)를 지원한다.

### 9.3 컬렉션 설정

컬렉션 설정 모달의 "문서 처리" 영역에는 다음 항목이 있다.

- 기본 워크플로우는 시스템 기본값("표준 전처리")이나 프로젝트의 PREPROCESS 워크플로우 중에서 고른다. 개인 컬렉션은 시스템 기본값만 고를 수 있다.
- 워크플로우를 쓸 수 있는 곳은 정해져 있다(2026-11-20 사용자 결정). 시스템 워크플로우는 어디서나 쓰고, 프로젝트 워크플로우는 같은 프로젝트의 컬렉션과 문서에만 쓴다. 서버가 다섯 곳에서 검사하고, 어긋나면 400과 함께 "'○○' 워크플로우는 '○○' 프로젝트 전용이라 …에는 쓸 수 없습니다"로 거부한다(`app/services/workflow_scope.py`).
  - 컬렉션 생성과 수정에서 기본 전처리, 기본 분석 워크플로우를 지정할 때
  - 업로드할 때 워크플로우를 직접 고를 때
  - 워크플로우 화면에서 문서나 컬렉션에 직접 실행할 때
  - 처음부터 다시 처리할 때: 다른 프로젝트의 컬렉션으로 옮긴 문서는 예전 워크플로우 대신 지금 컬렉션의 기본 워크플로우(없으면 표준 전처리)로 처리한다.
  - 블록부터 다시 처리할 때: 예전 실행의 앞 단계를 이어 쓰므로 워크플로우를 바꿀 수 없어, 다른 프로젝트 워크플로우로 처리된 문서는 거부하고 처음부터 다시 처리하도록 안내한다.
- 컬렉션을 다른 프로젝트로 옮기면 옛 프로젝트의 워크플로우 지정은 표준으로 되돌린다. 화면은 프로젝트를 바꾸는 순간 "프로젝트를 바꾸면 ○○ 워크플로우는 새 프로젝트에서 쓸 수 없어 표준으로 바뀝니다. 저장해야 적용됩니다"라고 알린다. 컬렉션, 업로드 화면의 선택지에는 같은 프로젝트의 워크플로우만 나온다(`frontend/src/lib/workflowScope.ts`). 예전에는 개인 컬렉션이 프로젝트 지정 없는 목록을 불러와 모든 프로젝트의 워크플로우가 보였다.
- 워크플로우 버전은 항상 최신 게시 버전을 쓰거나 특정 버전으로 고정한다.
- 기본 분석 워크플로우는 시스템 표준 분석이나 프로젝트의 분석 워크플로우 하나를 고른다(§7.5). 고른 워크플로우에 요약, 추천 태그, 분류 단계가 없으면 그 항목이 비워진다는 경고가 나온다.
- 재처리 버튼은 두 개다.
  - "처음부터 다시 처리": 확인 후 `reprocess-from-start`를 호출한다. 원본 파싱부터 다시 하므로 추출과 표, 쪽 번호 개선이 반영된다. 결과로 요청된 건수와 건너뛴 건수를 알려준다. 진행률 막대는 없다.
  - "청크·임베딩만 다시 만들기": 확인 후 레거시 `reprocess`를 호출한다. 이미 추출된 텍스트로 청크와 임베딩만 다시 만든다.
- 청크 크기와 전략을 정하는 입력란은 이 화면에서 제거되었다. 청크 설정은 문서 분할 블록에서 정한다. 블록 값이 없으면 컬렉션에 저장된 기본값을 쓴다.

### 9.4 업로드 흐름

- 업로드 모달은 파일 선택 버튼으로 파일을 고른다(여러 개 가능). 끌어다 놓기 영역은 없다.
- 프로젝트 문서 화면에서 연 업로드 모달은 그 프로젝트의 컬렉션만 보여준다(2026-11-24). 예전에는 어느 화면에서 열어도 모든 컬렉션이 나왔다. 프로젝트 밖의 전체 문서 화면에서는 모든 컬렉션이 나온다.
- 전처리 워크플로우 드롭다운은 "컬렉션 기본값 사용"과 PREPROCESS 워크플로우 목록을 보여준다.
- 분석 워크플로우 드롭다운은 "컬렉션 기본값 사용"과 고른 컬렉션 프로젝트의 ANALYSIS 워크플로우 목록을 보여준다(2026-11-24). 고른 값은 문서에 남아 전처리 뒤 자동 분석과 재처리 뒤 분석에 쓰인다(§7.5). 서버는 분석 종류인지, 같은 프로젝트에서 쓸 수 있는지, 게시된 버전이 있는지 확인하고 원본을 저장하기 전에 거부한다. 문서를 다른 프로젝트 컬렉션으로 옮기면 그 프로젝트 전용 분석 워크플로우 지정은 지운다.
- "같은 이름이 있어도 새 문서로 올리기" 체크박스를 끄면 같은 이름의 문서가 새 버전으로 이어진다.
- "검토 없이 자동 진행" 체크박스는 파일이 2개 이상이면 자동으로 켜지고 끌 수 없다.
- ZIP 일괄 업로드 탭은 등록됨, 중복, 건너뜀, 실패 건수를 집계해 보여준다.
- 업로드 후 문서 목록과 문서 상세는 처리 중인 문서가 있는 동안 주기적으로 다시 불러온다. 문서 상세의 "전처리 단계" 패널은 런의 스텝 타임라인(StepTimeline)으로 블록별 진행을 보여준다.

### 9.5 사전 관리 (`DictionaryPage`)

- 페이지는 불용어, 동의어, 사용자 사전 탭으로 나뉜다. 관리자만 접근할 수 있다.
- 탭마다 입력하는 항목은 다음과 같다.
  - 불용어 탭은 단어, 일치 방식(정확히 일치, 포함, 시작 문자열, 끝 문자열, 정규식), 대소문자 구분, 언어, 적용 범위, 제외 사유, 사용 여부를 입력받는다.
  - 동의어 탭은 대표 용어, 동의어 목록(Enter로 추가), 적용 방향(단방향, 양방향), 처리 방식(정규화, 치환, 검색 확장, 태깅), 대소문자 구분, 언어, 적용 범위, 설명을 입력받는다.
  - 사용자 사전 탭은 표준 용어, 변형 표현, 용어 유형(전문용어, 약어, 기관명, 인명, 제품명, 프로젝트명, 정책명, 기타), 처리 규칙(원문 유지, 표준어로 정규화, 치환, 태그 부여, 주요 개체 추출, 민감정보 마스킹, 처리 대상에서 제외), 발음, 정의, 적용 범위를 입력받는다.
- 상단 안내는 검색에 실제로 적용되는 규칙을 밝힌다. 치환, 태깅, 개체 추출, 마스킹 규칙은 저장은 되지만 검색 토큰화 단계에는 아직 적용되지 않으며, 검색에서는 정규화(KEEP, NORMALIZE)만 동작한다.
- 항목을 저장하면 영향받는 문서 수를 `ImpactModal`로 보여준다. 재처리 실행은 사용자가 따로 한다.
- "버전 이력" 보기(`RevisionView`)에서 리비전 목록을 본다.
- 엑셀 내려받기와 가져오기로 일괄 관리할 수 있다.

### 9.6 처리 현황 (`ProcessingStatusPage`)

- 메뉴 "처리 현황"(`/processing-status`)은 관리자 전용이 아니며 문서 처리 권한이 있는 사용자가 본다.
- 최근 24시간 지표로 처리 문서 수, 평균 품질, 실패율, 재처리율, 검토 대기 수, 큐 대기 시간을 보여준다.
- 블록별 성능 표(실행 수, 실패율, 평균 시간)와 최근 실패 목록을 보여준다.
- 좌측 메뉴의 "검토 대기"와 "실패" 항목에는 건수 배지가 있다. 배지 숫자는 주기적으로 갱신된다.
- 실패율 임계 알림은 구현되지 않았다. 관리자 대시보드에 별도 위젯을 두지 않았고 이 화면이 그 역할을 한다.

## 10. API 설계 (설계서 20장 정합)

현재 구현된 주요 엔드포인트는 다음과 같다. 접두사 `/api/v1`은 생략한다.

```
# 업로드
POST /documents/upload                          multipart. 폼 필드: collection_id, skip_review, workflow_version_id, new_document
POST /documents/upload-zip                      ZIP 일괄 업로드 (같은 폼 필드)

# 실행과 상태
GET  /documents/{id}/runs                       이 문서의 런 목록
GET  /documents/{id}/status                     문서 상태와 오류 메시지
GET  /workflows/runs/{runId}                    런 상세 (스텝 타임라인)
POST /workflows/runs/{runId}/resume             검토 승인 후 재개 (WAITING_REVIEW 상태에서만 허용)
POST /workflows/runs/{runId}/cancel             검토 반려 (run CANCELLED, 문서 FAILED)
GET  /documents/review-queue                    검토 대기 목록
GET  /documents/failure-queue                   실패 목록

# 재처리
POST /documents/{id}/reprocess                  start_block_type | start_block_instance_id, reason, timeout_overrides, use_latest_version
                                                (레거시: edited_text만 보내면 청크부터 다시 처리)

PATCH /documents/{id}/metadata                  메타데이터 수정 (title, language, category 등). 수정한 필드는 user_edited_fields에 기록되어 재처리가 덮어쓰지 않는다.

GET  /documents/{id}/revisions                  텍스트 리비전 목록
```

- **미구현**: 노드 경계 보정 API와 `targetNodeIds` 파라미터는 없다.
- **참고**: `POST /documents/{id}/proceed`는 레거시 경로의 REVIEW_PENDING 상태를 위한 API다. 워크플로우 검토 게이트(WAITING_REVIEW)는 런 승인과 반려 API를 쓰며 이 API와 별개다.

권한은 다음과 같다. 문서 조회는 viewer, 재처리, 검토 승인과 반려, 청크 수정은 editor 이상이다. 워크플로우 실행과 검토 승인, 반려도 editor 이상이다. 사전과 정제 규칙의 관리, 민감정보 원문 열람은 전역 admin만 할 수 있다(`require_admin`). 원문 조회는 감사 로그에 남긴다(`log_audit`).

## 10.5 실행 중단 감지 및 복구 (워치독)

설계 초안의 "5분 이상 RUNNING이면 FAILED로 확정" 의사코드는 구현되지 않았다. 실제 구현은 세 가지 경로로 나뉜다.

1. **시간 초과 판정**: RUNNING 스텝의 시작 시각이 블록 시간 제한(런의 `timeout_overrides`, 없으면 블록의 `timeoutSeconds`, 기본 1800초)과 유예 30초를 넘으면 스텝과 런을 FAILED로 확정한다. 오류 코드는 `TIMEOUT_EXCEEDED`다. 문서 상세 조회와 재처리 요청 시 `reconcile_stuck_run`이 이 판정을 수행한다.
2. **주기 sweep**: Celery beat이 30초마다 `sweep_stuck_workflow_runs`를 실행해 RUNNING 런 전체에 같은 판정을 적용한다. 문서를 아무도 열지 않아도 정리된다. Celery의 하드 시간 제한은 워커 프로세스를 강제로 죽이므로 애플리케이션 코드가 상태를 기록할 수 없고, 이 sweep이 그 공백을 메운다.
3. **고아 런 재디스패치**: RUNNING 스텝이 없고 마지막 활동(스텝의 완료, 시작, 생성 시각 중 가장 최근)이 600초를 넘으면, 완료된 스텝에서 다음 스텝을 다시 디스패치한다. 워커가 재시작되어 다음 스텝 메시지가 유실된 경우에 대비한다. 모든 스텝이 끝났는데 완료 처리만 빠진 경우에는 런을 COMPLETED로 닫는다.

- 시간 초과로 실패한 런은 "처리 시간 제한을 늘려 재처리" 흐름으로 복구한다. 재처리 모달에서 블록의 시간 제한을 이번 런에만 늘릴 수 있다.

| BlockExecutionCache 런 스코프 버그 | 캐시 히트 시 현재 런의 스코프 행을 만들지 않았다. | §2.4의 화이트리스트(`_CACHE_SAFE_BLOCK_TYPES`)로 file_validate, format_detect, text_extract만 캐시한다. | 수정 완료 (2026-07-25). 코드에서 확인했다. |

## 12. 알림 (설계서 23.2 발췌 적용)

현재 구현된 인앱 알림은 다음과 같다. 알림 대상은 `notifications` 테이블에 기록되고 알림 벨에 표시된다.

| 알림 | 수신자 | 발생 지점 |
|---|---|---|
| 검토를 기다리는 문서가 있습니다 (WAITING_REVIEW) | 문서 업로더 | 품질 검증이 검토 게이트에 걸린 시점 (`notify_review_waiting`) |
| 문서 처리에 실패했습니다 | 문서 업로더와 관리자 | 런이 실패로 끝난 시점 (`notify_document_failed`) |
| 파일 서버 동기화에 실패했습니다 | 관리자 | 커넥터 동기화 실패 (`notify_sync_failed`) |

- 설계의 "컬렉션 일괄 재처리 완료" 알림은 구현되지 않았다.
- 실패율 급증 같은 지표 임계 알림은 구현되지 않았다. 처리 현황 화면에서 지표를 보는 방식이다(§9.6).

## 13. 구현 순서 (의존성 기준, 범위 축소 아님)

전 범위를 구축하되, 의존성이 강제하는 빌드 순서만 정의한다. 2026-11-17 점검 기준으로 1번부터 9번까지는 코드에 반영되어 있다. 10번과 11번의 상태는 §16에 정리했다.

1. **데이터 모델과 마이그레이션** (§4 전체, §5 사전 버전)
2. **블록 공통 규격 확장** (config_schema, block_version, category, 아티팩트 저장, BlockContext 확장) 과 실행기 확장 (상태 파생, 캐시, WAITING_REVIEW, error_code)
3. **입력과 추출 블록 4종** (기존 parse_document 분해 이관). 이 시점에 업로드에서 워크플로우 경로로 전환되었고 고정 파이프라인의 함수는 대부분 제거되었다.
4. **정제와 정규화 블록 4종** + 정제 규칙 CRUD + 사전 버전 연동
5. **구조 분석과 민감정보 블록**
6. **분할과 저장 블록** (document_chunks 승격, rag_store). 청크 수정의 DB 재배선은 미완료(§4.6).
7. **품질 검증 블록과 검토 게이트** (레거시 REVIEW_PENDING 게이트를 일반화했다. 레거시 게이트는 `proceed` API로 남아 있다.)
8. **부분 재처리와 영향도 API**
9. **프론트엔드**: 에디터, 문서 상세 탭, 컬렉션 설정, 업로드 흐름, 사전 영향 제안, 처리 현황을 구현했다.
10. **표준 워크플로우 시드와 기존 문서 마이그레이션** (§14). 버그 3종 검증은 §11에 기록했다.
11. **테스트**: 블록 단위, 실행기(게이트, 캐시, 부분 재처리), E2E

각 단계는 TDD와 코드 리뷰를 거쳐 다음 단계로 넘어가는 것을 원칙으로 한다.

## 14. 기존 데이터 마이그레이션

- **표준 전처리 워크플로우 시드**: 마이그레이션 `c2d4e6f8a0b1`에서 시스템 소유 PREPROCESS 워크플로우를 만들었고, 이후 `d4f6a8b0c2e4`, `e6a8c0d2f4b6`, `a2c4e6f8b0d2`가 버전을 추가했다. 최신 게시 버전(v4)의 블록 순서는 다음과 같다. 파일 검증, 형식 판별, 텍스트 추출, 구조 분석, 텍스트 정제, 사용자 사전, 동의어, 불용어, 민감정보 탐지, 문서 분할, 품질 검증, RAG 저장. 설계 초안에 있던 OCR 분기, 병합, 요약, 키워드, 출력 블록은 포함되지 않는다. 요약, 키워드, 출력은 마이그레이션 `f1a3c5e7b9d1`이 시드에서 제거했다. 분석 처리는 §7.5가 맡는다.
- **기존 INDEXED 문서**: parsed_text, page_map, tables, images는 유지된다. Qdrant payload로 document_chunks를 역생성하는 설계가 구현되었는지는 이번 점검에서 확인하지 못했다(§16). 구조 트리, 정제 이력, 품질 리포트는 없을 수 있다. 재처리하면 생성된다.
- **진행 중 문서**: 중간 상태 문서를 FAILED로 표시하고 일괄 재처리를 제안하는 전환 절차는 이번 점검에서 확인하지 못했다.
- `processing_jobs` 테이블과 작업 타임라인 UI는 과거 이력 열람용으로 남아 있다. 신규 기록은 워크플로우 스텝이 담당하지만, text_extract 블록은 여전히 PARSE 작업을 기록한다.

## 15. 리스크

| 리스크 | 대응 |
|---|---|
| 고정 파이프라인 제거로 회귀 범위가 크다 | 표준 워크플로우를 현행 동작과 등가로 시드했다. 레거시 경로는 청크와 임베딩 재생성 API에 남겨 두었다. 전환 직후 업로드에서 INDEXED와 검색까지 이어지는 E2E를 게이트로 삼는다. |
| 아티팩트 저장으로 실행기 복잡도가 올라간다 | BlockContext와 실행기 안에 로드와 저장 로직을 가두었고, 블록 코드는 dict 입출력을 유지한다. |
| 사전 버전 근사 방식의 재현성 한계 | 시점 판정은 `updated_at` 근사를 쓴다. 삭제는 물리 삭제이므로 삭제된 항목은 과거 시점 재현에서 빠진다. 필요하면 항목 스냅샷(`snapshot_key`)으로 보강한다. |
| 의미 분할과 NER 같은 모델 의존 블록의 비용 | 캐시는 세 블록에만 적용된다. 시맨틱 분할은 블록 설정으로 선택한다. NER은 미구현이다. |
| 문서, 청크, 노드 행의 증가 | 노드 텍스트는 짧게 두고 원본은 아티팩트에 둔다. cleaning_changes는 표본만 저장한다. document_id와 run_id에 인덱스를 둔다. |
